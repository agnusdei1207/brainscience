## 0. 핵심 인사이트

> **핵심**: YAGNI는 미래에 필요할 것 같다는 이유만으로 기능과 확장을 미리 만들어 두지 말고, 실제 요구가 확인된 순간에 가장 단순한 형태로 구현하라는 원칙이다.
> **비유**: 언젠가 손님이 많이 올지도 모른다고 집을 지을 때부터 방을 열 개씩 만드는 대신, 실제 필요가 생겼을 때 증축하는 편이 관리비와 낭비를 줄이는 것과 같다.

## 1. 개요 및 필요성

YAGNI (You Aren't Gonna Need It)는 XP (Extreme Programming)에서 강조된 원칙으로, 현재 확정되지 않은 미래 요구를 위해 기능이나 구조를 미리 구현하지 말라는 뜻이다. 이는 단순한 기능 축소 전략이 아니라, 불확실성을 코드로 고정하지 않기 위한 경제적 원칙이다.

이 원칙이 필요한 이유는 미래 예측이 자주 틀리기 때문이다. 개발자는 “나중에 필요할 것 같은” 확장 포인트, 추상화, 옵션, 설정, 일반화를 미리 넣고 싶어 한다. 그러나 실제 요구가 다른 방향으로 바뀌면 그 준비 작업은 사용되지 않는 복잡성, 테스트 부담, 문서 비용, 유지보수 비용으로 남는다.

YAGNI는 따라서 “나중에 바꾸기 쉬운 구조”와 “지금 미리 만들어 두는 구조”를 구분하게 만든다. 확장 가능성을 아예 무시하라는 뜻은 아니며, 실제로 반복적 요구가 나타날 때 리팩토링을 통해 적절한 추상화를 도입하라는 뜻에 가깝다. 즉 선행 일반화보다 **피드백 기반 진화**를 택하는 원칙이다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 현재 요구 | 구현 기준 | 검증된 사용자 요구가 우선 |
| 미래 추측 | 보류 대상 | 가설만으로 구조를 고정하지 않음 |
| 피드백 루프 | 리팩토링 시점 결정 | 실제 반복 신호가 나타날 때 대응 |
| 선행 일반화 비용 | YAGNI가 줄이는 대상 | 코드, 테스트, 문서, 운영 비용 증가 |
| 진화적 설계 | 대안 접근 | 지금은 단순히 만들고, 필요 시 확장 |

YAGNI는 DRY와 자주 충돌하는 것처럼 보이지만 실제로는 균형 문제다. 반복이 한 번도 없는데 추상화로 묶으면 YAGNI 위반이고, 실제로 같은 지식이 여러 번 반복되는데도 계속 복제하면 DRY 위반이다. 따라서 YAGNI는 “언제 공통화할 것인가”를 조절하는 시간 축 원칙이라 볼 수 있다.

---

## 3. 구조 및 원리

**핵심 조건**: 확정되지 않은 미래 요구를 위해 기능·옵션·추상화를 선행 구현하지 말고, 실제 사용 시나리오와 반복 신호가 발생했을 때 그 시점에 맞는 최소 구조로 리팩토링해야 한다.

동작 순서:
1. **현재 요구를 확정한다**: 사용자 가치와 수용 기준이 명확한 기능만 대상으로 삼는다.
2. **미래 가정을 분리한다**: “언젠가 필요할 것”과 “현재 필요함”을 구분한다.
3. **최소 구현을 만든다**: 오늘의 요구를 만족하는 가장 단순한 구조를 선택한다.
4. **관찰 가능한 피드백을 수집한다**: 반복 요구, 변경 패턴, 실제 사용량을 본다.
5. **반복 신호가 생기면 리팩토링한다**: 그때 공통화, 확장 포인트, 추상화를 도입한다.
6. **쓰이지 않는 준비 코드를 제거한다**: dead code, unused option, dormant extension point를 정리한다.

```text
요구 등장
   │
   ├─ 현재 확정 요구? ── 아니오 ──> 구현 보류
   │
   └─ 예
       ▼
   최소 구현
       │
       ▼
사용/변경 패턴 관찰
       │
       ├─ 반복 신호 없음 ──> 단순 구조 유지
       └─ 반복 신호 있음 ──> 리팩토링/추상화 도입
```

예를 들어 결제수단이 카드 하나뿐인 서비스에서, 처음부터 12종 결제수단 플러그인 프레임워크를 만드는 것은 YAGNI 위반일 가능성이 높다. 반면 카드 외 계좌이체, 포인트, 간편결제가 실제 로드맵과 비즈니스 계약으로 확정되고 반복 확장이 시작되면, 그때 OCP 기반 구조로 전환하는 것이 합리적이다.

YAGNI는 “미래를 고려하지 말라”가 아니라 “미래를 위한 비용은 실제 미래가 도착했을 때 지불하라”는 원칙이다. 이 점을 이해해야 무책임한 단기주의와 구분할 수 있다.

---

## 4. 비교 및 연결

| 항목 | YAGNI | OCP | KISS |
|:---|:---|:---|:---|
| 초점 | 선행 구현 억제 | 확장 구조 설계 | 최소 복잡도 유지 |
| 핵심 질문 | 지금 정말 필요한가? | 반복 확장을 어떻게 흡수할까? | 더 단순한 해법이 있는가? |
| 적용 시점 | 구현 전 판단 | 반복 변경 신호 이후 유리 | 전체 설계 과정 전반 |

YAGNI는 OCP의 반대가 아니라 적용 시점 조절 장치다. 반복 확장 요구가 실제로 나타났을 때 OCP를 적용하면 된다. 또한 KISS와 함께 쓰면 불필요한 계층과 설정 포인트를 줄일 수 있고, DRY와 함께 쓰면 반복이 실제로 관찰된 뒤에만 공통화를 수행하는 균형을 잡을 수 있다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 요구 변동성이 크고 미래 예측 정확도가 낮을 때
- MVP (Minimum Viable Product)나 초기 제품 개발 단계일 때
- 과거에 사용되지 않는 추상화와 옵션이 많이 쌓인 경험이 있을 때

**회피 조건**:
- 법규, 계약, 기술 표준으로 미래 요구가 이미 확정된 경우
- 곧바로 다중 확장이 예정되어 있는데도 계속 임시 구현만 유지할 때
- 리팩토링 역량 없이 단순 구현만 반복해 부채를 키울 때

체크리스트:
1. 이 기능/옵션은 실제 요구인가, 추측인가?
2. 지금 추가하는 추상화가 현재 가치를 만드는가?
3. 반복되는 변경 신호가 이미 관찰되었는가?
4. 나중에 리팩토링 가능한 구조와 테스트 안전망이 있는가?
5. 쓰이지 않는 코드와 설정을 주기적으로 정리하는가?

실무에서는 관리자용 옵션, 다국어 프레임워크, 플러그인 시스템, 복잡한 정책 엔진을 너무 일찍 만드는 경우가 대표적 YAGNI 위반이다. 반대로 계약상 확정된 다국가 서비스에서 통화·세율 확장을 고려하지 않는 것은 현실 무시다. 결국 근거 기반 판단이 중요하다.

---

## 6. 기대효과 및 결론

YAGNI를 따르면 개발 속도가 빨라지고, 불필요한 복잡성과 테스트 비용을 줄일 수 있으며, 실제 사용자 피드백을 반영한 진화적 설계가 가능해진다. 특히 스타트업, 신제품, 요구가 자주 바뀌는 조직에서 매우 큰 효과가 있다.

그러나 리팩토링 문화와 테스트 안전망이 없으면 YAGNI는 임시방편의 핑계가 될 수 있다. 결론적으로 YAGNI는 미래를 무시하는 태도가 아니라, 불확실한 미래를 코드에 미리 굳히지 않겠다는 disciplined restraint다.

---

## 7. 발전 흐름도

```text
미래 추측 기반 선행 설계
        ↓
쓰이지 않는 기능 · 옵션 누적
        ↓
YAGNI 기반 최소 구현 전환
        ↓
실사용 데이터와 피드백 축적
        ↓
반복 신호 기반 리팩토링
        ↓
진화적 설계 문화 정착
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| XP (Extreme Programming) | YAGNI를 강조한 애자일 실천 배경 |
| KISS | 불필요한 복잡성 제거라는 점에서 강하게 연결 |
| OCP | 실제 확장 신호가 나타났을 때 적용할 원칙 |
| DRY | 반복이 확인된 뒤 공통화해야 YAGNI와 균형이 맞음 |
| 리팩토링 | YAGNI를 실천하기 위한 필수 후속 능력 |
| Dead Code | YAGNI 위반 결과로 남는 대표 산출물 |
