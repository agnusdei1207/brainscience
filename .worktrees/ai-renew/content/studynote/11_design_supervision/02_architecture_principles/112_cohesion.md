## 0. 핵심 인사이트

> **핵심**: 응집도 (Cohesion)의 본질은 “한 모듈 안의 요소들이 같은 이유로 함께 존재하는가”에 있다. 응집도가 높다는 것은 내부의 함수·데이터·규칙이 하나의 목적을 향해 정렬되어 있어, 모듈 경계가 곧 책임 경계가 된다는 뜻이다.
> **비유**: 잘 정리된 공구함은 전기 작업 도구, 배관 도구, 목공 도구가 목적별로 묶여 있어 꺼내 쓰기 쉽다. 반대로 아무 공구나 뒤섞인 상자는 찾기도 고치기도 어렵다.

## 1. 개요 및 필요성

응집도는 하나의 모듈 내부 요소들이 얼마나 강하게 관련된 하나의 목적을 공유하는지를 나타내는 품질 속성이다. 일반적으로 높을수록 바람직하며, 이는 모듈이 하나의 책임에 집중하고 있다는 의미다. 구조적 관점에서는 SRP (Single Responsibility Principle)의 모듈 수준 표현으로 볼 수 있다.

응집도가 중요한 이유는 변경 이유를 한곳에 모으기 때문이다. 주문 금액 계산, 배송 상태 갱신, 사용자 비밀번호 정책이 한 클래스 안에 섞여 있으면 서로 다른 업무 규칙이 한 모듈에 공존하게 된다. 그러면 한 기능의 수정이 다른 기능의 회귀 위험을 높이고, 테스트 범위도 과도하게 넓어진다. 반대로 같은 데이터와 같은 업무 흐름을 다루는 기능이 한 모듈에 모이면 변경 영향 범위를 예측하기 쉬워진다.

응집도가 낮은 시스템은 보통 “우선 동작하게 만든 코드”가 기능 축적 과정에서 계속 덧붙여진 결과다. 이런 구조에서는 코드 재사용도 떨어진다. 재사용하려는 순간 불필요한 책임까지 함께 딸려 오기 때문이다. 따라서 응집도는 단순한 미학이 아니라 유지보수 비용, 테스트 범위, 재사용성, 팀 분업 효율을 동시에 좌우하는 핵심 설계 지표다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 책임 (Responsibility) | 모듈이 수행해야 하는 업무 목적 | 하나의 모듈은 가능한 한 하나의 변경 이유를 가져야 함 |
| 데이터 집합 | 모듈 내부 기능이 함께 다루는 상태 | 동일 데이터에 함께 작용할수록 응집이 높음 |
| 행위 집합 | 기능을 이루는 메서드·절차 | 같은 업무 흐름을 완성하는가가 중요 |
| 인터페이스 | 외부에 노출되는 서비스 경계 | 내부 책임을 압축해서 드러내야 함 |
| 변경 축 (Change Axis) | 규칙이 변하는 이유와 방향 | 서로 다른 변경 축이 섞이면 낮은 응집 |

응집도는 단순히 “관련 메서드가 같은 파일에 있다”로 판단하지 않는다. 핵심은 내부 기능들이 같은 데이터·같은 규칙·같은 업무 사건을 공유하는지 여부다. 예를 들어 `UserService`가 회원 가입, 로그인, 결제 승인, 쿠폰 발행을 모두 처리한다면 이름은 통일되어 보여도 실제로는 변경 축이 여러 개이므로 응집도가 낮다.

---

## 3. 구조 및 원리

**핵심 조건**: 응집도가 높은 모듈은 내부 요소가 동일한 목적·동일한 데이터·동일한 변경 이유를 공유해야 한다. LCOM (Lack of Cohesion of Methods) 같은 지표가 낮을수록 일반적으로 바람직하다.

동작 순서:
1. **책임 식별**: 모듈이 해결하려는 업무 목표를 한 문장으로 정의한다. 한 문장으로 명확히 말하기 어렵다면 이미 응집이 깨졌을 가능성이 크다.
2. **행위-데이터 매핑**: 내부 메서드가 어떤 데이터와 규칙을 공유하는지 확인한다. 대부분의 메서드가 서로 전혀 다른 필드에만 접근하면 낮은 응집 신호다.
3. **변경 이유 분석**: 기능별로 어떤 요구사항 변화가 발생하는지 살핀다. 서로 다른 부서·서로 다른 릴리스 주기에 의해 수정되는 로직이 한 모듈에 섞이면 분리 대상이다.
4. **경계 재구성**: 함께 변하는 요소는 묶고, 독립적으로 변하는 요소는 분리한다. 이 과정에서 추상화 이름도 목적 중심으로 재정의한다.
5. **인터페이스 축소**: 모듈이 진짜 제공해야 할 기능만 외부에 공개한다. 공개 인터페이스가 지나치게 넓으면 내부 책임이 혼재되었을 가능성이 높다.

```
낮은 응집
┌────────────────────────────────────┐
│ UserManager                        │
│ - registerUser()                   │
│ - calculateDiscount()              │
│ - sendNotification()               │
│ - exportExcel()                    │
└────────────────────────────────────┘
        │ 서로 다른 변경 이유가 혼재
        ▼
높은 응집
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ UserService  │ │ PricingSvc   │ │ ReportSvc    │
│ 가입/인증     │ │ 할인 계산     │ │ 보고서 생성   │
└──────────────┘ └──────────────┘ └──────────────┘
```

고전적으로 응집도는 기능적(Function) 응집이 가장 높고, 우연적(Coincidental) 응집이 가장 낮다고 본다. 기능적 응집은 모든 요소가 하나의 결과를 만들기 위해 존재하는 상태다. 반대로 우연적 응집은 “그냥 같은 파일에 있다” 수준이라 변경과 테스트가 불안정하다. 중요한 점은 높은 응집이 반드시 작은 클래스만을 뜻하지는 않는다는 것이다. 기능은 넓을 수 있지만, **변경 이유가 하나**라면 여전히 높은 응집일 수 있다.

## 4. 비교 및 연결

| 구분 | 높은 응집 | 낮은 응집 |
|:---|:---|:---|
| 책임 수 | 하나의 목적 중심 | 여러 목적 혼재 |
| 변경 영향 | 국소적 | 광범위 |
| 재사용성 | 높음 | 낮음 |
| 테스트 범위 | 명확하고 작음 | 광범위하고 불명확 |
| 결합도와의 관계 | 대체로 낮은 결합을 유도 | 외부 의존 증가 경향 |

응집도와 결합도는 함께 봐야 한다. 높은 응집은 내부 책임을 선명하게 만들고, 그 결과 외부와의 인터페이스도 단순해져 결합도를 낮추기 쉽다. 반대로 낮은 응집 모듈은 외부 요구를 이것저것 흡수하며 거대한 허브가 되기 쉽고, 결국 높은 결합으로 이어진다. 다만 응집을 지나치게 잘게 쪼개면 오히려 모듈 간 협력이 늘어 결합도가 올라갈 수 있으므로, “최소 단위 분해”가 아니라 “변경 이유 기준 분해”가 중요하다.

## 5. 실무 적용 및 판단

채택 조건:
- 도메인 기능을 책임 단위로 명확히 분리하려는 경우
- 팀별 소유권과 변경 범위를 분명히 해야 하는 경우
- 테스트 격리와 재사용성이 중요한 핵심 모듈

회피 조건:
- 지나치게 미세 분해하여 오히려 협력 비용이 커지는 경우
- 현재 도메인 경계가 아직 탐색 단계여서 너무 이른 분해가 오히려 혼란을 주는 경우

체크리스트:
1. 이 모듈의 책임을 한 문장으로 설명할 수 있는가?
2. 내부 메서드들이 같은 데이터와 규칙을 공유하는가?
3. 서로 다른 조직/요구사항에 의해 별도로 수정되는 기능이 섞여 있지 않은가?
4. 클래스 이름과 실제 책임이 일치하는가?
5. 공개 메서드 대부분이 동일한 업무 시나리오를 지원하는가?

실무에서는 응집도 평가를 코드 리뷰에서 “이 코드가 왜 여기 있지?”라는 질문으로 자주 확인한다. 예를 들어 주문 서비스 안에 엑셀 다운로드, SMTP 전송, 배치 스케줄 계산이 동시에 들어 있다면 분리 신호다. 반대로 주문 생성과 주문 취소, 주문 상태 전이는 같은 애그리게이트 규칙을 공유하므로 같은 모듈에 남는 편이 자연스럽다.

---

## 6. 기대효과 및 결론

높은 응집도는 코드의 의미를 압축한다. 모듈 이름만으로 역할을 예측할 수 있고, 수정 시 어디를 봐야 하는지 즉시 판단할 수 있다. 그 결과 회귀 범위 축소, 테스트 단순화, 재사용성 향상, 팀 간 충돌 감소라는 효과가 생긴다.

그러나 응집도를 높인다는 명분으로 모든 기능을 잘게 쪼개면 협력 경계가 너무 많아져 전체 이해가 오히려 어려워질 수 있다. 따라서 응집도는 “작게 나누기”가 아니라 “같이 변하는 것끼리 묶기”라는 관점에서 봐야 한다. 결론적으로 응집도는 모듈 품질의 핵심 기준이며, 좋은 설계는 높은 응집도를 통해 변경을 국소화한다.

## 7. 발전 흐름도

```
우연적 응집 (그냥 모아둠)
    ↓
논리적·시간적 응집 (비슷해 보여 묶음)
    ↓
절차적·통신적 응집 (흐름/데이터 공유)
    ↓
순차적 응집 (출력이 다음 단계 입력)
    ↓
기능적 응집 (하나의 목적 중심)
    ↓
도메인 중심 응집 (변경 이유 기준 모듈화)
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| SRP | 응집도를 객체 설계 원칙으로 표현한 개념 |
| LCOM | 메서드 간 데이터 공유 정도를 통해 응집도를 추정하는 지표 |
| 결합도 | 응집도와 함께 모듈 품질을 판단하는 짝 개념 |
| DDD 애그리게이트 | 높은 응집을 도메인 규칙 단위로 구현한 구조 |
| 모듈화 | 응집도는 모듈 경계 설정의 핵심 기준 |
| 리팩토링 | Extract Class, Move Method가 응집도 개선에 직접 사용 |
| 관심사 분리 | 서로 다른 변경 이유를 분리해 응집도를 높임 |
| 빅 볼 오브 머드 | 낮은 응집과 높은 결합이 누적된 전형적 실패 구조 |
