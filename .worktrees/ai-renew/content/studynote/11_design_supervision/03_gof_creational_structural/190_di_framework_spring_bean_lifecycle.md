## 0. 핵심 인사이트

> **핵심**: DI (Dependency Injection) 프레임워크는 객체 생성과 의존성 배선을 컨테이너가 관리하고, Spring Bean 생명주기는 생성부터 초기화·사용·소멸까지의 표준 수명주기를 통해 모듈 결합도를 낮춘다.
> **비유**: 각 부품이 서로를 직접 조달하지 않고 조립 라인이 필요한 부품을 정해진 시점에 연결하고 점검하는 구조와 같다.

## 1. 개요 및 필요성

190. DI 프레임워크와 Spring Bean 생명주기 (DI Framework Spring Bean Lifecycle)은 의존성 주입 컨테이너와 빈 수명주기 관리 구조를 다루는 주제다.
이 패턴이 중요한 직접 배경은 객체가 스스로 의존 객체를 생성하면 구현 결합도가 높아지고 테스트와 교체가 어려워진다.
이를 해결하기 위한 구조적 가치로는 컨테이너가 생성, 주입, 초기화, 후처리, 소멸을 관리함으로써 모듈 분리와 프레임워크 확장을 지원한다.
설계자가 집중해야 하는 관점은 핵심 초점은 IoC (Inversion of Control), Bean Definition, lifecycle callback, scope, post processor다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Bean Definition | 객체 생성 메타데이터 | 타입·의존성·스코프 포함 |
| Container | 생성·주입·관리 주체 | ApplicationContext |
| Dependency Injection | 의존성 연결 방식 | constructor/setter/field |
| BeanPostProcessor | 초기화 전후 후처리 | AOP 프록시 생성 등 |
| Lifecycle Callback | init/destroy 훅 | @PostConstruct 등 |
| Scope | 빈 수명 범위 | singleton, prototype, request |
| Proxy/AOP | 부가기능 주입 | 트랜잭션, 보안 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Bean Definition는 객체 생성 메타데이터 역할을 가지며 전체 흐름에서 타입·의존성·스코프 포함 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Container는 생성·주입·관리 주체 역할을 가지며 전체 흐름에서 ApplicationContext 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Dependency Injection는 의존성 연결 방식 역할을 가지며 전체 흐름에서 constructor/setter/field 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- BeanPostProcessor는 초기화 전후 후처리 역할을 가지며 전체 흐름에서 AOP 프록시 생성 등 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Lifecycle Callback는 init/destroy 훅 역할을 가지며 전체 흐름에서 @PostConstruct 등 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Scope는 빈 수명 범위 역할을 가지며 전체 흐름에서 singleton, prototype, request 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Proxy/AOP는 부가기능 주입 역할을 가지며 전체 흐름에서 트랜잭션, 보안 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.

## 3. 구조 및 원리
**핵심 조건**: 객체 생성과 배선의 주도권을 컨테이너로 역전하고, 빈 수명주기 각 단계의 책임을 명확히 관리해야 한다.

IoC는 객체가 의존성을 직접 조달하지 않게 만드는 설계 전환이다.
생성자 주입은 불변성과 테스트 용이성 측면에서 가장 권장된다.
Bean 생명주기를 이해해야 초기화 시점 오류와 프록시 적용 순서를 설명할 수 있다.
BeanPostProcessor는 프레임워크 확장의 핵심 훅이다.
스코프가 다르면 thread safety와 상태 관리 전략이 달라진다.
Spring Bean은 단순 POJO (Plain Old Java Object)지만 컨테이너 관리 하에 더 풍부한 인프라 기능을 얻는다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **정의 수집**: 컨테이너가 설정 클래스, 컴포넌트 스캔, XML 등에서 Bean Definition을 읽는다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **인스턴스 생성**: 생성자 호출 또는 팩토리 메서드로 빈을 만든다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **의존성 주입**: 필요한 빈을 주입하여 객체 그래프를 완성한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **Aware/후처리**: BeanNameAware, BeanPostProcessor 등이 개입한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **초기화**: @PostConstruct, InitializingBean, custom init-method가 실행된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **사용**: 애플리케이션이 빈을 사용하며 AOP 프록시가 부가기능을 제공할 수 있다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **소멸**: 컨테이너 종료 시 destroy callback이 실행된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Bean Definition]
      |
      v
[Spring Container]
      |--> instantiate
      |--> dependency inject
      |--> BeanPostProcessor before
      |--> init callback
      |--> BeanPostProcessor after / proxy
      v
[Running Bean] --> [destroy callback on shutdown]
```

### 구조 해설

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| IoC | 제어 역전의 상위 개념 |
| Constructor Injection | 권장 주입 방식 |
| BeanPostProcessor | 후처리 확장 포인트 |
| AOP Proxy | 트랜잭션·보안 부가기능 연결 |
| Scope | 빈 생명 범위 |
| ApplicationContext | Spring 핵심 컨테이너 |
| Factory Method | 빈 생성 방식 중 하나 |
| Singleton | 기본 스코프와 연결 |
| Lifecycle Callback | init/destroy 훅 |
| Test Double | DI가 쉽게 만드는 대체 구현 |

### 정리 메모
- DI 프레임워크의 핵심은 new()를 없애는 것이 아니라, 객체 그래프와 수명주기 제어권을 컨테이너로 옮겨 구조적 결합을 줄이는 데 있다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
