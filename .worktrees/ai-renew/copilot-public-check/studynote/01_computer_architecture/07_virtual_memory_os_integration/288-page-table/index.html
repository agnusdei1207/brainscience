핵심 인사이트 (3줄 요약)

  1. 본질: 페이지 테이블 (Page Table)은 가상 페이지 번호를 물리 프레임 번호로 바꾸는 번역표이자, 운영체제가 메모리 보호 정책을 하드웨어에 전달하는 제어 표다.
  2. 가치: 프로그램은 연속된 가상 주소 공간을 쓰는 것처럼 보이지만, 실제 메모리는 흩어진 프레임으로 배치할 수 있어 효율과 격리를 동시에 얻는다.
  3. 판단 포인트: 페이지 테이블은 유연한 대신 메모리와 접근 지연 비용이 크므로, 다단계 구조·TLB·Huge Page 같은 보완책을 함께 봐야 한다.

Ⅰ. 개요 및 필요성

페이지 테이블 (Page Table)은 가상 주소를 물리 주소로 바꾸기 위한 운영체제의 핵심 자료구조다. CPU가 가상 주소를 생성하면, MMU (Memory Management Unit)는 그 주소의 가상 페이지 번호를 페이지 테이블에서 조회해 실제 메모리 프레임을 찾아낸다. 즉 프로그램이 보는 주소 세계와 하드웨어가 실제로 접근하는 주소 세계 사이에 놓인 공식 통역사라고 볼 수 있다.

이 구조가 필요한 이유는 프로그램이 사용하는 메모리와 실제 RAM의 배치 방식이 다르기 때문이다. 프로세스는 0번지부터 연속된 공간을 기대하지만, 물리 메모리는 여러 프로세스와 커널이 함께 쓰므로 조각나기 쉽다. 페이지 테이블이 없으면 운영체제는 프로세스마다 큰 연속 공간을 미리 확보해야 하고, 그 결과 외부 단편화와 보호 문제를 동시에 떠안게 된다.

또한 페이지 테이블은 단순 번역표가 아니라 보호 장치이기도 하다. 읽기 전용 코드 페이지, 사용자 접근 금지 커널 페이지, 아직 메모리에 없는 페이지를 모두 엔트리 상태로 표현할 수 있다. 그래서 페이지 테이블은 "주소를 어디로 보낼까?"와 "이 접근을 허용할까?"를 한 번에 결정한다.

  • 📢 섹션 요약 비유: 페이지 테이블은 대형 창고의 위치 안내 데스크와 같다. 손님은 "A구역 3번 상자"만 말하지만, 안내 데스크는 실제 창고 선반 위치와 출입 권한까지 함께 확인해 준다.

Ⅱ. 아키텍처 및 핵심 원리

페이지 테이블의 기본 단위는 PTE (Page Table Entry)다. 각 PTE에는 PFN (Page Frame Number) 같은 실제 위치 정보와 함께 Valid Bit, Dirty Bit, Accessed Bit, Protection Bit 같은 제어 정보가 들어간다. 그래서 한 줄의 엔트리만 읽어도 "어디 있는가, 메모리에 있는가, 수정되었는가, 읽기/쓰기/실행이 가능한가"를 동시에 판단할 수 있다.

주소 변환은 보통 가상 주소를 VPN (Virtual Page Number)과 Offset으로 나누는 것에서 시작한다. VPN은 페이지 테이블의 인덱스로 쓰이고, 조회 결과로 얻은 PFN 뒤에 원래 Offset을 붙이면 최종 물리 주소가 된다. 이때 현재 실행 중인 프로세스의 페이지 테이블 시작점은 PTBR (Page Table Base Register) 또는 아키텍처별 동등한 레지스터가 가리킨다.

아래 그림은 단일 페이지 테이블 기준의 핵심 흐름을 보여준다. 중요한 점은 페이지 테이블이 메모리 안에 존재하므로, 주소 하나를 번역하려 해도 페이지 테이블 자체를 한 번 읽어야 한다는 것이다. 그래서 페이지 테이블은 유연하지만 느릴 수 있고, 이를 보완하기 위해 TLB (Translation Lookaside Buffer)가 필수로 붙는다.

Ⅲ. 비교 및 연결

페이지 테이블을 이해하려면 먼저 "페이지"와 "페이지 테이블"을 구분해야 한다. 페이지는 가상 메모리를 나눈 데이터 조각이고, 페이지 테이블은 그 조각들이 어디에 배치되었는지 기록한 메타데이터다. 즉 페이징 (Paging)이 배치 방식이라면, 페이지 테이블은 그 배치 방식을 실행 가능하게 만드는 운영 장부다.

또한 단일 페이지 테이블은 구조가 단순하지만 주소 공간이 커질수록 메모리 낭비가 심해진다. 예를 들어 64비트 시스템에서 모든 가상 페이지에 대해 엔트리를 일괄 보관하면, 실제로 쓰지 않는 넓은 주소 범위까지 장부를 만들어야 한다. 그래서 현대 시스템은 다음 문서의 주제인 다단계 페이지 테이블 (Multilevel Page Table)로 확장해 필요한 부분만 계층적으로 생성한다.

세그먼트 테이블과 비교하면 경계도 더 선명해진다. 세그먼트 테이블은 코드, 데이터, 스택처럼 논리적 의미 단위를 관리하는 데 강하지만, 크기가 가변적이라 외부 단편화 관리 부담이 크다. 반면 페이지 테이블은 고정 크기 페이지를 전제로 하므로 공간 관리가 단순하고, 보호 비트와 결합해 하드웨어 친화적인 가상 메모리 체계를 만든다.

비교 축페이지 테이블세그먼트 테이블
관리 단위고정 크기 페이지가변 크기 논리 세그먼트
강점단편화 제어와 하드웨어 구현 용이의미 단위 보호와 공유 표현 쉬움
약점엔트리 수가 많아 장부가 커짐외부 단편화와 배치 복잡도 증가

  • 📢 섹션 요약 비유: 페이지 테이블은 규격 박스 창고의 선반 목록이고, 세그먼트 테이블은 책·옷·장난감처럼 종류별 보관 목록에 가깝다. 전자는 정리가 빠르고, 후자는 의미를 살리기 쉽다.

Ⅳ. 실무 적용 및 기술사 판단

실무에서 페이지 테이블은 성능과 보안을 동시에 건드린다. 페이지 테이블이 크고 깊어질수록 Page Table Walk 비용이 커지고, TLB 미스가 잦은 워크로드에서는 CPU가 실제 계산보다 주소 번역에 더 많은 시간을 쓸 수 있다. 반대로 권한 비트를 잘 설계하면 사용자 공간과 커널 공간을 분리하고, 코드 주입 공격에 대한 실행 제한도 하드웨어 수준에서 강제할 수 있다.

운영체제 스케줄러 관점에서도 중요하다. 컨텍스트 스위치가 발생하면 현재 프로세스의 페이지 테이블 기준점이 바뀌고, 그에 따라 기존 주소 번역 캐시의 유효성이 흔들릴 수 있다. 그래서 Address Space Identifier 같은 태그 기법, Huge Page 사용, 메모리 지역성 개선은 모두 페이지 테이블 오버헤드를 줄이기 위한 실무적 해법이다.

기술사 답안이나 아키텍처 판단에서는 다음 질문이 핵심이다. 첫째, 워크로드가 큰 연속 메모리 블록을 자주 접근하는가, 아니면 랜덤 접근이 많은가. 둘째, 보안 요구가 높아 페이지 단위 권한 분리가 중요한가. 셋째, 메모리 규모가 커서 단일 테이블이 비현실적인가. 이 질문들에 따라 다단계 페이지 테이블, Huge Page, TLB 튜닝, 커널-사용자 분리 전략을 함께 선택해야 한다.

안티패턴

  • 페이지 테이블 메모리 비용을 보지 않고 페이지 크기만 기본값으로 고정하는 설계

  • 실행 금지 비트를 무시해 데이터 페이지에서도 코드 실행이 가능한 상태를 방치하는 운영

  • 주소 지역성이 낮은 자료구조를 남발해 TLB와 페이지 테이블 양쪽 모두를 괴롭히는 구현

  • 📢 섹션 요약 비유: 페이지 테이블은 회사 건물 출입 시스템과 같다. 사무실 위치를 빨리 찾게 해줘야 하고, 동시에 아무나 서버실에 들어가지 못하게 막아야 한다.

Ⅴ. 기대효과 및 결론

페이지 테이블의 가장 큰 효과는 추상화와 통제의 동시 달성이다. 프로세스는 자신만의 연속된 메모리 공간을 가진 것처럼 단순하게 동작하고, 운영체제는 실제 메모리를 비연속적으로 배치하면서도 충돌 없이 관리할 수 있다. 이 덕분에 멀티프로그래밍, 프로세스 격리, 스와핑, 메모리 보호 같은 현대 운영체제 기능이 성립한다.

하지만 비용도 분명하다. 페이지 테이블 자체가 메모리를 먹고, 번역 과정은 추가 지연을 만든다. 그래서 페이지 테이블은 "좋은 개념"이 아니라 "필수지만 공짜는 아닌 개념"으로 기억해야 한다. 현대 시스템이 다단계 테이블, 역 페이지 테이블, Huge Page, 하드웨어 가속 번역을 계속 발전시키는 이유도 바로 이 비용을 줄이기 위해서다.

결론적으로 페이지 테이블은 가상 메모리의 부속품이 아니라, 가상 메모리를 실제로 작동시키는 실행 엔진이다. 페이지가 공간 분할의 단위라면, 페이지 테이블은 그 단위를 질서 있게 묶는 운영 규칙이다. 따라서 이 개념은 "주소 번역표"로만 외우기보다 "성능·보호·확장성의 균형점"으로 이해해야 오래 남는다.

  • 📢 섹션 요약 비유: 페이지 테이블은 도시 전체의 지번 체계와 같다. 주소가 정리되어 있어야 택배도 빨라지고, 출입 통제도 가능하며, 새 건물이 생겨도 도시가 혼란 없이 커질 수 있다.
