핵심 인사이트 (3줄 요약)

  1. 본질: CQRS (Command Query Responsibility Segregation)는 상태를 바꾸는 명령 모델과 화면·검색을 위한 조회 모델을 분리해, 하나의 객체 모델에 쓰기 규칙과 읽기 최적화를 동시에 짊어지게 하지 않는 설계 패턴이다.
  2. 가치: 쓰기 측은 트랜잭션과 비즈니스 불변식에 집중하고, 읽기 측은 화면별 투영 모델과 검색 구조에 집중할 수 있어, 읽기/쓰기 부하가 크게 다른 시스템에서 확장성과 단순성을 함께 얻는다.
  3. 판단 포인트: CQRS의 대가는 복잡도다. 읽기 모델 동기화, 최종 일관성 (Eventual Consistency), 재처리, 모니터링까지 감당할 가치가 있을 때만 채택해야 한다.

Ⅰ. 개요 및 필요성

전통적인 CRUD (Create, Read, Update, Delete) 기반 설계는 하나의 엔티티 모델과 하나의 저장소로 읽기와 쓰기를 함께 처리한다. 단순 업무 시스템에서는 이 방식이 가장 직관적이지만, 읽기와 쓰기의 성격이 크게 달라지는 순간 한 모델에 서로 다른 요구사항이 충돌하기 시작한다. 쓰기 측은 무결성, 트랜잭션, 도메인 규칙이 중요하고, 읽기 측은 조인, 검색, 정렬, 화면 맞춤형 집계가 중요하기 때문이다.

마이크로서비스 아키텍처 (MSA, Microservices Architecture) 에서는 이 충돌이 더 커진다. 주문, 회원, 상품 데이터가 각 서비스에 분산되면 과거처럼 하나의 데이터베이스에서 복잡한 조인을 수행하기 어렵다. 게이트웨이에서 여러 서비스를 호출해 결과를 합칠 수도 있지만, 네트워크 지연이 누적되고 장애 전파가 쉬워지며, 화면별 데이터 구조를 만들기 위해 애플리케이션 코드가 지나치게 복잡해진다.

┌────────────────────────────────────────────────────────────────────┐
│ Single model overload                                              │
├────────────────────────────────────────────────────────────────────┤
│ same domain model + same schema + same database                    │
│   ├─ Command needs transaction, validation, invariant              │
│   └─ Query needs join, search, pagination, denormalized view       │
│                                                                    │
│ 결과: 하나의 모델이 두 종류의 요구를 모두 억지로 떠안음              │
└────────────────────────────────────────────────────────────────────┘

CQRS는 바로 이 지점에서 출발한다. "같은 데이터를 다룬다"와 "같은 모델로 다뤄야 한다"는 가정을 분리하는 것이다. 즉 업무 규칙을 지키는 쓰기 모델과, 사용자가 빨리 읽을 수 있게 재구성한 조회 모델을 나누어 각자 다른 목표에 최적화한다.

  • 📢 섹션 요약 비유: 요리사가 주방에서 쓰는 조리대와 손님에게 보여 주는 뷔페 진열대는 같은 음식을 다루지만 모양과 목적이 다르다. CQRS는 그 둘을 억지로 같은 형태로 만들지 않는 생각이다.

Ⅱ. 아키텍처 및 핵심 원리

CQRS 아키텍처는 보통 명령 측, 이벤트 전달 계층, 조회 측의 세 부분으로 나뉜다. 명령 측은 주문 생성, 결제 승인, 재고 차감처럼 상태를 바꾸는 작업을 처리하며, 보통 정규화된 관계형 저장소와 도메인 검증을 사용한다. 조회 측은 사용자 화면이나 검색 API 에 필요한 형태로 데이터를 미리 투영해 두고, 문서 데이터베이스, 검색 엔진, 키-값 저장소 같은 읽기 친화형 구조를 선택할 수 있다.

구성 요소역할설계 포인트
Command Handler명령 수신과 유효성 검증중복 명령 처리, 권한, 입력 검증
Write Model / Aggregate비즈니스 규칙과 상태 변경불변식 보장, 트랜잭션 경계 명확화
Write Store시스템의 기준 데이터 저장보통 OLTP (Online Transaction Processing) 최적화
Outbox / Event Bus변경 사실 전달멱등성, 순서, 재시도, 장애 복구
Projector이벤트를 읽기 모델로 변환재처리 가능성, 버전 관리
Read Model화면·검색용 투영 데이터비정규화, 조회별 스키마 최적화
Query API읽기 전용 응답 제공낮은 지연시간, 페이지별 응답 구조

아래 그림은 CQRS의 전형적인 데이터 흐름을 요약한다.

├────────────────────────────────────────────────────────────────────┤
│ User command                                                       │
│   │                                                                │
│   ▼                                                                │
│ Command handler ─▶ Write model ─▶ Write store                      │
│                                 │                                  │
│                                 └─ outbox / event                  │
│                                            │                       │
│                                            ▼                       │
│                                      projector / consumer          │
│                                            │                       │
│                                            ▼                       │
│                                      Read model store              │
│                                            │                       │
│ User query  ───────────────────────────────┘                       │
│   └─ Query API reads optimized projection                          │
└────────────────────────────────────────────────────────────────────┘

이 구조에서 중요한 것은 읽기 저장소가 단순 복제본이 아니라는 점이다. 조회 모델은 "주문 상세 화면", "고객별 최근 주문 목록", "검색 자동완성"처럼 사용 사례별로 미리 가공된 데이터 뷰가 될 수 있다. 그래서 CQRS는 종종 머티리얼라이즈드 뷰 (Materialized View) 나 이벤트 기반 프로젝션과 함께 설명된다.

물론 이 구조는 즉시 일관성을 포기하는 대가를 요구한다. 명령이 쓰기 저장소에 반영된 직후 조회 모델로 전파되기까지는 지연이 생길 수 있다. 따라서 CQRS의 핵심 원리는 "읽기 모델이 순간적으로 늦을 수 있음"을 받아들이되, 그 대신 읽기와 쓰기를 각자 가장 적합한 구조로 분리하는 데 있다.

  • 📢 섹션 요약 비유: 주방에서 요리가 완성되면, 바로 손님용 진열대에 예쁘게 담아 놓는 과정이 따로 있는 셈이다. 조리는 주방 규칙을 따르고, 진열은 손님이 보기 편한 규칙을 따른다.

Ⅲ. 비교 및 연결

CQRS를 제대로 이해하려면 읽기 복제본과 이벤트 소싱 (Event Sourcing) 과 구분해야 한다. 읽기 복제본은 보통 같은 스키마를 다른 노드에 복제해 읽기 부하를 분산하는 구조이고, CQRS는 애초에 읽기 모델 자체를 다르게 설계한다. 이벤트 소싱은 변경 이벤트 자체를 진실 원천으로 삼는 패턴이고, CQRS는 그것 없이도 적용 가능하다.

방식읽기/쓰기 모델저장 원천장점한계
CRUD 단일 모델동일동일 데이터베이스단순함, 학습 비용 낮음읽기/쓰기 요구 충돌 시 비효율
읽기 복제본 (Read Replica)동일동일 스키마 복제읽기 부하 분산조회 구조 자체는 안 바뀜
CQRS분리쓰기 저장소 + 조회 저장소사용 사례별 최적화, 독립 확장동기화와 운영 복잡도 증가
CQRS + 이벤트 소싱분리이벤트 로그재생·감사 추적에 강함설계 난이도와 운영 부담 큼

또한 CQRS는 트랜잭셔널 아웃박스 (Transactional Outbox), 사가 (Saga), 이벤트 브로커와 자주 연결된다. 쓰기 측의 변경 사실을 안정적으로 조회 모델이나 다른 서비스로 퍼뜨리려면 Outbox 같은 패턴이 필요하고, 여러 서비스에 걸친 장기 업무 흐름은 Saga 로 이어질 수 있다. 즉 CQRS는 단독 기술이라기보다 이벤트 기반 분산 시스템의 한 축으로 이해하는 편이 정확하다.

실무에서 자주 생기는 오해는 "데이터베이스를 둘로 나누면 다 CQRS" 라는 생각이다. 하지만 읽기와 쓰기에 같은 스키마를 그대로 복제해 놓았다면 그건 대부분 읽기 복제에 가깝다. CQRS의 본질은 DB 개수보다 모델 책임의 분리에 있다.

  • 📢 섹션 요약 비유: 같은 책을 다른 선반에 한 권 더 두는 것은 복제본이고, 어린이용 요약본을 따로 만드는 것은 CQRS에 가깝다. 둘 다 읽기 편하게 만들지만 방식과 목적이 다르다.

Ⅳ. 실무 적용 및 기술사 판단

CQRS는 읽기와 쓰기의 비대칭이 큰 곳에서 빛난다. 예를 들어 주문 생성은 초당 수십 건인데, 주문 조회와 검색은 초당 수천 건이고 화면마다 요구하는 조인 구조가 다르다면, 조회 모델을 별도로 두는 편이 훨씬 단순하다. 반대로 단순한 사내 관리 시스템처럼 화면 수가 적고 읽기·쓰기 부하가 모두 크지 않다면, CQRS는 얻는 것보다 운영 부담이 더 클 수 있다.

또한 읽기 모델의 지연을 업무가 감수할 수 있는지도 중요하다. 주문 직후 조회 화면이 200밀리초 정도 늦게 갱신되는 것은 허용할 수 있지만, 금융 잔액처럼 즉시 반영이 절대적으로 중요한 화면은 별도 전략이 필요하다. 이때는 명령 응답 자체에 최신 상태를 함께 담거나, 일부 조회만 쓰기 측에서 직접 제공하는 혼합 전략을 검토할 수 있다.

기술사 판단 체크리스트

  1. 읽기 트래픽과 쓰기 트래픽의 규모·패턴이 실제로 많이 다른가?
  2. 조회 화면별로 필요한 데이터 형태가 크게 달라 별도 투영 모델 가치가 큰가?
  3. 읽기 모델 지연을 업무적으로 허용할 수 있는가?
  4. 이벤트 재처리, 프로젝션 재구축, 스키마 버전 변경 절차가 준비되어 있는가?
  5. 프로젝터와 소비자가 멱등하게 동작하고, 순서 문제를 감당할 수 있는가?
  6. 읽기 모델 장애, 적체, 지연을 관측할 모니터링 체계가 있는가?

자주 나오는 안티패턴

  • 단순 CRUD 시스템에도 유행처럼 CQRS를 도입해 팀 복잡도만 늘리는 경우
  • 쓰기 측의 비즈니스 검증을 지연된 읽기 모델에 의존하는 경우
  • 조회 모델을 화면별로 나누지 않고, 다시 범용 데이터베이스처럼 만들어 복잡성을 되살리는 경우
  • 프로젝션 재생이나 백필 (Backfill) 전략 없이 실시간 이벤트만 믿는 경우

실무 시나리오로 보면 더 분명하다. 전자상거래 시스템에서 주문 생성은 주문 서비스가 처리하고, 고객 주문 목록 화면은 주문·결제·배송 데이터를 합친 별도 조회 모델에서 읽는 구조가 CQRS에 잘 맞는다. 이때 조회 모델은 고객번호 기준 문서 구조나 검색 인덱스로 최적화할 수 있다. 반면 단일 팀이 운영하는 간단한 게시판 시스템에 같은 구조를 강제로 넣으면, 코드보다 운영 파이프라인 관리가 더 어려워질 수 있다.

  • 📢 섹션 요약 비유: 작은 가게 장부는 한 권이면 충분하지만, 대형 마트는 재고 관리 장부와 손님 안내 전광판을 따로 운영하는 편이 훨씬 효율적이다.

Ⅴ. 기대효과 및 결론

CQRS를 올바르게 적용하면 쓰기 측은 도메인 규칙과 트랜잭션을 단단하게 유지하고, 읽기 측은 화면과 검색 요구에 맞게 자유롭게 최적화할 수 있다. 그 결과 읽기/쓰기 독립 확장, 단순한 조회 API, 화면별 비정규화, 검색 엔진 결합, 장애 격리 같은 효과를 기대할 수 있다. 특히 MSA 환경에서는 서비스 경계를 지키면서도 복합 조회를 빠르게 제공하는 방법으로 큰 의미가 있다.

하지만 그 이면에는 저장소 이중화, 데이터 중복, 최종 일관성 처리, 이벤트 파이프라인 운영, 재처리 비용이 따라온다. 즉 CQRS는 "더 멋진 아키텍처"가 아니라, 읽기/쓰기 불균형을 다른 복잡도로 교환하는 선택이다. 그래서 도입 판단은 기술 유행보다, 읽기 모델 분리로 얻는 사업적 가치가 충분한지를 기준으로 해야 한다.

결론적으로 CQRS를 기억할 때 가장 중요한 문장은 이것이다. 같은 사실을 다루더라도, 상태를 바꾸는 모델과 보여 주기 위한 모델은 같을 필요가 없다. 이 관점을 이해하면 CQRS는 단순한 패턴 이름이 아니라, 대규모 시스템에서 책임을 분리하는 설계 원칙으로 남는다.

  • 📢 섹션 요약 비유: 주방 레시피 노트와 손님 메뉴판은 같은 음식을 말하지만, 쓰는 사람과 보는 사람이 다르니 당연히 모양도 달라야 한다.
