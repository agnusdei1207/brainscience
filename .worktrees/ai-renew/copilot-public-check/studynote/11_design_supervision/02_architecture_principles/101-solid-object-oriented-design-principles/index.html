0. 핵심 인사이트

핵심: SOLID는 객체지향 설계를 다섯 개의 관점으로 분해해, 변경은 국소화하고 의존성은 추상화로 제어하며 협력은 안정적으로 유지하게 만드는 설계 원칙 묶음이다. 비유: 건물을 지을 때 전기·배관·구조체를 뒤섞지 않고, 벽을 허물지 않아도 설비를 교체할 수 있게 만드는 설계 기준 세트와 같다.

📝 모범 답안

1. 개요 및 필요성

SOLID는 Robert C. Martin이 정리한 객체지향 설계 원칙 다섯 가지, 즉 SRP (Single Responsibility Principle), OCP (Open-Closed Principle), LSP (Liskov Substitution Principle), ISP (Interface Segregation Principle), DIP (Dependency Inversion Principle)를 말한다. 이 원칙들은 각각 독립적이지만, 실제로는 함께 작동하여 변경 비용을 낮추고 모듈 간 결합을 제어한다.

이 원칙이 필요한 배경은 객체지향이 클래스와 상속만 사용한다고 해서 자동으로 좋은 설계가 되지 않기 때문이다. 책임이 뒤섞인 거대 클래스, 조건문으로 가득한 확장 구조, 자식 객체가 부모 계약을 깨는 상속, 비대한 인터페이스, 구현체에 고정된 의존성은 모두 객체지향 문법으로도 쉽게 만들어진다. SOLID는 이러한 실패 패턴을 방지하는 설계 판단 기준이다.

아키텍처 관점에서 SOLID는 단순한 코딩 규칙이 아니라 변경 용이성 전술의 기반이다. 마이크로서비스, 헥사고날 아키텍처, 클린 아키텍처 같은 상위 구조도 내부 모듈이 SOLID 원칙을 어기면 금세 경직된다. 따라서 SOLID는 클래스 수준 원칙이면서 동시에 모듈·컴포넌트 수준의 품질 속성 확보 도구다.

2. 구성요소

요소역할핵심 포인트
SRP책임 분리변경 이유를 한 축으로 제한
OCP확장성 확보새 기능 추가 시 기존 코드 수정 최소화
LSP대체 가능성 보장상위 타입 계약을 하위 타입이 깨지 않음
ISP인터페이스 슬림화클라이언트마다 필요한 계약만 노출
DIP의존성 방향 제어구현이 아니라 추상화에 의존

다섯 원칙은 분절된 체크리스트가 아니다. SRP와 ISP는 “작게 나누는 방법”을, OCP와 DIP는 “확장과 의존성 제어 방법”을, LSP는 “상속과 다형성이 안전하게 작동하는 조건”을 설명한다. 결국 SOLID 전체는 높은 응집도와 낮은 결합도를 구현하는 체계라고 볼 수 있다.

3. 구조 및 원리

핵심 조건: SOLID는 변경 축을 분리하고, 확장은 추상화 뒤에 위치시키며, 대체 가능한 타입 계약을 유지하고, 클라이언트별 인터페이스를 좁히고, 의존성 방향을 안정된 추상으로 향하게 해야 한다.

동작 순서:

  1. 변경 축을 식별한다: 무엇이 자주 바뀌는지 확인하여 책임을 분리한다. 이것이 SRP의 출발점이다.
  2. 확장 포인트를 만든다: 새로운 기능이 기존 코드 대수정을 일으키지 않도록 OCP 기반 확장 구조를 만든다.
  3. 타입 계약을 명확히 한다: 하위 타입이 상위 계약을 깨지 않도록 LSP를 검증한다.
  4. 클라이언트별 인터페이스를 분리한다: 사용하지 않는 기능 강제를 막기 위해 ISP를 적용한다.
  5. 의존성 방향을 추상화로 역전한다: DIP를 통해 고수준 정책이 저수준 세부 구현에 묶이지 않게 한다.
  6. 반복적으로 리팩토링한다: SOLID는 처음부터 완벽히 설계하는 교리가 아니라, 변화 신호에 반응해 구조를 정제하는 기준이다.
변경 요구 발생
      │
      ▼
[SRP] 책임 분리
      │
      ▼
[OCP] 확장 포인트 설계
      │
      ▼
[LSP] 대체 가능성 검증
      │
      ▼
[ISP] 인터페이스 최소화
      │
      ▼
[DIP] 추상화로 의존성 역전
      │
      ▼
변경 영향 국소화 · 테스트 용이성 향상

SOLID의 핵심은 개별 원칙 암기가 아니라 상호작용 이해다. 예를 들어 DIP 없이 OCP를 구현하면 확장 포인트가 결국 구체 클래스에 묶여 진짜 확장성이 나오지 않는다. LSP를 어기면 OCP로 확장해도 다형성 교체가 안전하지 않다. ISP가 없으면 DIP를 적용해도 인터페이스가 너무 비대해 클라이언트 결합이 남는다. 즉 다섯 원칙은 서로 보완 관계다.

또한 SOLID는 “클래스를 잘게 쪼개라”는 뜻이 아니다. 책임과 계약이 명확해지는 방향이어야 하며, 과도한 분리는 오히려 복잡성을 증가시킨다. 따라서 SOLID는 구조를 무조건 분할하는 기준이 아니라 변경을 가장 낮은 비용으로 수용하기 위한 균형 기준이다.

4. 비교 및 연결

항목SOLID단순 객체지향 문법 사용아키텍처 패턴
초점변경 용이성과 결합도 제어캡슐화·상속 사용 자체시스템 수준 구조
범위클래스·모듈 설계 원칙언어 기능 활용계층·서비스·포트 구조
장점테스트·확장·재사용성 향상구현 속도는 빠를 수 있음전체 시스템 방향 제시
한계과도 적용 시 복잡화 가능설계 품질 보장 못 함내부 모듈 품질은 별도 관리 필요

SOLID는 DRY, KISS, YAGNI와 자주 함께 논의된다. DRY는 지식 중복 제거, KISS는 단순성 유지, YAGNI는 추측성 확장 억제를 강조한다. SOLID는 이 원칙들과 충돌하기보다, 언제 추상화가 가치 있고 언제 과도한지를 판단하는 정교한 기준을 제공한다.

5. 실무 적용 및 판단

채택 조건:

  • 변경이 잦고 기능 확장이 예상되는 도메인 로직일 때
  • 테스트 가능성과 모듈 교체 가능성이 중요한 시스템일 때
  • 팀 규모가 커져 역할 분리가 필요한 코드베이스일 때

회피 조건:

  • 매우 짧은 수명의 단순 스크립트에 과도한 추상화를 도입할 때
  • 실제 변경 축 없이 인터페이스와 계층만 늘릴 때
  • 원칙을 개별 체크박스로만 적용해 전체 복잡도를 악화시킬 때

체크리스트:

  1. 클래스나 모듈에 변경 이유가 여러 축으로 섞여 있는가?
  2. 새 기능 추가 시 기존 핵심 로직 수정이 반복되는가?
  3. 하위 타입 교체가 안전하게 가능한가?
  4. 인터페이스가 특정 클라이언트 요구를 넘어 과도하게 크지 않은가?
  5. 정책이 세부 구현에 직접 묶여 있지 않은가?

실무에서는 결제수단 추가, 메시지 브로커 교체, 저장소 구현 변경, 외부 API 제공 채널 확대 같은 상황에서 SOLID의 효과가 분명하게 드러난다. 특히 테스트 대역(Mock, Stub) 교체가 쉬운 구조는 대체로 DIP와 ISP가 잘 적용된 경우다.

6. 기대효과 및 결론

SOLID를 잘 적용하면 변경 영향이 좁아지고 테스트가 쉬워지며, 확장 시 기존 코드 손상이 줄어든다. 이는 유지보수 비용 감소, 팀 협업 안정화, 기술 부채 억제에 직결된다. 또한 상위 아키텍처가 바뀌더라도 핵심 도메인 로직을 더 오래 안정적으로 유지할 수 있다.

그러나 SOLID는 교조적으로 적용할 원리가 아니다. 변화 가능성이 거의 없는 영역까지 과도하게 추상화하면 KISS와 YAGNI를 어기고 복잡성만 늘어난다. 결론적으로 SOLID의 본질은 “무조건 분리”가 아니라 “변화의 축을 보고 가장 적절한 추상화를 선택하는 것”이다.
