0. 핵심 인사이트

핵심: ISP는 하나의 큰 인터페이스를 모두에게 강요하지 말고, 클라이언트가 실제로 사용하는 역할 단위로 계약을 쪼개 결합을 줄이라는 원칙이다. 비유: 모든 직원에게 회계·인사·보안·영업 권한이 다 들어 있는 만능 사원증을 주는 대신, 각자 필요한 출입 권한만 담은 카드로 나눠 주는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

ISP (Interface Segregation Principle)는 클라이언트가 자신이 사용하지 않는 메서드에 의존하지 않아야 한다는 원칙이다. 즉 인터페이스는 구현체 관점이 아니라 클라이언트 사용 관점에서 분리해야 한다. 하나의 거대한 인터페이스는 편해 보이지만, 실제로는 불필요한 결합과 가짜 구현, 빈 메서드, 불필요한 테스트를 낳는다.

이 원칙이 필요한 이유는 인터페이스가 넓을수록 변경 영향이 커지기 때문이다. 예를 들어 Machine 인터페이스에 print, scan, fax가 모두 들어 있으면, 프린터만 필요한 클라이언트도 전체 인터페이스에 묶인다. 이후 fax 계약이 바뀌면 프린터 관련 코드까지 재컴파일, 재테스트, 재배포 범위에 포함될 수 있다.

ISP는 단순히 인터페이스를 작게 만들자는 의미가 아니다. 중요한 기준은 사용자별 역할이다. 관리자 화면, 일반 사용자 화면, 배치 프로세스가 같은 서비스를 호출하더라도 필요한 계약은 서로 다를 수 있다. 따라서 인터페이스는 구현체 기준이 아니라 사용 문맥 기준으로 설계되어야 한다.

2. 구성요소

요소역할핵심 포인트
클라이언트인터페이스 사용자누가 어떤 메서드를 실제 사용하는지 기준
역할 인터페이스작고 명확한 계약읽기, 쓰기, 승인, 조회 등 역할별 분리
구현체여러 인터페이스 조합 가능필요 시 다중 역할을 구현
불필요 의존성제거 대상사용하지 않는 메서드, 빈 구현, 예외 던지기
테스트 경계영향 범위 축소인터페이스별 계약 테스트 가능

ISP의 장점은 계약을 소비 관점에서 설계하게 만든다는 점이다. 하나의 구현체가 여러 역할을 수행할 수는 있지만, 그 사실이 인터페이스를 크게 만들 이유는 되지 않는다. 오히려 역할 인터페이스를 나누면 같은 구현체도 더 유연하게 교체·테스트할 수 있다.

3. 구조 및 원리

핵심 조건: 인터페이스는 구현체의 편의가 아니라 클라이언트별 사용 행태를 기준으로 분리되어야 하며, 어떤 클라이언트도 사용하지 않는 메서드에 의존해서는 안 된다.

동작 순서:

  1. 클라이언트를 분류한다: 누가 어떤 기능을 실제로 쓰는지 역할별로 나눈다.
  2. 사용 메서드를 매핑한다: 각 클라이언트가 호출하는 메서드 집합을 확인한다.
  3. 비대한 인터페이스를 분해한다: 읽기 전용, 쓰기 전용, 관리 전용 등 역할별 계약으로 나눈다.
  4. 구현체를 재구성한다: 필요한 인터페이스만 구현하거나, 하나의 구현체가 여러 인터페이스를 동시에 구현하게 한다.
  5. 의존성을 재배치한다: 클라이언트는 자신이 사용하는 인터페이스만 참조한다.
  6. 테스트와 배포 범위를 줄인다: 특정 계약 변경이 모든 클라이언트로 퍼지지 않도록 한다.
[ISP 위반]
SmartDevice
 ├─ print()
 ├─ scan()
 ├─ fax()
 └─ staple()
   ▲      ▲
   │      └─ 프린터는 불필요

[ISP 적용]
Printable   Scannable   Faxable   Staplable
    ▲           ▲          ▲          ▲
    └────── MultiFunctionPrinter ─────┘

ISP는 DIP와 함께 적용될 때 효과가 크다. 고수준 모듈이 구체 구현이 아닌 추상 인터페이스에 의존하더라도, 그 인터페이스가 너무 크면 실제로는 여전히 강결합이다. 따라서 추상화의 품질을 높이려면 인터페이스도 역할별로 정교하게 나누어야 한다.

또한 CQRS (Command Query Responsibility Segregation)처럼 읽기와 쓰기를 분리하는 아키텍처도 넓게 보면 ISP 정신과 맞닿아 있다. 조회 클라이언트는 조회 계약만, 명령 클라이언트는 변경 계약만 바라보도록 하여 불필요한 결합을 줄이는 방식이기 때문이다.

4. 비교 및 연결

항목ISPSRPDIP
초점클라이언트별 계약 분리모듈의 책임 분리추상화 중심 의존성 역전
기준누가 무엇을 쓰는가무엇이 왜 바뀌는가누구에게 의존하는가
결과인터페이스 슬림화응집도 향상구현 교체 용이

ISP는 SRP의 인터페이스 버전으로 볼 수 있다. SRP가 구현 책임을 나눈다면, ISP는 외부에 노출되는 계약을 역할별로 나눈다. 또한 DIP의 전제조건이 되기도 한다. 추상화가 너무 비대하면 의존성은 역전되어도 결합도는 여전히 크기 때문이다.

5. 실무 적용 및 판단

채택 조건:

  • 하나의 인터페이스를 여러 종류의 클라이언트가 서로 다르게 사용할 때
  • 빈 구현, UnsupportedOperationException, 권한 없는 메서드 노출이 반복될 때
  • 테스트와 배포 영향 범위를 줄여야 할 때

회피 조건:

  • 실제 클라이언트 구분 없이 기계적으로 인터페이스를 잘게 쪼갤 때
  • 역할보다 구현 세부사항 기준으로 인터페이스를 나눌 때
  • 인터페이스 개수만 늘리고 의미 있는 경계를 만들지 못할 때

체크리스트:

  1. 클라이언트가 실제로 사용하는 메서드 집합이 다른가?
  2. 구현체가 빈 메서드나 예외 던지기로 계약을 억지 충족하는가?
  3. 인터페이스 변경이 불필요한 클라이언트까지 영향을 주는가?
  4. 조회/명령/관리 역할이 혼재되어 있는가?
  5. 분리 후에도 계약 이름과 책임이 이해하기 쉬운가?

실무에서는 외부 API SDK, 관리자 백오피스, 파일 저장소, 메시지 발송 채널, 리포트 조회 서비스에서 ISP 효과가 크다. 특히 공용 인터페이스를 여러 팀이 공유하는 환경일수록 비대한 계약의 비용이 커진다.

6. 기대효과 및 결론

ISP를 적용하면 클라이언트 결합이 줄고, 역할별 테스트가 쉬워지며, 작은 계약 단위로 진화할 수 있다. 이는 공용 라이브러리 안정성과 팀 간 독립성을 높이는 데 특히 유리하다. 또한 인터페이스 오염을 줄여 API 자체가 더 읽기 쉬워진다.

하지만 지나친 분리는 인터페이스 난립을 만들 수 있다. 따라서 ISP의 핵심은 “작게 만들기”가 아니라 “사용 문맥에 맞게 나누기”다. 클라이언트 관점이 분명할수록 좋은 인터페이스가 나온다.
