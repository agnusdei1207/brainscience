0. 핵심 인사이트

핵심: DRY는 코드 줄 수를 줄이라는 말이 아니라, 하나의 지식·규칙·의도를 여러 곳에 복제하지 말고 단일한 진실의 원천으로 관리하라는 원칙이다. 비유: 같은 집 주소를 주민등록, 택배, 우편, 출입 카드 시스템에 각각 따로 적어 두면 이사할 때마다 전부 바꿔야 하듯, 같은 규칙이 여러 군데 흩어지면 변경 때마다 누락이 생긴다.

📝 모범 답안

1. 개요 및 필요성

DRY (Don't Repeat Yourself)는 동일한 지식이 여러 장소에 중복되어 존재하지 않도록 하라는 원칙이다. 여기서 중요한 것은 텍스트의 유사성보다 지식의 중복이다. 우연히 비슷하게 보이는 코드 조각이더라도 의미가 다르면 중복이 아닐 수 있고, 문법은 달라도 같은 규칙을 반복 표현하면 DRY 위반일 수 있다.

이 원칙이 필요한 이유는 중복이 변경 누락과 불일치의 주요 원인이기 때문이다. 예를 들어 세율 계산식이 주문, 정산, 리포트 세 모듈에 각각 복제되어 있으면, 정책 변경 시 한 곳만 빠뜨려도 데이터 불일치가 발생한다. 중복은 단순한 귀찮음이 아니라 품질·정합성·운영 리스크 문제다.

다만 DRY는 모든 유사 코드를 무조건 하나로 합치라는 뜻이 아니다. 너무 이른 일반화는 오히려 KISS와 YAGNI를 해치고, 서로 다른 맥락의 코드를 부자연스럽게 결합시킬 수 있다. 핵심은 “같은 지식인가, 단순히 비슷한 모양인가”를 구분하는 것이다.

DRY를 잘 적용하려면 중복의 수준을 구분해야 한다. 코드 중복, SQL 중복, 설정 중복, 문서 중복, 테스트 데이터 중복 등 다양한 층에서 같은 지식이 반복될 수 있다. 따라서 DRY는 코딩 스타일 규칙이 아니라 지식 관리 원칙으로 보는 것이 정확하다.

3. 구조 및 원리

핵심 조건: 동일한 규칙이나 정책이 여러 위치에 반복된다면 하나의 권위 있는 원천으로 통합해야 하며, 유사해 보여도 의미가 다른 경우는 섣불리 통합하지 않아야 한다.

동작 순서:

  1. 중복 후보를 식별한다: 같은 계산식, 포맷, 상수, 검증 규칙이 여러 군데 있는지 찾는다.
  2. 지식 동일성을 판단한다: 같은 이유로 함께 바뀌는지 확인한다.
  3. 단일 진실 원천을 정한다: 함수, 정책 객체, 설정 파일, 스키마, 코드 생성 등 적절한 형태를 고른다.
  4. 호출/참조 구조로 전환한다: 복제 대신 재사용하게 만든다.
  5. 변경 전파를 검증한다: 원천 하나를 수정했을 때 모든 소비자가 올바르게 반영되는지 확인한다.
  6. 과잉 일반화를 점검한다: 의미가 다른 영역까지 억지 통합하지 않았는지 본다.
[DRY 위반]
주문 모듈   ── 세율 10%
정산 모듈   ── 세율 10%
리포트 모듈 ── 세율 10%

        ↓ 단일 원천화

TaxPolicy
 └─ taxRate = 10%
    ▲       ▲       ▲
    │       │       │
 주문    정산    리포트

DRY의 핵심은 함께 바뀌는 지식을 모으는 것이다. 예를 들어 배송비 계산 로직이 화면용과 배치용으로 각각 있어도, 실제 정책이 동일하다면 하나의 정책 모듈로 모으는 것이 맞다. 반대로 둘 다 format() 메서드를 가지더라도 하나는 사용자 UI 포맷, 다른 하나는 외부 기관 신고 포맷이라면 같은 지식이 아닐 수 있으므로 분리 유지가 더 바람직하다.

현대 개발에서는 코드 생성, OpenAPI 스키마, ORM 매핑, 인프라 선언형 구성도 DRY를 돕는다. 하지만 공통화가 지나쳐 모든 차이를 옵션으로 흡수하게 되면 복잡성이 폭발한다. 그러므로 DRY는 KISS와 균형 있게 써야 한다.

4. 비교 및 연결

항목DRYSRPYAGNI

DRY는 SRP와 자주 함께 작동한다. 책임이 잘 분리되어야 지식 중복을 명확히 식별할 수 있고, 반대로 지식이 한 곳에 모여야 응집도도 올라간다. 하지만 너무 이른 공통화는 YAGNI 위반이므로, 반복이 실제로 관찰된 뒤 추상화하는 편이 안전하다.

5. 실무 적용 및 판단

채택 조건:

  • 동일한 정책, 포맷, 매핑, 상수가 여러 모듈에 반복될 때
  • 변경 누락 때문에 데이터 불일치나 버그가 발생한 경험이 있을 때
  • 공통 규칙을 하나의 정책/스키마로 관리할 수 있을 때

회피 조건:

  • 아직 반복이 한 번도 발생하지 않은 코드를 성급히 일반화할 때
  • 의미가 다른 코드를 문법 유사성만으로 통합할 때
  • 공통화 후 옵션 플래그가 지나치게 늘어날 때

체크리스트:

  1. 이 중복은 같은 지식인가, 단순한 유사 코드인가?
  2. 함께 바뀌는가?
  3. 단일 원천으로 모을 때 오히려 복잡성이 증가하지 않는가?
  4. 테스트와 문서도 같은 원천을 바라보는가?
  5. 공통화 후 예외 처리 분기가 과도하게 늘지 않는가?

실무에서는 세금/수수료 정책, 사용자 권한 매핑, API 스키마, 메시지 포맷, 배포 환경 설정에서 DRY 효과가 크다. 반대로 UI 화면별 미세한 차이를 모두 한 컴포넌트로 합치려 하면 DRY보다 복잡성 비용이 더 커질 수 있다.

6. 기대효과 및 결론

DRY를 지키면 정책 변경이 빨라지고, 일관성이 높아지며, 결함과 운영 혼선을 줄일 수 있다. 특히 규제·세무·정산처럼 규칙 일관성이 중요한 도메인에서 효과가 크다. 또한 코드뿐 아니라 문서, 설정, 테스트 데이터를 포함한 전체 개발 체계의 품질을 높인다.

하지만 DRY는 “중복처럼 보이는 모든 것을 하나로 만들라”는 교리가 아니다. 결론적으로 DRY의 본질은 텍스트 축약이 아니라 지식의 단일화이며, 그 적용 시점은 KISS와 YAGNI로 균형을 잡아야 한다.
