0. 핵심 인사이트

핵심: 할리우드 원칙 (Hollywood Principle)의 본질은 제어 흐름의 주도권을 프레임워크·상위 정책이 쥐고, 하위 구현은 정해진 시점에만 호출되도록 만드는 것이다. 즉, 재사용의 핵심은 “무엇을 할지”보다 “누가 언제 호출권을 갖는가”를 설계하는 데 있다. 비유: 오디션에 합격한 배우가 스스로 방송 시간을 정하는 것이 아니라, 방송국 편성표에 맞춰 호출될 때 출연하는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

할리우드 원칙은 “Don't call us, we'll call you.”라는 문장으로 요약되는 설계 원칙이다. 라이브러리를 사용하는 전통적 방식에서는 애플리케이션 코드가 필요한 시점에 라이브러리 함수를 호출한다. 반대로 프레임워크 중심 구조에서는 프레임워크가 애플리케이션의 생명주기와 제어 흐름을 관리하고, 개발자가 제공한 확장 지점(Callback, Hook, Template Method, Event Handler)을 적절한 시점에 호출한다.

이 원칙이 필요한 이유는 대규모 시스템에서 공통 제어 흐름을 중앙에서 통제해야 하기 때문이다. 화면 렌더링, HTTP 요청 처리, 트랜잭션 경계, 이벤트 디스패치, 배치 스케줄링은 모든 기능마다 반복된다. 이때 각 모듈이 제각각 흐름을 제어하면 정책 일관성이 무너지고, 예외 처리·보안·자원 해제가 흩어진다. 상위 프레임워크가 흐름을 장악하면 하위 모듈은 자신의 핵심 로직만 구현하면 되므로 재사용성과 일관성이 동시에 높아진다.

할리우드 원칙이 없으면 플러그인 구조가 라이브러리 호출의 난립으로 바뀌고, 생명주기 제어가 모듈마다 흩어져 결합도가 증가한다. 특히 UI 프레임워크, 웹 프레임워크, 테스트 프레임워크처럼 “전체 흐름을 조정하는 소프트웨어”에서는 누가 주도권을 갖는지 명확하지 않으면 확장성과 통제 가능성이 급격히 떨어진다.

핵심은 상위 제어자와 하위 구현 사이에 계약 기반의 확장 지점이 존재한다는 점이다. 하위 모듈은 프레임워크 내부 루프를 직접 조작하지 않고, 자신이 제공할 수 있는 동작만 등록한다. 프레임워크는 등록된 구현체를 생명주기 내 적절한 위치에서 호출한다. 따라서 설계의 본질은 “호출을 막는 것”이 아니라 “호출권을 중앙화하는 것”이다.

3. 구조 및 원리

핵심 조건: 상위 정책이 실행 순서를 소유하고, 하위 구현은 공개된 확장 지점으로만 참여해야 한다. 하위 구현이 프레임워크 내부 흐름을 역으로 탐색하거나 우회 호출하기 시작하면 할리우드 원칙은 깨진다.

동작 순서:

  1. 프레임워크 기동: 컨테이너나 런타임이 초기화되며 전체 실행 루프를 만든다. 이 단계에서 이미 제어권은 프레임워크에 있다.
  2. 확장 지점 등록: 개발자는 Controller, Listener, Strategy, Test Case 같은 구현체를 등록한다. 등록 행위는 참여 의사 표시이지 실행 권한 획득이 아니다.
  3. 생명주기 진입: 요청 수신, 화면 이벤트, 스케줄 도래, 테스트 실행 등 특정 상황이 발생하면 프레임워크가 해당 지점을 해석한다.
  4. 역호출 (Inversion of Control): 프레임워크가 계약에 맞는 콜백을 찾아 호출한다. 이 지점이 제어의 역전 (IoC: Inversion of Control) 이 실현되는 순간이다.
  5. 공통 정책 적용: 호출 전후로 인증, 트랜잭션, 로깅, 예외 처리, 자원 회수 같은 횡단 관심사가 일괄 적용된다.
  6. 흐름 복귀: 하위 구현은 결과를 반환하고, 최종 응답 조립과 다음 단계 전환은 다시 상위 제어자가 맡는다.
┌─────────────────────────────────────────────────────────┐
│ Framework / Runtime                                    │
│                                                         │
│  1) bootstrap                                           │
│  2) register handlers                                   │
│  3) wait for lifecycle event                            │
│  4) call user code                                      │
│  5) apply common policy                                 │
└───────────────┬─────────────────────────────────────────┘
                │ callback / hook invocation
                ▼
        ┌──────────────────────┐
        │ User Extension Code  │
        │ Controller / Plugin  │
        │ Test Case / Listener │
        └──────────────────────┘
                │ result
                ▼
        Framework continues orchestration

이 구조가 중요한 이유는 공통 정책을 애플리케이션 곳곳에 복제하지 않아도 되기 때문이다. 예를 들어 Spring Framework는 요청이 들어오면 DispatcherServlet이 전체 흐름을 소유하고, 개발자가 작성한 Controller는 특정 시점에만 호출된다. JUnit도 테스트 순서, 예외 집계, 리포팅은 프레임워크가 담당하고 개별 테스트 메서드는 역호출된다. 즉, 할리우드 원칙은 재사용성보다 통제 가능성을 먼저 확보하고, 그 결과로 재사용성이 따라오는 구조다.

다만 확장 지점이 과도하게 세분화되면 프레임워크 학습 비용이 커지고, 반대로 확장 지점이 너무 적으면 우회 구현이 늘어난다. 따라서 공식 확장 지점의 설계 품질이 원칙의 실효성을 좌우한다.

할리우드 원칙은 IoC의 설명 문장이고, DIP는 이를 안전하게 구현하기 위한 구조 원칙이다. 예컨대 상위 프레임워크가 하위 모듈을 호출하더라도 구체 클래스에 직접 의존하면 확장성이 떨어진다. 그래서 인터페이스, 이벤트 계약, 어노테이션 메타데이터로 결합을 완화한다. 템플릿 메서드 패턴은 상위 클래스가 알고리즘 뼈대를 잡고 하위 클래스 Hook을 부르는 방식이므로 할리우드 원칙의 고전적 구현이다.

5. 실무 적용 및 판단

채택 조건:

  • 프레임워크가 전체 실행 흐름을 중앙 통제해야 하는 경우
  • 플러그인, 이벤트 핸들러, 테스트 케이스처럼 확장 가능한 포인트가 많은 경우
  • 공통 정책(보안, 트랜잭션, 로깅)을 일관되게 적용해야 하는 경우

회피 조건:

  • 단순 유틸리티 라이브러리처럼 호출 주도권을 애플리케이션이 가져도 되는 경우
  • 생명주기가 매우 짧고 프레임워크 도입 비용이 큰 소규모 스크립트
  • 팀이 프레임워크 내부 동작을 이해하지 못해 “왜 호출되는지 모르는 코드”가 누적되는 경우

체크리스트:

  1. 확장 지점이 명시적 계약으로 문서화되어 있는가?
  2. 하위 구현이 프레임워크 내부 객체를 과도하게 탐색하지 않는가?
  3. 공통 정책이 콜백 구현체에 중복 작성되지 않는가?
  4. 등록·실행·예외 처리의 생명주기가 관찰 가능하게 로깅되는가?
  5. 프레임워크가 없는 상태에서도 핵심 비즈니스 로직 테스트가 가능한가?

실무 사례로는 Spring Bean 생명주기, Servlet Filter/Controller 호출, React의 선언적 렌더링, JUnit 테스트 실행기, Jenkins Pipeline Step 확장 구조가 있다. 모두 개발자가 “언제 실행할지”보다 “무엇을 제공할지”를 정의하고, 실행 타이밍은 상위 엔진이 결정한다.

6. 기대효과 및 결론

할리우드 원칙을 적용하면 제어 흐름이 중앙 집중화되어 일관된 생명주기 관리, 횡단 관심사의 공통 처리, 확장 지점 기반 재사용이 가능해진다. 특히 대규모 팀에서는 “기능 코드”와 “운영 정책”을 분리해 코드베이스의 예측 가능성을 높이는 효과가 크다.

반면 프레임워크 의존이 심해지면 내부 호출 구조를 모르는 개발자는 디버깅에 어려움을 겪을 수 있다. 따라서 원칙의 성공 조건은 무조건적인 프레임워크화가 아니라, 명확한 계약·가시적인 생명주기·테스트 가능한 핵심 로직 확보에 있다. 결론적으로 할리우드 원칙은 단순한 구호가 아니라, 확장 가능한 플랫폼이 제어권을 어떻게 배분해야 하는가에 대한 설계 철학이다.
