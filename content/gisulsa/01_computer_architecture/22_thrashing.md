## 0. 핵심 인사이트

> **정의**: 프로세스가 실제 연산보다 **페이지 교체에 더 많은 시간을 소비**하는 현상
> **원인**: 물리 메모리 부족 → 과도한 페이지 폴트 → CPU 이용률 급락
> **시험 포인트**: 발생 원인 → 탐지(CPU 이용률 모니터링) → 해결(워킹셋 모델, PFF)

---

## 1. 개요 및 필요성

다중 프로그래밍 환경에서 메모리에 올라온 프로세스 수(다중 프로그래밍 정도)가 증가할수록 CPU 이용률이 높아지지만, 임계점을 초과하면 역설적으로 CPU 이용률이 급격히 하락한다. 이 현상이 스래싱이다.

스래싱 발생 시 운영체제는 CPU 이용률 저하를 감지하고 더 많은 프로세스를 메모리에 올리는 판단을 내리며, 이는 메모리 경쟁을 심화시켜 스래싱을 더욱 악화시키는 악순환에 빠진다.

---

## 2. 발생 원리

```
[다중 프로그래밍 정도 증가]
        ↓
[각 프로세스의 할당 페이지 수 감소]
        ↓
[워킹셋(자주 참조하는 페이지 집합)이 메모리에 올라오지 못함]
        ↓
[페이지 폴트 급증] → [페이지 교체 I/O 폭주]
        ↓
[CPU가 I/O 대기] → [CPU 이용률 급락]
        ↓
[OS: "이용률 낮으니 프로세스 더 올리자"] → 악순환
```

---

## 3. 구성요소 및 해결 방법

| 해결 기법 | 원리 | 장단점 |
|:---|:---|:---|
| **워킹셋 모델** | 최근 Δ 시간 참조 페이지를 워킹셋으로 정의, 워킹셋 크기만큼 프레임 보장 | 지역성 기반, 구현 복잡 |
| **PFF (Page Fault Frequency)** | 페이지 폴트율 상한/하한 설정, 초과 시 프레임 추가 또는 프로세스 교체 | 구현 단순, 반응 빠름 |
| **다중 프로그래밍 정도 감소** | 일부 프로세스 스왑 아웃 | 직접적 해결, 처리량 일시 감소 |
| **메모리 증설** | 근본적 해결 | 비용 발생 |
| **프리페칭** | 예측 기반 선행 적재 | 지역성 높은 작업에 효과적 |

---

## 4. 워킹셋 모델 상세

**워킹셋(Working Set)**: 시간 t에서 과거 Δ 시간 동안 참조된 페이지 집합 W(t, Δ)

```
예시) Δ = 10, 참조 문자열: 1,2,3,4,2,1,2,3,4,5
  W(t=10, Δ=10) = {1, 2, 3, 4, 5} → 5개 프레임 필요

총 워킹셋 크기 = Σ |W(ti, Δ)| > 전체 프레임 수 → 스래싱 발생
```

**OS의 판단**: 모든 프로세스 워킹셋 합이 가용 프레임 초과 시 → 프로세스 일시 중단

---

## 5. 실무 적용 및 시험 답안 포인트

**답안 작성 3단락 구조**:

- **1단락 (개념)**: "스래싱은 다중 프로그래밍 환경에서 프로세스에 할당된 프레임이 워킹셋보다 작을 때 페이지 폴트가 연속 발생하여 CPU가 페이지 교체에 대부분의 시간을 소비하는 현상이다."
- **2단락 (원리+해결)**: CPU 이용률 곡선(역 U자형), 워킹셋 모델, PFF 기법 도식 포함
- **3단락 (현대 트렌드)**: "클라우드 환경에서 VM 메모리 오버커밋(Overcommit) 시 스래싱과 유사한 메모리 벌루닝(Ballooning) 현상이 발생하며, K8s OOM Killer가 이를 해결한다."

---

## 6. 결론 및 최신 트렌드

클라우드/컨테이너 환경에서 메모리 오버커밋은 스래싱의 현대적 형태를 유발한다. Kubernetes의 OOM Killer, Memory Request/Limit 설정, Huge Pages 활용이 스래싱 방지의 현대적 기법이다. AI 워크로드에서 GPU VRAM 초과 시 발생하는 CUDA Out of Memory도 스래싱의 GPU 버전으로 이해할 수 있다.

| OOM Killer (K8s) | 컨테이너 환경의 스래싱 대응 |
| 메모리 벌루닝 | VM 환경의 스래싱 유사 현상 |
