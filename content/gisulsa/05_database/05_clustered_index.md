# 🎯 핵심 키워드: 클러스터드 인덱스, 비클러스터드 인덱스, B+-트리, 힙 파일

> **출제 빈도**: ★★★★★ | **기출**: ★136회

## 1. 정의

**클러스터드 인덱스(Clustered Index)**: 인덱스 키 순서대로 실제 **데이터가 물리적으로 정렬**되어 저장. 테이블당 1개.

**비클러스터드 인덱스(Non-Clustered Index)**: 인덱스 구조가 데이터와 **별도 저장**. 실제 데이터 위치(포인터) 참조. 테이블당 여러 개 가능.

## 2. 비교 (핵심 암기)

| 항목 | Clustered | Non-Clustered |
|------|-----------|---------------|
| 데이터 저장 | 인덱스 순서대로 정렬 | 별도 인덱스 페이지 |
| 개수 | 테이블당 1개 | 여러 개 가능 |
| 범위 검색 | ★매우 빠름 (순차 I/O) | 느림 (랜덤 I/O) |
| 단일 조회 | 빠름 | 인덱스→데이터 2단계 |
| Insert/Update | 느림 (재정렬) | 상대적 빠름 |
| 공간 | 추가 공간 없음 | 인덱스 별도 공간 |
| SQL Server | PK 기본 생성 | 명시 생성 |
| MySQL InnoDB | PK = 클러스터드 | Secondary Index |

## 3. 답안 목차 템플릿

**문제**: "클러스터드 인덱스와 비클러스터드 인덱스를 비교하고, 설계 시 고려사항을 설명하시오."

```
I. 인덱스 기초 & 필요성
   - 풀 스캔: O(N), 인덱스: O(log N) ~ O(1)
   - B+-트리: 리프 노드에 데이터/포인터, 범위 검색 최적

II. 클러스터드 인덱스 구조
   
   [B+-트리 Clustered Index]
   루트 노드: [30|70]
      ↓         ↓
   내부 노드: [10|20|30] [40|50|70]
      ↓              ↓
   리프 노드: ─ 실제 데이터 행 (정렬 순서) ─→ 다음 리프
   
   특징:
   - 리프 = 실제 데이터 페이지 (별도 힙 없음)
   - 범위 쿼리 WHERE id BETWEEN 100 AND 200: 연속 I/O

III. 비클러스터드 인덱스 구조
   
   [Non-Clustered Index + Heap]
   B+-트리 (인덱스 전용)
   리프 노드: [키값 | RID(포인터)]
                    ↓
              힙 테이블 (실제 데이터, 무순서)
   
   InnoDB (MySQL):
   Secondary Index 리프 = [키값 | PK값]
   → PK로 Clustered Index 재탐색 (두 번 B-트리 탐색)

IV. 설계 고려사항
   
   클러스터드 인덱스 선택 기준:
   - 범위 검색 많은 컬럼 (날짜, 연속 숫자)
   - 자주 정렬 기준이 되는 컬럼
   - 단조 증가 (Auto-increment PK) → 페이지 분할 최소화
   
   비클러스터드 인덱스 선택:
   - 등치 검색 많은 컬럼 (Email, 코드)
   - 필터 조건이 자주 사용되는 컬럼
   - 커버링 인덱스: SELECT 컬럼 모두 인덱스에 포함 → 힙 미접근
   
   성능 함정:
   - 랜덤 PK (UUID): Clustered 페이지 분할 심각 → ULID 권장
   - 인덱스 과다: 쓰기 성능 저하 (모든 인덱스 갱신)
```

## 4. 핵심 암기 포인트

- **Clustered = 데이터가 인덱스 순서로 물리 저장**, 1개만
- **Non-Clustered = 별도 인덱스+포인터**, 여러 개 가능
- **InnoDB**: PK가 자동으로 Clustered, 나머지 Secondary는 PK 포인터 사용
- **커버링 인덱스**: 조회 컬럼이 모두 인덱스에 있으면 힙 미접근 → 최속
