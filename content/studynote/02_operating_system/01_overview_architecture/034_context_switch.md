## 0. 핵심 인사이트

> **핵심**: 컨텍스트 스위칭 (Context Switch) 심화은(는) 운영체제가 자원을 추상화하고 통제하는 과정에서 성능, 보호, 응답성을 동시에 조율하기 위해 필요한 핵심 개념이다.
> **비유**: 컨텍스트 스위칭 (Context Switch) 심화은(는) 복잡한 교통을 한 번에 통제해 전체 흐름을 맞추는 신호 체계와 같다.

---

📝 모범 답안

## 1. 개요 및 필요성

컨텍스트 스위칭은 **인터럽트·시스템 콜·타임슬라이스 만료** 시 발생한다.

```
컨텍스트 스위칭 순서:

1. 인터럽트/시스템 콜 발생
   ↓
2. 현재 프로세스 A의 CPU 레지스터 상태 → PCB_A에 저장
   (PC, SP, 범용 레지스터, PSW 등)
   ↓
3. 스케줄러: 다음 프로세스 B 선택
   ↓
4. PCB_B에서 레지스터 상태 복원
   ↓
5. 프로세스 B 실행 재개
```

### PCB (Process Control Block) 저장 내용

| 항목              | 내용                        |
|-----------------|---------------------------|
| 프로세스 상태     | Running/Ready/Blocked      |
| 프로그램 카운터  | 다음 실행 명령 주소          |
| 스택 포인터      | 현재 스택 위치               |
| 범용 레지스터    | R0~R15 등                   |
| 메모리 관리 정보 | 페이지 테이블 기준 레지스터   |
| I/O 상태 정보   | 열린 파일·I/O 요청 상태       |

📢 **섹션 요약 비유**: 컨텍스트 스위칭은 책갈피 교체다 — A 학생 책의 책갈피(PCB)를 꽂고, B 학생 책에서 책갈피를 빼서 그 페이지부터 이어 읽는다.

## 2. 구성요소

### 직접 비용 (Direct Cost)

- 레지스터 저장/복원: ~수십 나노초
- 커널 모드 전환: 특권 레벨 변경 오버헤드

### 간접 비용 (Indirect Cost)

```
CPU 캐시 콜드 미스:
  프로세스 A의 워킹셋이 캐시에 있음
  → 스위칭 후 프로세스 B가 캐시 미스 반복
  → 성능 저하 (캐시 웜업 시간)

TLB 플러시:
  가상→물리 주소 변환 캐시(TLB) 무효화
  → 이후 페이지 테이블 접근 비용 증가
  → ASID(Address Space ID)로 플러시 회피 가능
```

📢 **섹션 요약 비유**: 간접 비용은 새 직원 적응 시간이다 — 직원 교체(스위칭) 자체는 빠르지만, 새 직원이 업무 파악(캐시 웜업)을 다시 해야 하는 시간이 더 크다.

## 3. 구조 및 원리

**핵심 조건**: 운영체제의 해당 메커니즘은 현재 상태 정보, 자원 제약, 정책 기준이 함께 정합성을 가질 때 안정적으로 동작한다.

동작 순서:
1. **요청 또는 이벤트 발생**: 사용자 요청, 인터럽트, 시스템 호출 등으로 커널이 해당 기능을 처리할 필요가 생긴다.
2. **현재 상태 확인**: 커널은 큐, 제어 블록, 메타데이터, 자원 가용량을 확인해 실행 가능 여부와 우선순위를 판단한다.
3. **정책 적용 및 자원 배정**: 해당 주제의 핵심 정책에 따라 상태 전이, 자원 할당, 보호 검사를 수행한다.
4. **결과 반영 및 후속 처리**: 처리 결과를 시스템 상태에 기록하고 다음 인터럽트·스케줄링·복구 단계로 연결한다.

| 항목            | 프로세스 간 전환          | 스레드 간 전환          |
|---------------|------------------------|----------------------|
| 주소 공간      | 변경 (TLB 플러시 필수)   | 동일 (TLB 유지 가능)   |
| 레지스터       | 저장/복원                | 저장/복원              |
| 메모리 맵      | 새 페이지 테이블 로딩     | 공유 (추가 비용 없음)  |
| 비용           | 무겁다 (마이크로초 수준) | 가볍다 (수백 나노초)   |

**코루틴/그린 스레드**: 사용자 공간에서 스케줄링 → 커널 개입 없어 더욱 빠름 (수십 나노초)

📢 **섹션 요약 비유**: 스레드 전환은 같은 책의 페이지 교체(공유 주소 공간)이고, 프로세스 전환은 다른 책으로 교체(새 주소 공간·TLB 플러시)다.

## 5. 실무 적용 및 판단

```
스레드 풀 최적 크기 공식 (Brian Goetz):
  I/O 집약적: N_threads = N_CPU × (1 + W/C)
  CPU 집약적: N_threads = N_CPU + 1

  W = 대기 시간 (I/O 블로킹)
  C = CPU 처리 시간

예시 (8코어, W/C = 9):
  N_threads = 8 × (1 + 9) = 80
```

### 컨텍스트 스위치 스톰 방지

```
문제: 스레드 1,000개 → 컨텍스트 스위치 오버헤드 > 실작업 시간
해결:
  1. 스레드 풀 크기 제한
  2. 비동기 I/O (epoll/io_uring) 사용
  3. 코루틴 (Go goroutine, Python asyncio)
  4. NUMA-aware 스레드 배치
```

📢 **섹션 요약 비유**: 스레드 풀 최적화는 요리사 수 결정이다 — 주방(CPU)보다 요리사(스레드)가 너무 많으면 서로 길이 막혀(컨텍스트 스위치) 실제 요리 시간이 줄어든다.

## 6. 기대효과 및 결론

| 유형             | 발생 원인              | 예시                     |
|----------------|----------------------|--------------------------|
| 자발적 (Voluntary) | 프로세스가 스스로 양보  | sleep(), I/O 대기, yield() |
| 비자발적 (Involuntary) | OS 스케줄러가 강제 교체 | 타임슬라이스 만료, 고우선순위 프로세스 도착 |

**성능 지표**:
```bash
vmstat 1          # cs 컬럼 = 초당 컨텍스트 스위치 수
pidstat -w 1      # 프로세스별 자발/비자발 스위치 수
```

📢 **섹션 요약 비유**: 자발적 스위치는 휴게시간에 교대하는 것이고, 비자발적 스위치는 상사가 "잠깐 멈춰!"라고 중단시키는 것이다.

## 7. 발전 흐름도

```
┌─────────────────────────────────────────────────────────────────┐
│              컨텍스트 스위칭 발전 흐름                           │
├──────────────┬────────────────────┬─────────────────────────────┤
│ 1960년대     │ 멀티프로그래밍 시작 │ 최초 컨텍스트 스위치 구현   │
│ 1970년대     │ Unix 멀티프로세싱   │ PCB 구조 표준화              │
│ 1990년대     │ 멀티스레딩 OS      │ 경량 TCB 컨텍스트 스위치    │
│ 2000년대     │ 멀티코어 CPU       │ 코어 수 증가 → 병렬성 활용  │
│ 2010년대     │ 코루틴/async       │ Go goroutine, Python asyncio|
│ 2020년대     │ io_uring (Linux)   │ 비동기 I/O로 스위칭 최소화  │
└──────────────┴────────────────────┴─────────────────────────────┘

핵심 키워드 연결:
인터럽트 → 컨텍스트 스위치 → PCB 저장 → 스케줄러 → 다음 프로세스
    ↓              ↓                ↓           ↓
타임슬라이스   레지스터 저장    TLB 플러시   우선순위 큐
    ↓
스레드 풀 최적화 → 비동기 I/O → 코루틴 → 컨텍스트 스위치 최소화
```
