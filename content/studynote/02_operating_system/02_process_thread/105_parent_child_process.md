## 0. 핵심 인사이트

> **핵심**: 부모 프로세스 (Parent Process)와 자식 프로세스 (Child Process)는 `fork()` 시스템 콜을 통해 생성되며, 자식이 부모의 식별자인 PPID (Parent Process ID)를 기록하여 형성하는 운영체제의 트리형 프로세스 계층 구조다.
> **비유**: 부모 프로세스 (Parent Process) / 자식 프로세스 (Child Process)은(는) 복잡한 교통을 한 번에 통제해 전체 흐름을 맞추는 신호 체계와 같다.

---

📝 모범 답안

## 1. 개요 및 필요성

유닉스 (Unix) 및 리눅스 (Linux) 환경에서 프로그램이 실행되는 기본 단위인 프로세스는 스스로를 복제하여 새로운 흐름을 만들어낸다. `fork()` 시스템 콜이 호출되면, 호출한 원본 프로세스는 '부모'가 되고 생성된 복사본은 '자식'이 된다. 자식 프로세스는 자신의 독립적인 PID (Process ID)를 발급받으면서도 PCB (Process Control Block) 안에 부모의 PID를 PPID로 저장함으로써 명확한 혈통 관계를 맺는다.

이러한 부모-자식 관계가 필요한 이유는 운영체제의 작업 병렬성과 격리성 때문이다. 사용자가 셸(Shell)에서 명령어를 입력할 때마다 셸 자체가 새로운 프로그램으로 변해버리면 셸은 영영 사라진다. 따라서 셸은 자신의 복제본(자식)을 만들어 명령어를 대신 실행(`exec()`)하게 하고, 자신은 자식이 작업을 끝낼 때까지 대기(`wait()`)하는 위임 체계를 갖춰야만 연속적인 시스템 운영이 가능해진다.

---

## 2. 구성요소

프로세스 트리의 핵심은 `fork()`, `exec()`, `wait()`, `exit()`로 이어지는 4단계의 라이프사이클 동기화 메커니즘이다.

```text
┌──────────────────────────────────────────────────────────────┐
│       부모-자식 프로세스의 생명주기 및 상태 전이 다이어그램  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  [ Parent Process ]             [ Child Process ]            │
│  (PID: 100, PPID: 10)                                        │
│          │                                                   │
│          ├─ fork() ──────────▶ (복제 및 분기)                │
│          │                     (PID: 101, PPID: 100)         │
│          │                              │                    │
│          │                              ├─ exec()            │
│          │                              │  (새 프로그램 로드)│
│          ▼                              ▼                    │
│      wait() 대기                    실행 중 (Running)        │
│    (수면 상태 진입)                     │                    │
│          │                              ├─ exit(status)      │
│          │                              ▼                    │
│          │◀── SIGCHLD 시그널 ─── [ Zombie 상태 진입 ]        │
│          │                       (메모리 해제, PCB 잔류)     │
│          ▼                              │                    │
│  상태 회수 및 자원 해제 ────────────────┘                    │
│    (종료 상태 획득)               [ 프로세스 완전 소멸 ]     │
└──────────────────────────────────────────────────────────────┘
```

1. **생성 (`fork`)**: 커널은 부모의 `task_struct`를 복사해 자식에게 할당한다. 이때 자원은 상속되나 주소 공간은 독립적으로 분리된다.
2. **변환 (`exec`)**: 자식은 상속받은 껍데기에 새로운 실행 파일의 코드와 데이터를 덮어씌워 완전히 다른 프로그램으로 탈바꿈한다.
3. **종료 (`exit`)**: 자식은 실행을 마치면 메모리를 반환하지만, 부모에게 전달할 종료 코드(Exit Status)를 보관하기 위해 PCB 껍데기만 남긴 채 좀비(Zombie) 상태가 된다.
4. **회수 (`wait`)**: 부모는 `wait()` 또는 `waitpid()`를 호출하여 자식의 종료 상태를 읽어 들인다. 이 순간 커널은 자식의 남은 PCB마저 파기하여 시스템에서 완전히 지운다.

## 3. 구조 및 원리

**핵심 조건**: 운영체제의 해당 메커니즘은 현재 상태 정보, 자원 제약, 정책 기준이 함께 정합성을 가질 때 안정적으로 동작한다.

동작 순서:
1. **요청 또는 이벤트 발생**: 사용자 요청, 인터럽트, 시스템 호출 등으로 커널이 해당 기능을 처리할 필요가 생긴다.
2. **현재 상태 확인**: 커널은 큐, 제어 블록, 메타데이터, 자원 가용량을 확인해 실행 가능 여부와 우선순위를 판단한다.
3. **정책 적용 및 자원 배정**: 해당 주제의 핵심 정책에 따라 상태 전이, 자원 할당, 보호 검사를 수행한다.
4. **결과 반영 및 후속 처리**: 처리 결과를 시스템 상태에 기록하고 다음 인터럽트·스케줄링·복구 단계로 연결한다.

부모-자식 프로세스 모델은 스레드 (Thread) 모델이나 고아 프로세스 대응 메커니즘과 비교할 때 그 특징이 명확해진다.

| 항목 | 부모-자식 프로세스 (멀티프로세스) | 부모-자식 스레드 (멀티스레드) |
|:---|:---|:---|
| **메모리 공간** | `fork()`로 완전히 독립된 공간 할당 | 생성 시 힙(Heap)과 데이터 영역 공유 |
| **안정성/격리성** | 자식이 죽어도 부모나 다른 자식에 영향 없음 | 한 스레드의 오류(Segfault)가 전체를 죽임 |
| **IPC 통신 비용** | 파이프, 공유 메모리 등 무거운 통신 필요 | 메모리 직접 접근으로 통신 비용 극소화 |
| **생성 오버헤드** | PCB 및 페이지 테이블 복제로 무거움 | 스택(Stack)만 할당하므로 매우 가벼움 |

부모 프로세스가 자식보다 먼저 비정상 종료되는 경우, 자식은 PPID를 잃어버리고 고아 (Orphan) 프로세스가 된다. 운영체제는 이러한 미아를 방치하지 않고 프로세스 트리의 최상위 조상인 `init` 프로세스(PID 1, 현대 리눅스의 systemd)에게 입양시킨다. `init`은 주기적으로 `wait()`를 호출하여 고아 프로세스가 종료될 때 좀비가 되지 않도록 안전하게 거두어들이는 백스톱(Backstop) 역할을 수행한다.

## 5. 실무 적용 및 판단

대규모 서버 아키텍처나 컨테이너 환경에서 부모-자식 프로세스의 수명주기 관리는 시스템 장애를 예방하는 가장 중요한 의사결정 포인트다.

### 체크리스트 및 판단 포인트
1. **좀비 프로세스 (Zombie Process) 누수 방어**: 부모 프로세스에 자식을 생성하는 로직만 있고 `wait()` 계열 시스템 콜을 호출하는 로직이 없거나 누락되었다면 최악의 안티패턴이다. 자식이 종료된 후에도 PID 테이블을 차지하는 좀비가 무한히 쌓이게 되며, 결국 커널의 PID 고갈(PID Exhaustion)로 이어져 시스템이 멈추게 된다. 반드시 비동기적 `SIGCHLD` 시그널 핸들러를 구현하여 `waitpid(WNOHANG)`으로 즉시 회수해야 한다.
2. **백그라운드 데몬화 (Daemonization) 전략**: 부모에 종속되지 않고 시스템 백그라운드에서 영구히 동작하는 데몬 프로세스를 만들려면 더블 포크 (Double Fork) 기법을 사용한다. 부모가 자식을 만들고 스스로 즉시 종료(`exit`)해 버리면, 손자 프로세스는 고아가 되어 `init`에 입양됨으로써 원래 터미널의 통제권에서 완전히 벗어난 진정한 백그라운드 워커가 된다.
3. **컨테이너 (Docker/K8s)의 PID 1 문제**: 도커 컨테이너 내부에서 일반 애플리케이션 애플리케이션을 PID 1로 띄우면, 이 앱은 `init` 프로세스가 아니기 때문에 하위 프로세스가 만든 좀비들을 수거할 능력이 없다. 이로 인해 컨테이너 내부에 좀비가 가득 차는 장애가 빈번히 발생한다. 이를 막기 위해 `tini`나 `dumb-init` 같은 경량 `init` 프로세스를 컨테이너의 Entrypoint로 세워 좀비 수거를 위임해야 한다.

## 6. 기대효과 및 결론

운영체제의 부모-자식 프로세스 모델은 복잡한 다중 작업을 안전하게 격리하고 위임하는 가장 검증된 뼈대다.

자원의 상속을 통해 무거운 초기화 비용을 극복하고, 독립된 주소 공간을 통해 하나의 작업 실패가 전체 시스템의 붕괴로 이어지는 것을 원천 차단한다. 현대의 클라우드 네이티브 환경에서는 이 프로세스 트리 계층 위에 cgroup과 PID Namespace (네임스페이스) 기술을 융합하여, 컨테이너라는 완벽히 독립된 가상의 부모-자식 왕국을 무한히 찍어내는 아키텍처로 진화했다. 프로세스 관계의 핵심은 단순히 낳는 것(`fork`)이 아니라, 책임지고 끝을 맺어주는 것(`wait`)에 있음을 기억해야 한다.

## 7. 발전 흐름도

```text
단일 프로세스 시스템 (MS-DOS)
    │
    ▼
부모-자식 프로세스 계층 (Unix fork/exec 모델 도입)
    │
    ▼
멀티스레딩 (Multithreading, 프로세스 내 자원 공유 및 경량화)
    │
    ▼
cgroup 및 Namespace (리눅스 커널의 자원 격리 기술)
    │
    ▼
컨테이너 기반 독립 프로세스 트리 (Docker, Kubernetes)
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| **fork() / exec()** | 부모가 자식을 복제 생성(fork)하고, 자식은 새로운 프로그램으로 탈바꿈(exec)하는 생성 사이클 콜. |
| **wait() / exit()** | 자식이 종료 코드를 남기고(exit), 부모가 이를 수거하여(wait) 자원을 최종 반환하는 소멸 사이클 콜. |
| **좀비 프로세스 (Zombie)** | 자식이 종료되었으나 부모가 `wait()`를 해주지 않아 시스템에 껍데기만 남아있는 프로세스. |
| **고아 프로세스 (Orphan)** | 부모가 먼저 죽어버려 갈 곳을 잃고 PID 1(`init`)에게 입양되는 프로세스. |
