## 0. 핵심 인사이트

> **핵심**: 인터넷 쇼핑몰의 완벽한 자물쇠인 TLS(SSL)는 '택배가 순서대로 도착해야만' 문을 열어주는 깐깐한 TCP 통신 위에서만 돌아간다. 그런데 가난한 IoT 센서들은 TCP 대신 우표만 붙여 대충 던지는 UDP(CoAP)를 쓴다. UDP의 순서가 뒤죽박죽 날아오더라도 어떻게든 자물쇠를 걸어 억지로 잠글 수 있게 TLS를 마개조한 돌연변이 보안 기술이 바로 DTLS다.
> **비유**: DTLS (Datagram TLS) 프로토콜 CoAP 결합은(는) IoT·WPAN·엣지 네트워크 안에서 데이터와 제어 규칙을 질서 있게 맞춰 주는 교통 체계와 같다.

> 📝 모범 답안

## 1. 개요 및 필요성

- **개념**: 연결 지향적인 TCP 프로토콜 기반 위에서 돌아가던 암호화 표준인 **TLS(SSL) 보안 기술을, 비연결성이고 데이터 유실이 잦은 UDP(Datagram) 통신 환경에서도 그대로 쓸 수 있도록 개조한 보안 프로토콜**입니다. (IETF RFC 6347)
- **왜 필요한가?**: 623번 문서에서 배운 초경량 IoT 프로토콜인 **CoAP**나 실시간 화상회의 프로토콜인 **WebRTC**는 속도와 전력 소모를 위해 무조건 UDP를 씁니다. 이런 데이터들이 허공에서 해킹당하지 않게 암호화하려면 DTLS가 유일한 해결책입니다.

- UDP는 패킷 번호표가 없어서 누가 먼저 온 패킷인지 모릅니다.
- DTLS는 암호화 패킷 겉면에다가 `[나는 1번 암호 패킷이야]`, `[나는 2번이야]`라고 **명시적인 번호표(Explicit Sequence Number)**를 큼직하게 달아줍니다. 덕분에 도착 순서가 뒤죽박죽 섞여도 수신기가 번호표를 보고 차례대로 예쁘게 퍼즐을 맞춰 암호를 풀 수 있습니다.

## 2. 구성요소

일반 TLS를 UDP에 그냥 얹으면 패킷 순서가 뒤섞이거나 하나만 날아가도 암호가 꼬여서 전체 통신이 영원히 마비되는 끔찍한 에러가 터집니다. DTLS는 이를 3가지 꼼수로 극복합니다.

- 암호 키를 처음 교환하는 핸드셰이크 과정 중에 UDP 패킷 하나가 허공으로 증발해 버릴 수 있습니다.
- TCP는 자기가 알아서 재전송해 주지만 UDP는 그런 기능이 없으므로, DTLS 프로토콜 자체가 **"타이머를 켜놓고 1초 동안 상대방 답장이 안 오면, 아까 보낸 암호 키를 내가 다시 쏜다!"라는 자체 재전송 로직**을 내장해 버렸습니다.

## 3. 구조 및 원리

**핵심 조건**: DTLS (Datagram TLS) 프로토콜 CoAP 결합은(는) 저전력, 센서, 게이트웨이 조건을 함께 만족할 때 안정적으로 동작한다.

동작 순서:

- 특정 패킷 하나가 해커의 노이즈 때문에 완전히 깨져서 도착하면, 기존 TLS는 전체 암호화 흐름이 꼬여 세션을 끊어버렸습니다.
- DTLS는 패킷 하나하나를 완전히 독립적으로 암호화 처리하여, **하나의 패킷이 깨져서 날아오면 그냥 쿨하게 버리고 다음 패킷 암호부터 정상적으로 풀어나가도록(오류 전파 억제)** 설계되었습니다.

사물인터넷(IoT) 기기들이 서로 대화할 때 데이터 유출을 막는 공식적인 아키텍처 조합입니다.
- **애플리케이션 계층**: CoAP (온도, 제어 명령어 생성)
- **보안 계층**: DTLS (CoAP 데이터를 AES 암호화)
- **전송 계층**: UDP (빠르고 가볍게 목적지로 던짐)
- **네트워크 계층**: IPv6 / 6LoWPAN

| 적용 범위 | IoT·WPAN·엣지 네트워크의 특정 문제를 직접 해결 | 상위·하위 계층 또는 대체 방식이 일부 기능을 분담 | 요구사항과 계층 경계 확인 |
| 장점 | 저전력과 센서을 구조적으로 통제 | 범용성 또는 단순성이 강점 | 목적에 맞는 선택 필요 |
| 한계 | 게이트웨이·운영 복잡도 증가 가능 | 기능은 단순하지만 제어력 제한 | 비용·표준 호환성 검토 |

핵심은 단순 우열 비교가 아니라, DTLS (Datagram TLS) 프로토콜 CoAP 결합이 어떤 맥락에서 더 적합한지와 인접 기술과의 역할 분담을 해석하는 데 있다.

## 5. 실무 적용 및 판단

**채택 조건**
- 저전력과 센서을 동시에 관리해야 할 때
- 운영 자동화 또는 표준화된 제어가 필요할 때
- 장애 분석 시 원인 구분이 명확해야 할 때

**회피 조건**
- 단순 환경이라 오버헤드가 더 큰 경우
- 장비·프로토콜 호환성이 확보되지 않은 경우
- 측정 지표 없이 관행적으로만 적용하는 경우

**체크리스트**
1. 요구 성능과 허용 지연이 정의되었는가?
2. 오류·혼잡·보안 처리 경계가 명확한가?
3. 표준·벤더 구현 차이를 검증했는가?
4. 운영 관측성 및 장애 대응 절차가 준비되었는가?

## 6. 기대효과 및 결론

DTLS (Datagram TLS) 프로토콜 CoAP 결합을 적용하면 저전력과 센서에 대한 통제력이 높아지고, 운영 일관성과 성능 예측 가능성을 확보할 수 있다. 반면 설정 복잡도, 표준 호환성, 장비 비용, 운영 숙련도라는 전제가 뒤따르므로 무조건적인 도입이 정답은 아니다. 결론적으로 이 주제는 IoT·WPAN·엣지 네트워크를 이해하는 기준점이며, 최근에는 자동화·가상화·지능형 제어와 결합해 더 세밀한 최적화 방향으로 진화하고 있다.
