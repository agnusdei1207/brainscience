## 0. 핵심 인사이트

> **핵심**: 소프트웨어 생명주기 (SDLC, Software Development Life Cycle)는 소프트웨어를 요구 도출부터 폐기까지 통제 가능한 단계와 피드백 루프로 분해해, 복잡한 개발을 관리 가능한 공정으로 바꾸는 틀이다.
> **비유**: 설계 없이 바로 공사에 들어가는 대신, 기획·설계·시공·검수·유지보수의 순서를 가진 건설 공정을 운영하는 것과 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

SDLC는 소프트웨어를 만드는 전 과정을 단계별 활동으로 정의한 프레임워크다. 일반적으로 요구사항 분석, 설계, 구현, 테스트, 배포, 운영 및 유지보수로 구성되며, 각 단계는 산출물과 검증 기준을 가진다. 핵심은 단계를 나누는 데 있지 않고, **각 단계의 책임과 피드백 경로를 명확히 한다는 점**에 있다.

SDLC가 필요한 이유는 소프트웨어 개발이 단순한 제작 활동이 아니기 때문이다. 요구사항은 계속 바뀌고, 설계는 품질 속성에 영향을 주며, 코드의 결함은 테스트와 운영에서 드러난다. 만약 이 흐름을 명시하지 않으면 개발은 "거의 다 됐다"는 감각적 표현만 남는 블랙박스가 된다.

또한 결함 발견 시점이 늦을수록 수정 비용은 급격히 증가한다. 요구 단계의 오류는 문서 수정으로 끝날 수 있지만, 운영 단계에서 발견되면 설계, 코드, 데이터, 사용자 교육, 배포 절차까지 함께 손봐야 할 수 있다. SDLC는 이런 비용 폭증을 줄이기 위해 **단계별 확인과 환류 구조**를 제공한다.

현대에는 SDLC가 고정된 폭포형 절차만을 의미하지 않는다. 애자일, DevOps, 보안 소프트웨어 생명주기 (Secure SDLC, SSDLC)도 모두 생명주기 개념 위에서 구현 방식만 다르게 가져가는 것이다. 따라서 SDLC는 특정 방법론이 아니라, 다양한 방법론이 공유하는 **공통 골격**으로 이해하는 것이 정확하다.

## 2. 구성요소

| 단계 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 요구사항 분석 | 무엇을 왜 만들지 정의 | 범위, 제약, 이해관계자 기대를 명확히 해야 이후 재작업을 줄일 수 있음 |
| 설계 | 어떻게 만들지 구조화 | 아키텍처, 데이터, 인터페이스가 품질과 변경 비용을 결정 |
| 구현 | 설계를 코드로 구체화 | 표준화된 코딩과 리뷰가 품질 편차를 줄임 |
| 테스트 | 산출물이 요구를 만족하는지 검증 | 단위·통합·시스템·인수 테스트가 계층적으로 작동 |
| 배포 | 운영 가능한 형태로 릴리즈 | 빌드, 패키징, 환경 반영, 롤백 전략이 중요 |
| 운영·유지보수 | 실제 사용 환경에서 서비스 유지 | 장애 대응, 성능 개선, 환경 적응, 예방 보수가 포함 |
| 종료·전환 | 시스템 폐기 또는 차세대 전환 | 데이터 이전, 계약 정리, 지식 인계가 필요 |

이 단계들은 단방향 직선이 아니라 입력과 출력이 연결된 네트워크다. 설계는 요구사항을 입력으로 받고, 테스트는 설계와 구현을 동시에 참조하며, 운영 단계의 장애 정보는 다시 요구사항과 아키텍처 개선의 재료가 된다. 그래서 SDLC는 단계 집합이 아니라 **산출물 흐름과 책임 흐름의 설계도**다.

특히 기준선 (Baseline)과 추적성은 SDLC의 숨은 축이다. 요구사항 ID가 설계, 코드, 테스트, 결함 관리와 연결되지 않으면 단계는 존재해도 실제 통제는 불가능하다.

## 3. 구조 및 원리

**핵심 조건**: 각 단계는 명확한 입력·출력·검증 기준을 가져야 하며, 후행 단계의 피드백이 선행 단계로 되돌아갈 수 있어야 한다.

이 조건이 중요한 이유는 생명주기가 "순서"만으로는 작동하지 않기 때문이다. 입력 산출물이 불명확하거나, 단계 종료 기준이 없거나, 피드백이 역류하지 못하면 SDLC는 형식적 체크리스트로 전락한다.

동작 순서:
1. **요구 정의**: 사용자 목표와 비즈니스 제약을 명세로 정리한다. 이 단계에서 성공 기준을 설정해야 테스트와 인수가 가능하다.
2. **설계 구체화**: 요구사항을 만족하는 구조와 인터페이스를 정의한다. 품질 속성은 이 단계에서 대부분 결정된다.
3. **구현 및 단위 검증**: 설계를 모듈 단위 코드로 전환하고, 기본 결함을 조기에 제거한다.
4. **통합 및 시스템 검증**: 모듈 간 상호작용과 전체 시나리오를 확인한다. 인터페이스 불일치와 비기능 요구 검증이 핵심이다.
5. **배포 및 운영 검증**: 실제 환경에 적용해 운영 특성과 사용자 반응을 확인한다. 개발 환경에서 보이지 않던 문제가 드러날 수 있다.
6. **변경 환류**: 운영 결과와 신규 요구를 다음 주기의 입력으로 반영한다. 이 환류가 끊기면 같은 실수가 반복된다.

```
[요구사항]
   ↓  산출물: 소프트웨어 요구사항 명세서 (SRS), 우선순위
[설계]
   ↓  산출물: 아키텍처, 데이터, 인터페이스
[구현]
   ↓  산출물: 코드, 단위 테스트
[검증]
   ↓  산출물: 결함 보고, 테스트 결과
[배포/운영]
   ↓  산출물: 로그, 장애, 사용자 피드백
[변경 관리]
   ↺  다음 요구사항으로 환류
```

실제로는 각 단계가 완전히 끝난 뒤 다음 단계로만 넘어가는 경우보다, 짧은 주기로 반복되는 경우가 많다. 그러나 반복적 모델이든 폭포수 모델이든 SDLC의 원리는 같다. 즉 **산출물을 명확히 정의하고, 검증 기준을 갖추고, 피드백을 역방향으로 연결하는 것**이다.

## 4. 비교 및 연결

| 항목 | 폭포수형 SDLC | 반복·증분형 SDLC | DevOps 지향 SDLC |
|:---|:---|:---|:---|
| 진행 방식 | 단계별 대규모 순차 진행 | 작은 기능 단위 반복 | 개발-배포-운영을 연속적으로 연결 |
| 강점 | 통제와 감사 용이 | 요구 변경 대응력 우수 | 배포 속도와 운영 피드백 반영 우수 |
| 약점 | 후반 리스크 집중 | 범위 관리가 어려울 수 있음 | 자동화·조직 역량이 부족하면 혼란 |
| 적합 환경 | 규제 강한 대형 프로젝트 | 변화가 빠른 제품 개발 | 서비스 운영 중심 조직 |

SDLC는 요구공학, 테스트, 형상 관리, DevOps의 공통 기반이다. 요구공학은 앞단의 품질을, 테스트는 중간의 검증을, 형상 관리는 산출물 정합성을, DevOps는 후단의 배포와 운영 피드백 속도를 담당한다. 즉 SDLC는 이들을 연결하는 상위 프레임이다.

또한 Secure SDLC는 생명주기의 각 단계에 보안 활동을 삽입한 형태다. 요구 단계의 위협 분석, 설계 단계의 보안 설계, 구현 단계의 시큐어 코딩, 테스트 단계의 취약점 진단, 운영 단계의 패치 관리가 이에 해당한다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 프로젝트 진행 상황을 단계와 산출물 기준으로 관리해야 할 때
- 다수 조직이 협업해 인수인계와 추적성이 중요할 때
- 규제·감사·품질 요구가 명확할 때

**주의 조건**:
- 단계만 있고 종료 기준과 환류 구조가 없는 경우
- 산출물은 많지만 실제 의사결정에 쓰이지 않는 경우
- 운영 데이터를 수집하지 않아 생명주기가 배포에서 끝나는 경우

체크리스트:
1. 각 단계의 입력·출력 산출물이 정의되어 있는가?
2. 요구사항과 테스트 케이스가 추적 가능한가?
3. 결함이나 운영 이슈가 상위 단계로 환류되는가?
4. 배포가 수작업 의존 없이 반복 가능한가?
5. 유지보수 유형(수정·적응·완전·예방)이 계획적으로 관리되는가?

실무에서는 금융권 차세대 시스템처럼 앞단 문서와 승인 절차가 강한 형태도 있고, 서비스형 소프트웨어 (SaaS) 제품처럼 지속적 통합/지속적 배포 (CI/CD)를 통해 하루에도 여러 번 생명주기를 도는 형태도 있다. 차이는 속도와 granularity에 있을 뿐, 둘 다 SDLC를 운영하는 것이다.

## 6. 기대효과 및 결론

SDLC의 가장 큰 효과는 개발 과정을 가시화하고, 결함과 변경을 더 이른 시점에 다룰 수 있게 만든다는 점이다. 단계가 명확하면 진척도, 책임, 품질 상태를 측정할 수 있고, 이는 일정과 비용 관리의 기반이 된다.

그러나 SDLC가 문서 절차로만 남으면 오히려 형식주의를 강화할 수 있다. 따라서 현대 조직은 생명주기의 원칙은 유지하되, 자동화와 짧은 피드백 루프를 결합해 실행력을 높여야 한다.

결론적으로 SDLC는 과거형 절차가 아니라, 소프트웨어를 공정으로 다루기 위한 기본 언어다. 무엇을 만들든, 어떤 방법론을 쓰든, 결국 잘 운영되는 조직은 SDLC를 자기 방식으로 명확히 정의하고 있다.

## 7. 발전 흐름도

```
Code-and-Fix 방식
    ↓
단계 분리 중심 SDLC 정립
    ↓
폭포수·V-모델 등 구조화된 생명주기 확산
    ↓
반복·증분형 모델 등장
    ↓
애자일·CI/CD·DevOps와 결합한 연속적 생명주기
    ↓
보안·관측성·AI 보조 개발을 포함한 확장형 SDLC
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| 요구공학 | SDLC의 출발점이며 잘못 시작하면 후속 단계 전체에 영향 |
| 폭포수 모델 | SDLC를 가장 순차적으로 구현한 전통적 형태 |
| V-모델 | 설계 단계와 테스트 단계를 대응시킨 확장 형태 |
| 형상 관리 | 생명주기 산출물의 버전과 변경을 통제 |
| DevOps | SDLC의 배포·운영 피드백을 고속화하는 확장 |
| 보안 소프트웨어 생명주기 (SSDLC) | 보안을 각 단계에 내재화한 생명주기 |
