## 0. 핵심 인사이트

> **핵심**: 기밀성 (Confidentiality)은 정보를 ‘아무도 못 보게’ 만드는 것이 아니라, **권한 있는 주체만 보게** 만드는 통제의 원칙이다.
> **비유**: 같은 건물 안에서도 출입증 등급에 따라 들어갈 수 있는 층이 달라지는 것과 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

기밀성은 비인가 사용자나 시스템이 정보 자산을 열람·복제·유출하지 못하도록 제한하는 보안 속성이다. 정보보안 논의에서 가장 먼저 떠올리는 개념이지만, 실제로는 “데이터를 숨기는 기술”보다 “열람 권한을 정교하게 통제하는 체계”에 더 가깝다. 따라서 암호화만 잘한다고 기밀성이 완성되는 것은 아니다.

현대 환경에서 기밀성이 중요한 이유는 데이터가 저장, 전송, 사용 전 단계에서 끊임없이 이동하기 때문이다. 온프레미스 시절에는 물리적 망 분리와 서버 접근 제한만으로 상당 부분 보호가 가능했다. 그러나 클라우드, SaaS, 원격 근무, API 연동 환경에서는 데이터가 경계 밖으로 계속 복제·전송되므로, 데이터 자체와 접근 주체를 동시에 통제해야 한다.

기밀성 실패는 단순 노출 사고를 넘어 법적 제재와 신뢰 상실로 이어진다. 개인정보, 연구개발 자료, 금융 거래 정보처럼 외부 노출 순간 가치가 붕괴하는 자산은 특히 그렇다. 그래서 기밀성은 단일 솔루션이 아니라 데이터 분류, 접근 제어, 암호화, 키 관리, DLP (Data Loss Prevention)까지 포함하는 **생명주기 기반 통제**로 이해해야 한다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 데이터 분류 | 민감도에 따라 보호 수준 정의 | 공개/내부/기밀/극비 등 등급화 |
| 접근 제어 | 권한 있는 주체만 접근 허용 | RBAC, ABAC, Need-to-Know 적용 |
| 암호화 | 저장·전송 중 데이터 노출 억제 | AES, TLS, VPN, TDE 활용 |
| 키 관리 | 암호화 실효성 유지 | HSM, KMS, 키 순환이 핵심 |
| 유출 방지 | 정상 사용자의 비정상 반출 차단 | DLP, DRM, 워터마킹, USB 통제 |

기밀성은 보통 “암호화 + 권한 관리 + 반출 통제”의 3층 구조로 구현된다. 데이터 분류가 선행되어야 어떤 자산에 강한 통제를 적용할지 판단할 수 있고, 접근 제어는 누가 볼 수 있는지를 제한한다. 암호화는 저장 장치 탈취나 전송 가로채기에 대비하는 보호막이며, DLP/DRM은 이미 열람 권한이 있는 사용자가 외부로 반출하는 위험을 줄인다.

---

## 3. 구조 및 원리

**핵심 조건**: 기밀성은 `주체 검증` + `권한 검증` + `데이터 상태별 보호(저장·전송·사용)` + `키 분리 보관`이 함께 만족될 때 성립한다.

동작 순서:
1. **데이터 등급 결정**: 어떤 정보가 어느 수준의 보호를 요구하는지 분류한다. 보호 대상이 명확해야 통제가 과하거나 부족하지 않다.
2. **주체 인증 및 권한 부여**: 사용자의 신원과 역할을 검증한 뒤 최소 권한만 부여한다. 기밀성은 “누구나 접근 후 암호화”가 아니라 “애초에 접근을 제한”하는 데서 시작한다.
3. **상태별 보호 적용**: 저장 중에는 디스크·DB 암호화, 전송 중에는 TLS/IPsec, 사용 중에는 메모리·화면·복제 통제를 적용한다.
4. **키 분리 관리**: 데이터가 암호화되어도 키가 노출되면 기밀성은 무너진다. 따라서 키는 데이터와 다른 신뢰 경계에 보관해야 한다.
5. **유출 행위 감시**: 대량 다운로드, 외부 메일 전송, 비인가 복사 같은 행위를 탐지하고 차단한다.

```text
[사용자/서비스]
      │
      ▼
[인증·인가]
      │  최소 권한 확인
      ▼
[데이터 접근 요청]
      │
      ├─ 저장 중 보호  → 디스크/DB 암호화
      ├─ 전송 중 보호  → TLS/VPN
      └─ 사용 중 보호  → DRM/DLP/TEE
      │
      ▼
[키 관리 시스템 (KMS/HSM)]
      │  데이터와 분리된 신뢰 경계
      ▼
[기밀성 유지]
```

실무에서 가장 중요한 원리는 “데이터보다 키가 더 민감하다”는 점이다. 데이터베이스를 암호화해도 애플리케이션 설정 파일에 키를 하드코딩하면 방어 효과는 거의 없다. 또한 정상 권한 사용자의 유출이 가장 흔한 사고 유형이므로, 기밀성은 외부 해커뿐 아니라 내부자와 과도 권한도 함께 통제해야 한다.

## 4. 비교 및 연결

| 항목 | 기밀성 보호 | 무결성 보호 | 가용성 보호 |
|:---|:---|:---|:---|
| 초점 | 열람·복제 차단 | 변경·위조 차단 | 중단·지연 방지 |
| 대표 기술 | 암호화, RBAC, DRM | 해시, HMAC, 전자서명 | HA, LB, 백업 |
| 실패 사례 | 개인정보 유출, 도청 | 거래 조작, 로그 위변조 | 서비스 마비, 장애 |
| 설계 갈등 | 강한 통제는 사용성 저하 가능 | 강한 검증은 처리 지연 가능 | 높은 개방성은 공격면 확대 가능 |

기밀성은 최소 권한 원칙, 알 필요성 원칙, 제로 트러스트와 밀접하다. 특히 제로 트러스트는 네트워크 내부라고 신뢰하지 않고 매 요청마다 신원과 맥락을 확인하므로, 기밀성을 네트워크 경계가 아닌 **세션·요청 단위의 동적 통제**로 재구성한다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 개인정보, 지식재산, 계약서, 자격증명 등 노출 피해가 큰 자산을 다룰 때
- 외부 협업, 클라우드 저장, 원격 접속이 빈번할 때
- 규제 준수와 법적 입증이 중요한 산업일 때

**회피 조건**:
- 데이터 등급 없이 전 자산에 동일한 강도 적용
- 암호화만 도입하고 권한·키 관리 체계는 방치
- 예외 계정, 공유 계정, 장기 미회수 권한을 허용하는 운영

체크리스트:
1. 민감 데이터 분류 기준이 존재하는가?
2. 최소 권한과 Need-to-Know가 실제 권한 모델에 반영되는가?
3. 저장·전송·사용 중 데이터 각각에 통제가 있는가?
4. 키가 데이터 저장소와 분리되어 관리되는가?
5. 대량 반출과 외부 공유를 탐지·차단하는가?

대표 사례로는 금융권의 DB 암호화와 키 분리 보관, SaaS 환경의 CASB (Cloud Access Security Broker), 기업 문서 반출 통제를 위한 DRM이 있다. 실무 판단의 핵심은 “누가 보는가”보다 “누가 언제 어떤 맥락에서 반출하는가”까지 통제 범위를 넓히는 것이다.

## 6. 기대효과 및 결론

기밀성이 잘 설계되면 정보 유출 사고 확률과 유출 범위를 동시에 줄일 수 있다. 또한 규제 준수, 고객 신뢰, 대외 협업 안전성을 높이고, 클라우드 전환 과정에서도 자산 보호 수준을 유지할 수 있다. 특히 암호화와 권한 통제가 결합되면 저장 매체 유실이나 계정 탈취 상황에서도 피해를 제한할 수 있다.

반면 한계도 분명하다. 정당한 권한을 가진 사용자의 오남용, 화면 촬영·복사 같은 우회 채널, 복잡한 권한 설계에 따른 운영 피로도는 완전히 제거하기 어렵다. 그래서 기밀성은 기술만이 아니라 권한 거버넌스와 사용자 행위 분석까지 결합해야 완성된다. 결론적으로 기밀성은 “숨김”이 아니라 **신뢰 가능한 열람 통제**다.

## 7. 발전 흐름도

```text
물리적 출입 통제 중심
    ↓
시스템 계정·권한 관리
    ↓
저장/전송 구간 암호화 보편화
    ↓
키 관리 분리 · DLP · DRM 확장
    ↓
제로 트러스트 · 데이터 중심 보안
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| 최소 권한 원칙 (Principle of Least Privilege) | 불필요한 열람 권한을 줄여 기밀성 기반을 형성 |
| 암호화 (Encryption) | 데이터 노출을 수학적으로 어렵게 만드는 핵심 수단 |
| 키 관리 시스템 (KMS) | 암호화의 실효성을 좌우하는 운영 중심 요소 |
| DLP | 정상 사용자에 의한 유출까지 통제 범위를 확장 |
| 제로 트러스트 | 기밀성을 요청 단위로 지속 검증하는 현대적 모델 |
