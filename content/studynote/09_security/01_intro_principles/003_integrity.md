## 0. 핵심 인사이트

> **핵심**: 무결성 (Integrity)은 데이터가 비인가 방식으로 바뀌지 않았음을 보장하는 속성이며, 결국 시스템이 ‘믿을 수 있는 상태’를 유지하게 만드는 기준이다.
> **비유**: 봉인된 계약서의 인장이 깨지지 않아야 문서 내용을 신뢰할 수 있는 것과 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

무결성은 정보가 생성, 저장, 전송, 처리되는 전 과정에서 인가되지 않은 변경, 삽입, 삭제, 순서 변경이 발생하지 않았음을 보장하는 보안 속성이다. 보안 사고에서 흔히 기밀성 침해가 더 주목받지만, 실제 운영 피해는 무결성 파괴가 더 치명적일 때가 많다. 잘못된 송금 금액, 조작된 로그, 악성 코드가 삽입된 업데이트 파일은 시스템 신뢰를 근본적으로 무너뜨린다.

무결성이 중요한 이유는 디지털 환경에서 “원본”을 육안으로 식별할 수 없기 때문이다. 복사본과 원본이 동일하게 보이는 세계에서는 수학적 검증이 없으면 변조 여부를 알기 어렵다. 이 때문에 단순 오류 검출을 위한 체크섬에서 시작해, 의도적 공격까지 견디는 해시, MAC (Message Authentication Code), 전자서명으로 보안 기술이 발전했다.

특히 현대 시스템은 공급망 공격, 내부자 조작, API 파라미터 변조처럼 정상 흐름을 가장한 위변조에 취약하다. 따라서 무결성은 저장 데이터만 지키는 개념이 아니라, **거래 흐름과 실행 코드까지 포함한 신뢰 체계**로 봐야 한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 체크섬/CRC | 우발적 오류 검출 | 노이즈·전송 오류 대응에는 효과적이나 악의적 공격 방어는 약함 |
| 해시 함수 | 데이터 요약값 생성 | 충돌 저항성, 위변조 탐지의 기초 |
| HMAC/CMAC | 키 기반 무결성 검증 | 송신자 공유 비밀을 이용해 위조 난이도 증가 |
| 전자서명 | 무결성 + 인증성 + 부인방지 | 개인키 기반으로 출처와 원본성까지 증명 |
| 변경 통제/FIM | 운영 환경 무결성 유지 | 파일, 설정, 배포 결과의 기준선 비교 |

이 요소들은 계층별로 역할이 다르다. 체크섬은 통신 오류를 빨리 찾는 데 적합하고, 해시는 파일이나 데이터의 변경 여부를 확인하는 기본 수단이다. HMAC은 공유 비밀이 있는 시스템 간 API 호출에 적합하며, 전자서명은 공개키 기반으로 제3자 검증과 법적 증명까지 가능하게 한다. 운영 측면에서는 FIM (File Integrity Monitoring)과 배포 승인 절차가 무결성을 지속 유지하게 한다.

## 3. 구조 및 원리

**핵심 조건**: 무결성은 `기준값 생성` + `보호된 검증값 저장/전달` + `비교 검증` + `비인가 변경 차단`이 반복적으로 수행될 때 유지된다.

동작 순서:
1. **원본 기준 생성**: 데이터나 파일에 대해 해시, MAC, 서명을 생성한다. 기준값 자체가 신뢰할 수 있어야 이후 비교가 의미 있다.
2. **보호된 전달 또는 저장**: 검증값을 공격자가 임의 변경할 수 없도록 별도 저장소, 서명 구조, 키 기반 방식으로 보호한다.
3. **수신·조회 시 비교**: 현재 데이터에서 다시 계산한 값과 기준값을 비교한다. 다르면 변경이 있었음을 의미한다.
4. **정상 변경과 비정상 변경 구분**: 패치, 배포, 승인된 수정은 기준선을 갱신하고, 승인되지 않은 변경은 사고로 본다.
5. **추적 및 복원**: 위변조가 확인되면 원인 분석, 격리, 복구, 재배포를 수행한다.

```text
[원본 데이터]
      │
      ├─ 해시/서명 생성 ───────────────┐
      ▼                              │
[보호된 기준값 저장소]                │
                                     ▼
                               [수신/실행 시점]
                                     │
                         현재 데이터에서 재계산
                                     │
                    기준값과 비교 ────┴───► 일치? ──► 정상 사용
                                     │
                                     └────► 불일치 ──► 변조 의심/격리
```

무결성의 핵심은 단순히 “값이 같은가”가 아니라 “공격자가 기준값까지 바꿀 수 있는가”를 함께 고려하는 데 있다. 예를 들어 평문 파일과 해시값을 같은 위치에 저장하면 공격자는 둘 다 바꿔버릴 수 있다. 그래서 HMAC은 비밀키를 이용하고, 전자서명은 공개키 검증 구조를 사용하며, 운영 환경에서는 기준선 저장소를 분리한다.

또한 무결성은 가용성과 긴장 관계를 가진다. 모든 요청을 강하게 검증하면 성능이 떨어질 수 있고, 분산 시스템에서는 일관성을 강하게 보장할수록 장애 시 쓰기 가용성이 낮아질 수 있다. 따라서 무결성 설계는 보안 강도와 처리 비용의 균형을 포함한다.

## 4. 비교 및 연결

| 항목 | 체크섬/CRC | 해시 | HMAC | 전자서명 |
|:---|:---|:---|:---|:---|
| 목적 | 우발 오류 탐지 | 변경 여부 확인 | 변경 + 송신자 공유비밀 검증 | 변경 + 출처 증명 + 부인방지 |
| 키 사용 | 없음 | 없음 | 대칭키 | 비대칭키 |
| 공격 저항성 | 낮음 | 중간 | 높음 | 매우 높음 |
| 대표 사용처 | 네트워크 프레임 | 파일 무결성 | API 요청 검증 | 코드서명, 계약 문서 |

무결성은 인증성, 부인방지, 공급망 보안과 직접 연결된다. 전자서명은 무결성을 넘어서 “누가 만들었는가”를 증명하고, 코드 서명은 소프트웨어 배포 무결성을 확보한다. 로그 무결성은 포렌식과 감사의 신뢰 전제가 된다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 금전 거래, 정책 설정, 배포 산출물처럼 변경 피해가 큰 데이터일 때
- API 간 통신에서 요청 위조를 막아야 할 때
- 감사 로그와 증적의 법적 신뢰성이 필요할 때

**회피 조건**:
- 단순 오류 검출 도구를 공격 방어 수단으로 오용하는 경우
- 기준 해시와 원본 파일을 동일 저장소에 두는 경우
- 승인된 변경 프로세스 없이 FIM만 도입해 오탐이 폭증하는 경우

체크리스트:
1. 어떤 데이터·코드·로그에 무결성 검증이 필요한지 정의되어 있는가?
2. 검증값이 별도 신뢰 경계에서 보호되는가?
3. 시스템 간 통신에 HMAC 또는 서명 검증이 적용되는가?
4. 변경 관리와 무결성 모니터링이 연동되는가?
5. 사고 발생 시 기준선 복원 절차가 존재하는가?

실무 사례로는 소프트웨어 저장소의 코드 서명, 금융 API 요청 서명, 중요 서버의 FIM, 불변 로그 저장소가 있다. 핵심 판단은 “이 데이터가 틀리면 얼마나 위험한가”에 따라 검증 강도를 차등화하는 것이다.

## 6. 기대효과 및 결론

무결성이 확보되면 조직은 데이터와 시스템 결과를 신뢰할 수 있게 된다. 이는 단순 보안 효과를 넘어 운영 안정성, 거래 신뢰, 감사 대응력, 공급망 안전성으로 이어진다. 특히 공격자가 내부에 침투하더라도 핵심 데이터나 로그의 변조를 어렵게 만들면 사고 탐지와 복구 가능성이 크게 높아진다.

다만 무결성은 공짜가 아니다. 강한 검증은 계산 비용과 운영 절차를 요구하며, 기준선 관리가 부실하면 오탐과 관리 피로가 커진다. 그럼에도 불구하고 무결성은 “데이터가 맞다”는 최소한의 신뢰를 제공하므로, 디지털 시스템의 본질적 기반이다. 기밀성이 비밀을 지키는 축이라면, 무결성은 **사실을 지키는 축**이다.

## 7. 발전 흐름도

```text
체크섬 기반 오류 검출
    ↓
암호학적 해시 함수 보편화
    ↓
HMAC · 전자서명 도입
    ↓
코드서명 · 로그 무결성 · FIM 확장
    ↓
공급망 보안 · 불변 인프라 중심 무결성 관리
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| 해시 함수 (Hash Function) | 무결성 검증의 핵심 수학 도구 |
| HMAC | 공유 비밀을 이용해 위조 난이도를 높인 실무형 검증 방식 |
| 전자서명 (Digital Signature) | 무결성과 인증성, 부인방지를 결합 |
| 파일 무결성 모니터링 (FIM) | 운영 환경에서 비인가 변경을 탐지 |
| 공급망 보안 (Supply Chain Security) | 코드와 배포 산출물 무결성 확보를 핵심 요구사항으로 삼음 |
