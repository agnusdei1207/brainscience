## 0. 핵심 인사이트

> **핵심**: OCP는 새로운 요구가 들어올 때 핵심 코드를 뜯어고치기보다, 안정된 추상화 뒤에 새 구현을 추가하여 확장으로 변화를 흡수하라는 원칙이다.
> **비유**: 멀티탭은 벽 내부 배선을 매번 뜯지 않고도 새 기기를 꽂아 확장할 수 있게 해 주듯, OCP는 기존 구조를 흔들지 않고 기능을 붙일 수 있게 만든다.

## 1. 개요 및 필요성

OCP (Open-Closed Principle)는 소프트웨어 엔티티가 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙이다. 여기서 “닫혀 있다”는 것은 절대 수정하지 않는다는 뜻이 아니라, 이미 검증된 핵심 로직을 새 요구마다 반복 수정하지 않도록 구조를 설계한다는 의미다.

이 원칙이 필요한 이유는 기능 추가가 기존 코드 수정을 동반할수록 결함 가능성과 회귀 범위가 커지기 때문이다. 대표적 위반 사례는 거대한 `if-else` 또는 `switch` 분기다. 결제수단이 하나 추가될 때마다 핵심 서비스의 분기가 늘어나면, 새 기능 하나가 기존 기능 전체를 흔들게 된다.

OCP는 다형성, 전략 패턴, 플러그인 구조, 이벤트 핸들러 등록 같은 방식으로 구현된다. 중요한 것은 무조건 인터페이스를 만드는 것이 아니라, **변화 가능성이 높은 축**에 대해 안정된 확장 포인트를 만드는 것이다. 그렇지 않으면 쓸모없는 추상화만 늘어난다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 안정된 핵심 | 쉽게 바뀌지 않는 정책/흐름 | 수정에 닫힌 영역 |
| 확장 포인트 | 새 기능이 끼어드는 지점 | 인터페이스, 훅, 콜백, 플러그인 등 |
| 구체 구현 | 실제 기능 추가 단위 | 새 타입 추가로 변화 흡수 |
| 조합/등록 메커니즘 | 구현체 연결 방식 | 팩토리, DI, 설정, 자동 등록 |
| 테스트 경계 | 핵심과 확장 검증 분리 | 회귀 범위 최소화 |

OCP의 실질적 구현은 “안정된 것과 변하는 것을 분리하는 것”이다. 결제 흐름 자체는 안정적일 수 있지만, 결제 수단 종류는 계속 늘어날 수 있다. 그렇다면 결제 수단 전략을 추상화하고, 흐름 오케스트레이션은 핵심 서비스에 남기는 식으로 분리해야 한다.

---

## 3. 구조 및 원리

**핵심 조건**: OCP는 변화 가능성이 높은 축을 추상화된 확장 포인트 뒤로 밀어내고, 새 요구를 기존 핵심 코드 수정이 아니라 새 구현 추가로 수용해야 한다.

동작 순서:
1. **변화 축을 식별한다**: 결제 유형, 배송 정책, 알림 채널처럼 자주 추가되는 축을 찾는다.
2. **안정된 흐름과 변하는 규칙을 분리한다**: 공통 실행 흐름은 남기고, 변하는 부분만 추상화한다.
3. **확장 포인트를 정의한다**: 인터페이스, 추상 클래스, 이벤트 계약 등을 설계한다.
4. **구현체를 추가 가능하게 만든다**: 신규 요구는 기존 코드 수정이 아니라 구현체 추가로 처리한다.
5. **조합 메커니즘을 분리한다**: 어떤 구현을 쓸지 DI 컨테이너, 팩토리, 설정 파일이 결정하게 한다.
6. **회귀 범위를 통제한다**: 핵심 서비스 테스트는 유지하고, 신규 구현체 테스트를 별도로 추가한다.

```text
[OCP 위반]
PaymentService
 ├─ if(card) ...
 ├─ else if(bank) ...
 └─ else if(point) ...

        ↓

[OCP 적용]
PaymentService ─────▶ PaymentMethod (추상화)
                         ├─ CardPayment
                         ├─ BankTransfer
                         └─ PointPayment

새 결제수단 추가 = 구현체 추가
기존 PaymentService 수정 최소화
```

OCP의 핵심은 확장 포인트의 위치 선정이다. 너무 이른 추상화는 YAGNI를 위반하고, 너무 늦은 추상화는 분기문 지옥을 만든다. 따라서 반복되는 변경 신호가 보이는 지점에서 추상화를 도입하는 것이 가장 효과적이다.

또한 OCP는 DIP와 함께 작동해야 한다. 핵심 서비스가 여전히 구체 구현체를 직접 생성하면, 인터페이스가 있어도 진정한 확장은 어렵다. 즉 OCP는 “확장 포인트 설계”, DIP는 “그 포인트에 대한 의존성 방향 제어”라고 볼 수 있다.

## 4. 비교 및 연결

| 항목 | OCP | SRP | YAGNI |
|:---|:---|:---|:---|
| 초점 | 기능 추가 시 수정 최소화 | 변경 이유 분리 | 불필요한 미래 확장 억제 |
| 핵심 질문 | 새 요구를 추가로 흡수할 수 있는가? | 무엇이 함께 바뀌는가? | 정말 지금 필요한가? |
| 위험 | 과잉 추상화 | 과잉 분리 | 필요한 확장성 부족 |

OCP는 플러그인 아키텍처, 전략 패턴, 템플릿 메서드, 이벤트 기반 확장 구조와 밀접하다. 다만 무분별한 일반화는 KISS와 YAGNI를 해칠 수 있으므로, 반복적 변경 패턴이 확인된 축에 대해서만 적용해야 실효성이 높다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 동일한 종류의 기능이 반복적으로 추가되는 영역일 때
- 핵심 서비스 안정성이 중요해 회귀 리스크를 줄여야 할 때
- 외부 파트너, 국가, 채널별 정책 차이가 계속 확장될 때

**회피 조건**:
- 한 번도 변한 적 없는 축까지 미리 추상화할 때
- 인터페이스만 만들고 조합 구조를 분리하지 않을 때
- 확장 포인트가 너무 많아 시스템 이해도가 떨어질 때

체크리스트:
1. 실제로 반복 추가되는 변화 축이 있는가?
2. 기존 핵심 코드를 반복 수정하는 패턴이 있는가?
3. 새 기능이 새 구현체 추가만으로 수용 가능한가?
4. 확장 포인트 선택이 YAGNI를 위반하지 않는가?
5. 조합/등록 메커니즘이 구체 구현 의존을 숨기고 있는가?

실무에서는 결제수단, 알림 채널, 할인 정책, 파일 포맷, 인증 제공자 확장에 OCP가 자주 적용된다. 반대로 한 번도 늘어난 적 없는 단순 규칙에 OCP를 과도 적용하면 인터페이스만 늘고 실익이 적다.

---

## 6. 기대효과 및 결론

OCP를 잘 적용하면 신규 요구 대응 속도가 빨라지고 기존 기능 회귀 위험이 줄어든다. 이는 제품 라인 확장, 국가별 정책 분기, 파트너 통합이 많은 시스템에서 특히 큰 이점을 준다. 또한 핵심 서비스가 안정적으로 유지되어 테스트 전략도 단순해진다.

그러나 지나친 일반화는 복잡성과 간접 참조를 늘린다. 결론적으로 OCP의 본질은 “수정하지 말라”가 아니라 “자주 바뀌는 축에 대해 안정된 확장 구조를 만들라”는 것이다.

## 7. 발전 흐름도

```text
조건문 기반 기능 분기
        ↓
반복 수정에 따른 회귀 증가
        ↓
OCP 기반 확장 포인트 설계
        ↓
전략/플러그인 구조 확산
        ↓
DI/설정 기반 동적 조합
        ↓
제품군/멀티테넌트 확장 최적화
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| SRP | 변화 축이 정리되어야 OCP 확장 포인트가 선명해짐 |
| DIP | 추상화에 의존해야 OCP의 실제 확장성이 확보됨 |
| Strategy Pattern | OCP를 구현하는 대표 설계 패턴 |
| Plugin Architecture | OCP를 시스템 수준으로 확장한 구조 |
| YAGNI | 불필요한 선행 추상화 방지를 위한 균형 원칙 |
| 분기문 지옥 | OCP 부재 시 나타나는 대표적 안티패턴 |
