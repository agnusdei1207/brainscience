## 0. 핵심 인사이트

> **핵심**: LSP는 상속 구조의 핵심이 “코드를 재사용했는가”가 아니라 “하위 타입이 상위 타입을 대신해도 시스템 의미가 깨지지 않는가”에 있음을 말한다.
> **비유**: 콘센트 모양은 같아도 꽂는 즉시 전압이 달라 기기가 타버린다면 같은 규격이라 할 수 없듯, 하위 타입도 겉모양이 아니라 동작 계약이 같아야 한다.

## 1. 개요 및 필요성

LSP (Liskov Substitution Principle)는 Barbara Liskov가 정리한 원칙으로, 하위 타입은 상위 타입을 대체할 수 있어야 한다고 말한다. 단순히 메서드 시그니처가 같다고 되는 것이 아니라, 상위 타입이 약속한 의미적 계약을 하위 타입이 깨지 않아야 한다.

이 원칙이 필요한 이유는 객체지향에서 상속이 자주 남용되기 때문이다. 코드 재사용을 목적으로 상속을 사용하면, 하위 클래스가 특정 메서드를 지원하지 않거나 더 강한 전제조건을 요구하거나, 예외를 다르게 던지는 경우가 생긴다. 그러면 클라이언트는 “부모 타입이면 동일하게 동작할 것”이라는 믿음을 잃고 타입별 분기문을 다시 작성하게 된다.

따라서 LSP는 상속의 허용 조건을 정의한다. 상속은 단순한 구현 재사용 수단이 아니라, **행동 계약의 보존**이 가능한 경우에만 써야 한다. 이 점에서 LSP는 다형성의 품질 기준이며, OCP가 안전하게 작동하기 위한 전제이기도 하다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 상위 타입 계약 | 공통 기대 동작 정의 | 사전조건, 사후조건, 불변식 포함 |
| 하위 타입 | 대체 가능한 구체 구현 | 계약을 강화가 아니라 유지·완화해야 함 |
| 대체 가능성 | 클라이언트 관점 검증 기준 | 타입 분기 없이 사용 가능해야 함 |
| 불변식 | 상태 일관성 규칙 | 상속 후에도 깨지면 안 됨 |
| 예외 규약 | 오류 처리 계약 | 하위 타입이 더 강한 실패를 강요하면 문제 |

LSP는 문법보다 계약의 문제다. 예를 들어 `Bird`가 `fly()`를 약속하는데 `Penguin`이 예외를 던진다면, 이는 상속 구조가 잘못된 것이다. 펭귄이 새인 것은 생물학적 분류이지, 소프트웨어 타입 계약의 적합성을 보장하지 않는다.

---

## 3. 구조 및 원리

**핵심 조건**: 하위 타입은 상위 타입의 사전조건을 더 강하게 만들면 안 되고, 사후조건을 더 약하게 만들면 안 되며, 불변식을 깨뜨리지 않아야 한다.

동작 순서:
1. **상위 타입 계약을 명시한다**: 입력 조건, 반환 보장, 상태 변화 규칙을 정의한다.
2. **하위 타입이 계약을 유지하는지 본다**: 메서드 의미와 오류 처리 방식이 동일 기대를 만족하는지 확인한다.
3. **강화·약화 여부를 점검한다**: 하위 타입이 더 까다로운 입력을 요구하거나 결과 보장을 줄이지 않는지 검토한다.
4. **클라이언트 치환 테스트를 수행한다**: 상위 타입을 쓰는 코드를 수정하지 않고 하위 타입으로 대체해 본다.
5. **문제 시 상속을 제거한다**: 진정한 is-a 관계가 아니면 조합이나 별도 추상화를 사용한다.

```text
상위 타입 계약
 ├─ 사전조건: 입력은 이 범위여야 함
 ├─ 사후조건: 결과는 이렇게 보장됨
 └─ 불변식: 상태는 항상 이 규칙 유지

        ▼
하위 타입 검증
 ├─ 사전조건 강화 금지
 ├─ 사후조건 약화 금지
 └─ 불변식 파괴 금지

        ▼
치환 가능하면 LSP 만족
```

대표적 예가 `Rectangle`-`Square` 문제다. 정사각형은 수학적으로 직사각형이지만, `setWidth`, `setHeight`가 독립 동작한다고 가정한 소프트웨어 계약에서는 `Square`가 이를 만족하지 못한다. 이때 상속은 수학적 분류와 소프트웨어 계약을 혼동한 결과다.

LSP를 위반하면 클라이언트 코드에 `instanceof` 분기, 예외 처리 우회, 숨은 제약 문서화가 늘어난다. 결국 다형성은 깨지고, OCP로 만들었던 확장 구조도 안전성을 잃는다. 그래서 상속보다 조합을 선호하라는 조언은 상당 부분 LSP 위반 위험을 줄이기 위한 실무적 결론이다.

## 4. 비교 및 연결

| 항목 | LSP | OCP | 조합(Composition) |
|:---|:---|:---|:---|
| 초점 | 대체 가능성 보장 | 확장 시 수정 최소화 | 상속 대신 유연한 재사용 |
| 핵심 질문 | 하위 타입이 부모를 대신할 수 있는가? | 새 기능을 추가로 흡수할 수 있는가? | 계약 위반 없이 기능을 조립할 수 있는가? |
| 실패 시 현상 | `instanceof` 분기, 예외 남발 | 조건문 증가, 핵심 코드 수정 반복 | 조립 복잡도 증가 가능 |

LSP는 OCP의 안전장치다. 새 하위 타입을 추가해도 상위 계약을 유지해야만 OCP가 진짜 확장성을 가진다. 또한 ISP와 DIP는 계약을 더 작고 명확하게 만들어 LSP 위반 가능성을 낮추는 데 도움을 준다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 상속 또는 인터페이스 다형성을 설계할 때
- 플러그인, 전략, 저장소 구현 교체처럼 타입 대체가 빈번할 때
- 계약 기반 테스트가 필요한 공용 API를 설계할 때

**회피 조건**:
- 구현 재사용만을 위해 억지 상속을 도입할 때
- 하위 타입마다 예외 규약이 제각각일 때
- “현실 세계 분류”를 그대로 타입 계층으로 옮길 때

체크리스트:
1. 하위 타입이 상위 타입의 모든 공개 계약을 충족하는가?
2. 더 강한 입력 제약을 요구하지 않는가?
3. 결과 보장이나 상태 불변식을 약화하지 않는가?
4. 클라이언트가 하위 타입 존재를 알 필요가 없는가?
5. 상속보다 조합이 더 적절한 구조는 아닌가?

실무에서는 결제 방식, 파일 저장소, 메시지 발송기, 인증 제공자처럼 교체 가능한 구현체를 설계할 때 LSP가 중요하다. 계약 테스트를 작성해 공통 시나리오를 모든 구현체에 적용하면 위반을 조기에 발견할 수 있다.

---

## 6. 기대효과 및 결론

LSP를 지키면 다형성이 진짜 의미를 갖게 되고, 구현체 교체가 안전해진다. 이는 테스트 단순화, 확장 안정성, 클라이언트 코드 단순화로 이어진다. 특히 공용 프레임워크나 SDK에서는 LSP 준수 여부가 생태계 품질을 좌우한다.

반대로 LSP 위반은 상속 구조 전체를 불신하게 만든다. 결론적으로 LSP는 “자식이 부모를 닮았는가”가 아니라 “부모 대신 써도 약속이 지켜지는가”를 묻는 원칙이다.

