## 0. 핵심 인사이트

> **핵심**: DIP는 고수준 정책이 저수준 구현에 끌려가지 않도록, 둘 다 안정된 추상화에 의존하게 만들어 의존성 방향을 제어하는 원칙이다.
> **비유**: 전자제품이 벽면 콘센트 모양에 직접 맞춰 설계되는 대신 표준 어댑터 규격을 기준으로 만들어져야 국가와 제조사가 바뀌어도 교체가 쉬운 것과 같다.

## 1. 개요 및 필요성

DIP (Dependency Inversion Principle)는 고수준 모듈은 저수준 모듈에 의존하면 안 되고, 둘 다 추상화에 의존해야 한다는 원칙이다. 또한 추상화는 세부사항에 의존하지 않고, 세부사항이 추상화를 따라야 한다. 이 원칙은 흔히 DI (Dependency Injection) 프레임워크와 함께 언급되지만, DI는 구현 기법이고 DIP는 설계 원칙이다.

이 원칙이 필요한 이유는 비즈니스 정책이 외부 세부 구현에 묶일수록 변화에 취약해지기 때문이다. 예를 들어 주문 도메인이 특정 DB 드라이버, 메일 서버 라이브러리, 결제 SDK 클래스에 직접 의존하면, 외부 구현 하나만 바뀌어도 핵심 정책 코드가 흔들린다. 테스트도 어려워지고 대체 구현도 힘들어진다.

DIP는 의존성 방향을 안정된 추상으로 모으게 한다. 이로써 도메인 로직은 인프라를 몰라도 되고, 인프라 구현은 도메인이 정의한 계약을 만족시키는 방식으로 연결된다. 헥사고날 아키텍처, 클린 아키텍처, 포트-어댑터 구조가 모두 DIP를 큰 규모에서 구현한 사례다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 고수준 모듈 | 핵심 정책/비즈니스 규칙 | 안정적이어야 함 |
| 저수준 모듈 | DB, 메시지, 외부 API 등 구현 세부사항 | 자주 교체 가능 |
| 추상화 | 의존성의 기준점 | 포트, 인터페이스, 계약 |
| 조립 메커니즘 | 실제 구현 연결 | DI 컨테이너, 팩토리, 구성 코드 |
| 테스트 대역 | 검증 용이성 확보 | Mock, Stub, Fake 적용 가능 |

DIP의 핵심은 단순히 인터페이스를 넣는 것이 아니라, **누가 인터페이스를 소유하는가**다. 이상적인 경우 추상화는 고수준 정책 가까이에 위치한다. 그래야 저수준 모듈이 그 계약을 구현하는 구조가 되고, 정책이 구현 세부사항에 끌려가지 않는다.

---

## 3. 구조 및 원리

**핵심 조건**: 의존성은 실행 시에는 고수준에서 저수준으로 협력하더라도, 소스코드 의존 방향은 추상화 쪽으로 향해야 하며 추상화는 정책 중심으로 정의되어야 한다.

동작 순서:
1. **핵심 정책을 식별한다**: 비즈니스 규칙처럼 오래 유지되어야 하는 코드를 구분한다.
2. **외부 세부사항을 식별한다**: DB, 파일, 네트워크, 메시지 브로커, 프레임워크 의존을 찾는다.
3. **정책 중심 추상화를 정의한다**: `OrderRepository`, `PaymentGateway`, `Notifier` 같은 포트를 만든다.
4. **저수준 구현이 추상화를 구현하게 한다**: 실제 DB/외부 SDK 어댑터가 계약을 구현한다.
5. **조립 코드를 분리한다**: 런타임에 어떤 구현체를 연결할지 별도 계층에서 결정한다.
6. **테스트 대역으로 검증한다**: 정책 코드를 실제 외부 시스템 없이도 테스트할 수 있게 한다.

```text
[전통적 의존]
OrderService ─────▶ MySqlOrderRepository
OrderService ─────▶ SmtpMailer

[의존성 역전]
OrderService ─────▶ OrderRepository (추상화)
OrderService ─────▶ MailSender      (추상화)
                         ▲                 ▲
                         │                 │
            MySqlOrderRepository   SmtpMailer

소스코드 의존 방향 = 구현 → 추상화
```

여기서 중요한 구분은 실행 흐름과 의존 방향이다. 주문 서비스는 실행 시 실제 MySQL 저장소를 호출할 수 있다. 그러나 코드 수준에서는 `OrderRepository` 인터페이스만 알고, MySQL 구현은 조립 단계에서 주입된다. 이것이 “역전”의 의미다. 호출 방향이 아니라 **정적 의존성 방향이 바뀌는 것**이다.

실무에서는 DI 컨테이너가 이 원칙을 구현해 주지만, DI 도구를 쓴다고 DIP가 자동으로 지켜지는 것은 아니다. 인터페이스가 인프라 세부사항에 오염되어 있거나, 고수준 모듈이 특정 구현 타입 캐스팅에 의존하면 DIP는 이미 깨진 것이다.

---

## 4. 비교 및 연결

| 항목 | DIP | DI | 헥사고날 아키텍처 |
|:---|:---|:---|:---|
| 성격 | 설계 원칙 | 구현 기법 | 아키텍처 스타일 |
| 초점 | 의존성 방향 제어 | 객체 주입 자동화/구성 | 포트와 어댑터로 경계 분리 |
| 핵심 질문 | 누구에게 의존하는가? | 어떻게 연결하는가? | 어디를 안쪽/바깥쪽으로 둘 것인가? |

DIP는 OCP, ISP와도 긴밀히 연결된다. OCP가 확장 포인트를 만들고, ISP가 추상화를 작고 역할 중심으로 만들며, DIP가 그 추상화를 기준으로 의존성 방향을 정리한다. 따라서 세 원칙은 함께 적용될 때 가장 강력하다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 핵심 도메인 로직을 인프라 변경으로부터 보호해야 할 때
- 테스트 대역을 쉽게 바꾸고 싶을 때
- DB, 메시징, 외부 API 구현 교체 가능성이 있을 때

**회피 조건**:
- 단순 CRUD 스크립트에 불필요한 추상화를 남발할 때
- 추상화가 오히려 세부 구현 용어에 오염되어 있을 때
- 조립 계층 없이 비즈니스 코드가 구현체 선택까지 담당할 때

체크리스트:
1. 고수준 정책이 구체 구현 클래스를 직접 참조하는가?
2. 추상화가 도메인 언어로 정의되어 있는가?
3. 런타임 조립과 비즈니스 로직이 분리되어 있는가?
4. 테스트에서 실제 외부 시스템 없이도 정책 검증이 가능한가?
5. 구현체 교체 시 핵심 로직 수정이 최소화되는가?

실무에서는 JPA 저장소 교체, 메시지 브로커 변경, 외부 결제사 전환, 클라우드 스토리지 교체 같은 상황에서 DIP가 큰 힘을 발휘한다. 특히 클린 아키텍처 기반 서비스에서는 도메인 계층이 프레임워크를 모르는 상태를 만드는 것이 중요한 목표다.

---

## 6. 기대효과 및 결론

DIP를 적용하면 핵심 정책의 안정성이 높아지고 테스트가 쉬워지며, 외부 구현 교체 비용이 크게 줄어든다. 이는 장기 운영 시스템, 멀티 벤더 통합, 프레임워크 의존이 큰 프로젝트에서 매우 큰 장점이다. 또한 모듈 간 경계가 명확해져 팀 책임 분리도 쉬워진다.

그러나 변화 가능성이 거의 없는 영역까지 추상화하면 복잡성이 증가한다. 결론적으로 DIP의 본질은 인터페이스 도입 자체가 아니라, **안정된 정책을 세부 구현으로부터 보호하는 의존성 구조를 만드는 것**이다.

## 7. 발전 흐름도

```text
구현체 직접 의존
        ↓
테스트 어려움 · 교체 비용 증가
        ↓
DIP 기반 추상화 도입
        ↓
DI/IoC 도구 확산
        ↓
헥사고날 · 클린 아키텍처 정착
        ↓
도메인 중심 포트-어댑터 표준화
```

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| DI (Dependency Injection) | DIP를 런타임 조립으로 구현하는 대표 기법 |
| IoC (Inversion of Control) | 제어 흐름과 조립 책임을 프레임워크/컨테이너로 넘김 |
| OCP | 추상화 기반 확장 포인트 설계와 결합됨 |
| ISP | 작고 응집된 추상화가 DIP 품질을 높임 |
| Hexagonal Architecture | DIP를 시스템 수준 포트-어댑터로 확장한 구조 |
| Test Double | DIP가 테스트 용이성을 높이는 대표 수단 |
