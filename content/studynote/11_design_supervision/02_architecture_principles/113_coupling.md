## 0. 핵심 인사이트

> **핵심**: 결합도 (Coupling)의 본질은 “한 모듈이 다른 모듈의 내부를 얼마나 많이 알아야 하는가”에 있다. 결합도가 낮다는 것은 협력은 하되, 상대의 내부 변경이 나에게 연쇄 충격을 주지 않도록 경계를 설계했다는 뜻이다.
> **비유**: 전원 콘센트는 내부 배선 구조를 몰라도 표준 플러그만 맞으면 쓸 수 있다. 반대로 벽을 뜯어 배선에 직접 연결해야 한다면 그 시스템은 극도로 강결합이다.

## 1. 개요 및 필요성

결합도는 서로 다른 모듈 간 상호 의존의 강도를 의미한다. 일반적으로 낮을수록 바람직하며, 그 이유는 변경 파급을 줄이고 독립적 테스트·배포·교체를 가능하게 하기 때문이다. 좋은 설계는 협력을 없애지 않는다. 대신 협력이 표준 인터페이스와 안정된 계약 위에서 이뤄지도록 만들어 의존의 충격을 줄인다.

결합도가 중요한 이유는 실제 시스템이 항상 여러 모듈의 협력으로 동작하기 때문이다. 화면, 도메인 로직, DB, 외부 API, 메시지 브로커는 반드시 연결된다. 문제는 연결의 존재가 아니라 연결 방식이다. 상대 모듈의 내부 데이터 구조, 호출 순서, 전역 상태, 제어 플래그까지 알아야 한다면 결합도가 높다. 반대로 추상화된 인터페이스와 메시지 계약만 알면 된다면 결합도가 낮다.

결합도가 높은 시스템은 작은 변경이 전파되기 쉽다. DB 스키마 변경 하나가 UI, 배치, 외부 연동까지 동시에 깨뜨릴 수 있다. 반면 낮은 결합 구조는 내부 구현을 바꿔도 계약이 유지되는 한 다른 모듈은 그대로 동작한다. 따라서 결합도는 유지보수 비용과 변화 대응력을 가르는 핵심 지표다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 인터페이스 | 모듈 간 공식 접점 | 안정된 계약이 결합도를 낮춤 |
| 데이터 교환 방식 | 무엇을 주고받는지 결정 | 필요한 최소 데이터만 전달할수록 유리 |
| 의존 방향 | 누가 누구를 참조하는지 규정 | 고수준 정책이 추상화에 의존해야 함 |
| 공유 자원 | 공통 DB, 전역 변수, 캐시 등 | 공유가 많을수록 숨은 결합 증가 |
| 호출 의미 | 단순 요청인지 제어 명령인지 | 상대의 흐름까지 통제하면 결합 상승 |

결합도는 코드의 `import` 개수만으로 판단되지 않는다. 같은 REST API를 호출하더라도 상대의 내부 상태 전이, 오류 코드, 재시도 규칙, 응답 구조 세부를 과도하게 알아야 하면 실제 결합은 높다. 즉 결합도는 **지식 의존성**과 **변경 영향도**의 문제다.

---

## 3. 구조 및 원리

**핵심 조건**: 모듈은 상대의 내부 구현이 아니라 공개 계약과 추상화에만 의존해야 한다. 필요한 최소 데이터만 교환하고, 제어 흐름과 저장소를 공유하지 않을수록 결합도는 낮아진다.

동작 순서:
1. **협력 지점 정의**: 두 모듈이 왜 협력하는지 목적을 정의한다. 목적이 불명확하면 불필요한 데이터와 제어가 새어 들어간다.
2. **계약 최소화**: 입력·출력을 필요한 최소 단위로 제한한다. 전체 객체를 통째로 넘기는 Stamp Coupling은 피하고, 필요한 값만 전달하는 Data Coupling을 지향한다.
3. **의존 방향 안정화**: 변하기 쉬운 구현은 변하지 않는 추상화에 의존하도록 설계한다. DIP가 여기서 중요하다.
4. **공유 상태 제거**: 전역 변수, 공유 DB 테이블, 공통 세션 상태처럼 숨은 결합을 만드는 요소를 줄인다.
5. **변경 영향 검증**: 상대 구현이 바뀌어도 계약만 유지되면 나의 수정이 필요 없는지 확인한다. 필요하다면 결합도가 여전히 높다는 신호다.

```
높은 결합
A ── 내부 필드 참조 ──► B
A ── 전역 상태 공유 ──► B
A ── 실행 순서 제어 ──► B

낮은 결합
A ── 공개 인터페이스 / 메시지 계약 ──► B
A ◄── 결과 값 / 이벤트 ───────────────── B
```

고전적 결합도는 대체로 다음 순서로 나쁜 편에서 좋은 편으로 정리한다.
- 내용 결합 (Content Coupling): 다른 모듈 내부를 직접 수정·참조
- 공통 결합 (Common Coupling): 전역 데이터 공유
- 외부 결합 (External Coupling): 외부 형식·프로토콜에 함께 종속
- 제어 결합 (Control Coupling): 플래그 값으로 상대 동작 분기 지시
- 스탬프 결합 (Stamp Coupling): 큰 구조체를 통째로 전달
- 데이터 결합 (Data Coupling): 필요한 데이터만 인자로 전달

중요한 점은 결합도를 0으로 만들 수는 없다는 사실이다. 시스템은 협력해야 하기 때문이다. 설계 목표는 “필요한 결합은 유지하되, 불필요한 내부 지식 의존은 제거”하는 것이다.

---

## 4. 비교 및 연결

| 항목 | 낮은 결합 | 높은 결합 |
|:---|:---|:---|
| 변경 파급 | 제한적 | 광범위 |
| 테스트 | 독립 테스트 용이 | 환경 의존적 |
| 배포 | 부분 교체 가능 | 동시 배포 필요 |
| 장애 전파 | 경계에서 흡수 가능 | 연쇄 장애 발생 |
| 대표 구조 | 인터페이스, 이벤트, 포트·어댑터 | 공유 DB, 전역 상태, 내부 탐색 |

결합도는 응집도와 균형을 이루어야 한다. 낮은 결합만 강조해 기능을 지나치게 잘게 나누면 호출 홉이 늘고 오히려 복잡성이 증가할 수 있다. 따라서 이상적인 상태는 “모듈 내부는 높게 응집되고, 모듈 사이는 느슨하게 결합된 구조”다. 헥사고날 아키텍처, 클린 아키텍처, MSA는 모두 이 원칙을 시스템 수준에서 확대한 사례다.

## 5. 실무 적용 및 판단

채택 조건:
- 독립 테스트·독립 배포·독립 교체가 중요한 경우
- 외부 시스템 교체 가능성을 열어두어야 하는 경우
- 팀 간 소유 경계를 명확히 해야 하는 경우

회피 조건:
- 지나친 추상화로 단순한 지역 협력까지 복잡하게 만드는 경우
- 성능상 매우 긴밀한 협력이 필요한 저수준 모듈을 무리하게 분리하는 경우

체크리스트:
1. 상대 모듈의 내부 클래스·필드·테이블 구조를 알아야만 동작하는가?
2. 필요한 최소 데이터만 주고받는가?
3. 전역 상태나 공유 DB가 사실상의 통신 채널로 쓰이지 않는가?
4. 인터페이스가 구현 세부사항을 노출하지 않는가?
5. 한 모듈을 교체할 때 다른 모듈의 재컴파일·재배포가 필수인가?

실무에서 흔한 고결합 사례는 마이크로서비스 간 공유 DB, 프런트엔드가 백엔드 내부 오류 코드를 세부적으로 해석하는 구조, 서비스 메서드가 boolean 플래그 여러 개로 상대 모듈의 분기를 제어하는 방식이다. 반대로 이벤트 발행, 포트 인터페이스, 안정된 API 계약, DTO 기반 통신은 결합도를 낮추는 전형적 방법이다.

## 6. 기대효과 및 결론

낮은 결합은 변경 격리, 테스트 독립성, 배포 자율성, 장애 국소화를 가능하게 한다. 특히 시스템 규모가 커질수록 “상대를 덜 알아도 되는 구조”의 가치가 급격히 커진다. 이는 조직 구조와도 연결되어 팀 간 협업 비용을 줄인다.

하지만 낮은 결합을 절대선으로 오해하면 과도한 간접 계층, 불필요한 추상화, 지나친 네트워크 분해가 발생할 수 있다. 따라서 결합도 평가는 항상 성능, 단순성, 응집도와 함께 이뤄져야 한다. 결론적으로 좋은 설계는 결합을 없애는 것이 아니라, **변화에 취약한 결합을 안정된 계약으로 치환하는 것**이다.


## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| 응집도 | 높은 응집과 낮은 결합이 함께 좋은 모듈을 만든다 |
| DIP | 구체 구현이 아닌 추상화에 의존하게 해 결합도를 낮춤 |
| Law of Demeter | 이웃 객체의 내부를 모르게 하여 결합을 줄임 |
| API Contract | 모듈 간 안정된 협력 경계를 제공 |
| Shared Database Anti-pattern | 서비스 간 결합도를 급격히 높이는 대표 사례 |
| Event-Driven Architecture | 시간적·공간적 분리를 통해 결합도를 낮춤 |
| Hexagonal Architecture | 포트와 어댑터로 외부 인프라 결합을 제어 |
| 리팩토링 | Introduce Interface, Move Method, Extract Module이 결합 완화에 사용 |
