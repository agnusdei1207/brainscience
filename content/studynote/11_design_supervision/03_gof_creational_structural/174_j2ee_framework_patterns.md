## 0. 핵심 인사이트

> **핵심**: J2EE (Java 2 Platform, Enterprise Edition) 프레임워크 패턴은 계층, 책임, 호출 경계를 명확히 나누어 웹 요청 처리와 엔터프라이즈 자원 접근을 반복 가능하고 통제 가능한 구조로 만드는 참조 설계 집합이다.
> **비유**: 복잡한 도심 교통을 임의 도로가 아니라 환승 체계와 관제 규칙으로 운영해야 전체 흐름이 안정되는 것과 같다.

## 1. 개요 및 필요성

174. J2EE 프레임워크 패턴 (J2EE Framework Patterns)은 엔터프라이즈 애플리케이션에서 프레젠테이션, 비즈니스, 통합, 영속 계층을 역할별 패턴으로 분리하는 설계 관행를 다루는 주제다.
이 패턴이 중요한 직접 배경은 요청 처리, 세션 관리, 비즈니스 호출, 원격 자원 접근을 한 클래스에 몰아넣으면 변경 파급과 테스트 난도가 급증한다.
이를 해결하기 위한 구조적 가치로는 DAO (Data Access Object), DTO (Data Transfer Object), Front Controller, Business Delegate, Service Locator 같은 패턴을 결합하면 웹 계층과 기업 자원 계층 사이의 결합도를 낮출 수 있다.
설계자가 집중해야 하는 관점은 핵심 초점은 역할 분리, 원격 호출 은폐, 예외 처리 일관성, 트랜잭션 경계 통합이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

### 등장 배경
- 초기 엔터프라이즈 자바 환경에서는 서블릿, JSP, EJB (Enterprise JavaBeans), JDBC (Java Database Connectivity)가 직접 연결되는 경우가 많았다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 이 구조는 화면 변경이 데이터 접근 코드 수정으로 이어지고, 원격 호출 예외가 화면 계층까지 노출되는 문제를 만들었다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 대규모 팀 개발에서는 동일한 처리 흐름을 여러 개발자가 반복 구현하면서 인증, 로깅, 예외 매핑이 중복되었다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- J2EE 패턴은 이러한 중복을 줄이고 프레임워크 기반 표준 구현을 가능하게 만들기 위해 등장했다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 오늘날 Spring 계열 아키텍처 역시 이름은 달라도 같은 문제를 해결하기 위해 유사한 패턴 세트를 사용한다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 따라서 이 주제는 과거 기술이 아니라 현대 엔터프라이즈 프레임워크의 구조적 기원을 이해하는 관점에서 중요하다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.

### 필요성 정리
- 웹 계층이 JDBC를 직접 호출하면 화면 요구사항과 SQL (Structured Query Language) 구조가 강결합된다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 원격 EJB 호출이나 외부 서비스 호출이 Controller에 섞이면 네트워크 장애와 비즈니스 오류를 구분하기 어렵다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- DTO 없이 엔티티를 그대로 노출하면 직렬화 범위가 커지고 도메인 모델이 외부 계약에 종속된다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- Front Controller가 없으면 인증, 인코딩, 로깅, 예외 매핑을 각 URL마다 중복 구현하게 된다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- Service Locator 또는 DI (Dependency Injection) 대체 수단이 없으면 자원 조회 코드가 전역적으로 확산된다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 결국 패턴 부재는 코드 중복보다 더 큰 문제인 변경 통제 불능을 만든다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.

### 설계감리 포인트
- 감리 관점에서는 계층 간 의존 방향이 상향 역전되지 않는지 확인해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 원격 호출과 데이터 접근 예외가 공통 예외 모델로 변환되는지 점검해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- DTO 경계가 명확한지, 엔티티 직접 노출이 없는지 API 계약을 검토해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- Front Controller 이후의 라우팅 정책이 일관되고 보안 필터 체인과 충돌하지 않는지 봐야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- Business Delegate와 Service Layer가 중복 계층이 되지 않도록 책임 범위를 분명히 해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 패턴 적용 자체보다 호출 경계와 책임 경계가 실제 코드에 반영되었는지를 검증해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Front Controller | 웹 요청의 단일 진입점 | 공통 전처리·라우팅·예외 매핑 수행 |
| Application Controller | 유스케이스 단위 흐름 조정 | 요청별 명령 선택과 화면 이동 결정 |
| Business Delegate | 원격 서비스 호출 캡슐화 | 프레젠테이션 계층에 EJB·REST 세부정보 은폐 |
| Service Layer | 업무 규칙과 트랜잭션 경계 관리 | 유스케이스 중심 API 제공 |
| DAO | 영속 저장소 접근 분리 | SQL, ORM (Object Relational Mapping), 연결 관리 격리 |
| DTO/VO | 계층 간 데이터 전달 | 직렬화 비용과 원격 호출 횟수 제어 |
| Service Locator | 인프라 자원 조회 표준화 | JNDI (Java Naming and Directory Interface) lookup 집중화 |
| View | JSP, 템플릿, 응답 렌더링 | 도메인 계산 대신 표현 책임만 유지 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Front Controller는 모든 요청을 먼저 수신하고 인증, 로깅, 로케일 설정 같은 공통 관심사를 처리한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Application Controller는 요청 파라미터와 명령을 해석하여 적절한 Service Layer 메서드를 선택한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Business Delegate는 프레젠테이션 계층이 원격 인터페이스를 직접 알지 못하게 하는 완충재 역할을 한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Service Layer는 여러 DAO 호출을 묶어 하나의 유스케이스 트랜잭션으로 통제한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- DAO는 데이터베이스나 메시징 저장소 세부 구현을 캡슐화하여 상위 계층의 변경 부담을 줄인다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- DTO는 계층 간에 필요한 상태만 전달하여 원격 호출 횟수와 직렬화 크기를 관리한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Service Locator는 자원 조회 중복을 줄이지만, 현대 환경에서는 DI 컨테이너로 대체되기도 한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- View는 최종 결과를 렌더링하지만 비즈니스 규칙을 다시 계산하지 않아야 구조가 안정된다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 프레젠테이션 계층은 사용자 요청과 응답 형식을 책임지되 비즈니스 규칙의 저장소가 되어서는 안 된다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 비즈니스 계층은 유스케이스 수준의 정책을 관리하며 데이터 접근 세부정보를 모르면 이상적이다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 통합 계층은 외부 시스템 호출과 자원 조회를 담당하며 상위 계층에 장애 형태를 표준화해 전달해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 영속 계층은 질의 최적화와 저장 전략을 담당하지만 도메인 의미를 과도하게 침식하지 않도록 주의해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 패턴 세트는 결국 경계별 책임을 언어 차원이 아니라 구조 차원에서 강제하는 역할을 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 이 경계가 무너지면 J2EE 패턴을 적용해도 실제 시스템은 모놀리식 트랜잭션 스크립트로 퇴행한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 요청 경계, 비즈니스 경계, 자원 접근 경계를 분리하고, 각 경계를 넘을 때는 전용 패턴으로 결합을 완충해야 한다.

J2EE 패턴의 핵심은 특정 기술을 외우는 것이 아니라, 엔터프라이즈 애플리케이션의 반복 문제를 구조로 분해하는 데 있다.
웹 요청은 사용자 입력, 세션, 보안, 예외 매핑을 동반하므로 단일 진입점이 필요하다.
비즈니스 호출은 유스케이스 중심으로 묶여야 트랜잭션 경계가 일관된다.
원격 호출과 데이터 접근은 실패 가능성이 높으므로 프레젠테이션 계층에 직접 노출하면 안정성이 떨어진다.
데이터 전달 객체를 별도로 두면 네트워크 경계와 도메인 내부 모델을 분리할 수 있다.
DAO는 영속성 전략을 캡슐화하여 저장소 변경이 서비스 계층으로 번지는 것을 막는다.
Business Delegate와 Service Locator는 원격 기술 종속성을 상위 계층에서 제거하는 역사적 해법이다.
현대 프레임워크에서도 이름만 바뀌었을 뿐 같은 구조 원리가 유지된다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **사용자 요청 수신**: 클라이언트 요청은 Front Controller에 집중되어 공통 보안과 인코딩 정책을 먼저 통과한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **명령 해석**: Application Controller가 URI, 파라미터, 세션 상태를 해석해 어떤 유스케이스를 실행할지 결정한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **비즈니스 위임**: 프레젠테이션 계층은 Business Delegate 또는 Service Layer 인터페이스를 호출해 업무 처리를 요청한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **서비스 실행**: Service Layer는 트랜잭션 경계를 열고 필요한 도메인 규칙과 검증을 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **자원 접근**: DAO와 통합 컴포넌트가 데이터베이스, 메시지 큐, 외부 시스템에 접근하고 결과를 수집한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **데이터 포장**: 응답에 필요한 상태는 DTO 또는 View Model로 변환되어 표현 계층에 전달된다.

7. **응답 렌더링**: View가 화면 또는 API 응답을 생성하고 Front Controller가 최종 응답 정책을 적용한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
