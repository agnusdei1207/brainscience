## 0. 핵심 인사이트

> **핵심**: DTO (Data Transfer Object)는 계층 또는 네트워크 경계를 넘을 때 필요한 상태만 평탄하게 묶어 전송함으로써 호출 횟수와 직렬화 비용, 모델 노출 범위를 통제하는 계약 객체다.
> **비유**: 여러 서류를 낱장으로 옮기지 않고 한 번에 제출 가능한 정리된 묶음으로 만드는 방식과 같다.

## 1. 개요 및 필요성

175. DTO (Data Transfer Object)은 비즈니스 행위보다 데이터 운반에 초점을 둔 전송 전용 객체를 다루는 주제다.
이 패턴이 중요한 직접 배경은 엔티티를 그대로 노출하거나 작은 데이터를 여러 번 호출로 나누어 전달하면 네트워크 왕복과 결합도가 함께 증가한다.
이를 해결하기 위한 구조적 가치로는 DTO는 외부 인터페이스 안정화, 직렬화 최적화, 내부 모델 보호를 동시에 지원한다.
설계자가 집중해야 하는 관점은 핵심 초점은 경계 분리, 필드 선별, 버전 관리, 매핑 전략이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

### 등장 배경
- 원격 호출 비용이 큰 분산 시스템에서는 여러 필드를 한 번에 묶어 보내는 전략이 필요했다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 웹 API와 모바일 API가 확산되면서 내부 엔티티 구조를 그대로 노출하는 위험이 커졌다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 도메인 모델은 풍부한 행위를 갖지만, 외부 계약은 단순하고 안정적인 데이터 구조를 원한다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 직렬화 프레임워크는 순환 참조나 지연 로딩 프록시와 만나면 예기치 않은 성능 문제를 만들 수 있다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- DTO는 이러한 문제를 경계 전용 모델로 차단하는 기본 수단으로 정착했다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 따라서 DTO는 단순한 클래스가 아니라 경계 설계와 API 거버넌스의 핵심 수단이다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.

### 필요성 정리
- 엔티티 직접 노출은 내부 필드와 관계 구조가 API 계약으로 고착되는 문제를 만든다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 작은 요청을 여러 번 왕복하면 채팅성 API가 되어 지연 시간이 급증한다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 직렬화 시 불필요한 연관 객체까지 끌려 나오면 응답 크기와 쿼리 수가 함께 증가한다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 입력 DTO 없이 엔티티에 바로 바인딩하면 검증과 권한 제어 지점이 모호해진다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- DTO 설계 없이 버전 관리를 시작하면 필드 변경이 곧장 클라이언트 장애로 이어질 수 있다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 결국 DTO 부재는 성능 문제와 계약 불안정을 동시에 만든다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.

### 설계감리 포인트
- 입력 DTO와 출력 DTO를 분리하여 쓰기 권한과 읽기 노출 범위를 독립적으로 제어해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- DTO는 행위를 최소화하고 검증 어노테이션 또는 명시적 검증 규칙을 부여하는 수준으로 유지하는 것이 일반적이다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 필드 명명 규칙과 null 정책이 API 전체에서 일관되는지 확인해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 버전 필드 또는 미디어 타입 버전 전략이 필요한지 서비스 특성에 따라 판단해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 엔티티-DTO 매핑 규칙이 코드 생성 또는 매퍼 프레임워크에 의해 표준화되는지도 중요하다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 감리 관점에서는 DTO가 정말 경계 안정화에 기여하는지, 아니면 단순 복사 객체만 늘리는지 구분해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Input DTO | 클라이언트 입력 수용 | 검증과 권한 제어의 첫 경계 |
| Output DTO | 응답 데이터 전달 | 노출 범위와 표현 형식 통제 |
| Mapper | 엔티티와 DTO 변환 | 수작업 또는 MapStruct 같은 도구 활용 |
| Assembler | 복수 객체를 조합해 응답 생성 | 화면 또는 API 맞춤형 집계 |
| Validation Rule | 필드 값 검증 | 형식·범위·필수 여부 확인 |
| Versioning Policy | 계약 진화 관리 | 필드 추가·폐기 규칙 정의 |
| Serialization Layer | JSON/XML/ProtoBuf 변환 | 포맷별 효율과 호환성 관리 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Input DTO는 컨트롤러 경계에서 생성되어 검증을 거친 뒤 서비스 계층으로 전달된다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 서비스 계층은 Input DTO를 도메인 명령이나 엔티티 생성용 값으로 변환한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 도메인 모델은 비즈니스 규칙을 수행하지만 외부 형식인 DTO를 직접 의존하지 않는 편이 바람직하다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Output DTO는 엔티티 전체가 아니라 응답에 필요한 필드만 선택적으로 담는다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Mapper는 구조 변환 책임을 집중시켜 서비스 코드의 중복 매핑을 줄인다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Assembler는 여러 엔티티와 외부 시스템 결과를 한 응답 DTO로 합성할 때 유용하다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Versioning Policy는 DTO 구조가 진화할 때 하위 호환성과 폐기 절차를 정의한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Serialization Layer는 DTO를 실제 전송 포맷으로 변환하므로 성능과 보안 정책의 마지막 경계가 된다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- DTO는 데이터 전달용이므로 도메인 규칙을 담는 주 저장소가 되어서는 안 된다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 반대로 엔티티는 풍부한 규칙을 담을 수 있으나 외부 계약 안정성을 위해 직접 노출하지 않는 것이 좋다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- Value Object와 DTO는 모두 데이터 중심처럼 보이지만, 전자는 도메인 의미를 갖고 후자는 전달 경계를 담당한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 읽기 모델과 쓰기 모델을 분리하면 API 변화에 더 유연하게 대응할 수 있다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- DTO 경계 설계는 결국 어떤 정보를 누구에게, 어떤 시점에, 어떤 형식으로 공개할지 결정하는 일이다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 이 경계가 명확할수록 내부 리팩터링 자유도가 커진다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 전달 효율과 계약 안정성이 목적일 때는 행위보다 데이터 구조의 명시성, 선택성, 버전 관리가 우선되어야 한다.

DTO는 데이터 묶음이지 도메인 객체의 축소판이 아니다.
외부 계약은 내부 모델보다 오래 살아남는 경우가 많으므로 독립적 진화가 가능해야 한다.
직렬화 비용은 필드 수와 중첩 구조, 연관 객체 범위에 직접 영향을 받는다.
입력 DTO와 출력 DTO를 분리하면 보안과 표현 요구를 독립적으로 다룰 수 있다.
매핑은 비용이 들지만, 그 비용으로 경계 안정성과 성능 제어 권한을 얻는다.
DTO가 너무 세분되면 관리 복잡도가 커지므로 유스케이스 중심으로 범위를 조정해야 한다.
조회 최적화가 중요한 경우 CQRS (Command Query Responsibility Segregation)와 결합한 읽기 전용 DTO 모델이 효과적이다.
결국 DTO는 계층 간 번역 계층이며, 번역 기준이 곧 API 정책이다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **요청 수신**: 클라이언트가 JSON, XML, gRPC 등 형식으로 데이터를 전송하면 프레임워크가 Input DTO로 역직렬화한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **입력 검증**: 필수값, 형식, 범위, 권한을 Input DTO 기준으로 검증하여 잘못된 요청을 조기에 차단한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **도메인 변환**: 서비스 계층은 Input DTO를 도메인 명령, 엔티티 생성 파라미터, 값 객체 등으로 변환한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **업무 처리**: 도메인 규칙과 저장소 접근이 수행되어 필요한 결과가 생성된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **응답 조합**: 서비스 또는 Assembler가 엔티티, 계산 결과, 외부 응답을 결합해 Output DTO를 만든다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **직렬화**: Output DTO는 전송 포맷에 맞게 직렬화되어 네트워크 경계를 넘는다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **계약 진화**: 필드 추가, 폐기, 호환성 정책을 DTO 버전 규칙에 따라 관리한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
Client
  | request payload
  v
[Input DTO] --validate--> [Service / Application Layer] --map--> [Domain Model]
                                                        |
                                                        v
                                                   [Repository / DAO]
                                                        |
                                                        v
                                            [Assembler / Mapper]
                                                        |
                                                        v
                                                   [Output DTO]
                                                        | serialize
                                                        v
                                                      Client
```

### 구조 해설
- Input DTO: 클라이언트 입력 수용. 검증과 권한 제어의 첫 경계라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Input DTO의 책임이 다른 요소와 뒤섞이면 175. DTO (Data Transfer Object)의 핵심 이점이 약해질 수 있다.
- Output DTO: 응답 데이터 전달. 노출 범위와 표현 형식 통제라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

- Serialization Layer: JSON/XML/ProtoBuf 변환. 포맷별 효율과 호환성 관리라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

## 4. 비교 및 연결

| 비교 항목 | DTO | Value Object | 핵심 의미 |
|:---|:---|:---|:---|
| 주 목적 | 데이터 전달 | 도메인 개념 표현 | 계층 경계와 도메인 내부의 역할이 다르다. |
| 행위 보유 | 최소 또는 없음 | 도메인 의미 있는 행위 가능 | 풍부한 모델링 여부가 달라진다. |

| 위치 | API/서비스 경계 | 도메인 모델 내부 | 사용 맥락이 다르다. |

### 연결 개념
- Value Object: 도메인 내부 값 개념과 DTO의 차이를 설명할 때 함께 비교됨
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.
- Entity: DTO가 직접 노출을 막아야 하는 내부 모델
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.
- Mapper: 엔티티와 DTO 사이 변환 책임을 담당
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.
- Assembler: 복합 응답 DTO를 조합하는 보조 객체
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.
- CQRS: 조회 전용 DTO를 적극 활용하는 아키텍처
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.
- Serialization: DTO가 실제 전송 포맷으로 바뀌는 단계
  - 인접 개념과의 연결을 이해해야 패턴 오남용을 줄일 수 있다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|

| Entity | DTO가 직접 노출을 막아야 하는 내부 모델 |
| Mapper | 엔티티와 DTO 사이 변환 책임을 담당 |

| Versioning | DTO 계약 진화를 관리하는 핵심 정책 |
| BFF | 채널별 DTO 최적화를 수행하는 아키텍처 |
| API Contract Test | DTO 호환성을 자동으로 검증하는 방법 |
