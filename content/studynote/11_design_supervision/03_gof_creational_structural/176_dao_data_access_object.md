## 0. 핵심 인사이트

> **핵심**: DAO (Data Access Object)는 비즈니스 규칙이 저장소 접근 세부구현을 알지 못하게 함으로써 SQL, 연결 관리, 매핑 전략의 변화를 데이터 접근 계층 안에 가두는 분리 패턴이다.
> **비유**: 업무 담당자가 창고의 선반 위치와 열쇠 체계를 직접 기억하지 않고 창고 담당 창구를 통해 물건을 받는 구조와 같다.

## 1. 개요 및 필요성

176. DAO (Data Access Object) 패턴은 애플리케이션의 데이터 접근 로직을 전용 객체로 분리하는 패턴를 다루는 주제다.
이 패턴이 중요한 직접 배경은 서비스나 컨트롤러가 직접 SQL과 연결 코드를 가지면 저장소 변경과 예외 처리가 전 계층으로 확산된다.
이를 해결하기 위한 구조적 가치로는 DAO는 질의, 매핑, 연결, 예외 변환을 캡슐화해 서비스 계층을 업무 중심으로 유지한다.
설계자가 집중해야 하는 관점은 핵심 초점은 저장소 추상화, 트랜잭션 경계 협력, 질의 책임 분리다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

### 등장 배경
- 초기 엔터프라이즈 시스템에서는 화면 코드나 서비스 코드에 SQL이 직접 삽입되는 경우가 많았다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 이 방식은 데이터베이스 스키마 변경이 곧 서비스 로직 변경으로 이어지는 문제를 만들었다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 연결 관리, 자원 해제, 예외 변환을 반복 구현하면서 코드 중복과 장애가 증가했다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- DAO 패턴은 영속 계층 책임을 분리하여 서비스 계층이 유스케이스에 집중하게 만들었다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- ORM 도입 이후에도 DAO는 질의 조합, 성능 튜닝, 맞춤형 조회를 구조화하는 역할을 계속 가진다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.
- 따라서 DAO는 JDBC 시대의 유산이 아니라 저장소 경계 설계의 기본 패턴으로 이해해야 한다.
  - 이는 단순 구현 기법이 아니라 구조적 필요에서 출발했음을 보여 준다.

### 필요성 정리
- 서비스 계층에서 SQL을 직접 작성하면 비즈니스 규칙과 질의 최적화가 섞인다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 여러 곳에서 연결과 자원 해제를 처리하면 누수와 중복 로직이 증가한다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 데이터베이스 예외가 상위 계층으로 그대로 노출되면 오류 의미가 불명확해진다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 동일한 조회 조건이 여러 서비스에 흩어지면 일관된 성능 개선이 어려워진다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 단위 테스트가 저장소 없이 불가능해져 서비스 로직 검증이 느려진다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.
- 결국 DAO 부재는 저장소 세부 구현이 시스템 전체를 오염시키는 결과를 낳는다.
  - 따라서 패턴이 없다면 변경 비용과 운영 위험이 누적될 가능성이 높다.

### 설계감리 포인트
- DAO 인터페이스는 도메인 의미 있는 질의 단위로 설계해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 트랜잭션은 보통 서비스 계층이 시작하고 DAO는 그 경계 안에서 협력하는 방식이 일반적이다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 예외는 기술 예외에서 업무 해석 가능한 예외로 변환되는 정책이 있어야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 읽기 전용 DAO와 갱신 DAO를 분리할지 시스템 성격에 따라 결정할 수 있다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- DAO가 지나치게 범용 CRUD 저장소가 되면 도메인 의미가 약해질 수 있다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.
- 감리에서는 DAO 수 자체보다 질의 책임과 서비스 책임이 잘 분리되었는지를 확인해야 한다.
  - 문서와 코드가 일치하는지까지 확인해야 실제 구조 품질을 판단할 수 있다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| DAO Interface | 상위 계층이 의존하는 추상 계약 | 도메인 의미 있는 메서드 제공 |
| DAO Implementation | 실제 JDBC/JPA/MyBatis 처리 | 저장소 기술 세부사항 포함 |
| Connection / Session Manager | 연결과 세션 관리 | 트랜잭션 경계와 협력 |
| Mapper | ResultSet 또는 엔티티 매핑 | 객체 변환 일관성 유지 |
| Query Builder | 질의 구성 | 동적 조건과 파라미터 바인딩 관리 |
| Exception Translator | 기술 예외 변환 | 상위 계층에 의미 있는 오류 제공 |
| Unit of Work / Persistence Context | 변경 추적 협력 | ORM 환경에서 DAO와 연동 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- 서비스 계층은 DAO 인터페이스에만 의존하여 저장소 기술을 모르게 설계한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- DAO 구현체는 데이터베이스 연결, 세션, 매퍼, 질의 생성을 내부에서 조합한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 조회 결과는 엔티티, DTO, 프로젝션 객체 등 호출 목적에 맞는 형태로 반환될 수 있다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 쓰기 메서드는 트랜잭션 경계 안에서 실행되어 여러 DAO 호출과 함께 원자성을 보장한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 예외 변환기는 SQL 예외를 도메인 친화적인 오류로 바꾸어 서비스가 의도적으로 처리하게 돕는다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Query Builder는 동적 조건 조합 시 SQL 주입 방지와 재사용성을 동시에 지원한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- ORM 환경에서는 DAO가 Persistence Context와 협력해 변경 추적과 flush 전략을 조율한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- 결국 DAO는 상위 계층과 저장소 사이의 번역기이자 방화벽 역할을 한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 서비스 계층은 업무 규칙과 트랜잭션을 담당하고 DAO는 저장소 접근을 담당해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- DAO가 업무 규칙을 가지기 시작하면 서비스와 책임이 겹치게 된다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 반대로 서비스가 질의 최적화와 SQL 구조를 알아야 한다면 DAO 경계가 약한 것이다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- Repository 패턴은 도메인 관점이 더 강하지만, 저장소 세부 구현 격리라는 핵심은 DAO와 공유한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 읽기 모델 최적화가 강한 시스템에서는 DAO가 DTO 프로젝션 반환을 담당하기도 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 이 경계 설계는 유지보수성뿐 아니라 성능 진단의 초점도 분명하게 만든다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 업무 로직은 저장소 세부기술을 모르고, 저장소 기술 변화는 DAO 안에서 흡수되어야 한다.

DAO는 단순 CRUD 래퍼가 아니라 저장소 접근의 의미 단위를 제공하는 계층이다.
상위 계층이 SQL 문법, 커넥션 관리, 매핑 규칙을 알지 못하게 하는 것이 가장 중요한 목적이다.
질의와 트랜잭션은 구분해야 하며, 대개 트랜잭션은 서비스 계층이 소유한다.
DAO는 성능 최적화의 실무 지점이므로 인덱스 전략과 페치 전략을 반영한 질의를 가질 수 있다.
테스트에서는 DAO를 대체하는 가짜 구현이나 인메모리 저장소를 주입해 서비스 검증을 쉽게 할 수 있다.
DAO가 모든 테이블 접근을 범용 메서드로만 제공하면 오히려 의미가 약해진다.
도메인 모델 중심이면 Repository가 더 적합할 수 있지만, 데이터 접근 분리 원칙은 동일하다.
따라서 DAO는 저장소 세부사항을 은닉하는 설계 압력의 결과라고 볼 수 있다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **서비스 호출**: 서비스 계층이 유스케이스 수행 중 필요한 저장소 작업을 DAO 인터페이스에 요청한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **질의 구성**: DAO 구현체가 고정 SQL, 동적 SQL, Criteria API 등을 사용해 적절한 질의를 만든다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **연결·세션 확보**: 트랜잭션 컨텍스트에 맞는 연결이나 ORM 세션을 획득한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **실행과 매핑**: 질의를 실행하고 결과를 엔티티, DTO, 프로젝션으로 매핑한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **예외 변환**: 저장소 기술 예외를 상위 계층이 이해 가능한 예외로 변환한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **트랜잭션 협력**: 갱신인 경우 서비스 트랜잭션 경계 안에서 flush, commit, rollback 정책과 협력한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **결과 반환**: 서비스는 저장소 세부사항 대신 의미 있는 결과만 받아 후속 업무 규칙을 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Controller]
    |
    v
[Service Layer] --transaction--> [DAO Interface]
                                   |
                                   v
                           [DAO Implementation]
                             |      |      |
                             |      |      +--> [Exception Translator]
                             |      +---------> [Mapper / Query Builder]
                             v
                      [Connection / Session]
                             |
                             v
                            [DB]
```

### 구조 해설
- DAO Interface: 상위 계층이 의존하는 추상 계약. 도메인 의미 있는 메서드 제공라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - DAO Interface의 책임이 다른 요소와 뒤섞이면 176. DAO (Data Access Object) 패턴의 핵심 이점이 약해질 수 있다.
- DAO Implementation: 실제 JDBC/JPA/MyBatis 처리. 저장소 기술 세부사항 포함라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

### 보강 전략
- DAO 메서드는 데이터베이스 테이블이 아니라 유스케이스가 요구하는 조회 단위를 기준으로 설계하는 편이 낫다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- 읽기 성능이 중요한 경우 전용 조회 DAO와 커맨드 DAO를 나누는 전략이 실무에서 자주 사용된다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- JPA를 사용할 때도 복잡한 네이티브 쿼리와 벌크 작업은 별도 DAO 성격의 컴포넌트가 필요할 수 있다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- DAO 테스트는 SQL 정확성, 인덱스 활용, 매핑 정확성을 검증하는 통합 테스트 성격이 강하다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- 서비스 테스트는 DAO를 대체 가능해야 하므로 인터페이스 분리가 중요하다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- DAO 네이밍과 패키지 구조가 통일되지 않으면 계층 규칙이 쉽게 붕괴한다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- 감리 시에는 DAO 없는 직접 SQL보다, DAO가 있어도 상위 계층이 SQL 문자열을 알고 있는 구조를 더 위험하게 본다.
  - 이런 보강책을 함께 고려해야 패턴이 실무 품질로 연결된다.
- DAO 패턴은 저장소 기술 은닉과 운영 가능한 질의 구조를 동시에 만족시켜야 완성된다.
