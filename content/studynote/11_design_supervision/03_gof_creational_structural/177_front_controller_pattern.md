## 0. 핵심 인사이트

> **핵심**: Front Controller Pattern은 모든 웹 요청을 단일 진입점에 집중시켜 공통 정책을 먼저 적용한 뒤 적절한 핸들러로 위임하는 요청 제어 패턴이다.
> **비유**: 여러 부서 방문객을 각 문으로 흩어 보내지 않고 안내 데스크에서 신원 확인과 안내를 먼저 수행하는 체계와 같다.

## 1. 개요 및 필요성

177. 프론트 컨트롤러 패턴 (Front Controller Pattern)은 웹 계층의 단일 진입점 제어 구조를 다루는 주제다.
이 패턴이 중요한 직접 배경은 요청별로 개별 서블릿이나 컨트롤러가 직접 보안, 로깅, 예외 처리를 수행하면 중복과 편차가 커진다.
이를 해결하기 위한 구조적 가치로는 DispatcherServlet 같은 단일 진입점을 통해 라우팅, 인증, 국제화, 예외 매핑을 일관되게 관리할 수 있다.
설계자가 집중해야 하는 관점은 핵심 초점은 공통 처리 집중, 라우팅 일관성, 확장 가능한 핸들러 위임이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Front Controller | 단일 요청 진입점 | 공통 처리와 라우팅 담당 |
| Handler Mapping | 요청과 핸들러 연결 | URI·메서드·조건 매핑 |
| Handler Adapter | 다양한 핸들러 호출 통합 | 프레임워크 확장성 확보 |
| Interceptor | 전후 공통 로직 처리 | 인증, 권한, 추적 |
| Exception Resolver | 예외를 응답으로 변환 | 일관된 오류 모델 제공 |
| View Resolver | 뷰 이름을 실제 렌더러로 변환 | JSP, 템플릿, JSON 응답 지원 |
| Controller | 개별 유스케이스 처리 | 도메인 호출과 응답 모델 작성 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Front Controller는 단일 요청 진입점 역할을 가지며 전체 흐름에서 공통 처리와 라우팅 담당 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Handler Mapping는 요청과 핸들러 연결 역할을 가지며 전체 흐름에서 URI·메서드·조건 매핑 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Handler Adapter는 다양한 핸들러 호출 통합 역할을 가지며 전체 흐름에서 프레임워크 확장성 확보 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Interceptor는 전후 공통 로직 처리 역할을 가지며 전체 흐름에서 인증, 권한, 추적 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Exception Resolver는 예외를 응답으로 변환 역할을 가지며 전체 흐름에서 일관된 오류 모델 제공 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- View Resolver는 뷰 이름을 실제 렌더러로 변환 역할을 가지며 전체 흐름에서 JSP, 템플릿, JSON 응답 지원 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Controller는 개별 유스케이스 처리 역할을 가지며 전체 흐름에서 도메인 호출과 응답 모델 작성 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.

  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 경계는 예외 처리 방식과 테스트 전략에도 직접 영향을 준다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 데이터와 제어가 경계를 넘을 때 어떤 변환이 일어나는지 명확해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 운영 중 문제 추적이 가능한 경계일수록 유지보수성이 높다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 즉, 좋은 패턴 적용은 코드 분할보다 의존성 통제에서 드러난다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 모든 요청은 공통 정책을 단일 진입점에서 통과한 뒤, 전용 핸들러로 위임되어야 한다.

요청 진입점이 분산되면 공통 정책의 일관성을 보장하기 어렵다.
단일 진입점은 라우팅 규칙과 오류 응답 형식의 표준화를 가능하게 만든다.
핸들러 위임 구조를 분리하면 프론트 컨트롤러 자체는 확장에 열려 있으면서도 핵심 흐름은 안정적이다.
인터셉터 체인은 횡단 관심사를 개별 비즈니스 코드에서 분리한다.
예외 해결과 뷰 해결을 별도 전략으로 두면 웹 기술 변화에 유연하게 대응할 수 있다.
Front Controller는 MVC, API, SSR (Server Side Rendering) 모두에서 반복되는 제어 패턴이다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **요청 수신**: HTTP 요청이 Front Controller로 먼저 도달한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **공통 전처리**: 인증, 로깅, 인코딩, 로케일, 추적 ID 설정이 수행된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **핸들러 탐색**: Handler Mapping이 요청에 맞는 컨트롤러를 찾는다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **전용 처리**: Controller가 서비스 계층을 호출하여 유스케이스를 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **예외/후처리**: 인터셉터 후처리와 예외 해결기가 공통 정책을 적용한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **응답 렌더링**: View Resolver 또는 메시지 컨버터가 최종 응답을 만든다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **응답 반환**: 일관된 헤더와 상태 코드 정책을 적용한 응답이 반환된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
Client
  |
  v
[Front Controller]
  |-- preHandle --> [Interceptor Chain]
  |-- map -------> [Handler Mapping]
  |-- invoke ----> [Controller]
  |                   |
  |                   v
  |               [Service Layer]
  |
  |-- resolve ---> [Exception Resolver / View Resolver]
  |
  v
Response
```

### 구조 해설
- Front Controller: 단일 요청 진입점. 공통 처리와 라우팅 담당라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Front Controller의 책임이 다른 요소와 뒤섞이면 177. 프론트 컨트롤러 패턴 (Front Controller Pattern)의 핵심 이점이 약해질 수 있다.
- Handler Mapping: 요청과 핸들러 연결. URI·메서드·조건 매핑라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Handler Mapping의 책임이 다른 요소와 뒤섞이면 177. 프론트 컨트롤러 패턴 (Front Controller Pattern)의 핵심 이점이 약해질 수 있다.
- Handler Adapter: 다양한 핸들러 호출 통합. 프레임워크 확장성 확보라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Handler Adapter의 책임이 다른 요소와 뒤섞이면 177. 프론트 컨트롤러 패턴 (Front Controller Pattern)의 핵심 이점이 약해질 수 있다.
- Interceptor: 전후 공통 로직 처리. 인증, 권한, 추적라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

  - 구현 기술은 바뀌어도 근본적인 설계 압력은 계속 남는다.

## 7. 발전 흐름도

```
개별 Servlet 분산
    ↓
Front Controller 도입
    ↓
인터셉터 체인 정착
    ↓
예외·뷰 전략 분리
    ↓
REST/JSON 중심 진화
    ↓
API Gateway와 연계
```

### 흐름 해설
- 개별 Servlet 분산 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- Front Controller 도입 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- 인터셉터 체인 정착 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- 예외·뷰 전략 분리 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- REST/JSON 중심 진화 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- API Gateway와 연계 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Interceptor | Front Controller 전후 공통 로직을 연결 |
| Handler Mapping | 요청을 적절한 처리기로 연결 |
| View Resolver | 논리 뷰 이름을 실제 응답으로 해석 |
| Exception Resolver | 예외를 HTTP 응답으로 변환 |
| MVC | 프레젠테이션 계층 구조와 연결 |
| Filter | 서블릿 컨테이너 단계 공통 처리와 비교 대상 |
| API Gateway | 시스템 외곽의 확장된 프론트 컨트롤러 역할 |
| DI Container | 핸들러와 인프라 배선을 지원 |
| Routing | 핵심 제어 기능 |
| Observability | 중앙 로그와 추적의 기반 |

### 정리 메모
- Front Controller의 핵심은 중앙화 자체가 아니라 공통 정책을 일관되게 적용한 뒤 개별 처리기로 위임하는 흐름 제어에 있다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
