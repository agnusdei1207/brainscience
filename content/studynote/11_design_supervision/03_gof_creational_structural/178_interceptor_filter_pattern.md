## 1. 개요 및 필요성

178. 인터셉터와 필터 패턴 (Interceptor / Filter Pattern)은 요청 처리 전후에 공통 로직을 적용하는 가로채기 체인 구조를 다루는 주제다.
이 패턴이 중요한 직접 배경은 인증, 로깅, 인코딩, 감사, 성능 측정이 각 컨트롤러에 퍼지면 중복과 누락이 발생한다.
이를 해결하기 위한 구조적 가치로는 필터는 컨테이너 수준에서, 인터셉터는 프레임워크 수준에서 공통 정책을 적용한다.
설계자가 집중해야 하는 관점은 핵심 초점은 적용 계층 차이, 순서 제어, 중단 가능성, 책임 분리다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Filter | 서블릿 컨테이너 전처리 | Request/Response 래핑 가능 |
| Filter Chain | 다수 필터 순차 실행 | 순서가 의미를 결정 |
| Interceptor | 핸들러 전후 제어 | MVC 맥락 정보 접근 가능 |
| Handler | 실제 비즈니스 처리기 | 체인의 목표 지점 |
| Exception Handler | 예외 공통 처리 | 횡단 관심사와 결합 |
| Security Context | 인증 정보 저장 | 필터/인터셉터 결과 전달 |
| Metrics/Tracing | 관측성 수집 | 전후 지점 측정 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Filter는 서블릿 컨테이너 전처리 역할을 가지며 전체 흐름에서 Request/Response 래핑 가능 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Filter Chain는 다수 필터 순차 실행 역할을 가지며 전체 흐름에서 순서가 의미를 결정 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Interceptor는 핸들러 전후 제어 역할을 가지며 전체 흐름에서 MVC 맥락 정보 접근 가능 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Handler는 실제 비즈니스 처리기 역할을 가지며 전체 흐름에서 체인의 목표 지점 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Exception Handler는 예외 공통 처리 역할을 가지며 전체 흐름에서 횡단 관심사와 결합 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Security Context는 인증 정보 저장 역할을 가지며 전체 흐름에서 필터/인터셉터 결과 전달 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Metrics/Tracing는 관측성 수집 역할을 가지며 전체 흐름에서 전후 지점 측정 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.

- 데이터와 제어가 경계를 넘을 때 어떤 변환이 일어나는지 명확해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 운영 중 문제 추적이 가능한 경계일수록 유지보수성이 높다.

## 3. 구조 및 원리
**핵심 조건**: 횡단 관심사는 본업 로직에서 제거하고, 요청 흐름에 결합 가능한 체인으로 외부화해야 한다.

필터는 웹 컨테이너 수준에서 더 이른 단계에 동작한다.
인터셉터는 컨트롤러 선택 이후 더 풍부한 MVC 문맥을 활용한다.
순서가 바뀌면 인증, 압축, 로깅 결과가 달라질 수 있으므로 체인 정의가 중요하다.
중단 가능한 체인은 권한 거부나 요청 차단에 효과적이다.
공통 정책을 체인으로 분리하면 테스트와 운영 변경이 쉬워진다.
필터와 인터셉터는 경쟁 관계가 아니라 적용 지점이 다른 보완 관계다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **요청 진입**: 클라이언트 요청이 먼저 필터 체인을 통과한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **컨테이너 전처리**: 필터가 인코딩, CORS, 보안 헤더, 인증 초기 처리를 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **프레임워크 진입**: 핸들러가 결정되면 인터셉터가 preHandle 단계에서 추가 검사를 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **업무 처리**: 핸들러가 서비스 로직을 실행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **후처리**: 인터셉터 postHandle 및 afterCompletion이 로그, 정리, 메트릭 수집을 수행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **응답 후처리**: 필터가 응답 헤더 조정, 압축, 추적 기록을 마무리한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **완료**: 체인 전체가 종료되며 일관된 정책이 적용된 응답이 반환된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
Client
  |
  v
[Filter 1] -> [Filter 2] -> [Filter N]
                                   |
                                   v
                           [Dispatcher / Handler Mapping]
                                   |
                                   v
                     [Interceptor preHandle]
                                   |
                                   v
                              [Handler]
                                   |
                     [Interceptor post/after]
                                   |
                                   v
                                Response
```

### 구조 해설
- Filter: 서블릿 컨테이너 전처리. Request/Response 래핑 가능라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Filter의 책임이 다른 요소와 뒤섞이면 178. 인터셉터와 필터 패턴 (Interceptor / Filter Pattern)의 핵심 이점이 약해질 수 있다.
- Filter Chain: 다수 필터 순차 실행. 순서가 의미를 결정라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Filter Chain의 책임이 다른 요소와 뒤섞이면 178. 인터셉터와 필터 패턴 (Interceptor / Filter Pattern)의 핵심 이점이 약해질 수 있다.
- Interceptor: 핸들러 전후 제어. MVC 맥락 정보 접근 가능라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.
  - Interceptor의 책임이 다른 요소와 뒤섞이면 178. 인터셉터와 필터 패턴 (Interceptor / Filter Pattern)의 핵심 이점이 약해질 수 있다.
- Handler: 실제 비즈니스 처리기. 체인의 목표 지점라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Front Controller | 필터·인터셉터가 연결되는 중앙 요청 흐름 |
| AOP | 메서드 레벨 횡단 관심사 처리와 비교 |
| Middleware | 웹 프레임워크 전반의 유사 개념 |
| Security Context | 인증 정보 전달 저장소 |
| Tracing | 전후 단계 성능 추적 |
| CORS | 필터에서 자주 처리하는 정책 |
| HandlerInterceptor | Spring 구현 |
| Servlet Filter | 컨테이너 단계 구현 |
| Exception Handling | 후처리와 오류 응답 연결 |
| Observability | 체인 기반 공통 관측성 |

### 정리 메모
- Filter와 Interceptor는 어디에서 가로챌 것인가의 차이를 가지며, 둘을 함께 설계해야 요청 흐름의 정책 일관성이 완성된다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
