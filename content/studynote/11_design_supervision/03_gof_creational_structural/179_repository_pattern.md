## 0. 핵심 인사이트

> **핵심**: Repository Pattern은 도메인 객체 집합을 메모리 컬렉션처럼 다루게 하여 도메인 계층이 저장소 기술보다 모델 의미에 집중하도록 만드는 패턴이다.
> **비유**: 업무 담당자가 보관 창고의 내부 장비보다 필요한 문서를 찾고 보관하는 규칙 자체에 집중하는 방식과 같다.

## 1. 개요 및 필요성

179. 레파지토리 패턴 (Repository Pattern)은 DDD (Domain-Driven Design) 관점의 도메인 중심 저장소 추상화를 다루는 주제다.
이 패턴이 중요한 직접 배경은 도메인 서비스가 SQL과 테이블 구조를 알게 되면 모델이 저장소 구현에 끌려간다.
이를 해결하기 위한 구조적 가치로는 Repository는 애그리거트 조회, 저장, 삭제를 도메인 언어로 표현하게 한다.
설계자가 집중해야 하는 관점은 핵심 초점은 애그리거트 경계, 컬렉션 의미, 인프라 은닉이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Repository Interface | 도메인 계층 계약 | 애그리거트 단위 메서드 제공 |
| Repository Implementation | 인프라 계층 구현 | JPA, SQL, NoSQL 등 기술 의존 |
| Aggregate Root | 저장 단위 기준 | 일관성 경계의 중심 |
| Specification/Query Object | 복잡한 조회 조건 표현 | 도메인 친화적 질의 |
| Mapper | 도메인-영속 모델 변환 | 필요 시 분리 |
| Unit of Work | 변경 추적 협력 | 트랜잭션과 flush 관리 |
| Domain Service | Repository 사용 주체 | 업무 규칙 수행 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

## 3. 구조 및 원리
**핵심 조건**: 도메인 계층은 저장 방식이 아니라 애그리거트 의미에 의존해야 하며, 저장소는 컬렉션처럼 보이되 인프라 구현을 숨겨야 한다.

Repository는 테이블 단위보다 애그리거트 단위가 중요하다.
도메인 언어로 메서드를 설계해야 모델 가독성이 높아진다.
모든 조회를 Repository에 억지로 넣기보다 복잡도에 따라 Query Object를 병행할 수 있다.
Repository는 도메인 순수성을 높이지만 성능 최적화와 균형을 잡아야 한다.
인프라 구현은 교체 가능하지만 인터페이스는 도메인 모델의 일부처럼 읽혀야 한다.
DAO보다 도메인 중심성이 강한 것이 핵심 차이다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **도메인 요청**: 애플리케이션 서비스가 애그리거트 검색 또는 저장을 요청한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **저장소 계약 호출**: 도메인 계층은 Repository 인터페이스에만 의존한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **인프라 구현 선택**: 구현체가 JPA, SQL, 캐시, 외부 저장소 전략을 사용한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **애그리거트 복원**: 조회 결과를 애그리거트 루트와 연관 객체로 재구성한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **도메인 변경**: 애그리거트가 규칙에 따라 상태를 바꾼다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **변경 반영**: Unit of Work 또는 저장 메서드가 변경을 영속화한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **도메인 반환**: 상위 계층은 저장 기술이 아닌 도메인 결과만 다룬다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Application Service]
         |
         v
[Repository Interface] ---> [Specification / Query Object]
         |
         v
[Repository Impl] ---> [ORM / SQL / NoSQL]
         |
         v
[Aggregate Root + Entities + Value Objects]
         |
         v
[Unit of Work / Transaction]
```

- Domain Service: Repository 사용 주체. 업무 규칙 수행라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Aggregate | Repository가 다루는 일관성 단위 |
| DAO | 데이터 접근 중심 비교 대상 |
| Unit of Work | 변경 추적과 커밋 협력 |
| Domain Service | Repository를 사용하는 상위 규칙 계층 |
| Specification | 조회 조건 캡슐화 |
| Entity | 애그리거트 내부 구성요소 |
| Value Object | 애그리거트 상태 구성 요소 |
| CQRS | 읽기·쓰기 저장소 분리 확장 |
| ORM | 대표 구현 기술 |
| DDD | Repository 패턴의 이론적 배경 |

### 정리 메모
- Repository는 저장소 추상화이지만, 진짜 초점은 도메인 모델이 저장 기술 언어가 아닌 업무 언어로 읽히게 만드는 데 있다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
