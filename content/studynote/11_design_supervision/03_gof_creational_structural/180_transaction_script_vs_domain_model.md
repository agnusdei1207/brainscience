## 0. 핵심 인사이트

> **핵심**: Transaction Script는 유스케이스를 절차형 함수로 직접 구현하고, Domain Model은 규칙을 객체에 분산 배치해 의미와 일관성을 유지하는 서로 다른 업무 구조 전략이다.
> **비유**: 업무 지침서를 한 장의 절차서로 처리할지, 역할별 전문 담당 체계로 나눌지에 대한 선택과 같다.

## 1. 개요 및 필요성

180. 트랜잭션 스크립트 vs 도메인 모델 (Transaction Script vs Domain Model)은 단순 절차형 서비스 방식과 풍부한 객체 모델 방식의 비교 주제를 다루는 주제다.
이 패턴이 중요한 직접 배경은 모든 업무를 함수형 절차로만 쌓으면 빠르게 개발되지만 규칙이 커질수록 갓 클래스와 중복 규칙이 생긴다.
이를 해결하기 위한 구조적 가치로는 두 패턴의 차이를 이해하면 복잡도에 맞는 설계 전략을 선택할 수 있다.
설계자가 집중해야 하는 관점은 핵심 초점은 복잡도, 규칙 응집도, 유지보수 비용, 진화 가능성의 차이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Transaction Script | 유스케이스 절차 함수 | 단순 CRUD에 적합 |
| Domain Model | 행위를 가진 객체 모델 | 복잡한 규칙 응집 |
| Service Layer | 두 패턴 모두에서 조정 역할 가능 | 경계 제어 |
| Repository/DAO | 영속화 담당 | 저장소 기술 분리 |
| Validation Rule | 입력 검증 | 위치가 구조에 따라 달라짐 |
| Aggregate | Domain Model의 일관성 단위 | Script에서는 약함 |
| Application Service | 유스케이스 오케스트레이션 | 패턴 선택에 따라 책임 변화 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Transaction Script는 유스케이스 절차 함수 역할을 가지며 전체 흐름에서 단순 CRUD에 적합 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Domain Model는 행위를 가진 객체 모델 역할을 가지며 전체 흐름에서 복잡한 규칙 응집 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Service Layer는 두 패턴 모두에서 조정 역할 가능 역할을 가지며 전체 흐름에서 경계 제어 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Repository/DAO는 영속화 담당 역할을 가지며 전체 흐름에서 저장소 기술 분리 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Validation Rule는 입력 검증 역할을 가지며 전체 흐름에서 위치가 구조에 따라 달라짐 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Aggregate는 Domain Model의 일관성 단위 역할을 가지며 전체 흐름에서 Script에서는 약함 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Application Service는 유스케이스 오케스트레이션 역할을 가지며 전체 흐름에서 패턴 선택에 따라 책임 변화 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 상위 계층은 하위 구현의 세부사항을 최소한으로만 알아야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 경계는 예외 처리 방식과 테스트 전략에도 직접 영향을 준다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 데이터와 제어가 경계를 넘을 때 어떤 변환이 일어나는지 명확해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 운영 중 문제 추적이 가능한 경계일수록 유지보수성이 높다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 즉, 좋은 패턴 적용은 코드 분할보다 의존성 통제에서 드러난다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 업무 복잡도와 규칙 변화 빈도에 따라 절차 중심 설계와 모델 중심 설계 중 적절한 응집 전략을 선택해야 한다.

Transaction Script는 빠르고 직관적이지만 규칙이 커지면 중복되기 쉽다.
Domain Model은 초기 설계 비용이 있지만 규칙이 복잡할수록 유지보수성이 좋아진다.
모든 시스템에 풍부한 도메인 모델이 필요한 것은 아니다.
반대로 단순 CRUD라고 시작한 서비스도 규칙이 누적되면 구조 전환 신호가 나타난다.
패턴 선택은 기술 선호가 아니라 복잡도와 변경 방향을 기준으로 해야 한다.
혼합형 구조도 현실적으로 자주 사용된다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **업무 분석**: 업무 규칙의 수와 상호작용 정도를 파악한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **단순성 판단**: 규칙이 적고 절차가 직선적이면 Transaction Script가 유리하다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **응집도 판단**: 규칙이 엔티티 상태와 강하게 결합되면 Domain Model이 유리하다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **구현 구조 선택**: 서비스 함수 중심 또는 객체 행위 중심 구조를 채택한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **저장소 연결**: DAO/Repository를 통해 영속화 전략을 분리한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **성장 모니터링**: 규칙 증가, 중복 증가, 갓 클래스 징후를 관찰한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **구조 전환**: 필요 시 Script에서 Model로 점진 전환한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Request]
   |
   +--> [Transaction Script Service] --> [DAO/Repository]
   |
   +--> [Application Service] --> [Domain Model Aggregate] --> [Repository]
                                          |
                                          v
                                     [Rules / Invariants]
```

- Transaction Script: 유스케이스 절차 함수. 단순 CRUD에 적합라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

```
서비스 비대화
    ↓
핵심 규칙 모델화
    ↓
Domain Model/Repository 도입
    ↓
혼합형 아키텍처
```

### 흐름 해설
- 단순 CRUD 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| God Class | Transaction Script 과도 사용 시 발생하기 쉬운 안티패턴 |
| Domain Service | Domain Model 보조 규칙 위치 |
| Repository | Domain Model 저장소 |
| DAO | Transaction Script와 자주 결합되는 저장소 패턴 |
| Aggregate | 복잡한 규칙의 응집 단위 |
| Anemic Domain Model | 형식만 모델이고 규칙은 서비스에 남은 상태 |
| CRUD | Transaction Script 적합성이 높은 업무 |
| Invariant | Domain Model이 잘 표현하는 핵심 조건 |
| Refactoring | Script에서 Model로의 전환 과정 |
| Application Service | 두 구조 사이 조정자 |

### 정리 메모
- 이 주제의 핵심은 어느 패턴이 우월한가가 아니라, 업무 복잡도와 변화 속도에 맞는 응집 위치를 선택하는 데 있다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
