## 0. 핵심 인사이트

> **핵심**: Lazy Loading Pattern은 실제로 필요해질 때까지 연관 객체나 무거운 자원 로딩을 미루어 초기 비용을 줄이는 가상 프록시 기반 최적화 패턴이다.
> **비유**: 필요할 가능성이 있는 자료 전체를 미리 꺼내 두지 않고, 실제 요청이 생길 때만 보관실에서 가져오는 방식과 같다.

## 1. 개요 및 필요성

182. 지연 로딩 패턴 (Lazy Loading Pattern)은 필요 시점에 자원을 조회하는 지연 초기화 패턴를 다루는 주제다.
이 패턴이 중요한 직접 배경은 연관 객체를 항상 즉시 로드하면 불필요한 쿼리와 메모리 사용이 늘어난다.
이를 해결하기 위한 구조적 가치로는 초기 조회 비용을 줄이되, 실제 접근 시점에 데이터 로딩을 수행해 효율을 높일 수 있다.
설계자가 집중해야 하는 관점은 핵심 초점은 프록시, 지연 시점, 세션 범위, N+1 문제 관리다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Proxy | 실제 객체 대리자 | 호출 시 로딩 트리거 |
| Loader | 실제 조회 수행 | 세션/리포지토리 협력 |
| Persistence Context | 지연 로딩 컨텍스트 | 세션 유효 범위 중요 |
| Association Metadata | 연관 관계 정의 | LAZY/EAGER 설정 |
| Fetch Strategy | 로딩 방식 선택 | join fetch, batch fetch |
| Domain Entity | 프록시가 감싸는 대상 | 투명한 사용 기대 |
| Transaction Scope | 지연 조회 가능 범위 | 세션 종료 후 접근 주의 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

- Proxy는 실제 객체 대리자 역할을 가지며 전체 흐름에서 호출 시 로딩 트리거 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Persistence Context는 지연 로딩 컨텍스트 역할을 가지며 전체 흐름에서 세션 유효 범위 중요 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Association Metadata는 연관 관계 정의 역할을 가지며 전체 흐름에서 LAZY/EAGER 설정 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Fetch Strategy는 로딩 방식 선택 역할을 가지며 전체 흐름에서 join fetch, batch fetch 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Domain Entity는 프록시가 감싸는 대상 역할을 가지며 전체 흐름에서 투명한 사용 기대 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Transaction Scope는 지연 조회 가능 범위 역할을 가지며 전체 흐름에서 세션 종료 후 접근 주의 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

## 3. 구조 및 원리
**핵심 조건**: 실제 접근 전까지 비용을 미루되, 접근 시점에는 유효한 컨텍스트와 예측 가능한 로딩 전략이 보장되어야 한다.

Lazy Loading은 비용을 없애는 것이 아니라 시점을 뒤로 미루는 것이다.
프록시는 실제 객체와 유사하게 보이지만 세션 종료 후 접근 시 실패할 수 있다.
즉시 로딩보다 빠를지 여부는 접근 패턴에 따라 달라진다.
N+1 문제는 Lazy Loading의 대표적 부작용이다.
fetch join, entity graph, batch size 조정으로 부작용을 관리할 수 있다.
프록시 존재를 모른 채 직렬화하면 장애가 발생할 수 있다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **기본 조회**: 주 엔티티를 조회하되 연관 객체는 프록시로 남긴다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **프록시 보유**: 엔티티는 실제 객체 대신 프록시 참조를 가진다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **접근 발생**: 코드가 연관 속성에 접근하면 프록시가 이를 감지한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **실제 조회**: 세션과 로더가 추가 쿼리를 실행해 데이터를 가져온다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **객체 대체**: 프록시가 실제 데이터를 로드한 뒤 결과를 반환한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **반복 접근**: 같은 컨텍스트 안에서는 캐시된 결과를 재사용한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **예외/최적화**: 세션 종료, N+1, 직렬화 문제를 fetch 전략으로 조정한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Entity] --association--> [Proxy]
                         | access
                         v
                    [Loader]
                         |
                         v
                [Persistence Context]
                         |
                         v
                         [DB]
```

- Transaction Scope: 지연 조회 가능 범위. 세션 종료 후 접근 주의라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

- DTO 프로젝션 병행 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- 정밀한 로딩 정책 관리 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Proxy | Lazy Loading의 구현 핵심 |
| Virtual Proxy | 무거운 객체 접근 지연의 일반 개념 |
| Persistence Context | 지연 조회가 가능한 유효 범위 |
| N+1 Query | 대표적 성능 문제 |
| Fetch Join | 지연 로딩 보완 전략 |
| Entity Graph | 선택적 즉시 로딩 제어 |
| DTO Projection | 연관 조회 회피 대안 |
| Open Session In View | 프레젠테이션 계층까지 세션을 유지하는 전략 |
| Serialization | 프록시 노출 시 문제 발생 지점 |
| ORM | 지연 로딩 구현 기술 |

### 정리 메모
- Lazy Loading은 만능 성능 패턴이 아니라 접근 시점 제어 패턴이며, 프록시와 세션 범위를 함께 이해해야 제대로 사용할 수 있다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
