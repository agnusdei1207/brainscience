## 0. 핵심 인사이트

> **핵심**: Event Bus와 Publish/Subscribe Pattern은 발행자와 구독자를 직접 연결하지 않고 이벤트 채널을 매개로 비동기 통신하게 하여 결합도를 낮추는 이벤트 중심 통신 패턴이다.
> **비유**: 모든 수신자에게 개별 연락하지 않고 공지 채널에 게시하면 필요한 대상이 각자 구독해 받는 구조와 같다.

## 1. 개요 및 필요성

184. 이벤트 버스와 Pub/Sub 패턴 (Event Bus / Pub-Sub Pattern)은 발행자와 구독자를 느슨하게 연결하는 이벤트 전달 패턴를 다루는 주제다.
이 패턴이 중요한 직접 배경은 직접 호출 구조는 발행자가 수신자 수와 실패 상태를 모두 알아야 하므로 확장이 어렵다.
이를 해결하기 위한 구조적 가치로는 비동기 확장, 다중 구독, 느슨한 결합, 이벤트 기반 확장을 가능하게 한다.
설계자가 집중해야 하는 관점은 핵심 초점은 채널, 전달 보장, 순서성, 멱등성, 관측성이다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Publisher | 이벤트 발행 | 수신자 지식 최소화 |
| Event Bus/Broker | 이벤트 전달 중개 | 라우팅·버퍼링 |
| Topic/Channel | 구독 단위 | 분류 기준 |
| Subscriber | 이벤트 소비 | 독립 배포 가능 |
| Schema | 이벤트 계약 | 버전 관리 필요 |
| Retry/DLQ | 실패 처리 | 내결함성 확보 |
| Consumer Group | 병렬 소비 | 확장성과 순서 제어 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Publisher는 이벤트 발행 역할을 가지며 전체 흐름에서 수신자 지식 최소화 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Event Bus/Broker는 이벤트 전달 중개 역할을 가지며 전체 흐름에서 라우팅·버퍼링 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Topic/Channel는 구독 단위 역할을 가지며 전체 흐름에서 분류 기준 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Subscriber는 이벤트 소비 역할을 가지며 전체 흐름에서 독립 배포 가능 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Schema는 이벤트 계약 역할을 가지며 전체 흐름에서 버전 관리 필요 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Retry/DLQ는 실패 처리 역할을 가지며 전체 흐름에서 내결함성 확보 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Consumer Group는 병렬 소비 역할을 가지며 전체 흐름에서 확장성과 순서 제어 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 상위 계층은 하위 구현의 세부사항을 최소한으로만 알아야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 경계는 예외 처리 방식과 테스트 전략에도 직접 영향을 준다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 데이터와 제어가 경계를 넘을 때 어떤 변환이 일어나는지 명확해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 운영 중 문제 추적이 가능한 경계일수록 유지보수성이 높다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 발행자는 구독자 존재를 몰라도 되어야 하며, 이벤트 계약과 전달 보장 정책이 명확해야 한다.

이벤트 버스는 통합 허브이지만 과도한 중앙집중이 되지 않도록 도메인 경계를 고려해야 한다.
Pub/Sub는 느슨한 결합을 제공하지만 전달 보장과 순서성 문제를 새로 만든다.
이벤트는 사실(fact) 중심으로 설계해야 하며, 명령(command)과 혼동하면 결합이 증가한다.
멱등성 없이는 재시도와 중복 전달을 안전하게 처리할 수 없다.
스키마 버전 관리와 소비자 독립 배포가 실무 성공의 핵심이다.
관측성 없이는 이벤트 흐름 추적이 매우 어렵다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **사실 발생**: 도메인 또는 시스템에서 중요한 상태 변화가 발생한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **이벤트 생성**: 발행자가 스키마에 맞는 이벤트를 만든다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **버스 게시**: 이벤트 버스나 브로커에 토픽 기준으로 게시한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **구독자 전달**: 구독자 또는 소비자 그룹이 이벤트를 수신한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **개별 처리**: 각 구독자가 독립적으로 후속 작업을 실행한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **실패 대응**: 재시도, DLQ, 보상 로직으로 실패를 관리한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **관측/진화**: 스키마와 소비자 버전을 관리하며 흐름을 추적한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

```
[Publisher]
    | publish event
    v
[Event Bus / Broker] --> [Topic A] --> [Subscriber 1]
                      |             --> [Subscriber 2]
                      +--> [Topic B] --> [Subscriber 3]
    
Retry / DLQ / Monitoring around broker
```

- 스트리밍 플랫폼 발전 단계는 이전 구조의 한계를 보완하며 나타난 진화다.
  - 기술 진화는 항상 이전 단계의 병목을 해결하려는 방향으로 나타난다.
- 도메인 이벤트와 데이터 제품 확장 단계는 이전 구조의 한계를 보완하며 나타난 진화다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Event-Driven Architecture | 상위 아키텍처 개념 |
| Broker | 이벤트 전달 인프라 |
| Topic | 이벤트 분류 채널 |
| Consumer Group | 병렬 소비 단위 |
| DLQ | 실패 이벤트 격리 |
| Idempotency | 중복 소비 안전성 |
| Eventual Consistency | 비동기 통신 결과 모델 |
| Saga | 분산 업무 조정과 연결 |
| Schema Registry | 이벤트 계약 관리 |
| Outbox Pattern | DB 변경과 이벤트 발행 정합성 확보 |

### 정리 메모
- 이벤트 버스의 장점은 연결을 끊는 데 있지만, 그 대가로 전달 보장·멱등성·관측성 설계가 필수적으로 따라온다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
