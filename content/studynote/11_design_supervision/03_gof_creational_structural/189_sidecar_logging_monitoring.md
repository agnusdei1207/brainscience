## 0. 핵심 인사이트

> **핵심**: Sidecar Pattern은 애플리케이션과 분리된 보조 프로세스를 같은 배포 단위에 붙여 로깅, 모니터링, 프록시, 보안 기능을 애플리케이션 코드 밖으로 분리하는 패턴이다.
> **비유**: 본체 장비를 바꾸지 않고 옆에 붙는 보조 모듈이 관측과 제어 기능을 맡는 구조와 같다.

## 1. 개요 및 필요성

189. 사이드카 패턴 (Sidecar Pattern)은 주 애플리케이션 옆에 보조 기능을 분리 배치하는 아키텍처 패턴를 다루는 주제다.
이 패턴이 중요한 직접 배경은 각 서비스가 로깅, 메트릭 수집, 프록시, 인증서를 직접 구현하면 중복과 언어별 편차가 커진다.
이를 해결하기 위한 구조적 가치로는 공통 운영 기능을 사이드카로 외부화해 애플리케이션 코드를 단순화하고 운영 일관성을 높인다.
설계자가 집중해야 하는 관점은 핵심 초점은 배포 동반성, 공통 기능 분리, 관측성, 서비스 메시 연계다.
이 섹션에서는 왜 이 구조가 필요해졌는지와, 어떤 비용을 줄이기 위해 등장했는지를 논리적으로 정리한다.

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| Main Container/App | 주 비즈니스 로직 | 핵심 기능 수행 |
| Sidecar Container | 보조 기능 제공 | 로그 수집·프록시·보안 |
| Shared Network Namespace | 통신 공유 | localhost 프록시 가능 |
| Shared Volume | 로그/파일 공유 | 에이전트 수집 |
| Control Plane | 설정 배포 | 사이드카 정책 관리 |
| Telemetry Backend | 로그·메트릭 저장 | 운영 분석 |
| Orchestrator | 같은 수명주기 배포 | 쿠버네티스 Pod 등 |

구성요소는 개별 기능보다 상호작용을 통해 의미를 가진다.
각 요소가 어떤 경계에서 책임을 갖고, 어디까지 추상화를 제공하는지가 설계 품질을 좌우한다.

### 요소 간 관계
- Main Container/App는 주 비즈니스 로직 역할을 가지며 전체 흐름에서 핵심 기능 수행 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Sidecar Container는 보조 기능 제공 역할을 가지며 전체 흐름에서 로그 수집·프록시·보안 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Shared Network Namespace는 통신 공유 역할을 가지며 전체 흐름에서 localhost 프록시 가능 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Shared Volume는 로그/파일 공유 역할을 가지며 전체 흐름에서 에이전트 수집 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Control Plane는 설정 배포 역할을 가지며 전체 흐름에서 사이드카 정책 관리 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Telemetry Backend는 로그·메트릭 저장 역할을 가지며 전체 흐름에서 운영 분석 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.
- Orchestrator는 같은 수명주기 배포 역할을 가지며 전체 흐름에서 쿠버네티스 Pod 등 관점을 담당한다.
  - 이 관계가 안정적일수록 변경 파급 범위를 더 잘 통제할 수 있다.

### 경계 해석
- 구조를 나누는 목적은 기술 자체보다 책임을 국소화하는 데 있다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 상위 계층은 하위 구현의 세부사항을 최소한으로만 알아야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 경계는 예외 처리 방식과 테스트 전략에도 직접 영향을 준다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 데이터와 제어가 경계를 넘을 때 어떤 변환이 일어나는지 명확해야 한다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 운영 중 문제 추적이 가능한 경계일수록 유지보수성이 높다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.
- 즉, 좋은 패턴 적용은 코드 분할보다 의존성 통제에서 드러난다.
  - 결국 경계가 명확해야 테스트와 운영 책임도 함께 분리된다.

## 3. 구조 및 원리
**핵심 조건**: 보조 기능은 주 애플리케이션과 함께 배포되되, 코드와 언어 런타임에서는 분리되어야 한다.

사이드카는 공통 기능을 코드에서 분리해 언어 독립성을 얻는다.
같은 배포 단위에 있으므로 네트워크 지연이 낮고 동반 배포가 쉽다.
그러나 컨테이너 수와 자원 사용량이 증가한다.
사이드카는 앱 로직을 대체하는 것이 아니라 운영·통신 보조 기능을 담당해야 한다.
서비스 메시 프록시는 Sidecar Pattern의 대표적 확장 형태다.
로그 수집, 메트릭, 보안 인증서 갱신 같은 운영 기능에 특히 유용하다.
이 조건이 지켜질 때 구조는 단순 분할이 아니라 실제 동작 원리로 기능한다.

동작 순서:
1. **공동 배포**: 주 애플리케이션과 사이드카를 같은 Pod/배포 단위에 배치한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
2. **공유 자원 연결**: 네트워크 또는 볼륨을 공유해 로그와 트래픽을 전달한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
3. **보조 기능 수행**: 사이드카가 로그 수집, 메트릭 전송, 프록시, 인증서 갱신을 담당한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
4. **앱 단순화**: 주 애플리케이션은 본업 로직에 집중한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
5. **중앙 제어**: Control Plane 또는 설정 관리가 사이드카 정책을 배포한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
6. **운영 관측**: 사이드카가 수집한 텔레메트리가 백엔드로 전송된다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.
7. **수명주기 종료**: 앱과 사이드카가 함께 시작·종료되어 운영 일관성을 유지한다.
   - 이 단계는 앞 단계의 결과를 제약 조건으로 이어받으며, 누락되면 전체 흐름의 안정성이 떨어진다.

- Telemetry Backend: 로그·메트릭 저장. 운영 분석라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

- Orchestrator: 같은 수명주기 배포. 쿠버네티스 Pod 등라는 설계 포인트 때문에 전체 구조에서 독립적인 검토 대상이 된다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Service Mesh | 사이드카 패턴의 대표 확장 |
| Ambassador | 대행 통신 역할과 비교 |
| Adapter | 기능 변환 보조 구조 |
| Observability | 로그·메트릭·트레이스 수집 목적 |
| Proxy | 트래픽 중개 역할 |
| Fluent Bit | 로그 수집 구현 예 |
| Envoy | 프록시 사이드카 대표 기술 |
| Control Plane | 정책 중앙 관리 |
| Pod | 쿠버네티스 배포 단위 |
| Resource Overhead | 패턴 도입의 비용 요소 |

### 정리 메모
- Sidecar는 앱을 더 똑똑하게 만드는 패턴이 아니라, 운영 기능을 코드 밖으로 분리해 조직 전체의 일관성을 높이는 패턴이다.
  - 관련 개념까지 함께 묶어 이해하면 주제의 실전 활용도가 높아진다.
