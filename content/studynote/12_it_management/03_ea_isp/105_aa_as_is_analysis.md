## 0. 핵심 인사이트

> **핵심**: 애플리케이션 아키텍처 (AA: Application Architecture) 현황 분석의 본질은 어떤 업무가 어떤 시스템과 모듈에 의해 구현되고 서로 어떻게 연결되는지 드러내어 중복 기능과 복잡한 연계를 정리하는 것이다.

> **비유**: 도시 지도에서 건물만 보는 것이 아니라 건물 사이를 잇는 도로와 지하 통로까지 함께 확인하는 교통망 조사와 같다.

## 1. 개요 및 필요성

애플리케이션 아키텍처 (AA: Application Architecture) 현황 분석은 현행 시스템 포트폴리오, 기능 분담, 인터페이스 구조를 진단하는 작업이다. 대형 조직에서는 업무 요구가 생길 때마다 시스템을 덧붙이는 방식으로 진화해 동일 기능이 여러 시스템에 중복되고 연계는 점점 복잡해진다. 이런 상태에서는 신규 사업을 시작할 때마다 영향도 분석과 테스트 비용이 급격히 증가한다.

AA 분석이 중요한 이유는 시스템 수를 줄이는 것보다 기능 책임을 분명히 하는 데 있다. 어떤 시스템이 시스템 오브 레코드(System of Record)인지, 어떤 모듈이 공통 서비스인지, 어떤 연계가 기술 부채인지 파악해야 TO-BE 애플리케이션 포트폴리오를 설계할 수 있다.

---

## 2. 구성요소

| 요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| 시스템 포트폴리오 | 업무별 시스템 현황 목록화 | 중복 시스템과 노후 시스템 식별 |
| 모듈 구성도 | 시스템 내부 기능 구조 파악 | 기능 경계와 재사용성 진단 |
| 연계도 | 시스템 간 인터페이스 구조 파악 | 실시간/배치/API 연계 복잡도 확인 |
| 운영 속성 | 사용자 수, 장애 빈도, 유지보수 비용 정리 | 통폐합 및 현대화 우선순위 판단 |

시스템 포트폴리오는 전사 관점의 지도이고, 모듈 구성도는 각 시스템 내부의 기능 책임을 보여준다. 연계도는 시스템 사이 의존 관계를 드러내며, 운영 속성은 기술 부채의 크기와 사업 리스크를 계량화한다. 이 네 요소를 함께 봐야 단순 통폐합이 아니라 구조적 재배치가 가능하다.

---

## 3. 구조 및 원리

**핵심 조건**: 업무 기능, 시스템, 모듈, 인터페이스가 서로 추적 가능해야 하며, 각 기능의 주 시스템과 중복 지원 시스템이 구분되어야 한다.

AA 현황 분석의 핵심은 기능과 시스템을 분리해 보는 것이다. 시스템 이름만 보면 다른 것처럼 보여도 기능은 중복될 수 있고, 반대로 하나의 시스템 안에 너무 많은 업무가 뒤섞여 있을 수 있다. 따라서 기능 분해, 시스템 포트폴리오, 인터페이스 연결도를 동시에 작성해 응집도와 결합도를 진단해야 한다.

동작 순서:
1. 시스템 목록화: 업무 영역별 현행 애플리케이션을 수집하고 생명주기·기술 스택·사용 부서를 정리한다.
2. 기능 분해: 각 시스템의 핵심 모듈과 지원 기능을 나누어 업무 기능 대비 책임 범위를 확인한다.
3. 연계 구조 진단: 배치, 파일, API, 메시지 등 인터페이스 유형과 빈도를 파악해 복잡도를 계산한다.
4. 중복·노후 분석: 동일 기능 중복, 특정 시스템 집중 의존, 노후 프레임워크 리스크를 식별한다.

```text
[업무 기능]
   ├─ 주문 ─▶ [시스템 A] ─API─▶ [시스템 B]
   ├─ 정산 ─▶ [시스템 C] ─Batch▶ [DW]
   └─ 고객 ─▶ [시스템 A] ─File─▶ [CRM]
        │
        └─ 모듈 구성: 접수 / 승인 / 정산 / 공통코드
```

AA 현황 분석에서는 인터페이스 개수보다 변경 파급도가 더 중요하다. 인터페이스가 적어도 하나의 핵심 시스템에 모든 기능이 몰려 있으면 변경 시 전체 테스트 범위가 폭증한다. 반대로 인터페이스가 많아도 표준 API와 이벤트 구조가 정리되어 있으면 운영 복잡도는 낮아질 수 있다.

## 4. 비교 및 연결

| 항목 | AA 현황 분석 | 시스템 운영 목록 | TA 현황 분석 |
|:---|:---|:---|:---|
| 관점 | 업무 기능과 시스템 구조 | 자산 보유 현황 | 인프라와 기술 구성 |
| 주요 대상 | 애플리케이션, 모듈, 연계 | 시스템 수와 운영 상태 | 서버, 네트워크, 보안 장비 |
| 핵심 질문 | 무엇이 어디서 구현되는가? | 무엇을 운영 중인가? | 어디에서 구동되는가? |
| 주요 성과 | 중복 기능 제거, 포트폴리오 정비 | 운영 통계 확보 | 기술 표준화 |

운영 목록이 자산 관리 차원의 현황이라면 AA 현황 분석은 기능 구조와 관계를 설명한다. 또한 TA가 인프라 관점이라면 AA는 애플리케이션 책임 분담과 연계 복잡도를 다룬다. 전환 전략을 세우려면 AA와 TA를 분리하면서도 연결해서 봐야 한다.

## 5. 실무 적용 및 판단

**채택 조건**:
- 레거시 통폐합, MSA 전환, 패키지 재구축 전
- 연계 시스템이 많아 장애 원인 추적이 어려울 때
- 시스템 중복 투자와 유지보수 비용이 커질 때

**회피 조건**:
- 시스템 명칭만 수집하고 실제 기능과 인터페이스를 파악하지 않는 경우
- 사용 빈도·장애·비용 같은 운영 속성을 배제하는 경우
- 업무 기능 매핑 없이 기술 스택만으로 통폐합을 결정하는 경우

체크리스트:
1. 업무 기능별 주 시스템이 식별되었는가?
2. 시스템 간 인터페이스 유형과 방향이 정리되었는가?
3. 중복 기능과 노후 시스템이 구분되었는가?
4. 공통 서비스 후보와 현대화 대상이 도출되었는가?

차세대 구축이나 MSA 전환에서는 AA 현황 분석을 통해 공통 인증, 상품, 고객, 정산 기능을 분리하고, 인터페이스 허브와 API 게이트웨이 설계의 기초 자료로 활용한다. 공공기관 통합 정보시스템 사업에서도 시스템 연계도와 모듈 맵이 RFP 범위 정의에 مباشرة 연결된다.

---

## 6. 기대효과 및 결론

AA 현황 분석은 “시스템이 몇 개 있는가”를 넘어서 “업무 기능이 어떤 구조로 분산되어 있는가”를 밝히는 단계다. 이를 통해 통폐합, 패키지 전환, MSA 분해, API 표준화의 타당성을 설명할 수 있다. 미래에는 애플리케이션 포트폴리오 관리(APM)와 관측성 데이터가 결합되면서 현행 AA도 상시 업데이트되는 자산이 될 것이다.
