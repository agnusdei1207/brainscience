## 0. 핵심 인사이트

> **핵심**: 트랜잭션 기능 (Transaction Functions)의 본질은 EI (외부 입력, Insert/Update), EO (외부 출력, 수식/계산 동반 조회), EQ (외부 조회, 단순 Select)를 비즈니스 가치, 통제, 실행 관점에서 일관되게 연결하는 데 있다.
> **비유**: 대형 프로젝트의 건강 상태를 수치로 읽어 내는 계기판과 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

어플리케이션의 정적인 크기가 데이터 기능(ILF, EIF)이라면, **트랜잭션 기능(Transaction Functions)**은 사용자가 시스템과 상호작용하며 데이터를 처리하는 동적인 크기를 의미한다. 이는 사용자가 버튼을 누르거나 API를 호출했을 때 발생하는 의미 있는 비즈니스 프로세스의 단위로, 전체 FP 산정의 절반 이상을 차지하는 핵심 요소다.

---

## 2. 구성요소

```text
[ User / External System ]
          | (Trigger Action)
    +-----+-----------------+
    |   [ EI ] (Input)      | ----    |   - Register, Update  |
    +-----------------------+
          |
    +-----+-----------------+
    |   [ EQ ] (Query)      | <---- (Reference ILF/EIF)
    |   - Simple View       |
    +-----------------------+
          |
    +-----+-----------------+
    |   [ EO ] (Output)     | <---- (Reference + Calculation)
    |   - Report, Graph     |
    +-----------------------+

Bilingual ASCII Diagram:
+-------------------+       +---------------------------+       +-------------------+
|      User         | ----> |   Application Boundary    | ----> |      Output       |
|   (사용자 입력)   |       |   (애플리케이션 경계)     |       |   (결과 보고서)   |
+---------+---------+       +-------------+-------------+       +---------+---------+
          |                               |                               ^
          |           [ EI ]              |           [ EO ]              |
          +-----------------------------> | (Maintain / Update ILF) ------+
          |                               |                               |
          |           [ EQ ]              |                               |
          +-----------------------------> | (Simple Retrieval ILF/EIF) ---+
```

- **EI (External Input, 외부 입력):** 애플리케이션 경계 외부에서 들어오는 데이터나 제어 정보로, 하나 이상의 ILF를 유지(등록/수정/삭제)하는 기능.
- **EO (External Output, 외부 출력):** 보고서 작성, 계산 등을 통해 가공된 정보를 외부로 보내는 기능. 적어도 하나 이상의 수학적 계산이나 파생 데이터 생성이 포함되어야 함.
- **EQ (External Inquiry, 외부 조회):** 데이터를 가공 없이 단순 검색하여 결과를 화면에 보여주는 기능.
- **측정 기준:**
    - **DET (Data Element Type):** 입출력 화면에 나타나는 고유한 데이터 항목 수.
    - **FTR (File Type Referenced):** 해당 기능을 수행하기 위해 참조하거나 수정하는 ILF 또는 EIF의 개수.

## 3. 구조 및 원리

트랜잭션 기능 (Transaction Functions)의 구조를 이해할 때 중요한 것은 구성요소를 나열하는 것이 아니라, 어떤 입력이 어떤 판단 규칙을 거쳐 어떤 결과와 증빙으로 이어지는지를 보는 것이다. 즉 트랜잭션 기능 (Transaction Functions)는 기준선, 실행 경로, 피드백 루프가 결합된 운영 메커니즘으로 이해해야 한다.

**핵심 조건**: 측정값이 동일한 정의와 시점으로 수집되고, 임계치와 해석 기준이 사전에 합의되어야 한다.

동작 순서:
1. **측정 범위 정의**: 이 단계는 트랜잭션 기능 (Transaction Functions)가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
2. **원천 데이터 수집**: 이 단계는 트랜잭션 기능 (Transaction Functions)가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
3. **지표 계산**: 이 단계는 트랜잭션 기능 (Transaction Functions)가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
4. **결과 해석 및 조치**: 이 단계는 트랜잭션 기능 (Transaction Functions)가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.

```text
[기준선 설정] -> [원천 데이터 수집] -> [트랜잭션 기능 (Transaction Functions) 계산] -> [임계치 비교] -> [조치 결정]
```

이 구조에서 핵심은 선행 조건이 충족되지 않으면 뒤 단계의 효율이 높아도 전체 품질이 보장되지 않는다는 점이다. 예를 들어 지표 정의가 불명확하거나 승인 경계가 흐리면, 자동화가 오히려 오류를 빠르게 확산시키는 결과가 된다. 따라서 구조 설계에서는 속도보다 정합성, 개별 최적화보다 전체 제어성을 함께 고려해야 한다.

## 4. 비교 및 연결

**기술사적 판단:** 트랜잭션 식별의 성패는 **기본 프로세스(Elementary Process)**의 독립성을 얼마나 잘 정의하느냐에 달려 있다.
1. **버튼 vs 기능:** 화면에 버튼이 5개라고 해서 기능이 5개는 아님. '취소'나 '이전' 버튼은 비즈니스 로직이 아니므로 제외하고, '저장' 버튼이 실제 ILF를 변경하는 최소 단위인지를 검토해야 함.
2. **EO와 EQ의 구분:** 단순 조회가 아니라 '평균값 계산'이나 '전년 대비 증감' 등 데이터 가공 로직이 들어가면 반드시 EO로 산정하여 가중치를 확보해야 함.
3. **일괄 처리(Batch):** 화면 없이 백그라운드에서 주기적으로 돌아가는 배치 작업도 하나의 EI나 EO로 식별하여 규모에 포함시켜야 함.

---

## 5. 실무 적용 및 판단

트랜잭션 기능 산정은 사용자 요구사항 정의의 완전성을 검증하는 도구다. 요구사항 명세서(RFP) 상의 기능 목록이 EI/EO/EQ로 매핑되지 않는다면, 이는 요구사항이 불명확함을 의미한다. 앞으로 마이크로서비스 간의 통신(REST API)이 복잡해질수록, API 하나하나를 독립적인 트랜잭션 기능으로 식별하고 그 복잡도(FTR)를 관리하는 것이 소프트웨어 공학의 핵심 관리 기준이 될 것이다.

---

## 6. 기대효과 및 결론

트랜잭션 기능 (Transaction Functions)를 올바르게 적용하면 의사결정의 일관성, 운영의 재현성, 통제의 추적성이 동시에 향상된다. 즉 “누가 무엇을 왜 했는가”가 남기 때문에 조직이 커질수록 효과가 커진다.

다만 트랜잭션 기능 (Transaction Functions)는 문서만 잘 만들어도 성공하는 영역이 아니다. 정의와 실행이 분리되면 형식주의가 되고, 자동화만 앞서면 통제 목적이 사라진다. 따라서 표준화와 민첩성, 통제와 생산성 사이의 균형이 항상 필요하다.

향후에는 정책 코드화(Policy as Code), 실시간 관측성(Observability), AI 기반 이상 탐지와 의사결정 지원이 결합되면서 관리 체계가 더 자동화되고 증거 중심으로 진화할 가능성이 크다. 결론적으로 핵심은 도구가 아니라 기준선이며, 기준선이 명확할 때만 자동화와 확장이 의미를 가진다.
