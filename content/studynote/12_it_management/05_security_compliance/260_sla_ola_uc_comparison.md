## 0. 핵심 인사이트

> **핵심**: SLA / OLA / UC의 본질은 SLA / OLA / UC의 목적·구성·운영 기준을 명확히 설명하는 주제를 비즈니스 가치, 통제, 실행 관점에서 일관되게 연결하는 데 있다.
> **비유**: 비슷해 보이는 선택지의 차이를 판별하는 감별 렌즈와 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

SLA (Service Level Agreement)는 IT 서비스 제공자(조직)와 고객(비즈니스 부서) 간의 공식 서비스 품질 합의서다. "시스템 가용성 99.9%, 응답시간 2초 이내"와 같이 측정 가능한 지표로 계약된다.

SLA를 이행하려면 IT 조직 내부(OLA)와 외부 공급업체(UC)의 지원이 필요하다. 예를 들어, ERP 가용성 99.9% SLA를 맞추려면 DB팀(OLA: 99.95%)과 IDC 전용회선 업체(UC: 99.99%)가 각자의 서비스 수준을 보장해야 한다.

---

## 2. 구성요소

```
┌──────────────────────────────────────────┐
│  고객(Business)                           │
│       ↕ SLA (공식 서비스 품질 계약)        │
│  IT 조직 (Service Provider)              │
│       ↕ OLA (내부 팀 간 운영 협약)        │
│  [서버팀] [네트워크팀] [DBA팀]            │
│       ↕ UC (외부 공급업체 계약)           │
│  [통신사] [IDC] [SW벤더]                 │
└──────────────────────────────────────────┘
```

| 계약 | 당사자 | 특성 |
|:---|:---|:---|
| SLA | IT조직 ↔ 고객 | 공식·법적 구속력 |
| OLA | IT 내부 팀 간 | 비공식·운영 협약 |
| UC | IT조직 ↔ 외부공급자 | 법적 계약 |

---

## 3. 구조 및 원리

SLA / OLA / UC의 구조를 이해할 때 중요한 것은 구성요소를 나열하는 것이 아니라, 어떤 입력이 어떤 판단 규칙을 거쳐 어떤 결과와 증빙으로 이어지는지를 보는 것이다. 즉 SLA / OLA / UC는 기준선, 실행 경로, 피드백 루프가 결합된 운영 메커니즘으로 이해해야 한다.

**핵심 조건**: 정책·프로세스·지표가 같은 목표를 향해 정렬되고, 예외 처리 기준이 문서화되어야 한다.

동작 순서:
1. **비교 기준 정의**: 이 단계는 SLA / OLA / UC가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
2. **대안 분석**: 이 단계는 SLA / OLA / UC가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
3. **적용 맥락 판단**: 이 단계는 SLA / OLA / UC가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.
4. **최적 대안 선택**: 이 단계는 SLA / OLA / UC가 단순 개념이 아니라 실제 통제와 실행으로 이어지게 만드는 연결점이다.

```text
[정책 수립] -> [표준화] -> [운영 실행] -> [측정] -> [개선]
```

이 구조에서 핵심은 선행 조건이 충족되지 않으면 뒤 단계의 효율이 높아도 전체 품질이 보장되지 않는다는 점이다. 예를 들어 지표 정의가 불명확하거나 승인 경계가 흐리면, 자동화가 오히려 오류를 빠르게 확산시키는 결과가 된다. 따라서 구조 설계에서는 속도보다 정합성, 개별 최적화보다 전체 제어성을 함께 고려해야 한다.

---

## 4. 비교 및 연결

| 비교 항목 | SLA | OLA | UC |
|:---|:---|:---|:---|
| 관계 | 고객과 IT 서비스 제공자 간 약속 | IT 내부 조직 간 운영 약속 | 외부 공급자와의 지원 계약 |
| 주요 초점 | 고객 체감 품질 | 내부 협업 책임 | 외부 벤더 책임 |
| 왜 중요한가 | 비즈니스 기대치 관리 | 내부 실행력 보장 | 외부 의존 리스크 통제 |

비교의 핵심은 SLA / OLA / UC를 단독 용어로 이해하지 않고, 인접 개념과의 경계에서 언제 더 적합한지 판단하는 데 있다.

---

## 5. 실무 적용 및 판단

**채택 조건**:
- SLA / OLA / UC가 해결하려는 문제의 범위와 책임 주체가 명확할 때
- 정책·프로세스·도구·지표를 함께 설계할 수 있을 때
- 운영 증빙과 사후 개선 루프를 지속적으로 유지할 수 있을 때

**회피 조건**:
- 용어만 도입하고 실제 권한·책임 구조를 바꾸지 않을 때
- 정량 기준 없이 선언적 문구만 남는 경우
- 자동화가 필요한데 표준 데이터와 인터페이스가 준비되지 않은 경우

체크리스트:
1. 목표와 범위가 문서화되어 있는가?
2. 승인·예외 처리·에스컬레이션 경로가 정의되어 있는가?
3. 운영 데이터와 감사 증빙을 수집할 수 있는가?
4. 성과 지표가 비즈니스 영향과 연결되는가?
5. 실패 시 롤백·보완·재평가 절차가 준비되어 있는가?

실무에서는 SLA / OLA / UC를 독립 프로젝트로 보는 것보다, 기존 거버넌스·보안·개발·운영 체계와 어떻게 접합할지를 함께 설계해야 성공 확률이 높다.

---

## 6. 기대효과 및 결론

SLA / OLA / UC를 올바르게 적용하면 의사결정의 일관성, 운영의 재현성, 통제의 추적성이 동시에 향상된다. 즉 “누가 무엇을 왜 했는가”가 남기 때문에 조직이 커질수록 효과가 커진다.

다만 SLA / OLA / UC는 문서만 잘 만들어도 성공하는 영역이 아니다. 정의와 실행이 분리되면 형식주의가 되고, 자동화만 앞서면 통제 목적이 사라진다. 따라서 표준화와 민첩성, 통제와 생산성 사이의 균형이 항상 필요하다.

향후에는 정책 코드화(Policy as Code), 실시간 관측성(Observability), AI 기반 이상 탐지와 의사결정 지원이 결합되면서 관리 체계가 더 자동화되고 증거 중심으로 진화할 가능성이 크다. 결론적으로 핵심은 도구가 아니라 기준선이며, 기준선이 명확할 때만 자동화와 확장이 의미를 가진다.
