## 0. 핵심 인사이트

> **핵심**: Database per Service는 **각 마이크로서비스가 독립적인 데이터베이스를 소유**하여 다른 서비스가 직접 DB에 접근하지 못하고 **오직 API로만 통신**하는 MSA 데이터 패턴이다.
> **비유**: 복잡한 시스템을 작은 운영 규칙으로 정리해 안정적으로 굴러가게 만드는 교통 관제 체계와 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

```text
공유 DB: 서비스 A·B·C → 같은 DB (커플링)
DB per Service: A→DB_A, B→DB_B, C→DB_C (독립)
  서비스 간: API·이벤트로만 통신
```

---

## 2. 구성요소

| 비교 | 공유 DB | DB per Service |
|:---|:---|:---|
| **커플링** | 높음 | **낮음** |
| **배포** | 종속 | **독립** |
| **JOIN** | 가능 | **불가 → API/이벤트** |
| **일관성** | Strong | **Eventual** |
## Ⅲ~Ⅴ. 결론

DB per Service는 **MSA의 데이터 독립성 핵심 원칙**이며, Saga·CQRS·이벤트 소싱과 함께 적용해야 한다.

---

## 3. 구조 및 원리

**핵심 조건**: 분산 서비스 환경에서는 서비스 경계, 상태 관리, 호출 정책, 장애 격리, 데이터 일관성 전략이 명확해야 전체 시스템이 안정적으로 동작한다.

동작 순서:
1. 요청이 API 게이트웨이·이벤트 소스·메시지 브로커를 통해 유입된다.
2. 서비스 디스커버리와 라우팅 계층이 적절한 실행 주체를 결정한다.
3. 각 서비스나 함수가 독립적으로 로직을 수행하고 필요한 데이터를 조회·갱신한다.
4. 비동기 이벤트, 보상 트랜잭션, 캐시 전략으로 분산 일관성 문제를 완화한다.
5. 관측성·재시도·회로 차단·배포 전략으로 장애 전파를 제어한다.

---

## 4. 비교 및 연결

Database per Service - MSA 데이터 분리 패턴는 인접 기술과 비교할 때 책임 경계, 운영 복잡도, 자동화 수준, 이식성, 비용 구조에서 차이가 난다. 따라서 단순한 장단점 나열보다도 어떤 조건에서 더 적합한지, 다른 기술과 어떻게 결합되는지가 중요하다.

특히 클라우드 아키텍처에서는 동일한 기술도 조직 규모, 규제 수준, 데이터 특성, 트래픽 패턴에 따라 최적 해법이 달라지므로 비교 관점이 곧 의사결정 기준이 된다.

---

## 5. 실무 적용 및 판단

실무에서 Database per Service - MSA 데이터 분리 패턴를 채택할 때는 기술 자체보다 운영 체계와 조직 역량을 먼저 점검해야 한다. 자동화 수준, 보안 요구, 장애 복구 목표, 비용 정책, 관측 가능성이 준비되지 않으면 기대효과보다 복잡도만 커질 수 있다.

따라서 PoC, 표준 템플릿, 체크리스트, 가드레일을 함께 설계하고, 관리형 서비스나 플랫폼 팀과 결합해 운영 부담을 줄이는 접근이 바람직하다.

---

## 6. 기대효과 및 결론

Database per Service - MSA 데이터 분리 패턴를 올바르게 적용하면 확장성, 운영 안정성, 자동화 수준, 가시성을 함께 높일 수 있다. 다만 이 효과는 기술 자체만으로 생기지 않으며, 책임 경계·표준화·보안 통제·비용 관리가 함께 설계될 때 비로소 현실화된다.

향후에는 관리형 서비스, 정책 자동화, AI 기반 운영 최적화와 결합되면서 Database per Service - MSA 데이터 분리 패턴의 중요성이 더 커질 것이다. 따라서 핵심은 특정 도구를 도입하는 것이 아니라, 업무 특성과 조직 역량에 맞는 적용 범위와 운영 모델을 설계하는 데 있다.

