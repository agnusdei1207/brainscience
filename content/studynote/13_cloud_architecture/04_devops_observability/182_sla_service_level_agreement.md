## 0. 핵심 인사이트

> **핵심**: SLA(Service Level Agreement, 서비스 수준 협약)는 서비스 제공자와 고객 간의 법적 계약으로, 미달성 시 위약금(크레딧 지급, 계약 해지 등)이 따르는 강제력 있는 약속이다.
> **비유**: SLA는 상점 환불 정책이다. "7일 이내 결함 있으면 교환 보장"처럼 고객과의 공식 약속이며, 이를 어기면 법적 분쟁으로 이어질 수 있다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

AWS, Azure, GCP 모두 자사 서비스에 대한 SLA를 공개한다. AWS S3의 SLA는 월 99.9% 가용성이며, 미달성 시 서비스 크레딧을 지급한다. 이처럼 SLA는 클라우드 서비스 선택의 핵심 기준이자 법적 보호 장치다.

SLA가 SLO, SLI와 다른 핵심 차이는 "법적 구속력"이다. SLO는 내부 목표여서 미달해도 내부 대화로 끝나지만, SLA를 위반하면 실제 비즈니스 손실(페널티 지급, 계약 해지, 평판 손상)이 발생한다. 이 차이가 SLA를 SLO보다 항상 낮게(완화되게) 설정해야 하는 이유다.

예를 들어 내부 SLO가 99.95%라면 SLA는 99.9%로 설정한다. SLO 위반 시 남은 0.05% 완충 구간이 있어 SLA까지 위반하지 않도록 보호한다.

## 2. 구성요소

### SLI → SLO → SLA 계층 구조

```
                    고객 관점
        ┌──────────────────────────────┐
        │  SLA (Service Level          │
        │  Agreement) 99.9%            │
        │  [법적 계약, 페널티 수반]    │
        ├──────────────────────────────┤
        │  SLO (Service Level          │
        │  Objective) 99.95%           │
        │  [내부 목표, 완충 버퍼]      │
        ├──────────────────────────────┤
        │  SLI (Service Level          │
        │  Indicator) 99.97%           │
        │  [실제 측정값]               │
        └──────────────────────────────┘
                  운영 팀 관점

SLA 위반 여부: SLI(실측) ≥ SLO(목표) ≥ SLA(계약)
완충 구간: SLO - SLA = 안전 마진
```

| 다운타임 | 가용성 | SLA 수준 | 비고 |
|:---|:---|:---|:---|
| 월 432분 | 99% | 기본 |비업무 시간 포함 |
| 월 43.2분 | 99.9% | 일반 상용 | 대다수 SaaS |
| 월 21.6분 | 99.95% | 엔터프라이즈 | 금융권 하한선 |
| 월 4.32분 | 99.99% | 고가용성 | 결제, 통신 |
| 월 25.9초 | 99.999% | 파이브 나인 | 핵심 인프라 |

## 3. 구조 및 원리

**핵심 조건**: 변경 자동화와 운영 안정성은 별개가 아니라 하나의 루프이며, 빌드·검증·배포·관측·피드백이 끊기지 않아야 지속 개선이 가능하다.

동작 순서:
1. 변경 사항을 버전 관리 시스템에서 감지한다.
2. 빌드·테스트·보안 검증으로 변경의 품질을 빠르게 확인한다.
3. 승인된 산출물을 선언형 배포나 자동화 파이프라인으로 운영 환경에 반영한다.
4. 메트릭·로그·트레이스를 통해 실제 동작 결과를 관측한다.
5. 피드백을 다음 개선 주기에 연결해 반복적으로 신뢰성을 높인다.

### SLA 구성 요소

| 구성 요소 | 내용 |
|:---|:---|
| 서비스 범위 | 어떤 서비스, 어떤 기능에 적용되는가 |
| 가용성 목표 | 월/연간 가용성 수치 |
| 측정 방법 | SLI 계산 방식, 집계 기간 |
| 제외 항목 | 유지보수 창, 불가항력, 고객 귀책 |
| 페널티 | 위반 시 서비스 크레딧 비율 |
| 보고 방법 | 상태 페이지, 월간 보고서 |

**주요 클라우드 SLA 비교:**
| 서비스 | SLA 가용성 | 페널티 |
|:---|:---|:---|
| AWS S3 | 99.9% | 크레딧 10~25% |
| AWS EC2 | 99.99% | 크레딧 10~30% |
| Azure VM | 99.9~99.99% | 크레딧 10~25% |
| GCP GCE | 99.99% | 크레딧 10~50% |

## 4. 비교 및 연결

**SLA 설계 Best Practice:**
1. **측정 방법 명시**: 어떤 SLI를 어떻게 집계하는지 명확히 기재
2. **제외 조항 명확화**: 예약된 유지보수, 고객 측 네트워크 장애 제외
3. **에스컬레이션 절차**: SLA 위반 시 알림 경로와 대응 SLA 명시
4. **크레딧 자동화**: 위반 시 자동 크레딧 지급 메커니즘

**SLA 모니터링 도구:**
- **상태 페이지(Status Page)**: Statuspage.io, Atlassian Statuspage
- **Uptime 모니터링**: Pingdom, New Relic Synthetics
- **SLA 보고**: Datadog SLO 대시보드에서 자동 생성

**SLA 위반 시나리오 대응:**
- 고객에게 즉시 사고 알림
- RCA(Root Cause Analysis, 근본 원인 분석) 48시간 내 완료
- 크레딧 자동 적용 또는 청구서 조정
- 재발 방지 조치 30일 이내 공유

## 5. 실무 적용 및 판단

SLA는 서비스 신뢰성을 비즈니스 책임으로 만든다. 고객은 SLA를 기준으로 서비스 의존 가능 여부를 판단하고, 공급자는 페널티를 피하기 위해 신뢰성에 투자한다. 이 선순환이 클라우드 인프라의 전반적인 신뢰성을 높이는 원동력이다.

기술사 관점에서 SLA 설계 시 가장 중요한 것은 "측정 가능성"과 "현실성"이다. 달성 불가능한 SLA는 만성적 위반으로 신뢰를 잃고, 너무 느슨한 SLA는 고객에게 신뢰를 주지 못한다. 과거 운영 데이터와 SLO를 기반으로 현실적이고 엄격한 SLA를 설정하는 것이 핵심이다.

---

## 6. 기대효과 및 결론

SLA (Service Level Agreement, 서비스 수준 협약)를 올바르게 적용하면 확장성, 운영 안정성, 자동화 수준, 가시성을 함께 높일 수 있다. 다만 이 효과는 기술 자체만으로 생기지 않으며, 책임 경계·표준화·보안 통제·비용 관리가 함께 설계될 때 비로소 현실화된다.

향후에는 관리형 서비스, 정책 자동화, AI 기반 운영 최적화와 결합되면서 SLA (Service Level Agreement, 서비스 수준 협약)의 중요성이 더 커질 것이다. 따라서 핵심은 특정 도구를 도입하는 것이 아니라, 업무 특성과 조직 역량에 맞는 적용 범위와 운영 모델을 설계하는 데 있다.

## 7. 발전 흐름도

```text
SLI (지표) → SLO (내부 목표) → SLA (외부 계약)
    │
    ▼
SLA 위반: 서비스 크레딧 · 보상 · 계약 해지 조항
    │
    ▼
Multi-SLA: 티어별 차등 (Gold 99.99% / Silver 99.9%)
```
