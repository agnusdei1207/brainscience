## 0. 핵심 인사이트

> **핵심**: ETL(Extract·Transform·Load)은 이기종 소스에서 데이터를 추출해 변환·정제 후 데이터 웨어하우스에 적재하는 데이터 통합 파이프라인의 핵심 패턴이다.
> **비유**: 여러 공정이 연결된 생산 라인처럼, 앞단의 입력 품질과 중간 단계의 흐름 제어가 최종 결과를 좌우하는 구조와 같다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

ETL(Extract, Transform, Load)은 **다수의 이기종 소스에서 데이터를 추출·변환하여 분석 목적의 데이터 저장소에 적재**하는 파이프라인이다.

```
소스 시스템                   ETL 파이프라인              목적지
┌──────────┐
│ ERP (DB) │──→  Extract ──→  Transform ──→  Load ──→  DWH/DM
│ CRM      │     (추출)       (변환·정제)      (적재)   Snowflake
│ 로그파일 │                                            BigQuery
│ API      │
└──────────┘
```

---

## 2. 구성요소

| 단계      | 작업                              | 도구/기법               |
|---------|----------------------------------|------------------------|
| Extract | 소스에서 데이터 읽기               | JDBC, API, 파일, CDC   |
| Transform | 정제·변환·집계·품질 검증         | 데이터 클렌징, 조인, 타입 변환 |
| Load    | 목적지에 적재                      | COPY, INSERT, Upsert   |

---

## 3. 구조 및 원리

**핵심 조건**: ETL (Extract, Transform, Load)은 입력 데이터의 품질, 처리 단계의 일관성, 결과 활용 단계의 운영 제어가 동시에 맞아야 기대 효과를 낸다.

dbt는 **SQL SELECT 문으로 데이터 변환 모델을 정의하고, 버전 관리·테스트·문서화를 제공**하는 데이터 변환 도구다.

```
dbt 모델 구조:
models/
├── staging/           # 원시 데이터 정규화
│   ├── stg_orders.sql
│   └── stg_customers.sql
├── intermediate/      # 중간 변환
│   └── int_order_items.sql
└── marts/             # 최종 분석 테이블
    ├── fct_orders.sql
    └── dim_customers.sql
```

---

## 4. 비교 및 연결

```
소스 → ETL 서버(변환 처리) → DWH 적재
  특징: 변환 서버에 부하 집중
  적합: 온프레미스 DWH, 보안 민감 변환
```

---

## 5. 실무 적용 및 판단

```
소스 → Cloud Storage (원시 데이터) → Cloud DWH (변환)
     Fivetran/Airbyte  (S3/GCS)    Snowflake/BigQuery
  특징: DWH의 컴퓨팅 파워 활용
  적합: 클라우드 스케일, 대용량, 빠른 탐색
```

| 항목        | ETL               | ELT                   |
|----------|------------------|-----------------------|
| 변환 위치  | ETL 서버 (중간)   | 목적지 DWH (최종)      |
| 원시 데이터 | 저장 안 함       | 저장 (Data Lake)       |
| 재처리    | 어려움             | 원시 데이터로 재처리 용이|
| 비용      | ETL 서버 비용     | DWH 컴퓨팅 비용        |

```sql
-- models/staging/stg_orders.sql
-- dbt config: materialized='view'

SELECT
    order_id,
    customer_id,
    CAST(created_at AS TIMESTAMP) AS order_at,
    UPPER(status) AS order_status,
    total_amount / 100.0 AS total_amount_usd
FROM raw.orders
WHERE created_at >= '2020-01-01'
```

| 도구              | 특징                               |
|-----------------|-----------------------------------|
| Apache Airflow   | Python DAG, 오픈소스, 광범위 사용  |
| Prefect          | 코드 중심, 클라우드 오케스트레이션 |
| Dagster          | 자산 중심, dbt 통합 강력           |
| AWS Glue         | 서버리스 ETL, AWS 통합              |
| Fivetran/Airbyte | 관리형 커넥터 기반 EL 자동화       |

```
소스 → Fivetran (EL) → Snowflake Raw → dbt (T)
              ↓                              ↓
         S3 Data Lake              Marts → Looker/Tableau
```

```yaml
# schema.yml
models:
  - name: stg_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: order_status
        tests:
          - accepted_values:
              values: ['pending', 'shipped', 'delivered']
```

```
원시 데이터 → stg_orders → int_order_items → fct_orders → 대시보드
  (소스)         (정규화)      (중간 집계)      (팩트 테이블)
```

- 계보 파악으로 장애 영향도 분석·규제 감사 대응
- dbt Cloud·DataHub·OpenLineage로 계보 자동화

---

## 6. 기대효과 및 결론

계보 파악으로 장애 영향도 분석·규제 감사 대응 dbt Cloud·DataHub·OpenLineage로 계보 자동화

ETL (Extract, Transform, Load)의 효과는 성능 향상 자체보다도 예측 가능성과 운영 일관성을 확보하는 데 있다. 반대로 데이터 품질, 거버넌스, 모니터링 없이 도입하면 복잡도만 늘고 실질 가치는 줄어든다. 따라서 이 주제는 기능 도입이 아니라 구조적 운영 역량과 함께 판단해야 하며, 향후에는 자동화·실시간성·설명 가능성·비용 최적화와 결합된 방향으로 발전한다.

## 7. 발전 흐름도

```
┌─────────────────────────────────────────────────────────────────┐
│                 ETL 기술 발전 흐름                               │
├──────────────┬────────────────────┬─────────────────────────────┤
│ 1990년대     │ 전통 ETL 툴        │ Informatica·DataStage 등장  │
│ 2000년대     │ 온프레미스 DWH     │ Oracle·Teradata 중심 ETL    │
│ 2010년대     │ 클라우드 DWH       │ Redshift·BigQuery → ELT 전환│
│ 2016년       │ dbt 오픈소스 출시  │ SQL 기반 Transform 혁명      │
│ 2018년       │ Fivetran·Airbyte   │ 커넥터 기반 EL 자동화        │
│ 2020년대     │ Modern Data Stack  │ Snowflake+dbt+Looker 표준화 │
└──────────────┴────────────────────┴─────────────────────────────┘

핵심 키워드 연결:
소스 → Extract(Fivetran) → Load(DWH) → Transform(dbt)
  ↓          ↓                 ↓              ↓
RDBMS·API  커넥터 표준화   원시 데이터 보존  SQL 모델링
  ↓
데이터 계보 → 품질 테스트 → Looker/Tableau 시각화
```

ETL (Extract, Transform, Load)

    ├── dbt 테스트 (unique·not_null)
    ├── Data Lineage (계보)
