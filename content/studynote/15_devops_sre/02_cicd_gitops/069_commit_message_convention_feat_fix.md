## 0. 핵심 인사이트

> **핵심**: 커밋 메시지 컨벤션은 변경 의도를 짧고 일관되게 표현하는 규칙이다.
> **비유**: 상자에 내용물 이름을 붙여 두는 일이다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

커밋 히스토리는 나중에 읽는 문서다. 메시지가 일관되면 나중에 추적하기 쉽다.

그래서 접두어 규칙이 중요하다.

---

## 2. 구성요소

```text
type(scope): subject
```

| 타입 | 의미 |
| :-- | :-- |
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 변경 |
| refactor | 구조 개선 |

커밋 컨벤션은 변경 목적을 한눈에 보이게 해 주는 메타데이터다. 그래서 릴리스 노트와 자동화 도구에 유리하다.

---

## 3. 구조 및 원리

**핵심 조건**: 모든 변경이 버전 관리되고, 자동 검증을 통과하며, 배포 상태와 롤백 경로가 추적 가능해야 한다.

동작 순서:
1. 코드와 배포 정의를 저장소에 커밋해 변경 이력을 단일 진실 공급원으로 만든다.
2. 빌드·테스트·보안 검사를 자동 수행해 배포 가능 아티팩트를 만든다.
3. 환경별 설정을 분리하면서도 동일한 파이프라인으로 일관성을 유지한다.
4. 배포 후 메트릭과 로그를 확인하고 이상 시 즉시 롤백하거나 다음 단계 승인을 중단한다.

```text
소스 변경
   ↓
CI 검증
   ↓
아티팩트 저장
   ↓
CD/GitOps 동기화
   ↓
운영 반영·롤백
```

| 타입 | 용도 |
| :-- | :-- |
| feat | 새 기능 |
| fix | 결함 수정 |
| docs | 문서 |
| chore | 작업성 변경 |

| 효과 | 의미 |
| :-- | :-- |
| 가독성 | 히스토리 이해 쉬움 |
| 자동화 | 릴리스/체인지로그 |
| 협업 | 변경 의도 공유 |

컨벤션은 강제보다 합의가 중요하다. 하지만 합의된 규칙을 일관되게 유지해야 진짜 효과가 난다.

---

## 4. 비교 및 연결

### 체크리스트

1. 팀 공통 규칙이 있는가?
2. type이 일관적인가?
3. subject가 짧고 명확한가?
4. 릴리스 노트와 연결되는가?
5. 예외 처리 규칙이 있는가?

### 안티패턴

- 사람마다 제멋대로 쓰는 설계
- 의미 없는 제목을 쓰는 설계
- 접두어 없이 커밋하는 설계
- 규칙은 있으나 지키지 않는 설계

기술사 관점에서는 커밋 메시지 컨벤션을 "협업 히스토리의 표준화"로 설명해야 한다.

---

## 5. 실무 적용 및 판단

커밋 메시지 규칙을 지키면 히스토리가 읽기 쉬워지고, 자동화도 쉬워진다.

---

## 6. 기대효과 및 결론

적으로 커밋 메시지 컨벤션은 변경 의도 표준화 규칙이다.

---

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Git | 모든 변경 이력과 협업 흐름의 기준점 |
| CI | 통합 오류를 조기에 발견하는 자동 검증 단계 |
| 아티팩트 | 검증된 결과물을 불변 객체로 보관하는 단위 |
| 배포 전략 | 롤링·블루그린·카나리처럼 위험을 조절하는 기법 |
| GitOps | 목표 상태를 Git에 선언하고 클러스터와 지속 동기화하는 방식 |
