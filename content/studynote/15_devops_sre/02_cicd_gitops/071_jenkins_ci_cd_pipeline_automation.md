## 0. 핵심 인사이트

> **핵심**: Jenkins는 플러그인 기반의 오픈소스 CI/CD 자동화 서버다.
> **비유**: 일을 대신 해 주는 자동화 공장이다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

반복 빌드와 배포를 수동으로 하면 느리고 실수도 많다.

Jenkins는 그 반복을 자동화한다.

---

## 2. 구성요소

```text
Source
  ↓
Jenkins Pipeline
  ↓
Build / Test / Deploy
```

| 요소 | 의미 |
| :-- | :-- |
| Job | 작업 |
| Pipeline | 단계 흐름 |
| Agent | 실행 노드 |

Jenkins는 파이프라인을 정의해 자동화하고, 에이전트로 작업을 분산한다.

---

## 3. 구조 및 원리

**핵심 조건**: 모든 변경이 버전 관리되고, 자동 검증을 통과하며, 배포 상태와 롤백 경로가 추적 가능해야 한다.

동작 순서:
1. 코드와 배포 정의를 저장소에 커밋해 변경 이력을 단일 진실 공급원으로 만든다.
2. 빌드·테스트·보안 검사를 자동 수행해 배포 가능 아티팩트를 만든다.
3. 환경별 설정을 분리하면서도 동일한 파이프라인으로 일관성을 유지한다.
4. 배포 후 메트릭과 로그를 확인하고 이상 시 즉시 롤백하거나 다음 단계 승인을 중단한다.

```text
소스 변경
   ↓
CI 검증
   ↓
아티팩트 저장
   ↓
CD/GitOps 동기화
   ↓
운영 반영·롤백
```

| 구분 | Jenkins | 단순 스크립트 |
| :-- | :-- | :-- |
| 자동화 | 높음 | 낮음 |
| 확장성 | 높음 | 낮음 |
| 관리 | 플러그인 | 수동 |

| 개념 | 의미 |
| :-- | :-- |
| Pipeline as Code | 코드로 정의 |
| Plugin | 기능 확장 |

Jenkins는 유연하지만 플러그인 관리가 중요하다. 그래서 운영 표준이 필요하다.

---

## 4. 비교 및 연결

### 체크리스트

1. Pipeline as Code를 쓰는가?
2. 에이전트를 적절히 분리하는가?
3. 플러그인을 관리하는가?
4. 빌드/테스트/배포를 자동화하는가?
5. 보안과 자격 증명을 관리하는가?

### 안티패턴

- 수동 Job만 잔뜩 쌓는 설계
- 플러그인 업데이트를 방치하는 설계
- 자격 증명을 노출하는 설계
- 파이프라인 코드화 없이 운영하는 설계

기술사 관점에서는 Jenkins를 "CI/CD 파이프라인 자동화 서버"로 설명해야 한다.

## 8. 관련 개념 맵

| 개념 | 연결 포인트 |
|:---|:---|
| Git | 모든 변경 이력과 협업 흐름의 기준점 |

| 아티팩트 | 검증된 결과물을 불변 객체로 보관하는 단위 |

| GitOps | 목표 상태를 Git에 선언하고 클러스터와 지속 동기화하는 방식 |
