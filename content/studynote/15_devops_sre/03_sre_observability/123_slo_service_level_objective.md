## 0. 핵심 인사이트

> **핵심**: SLO는 **SLI(측정 지표)에 대한 목표 임계치**이며, "가용성 SLI ≥ 99.9%"처럼 정의하여 **서비스 신뢰성의 정량적 기준**을 제공한다.
> **비유**: SLO는 **합격 기준(90점)**이고, Error Budget은 **틀려도 되는 문제 수(10문제)**이다. 10문제 이상 틀리면 보충 수업(안정화)을 받아야 한다.

---

> 📝 모범 답안

## 1. 개요 및 필요성

```text
┌───────────────────────────────────────────────────────┐
│    SLO → Error Budget → 의사결정                     │
├───────────────────────────────────────────────────────┤
│  SLO = 99.9% (30일 기준)                              │
│  Error Budget = 0.1% = 43.2분/월                     │
│                                                       │
│  [Budget 남음 (장애 10분만 발생)]                     │
│   → 피처 개발 계속! 카나리 배포 승인!                │
│                                                       │
│  [Budget 소진 (장애 50분 발생)]                       │
│   → 피처 개발 중단! 안정화·테스트·관측성 개선!       │
└───────────────────────────────────────────────────────┘
```

---

## 2. 구성요소

### SLO 설정 원칙
1. **100% 금지**: 혁신·배포가 불가능해짐.
2. **사용자 기대 기반**: 내부 도구는 99.5%, 결제는 99.99%.
3. **SLO < SLA**: 내부 목표가 계약보다 엄격해야 여유 확보.

### SLI → SLO → Error Budget → SLA 체인

| 단계 | 정의 | 예 |
|:---|:---|:---|
| **SLI** | 측정 | 가용성 99.95% |
| **SLO** | 목표 | ≥ 99.9% |
| **Error Budget** | 여유 | 0.1% (43분) |
| **SLA** | 계약 | ≥ 99.5% (위반 시 크레딧) |

---

## 3. 구조 및 원리

**핵심 조건**: 측정 가능한 SLI, 합의된 SLO, 실행 가능한 경보·복구 절차가 하나의 폐쇄 루프를 이뤄야 한다.

동작 순서:
1. 사용자 경험을 대표하는 지표를 선택해 서비스 상태를 수치화한다.
2. 허용 가능한 목표치와 에러 버짓을 정해 변화 속도와 안정성의 기준선을 만든다.
3. 메트릭·로그·트레이스로 이상 징후를 탐지하고 원인을 빠르게 국소화한다.
4. 장애 이후 포스트모템과 자동화를 통해 토일을 줄이고 재발 방지책을 시스템에 반영한다.

```text
서비스 요청
   ↓
측정(SLI)
   ↓
목표(SLO)·예산
   ↓
알림·복구
   ↓
학습·자동화
```

| 비교 | SLO 없음 | SLO 있음 |
|:---|:---|:---|
| **판단** | 주관적 | **데이터 기반** |
| **개발 속도** | 느림 (공포) | **Budget 내 빠름** |
| **안정화** | 장애 후 사후 | **Budget 소진 시 즉시** |

---

## 4. 비교 및 연결

### Error Budget 정책 예시
- Budget > 50%: 공격적 배포·실험 허용.
- Budget 10~50%: 카나리·A/B 테스트로 신중 배포.
- Budget < 10%: 피처 동결, 안정화 집중.
- Budget 소진: **배포 중단 (Release Freeze)**.

---

## 5. 실무 적용 및 판단

SLO는 **SRE의 가장 핵심적 의사결정 도구**이며, Error Budget을 통해 엔지니어링 팀과 비즈니스 팀 간의 갈등(속도 vs 안정)을 **데이터로 해결**한다.

---

## 6. 기대효과 및 결론

SLO (Service Level Objective)을(를) 도입하면 자동화와 표준화를 통해 속도·안정성·가시성의 균형을 높일 수 있다. 다만 효과를 얻으려면 측정 가능한 SLI, 합의된 SLO, 실행 가능한 경보·복구 절차가 하나의 폐쇄 루프를 이뤄야 한다는 전제가 충족되어야 하며, 도구만 도입하고 운영 원칙을 바꾸지 않으면 기대 효과가 빠르게 한계에 부딪힌다.

결론적으로 SLO (Service Level Objective)은(는) 개별 기능이 아니라 운영 체계 전체의 품질을 재정렬하는 방식이며, 향후에는 플랫폼화·정책화·AI 기반 최적화와 결합해 더 높은 수준의 자동 운영으로 확장된다.
