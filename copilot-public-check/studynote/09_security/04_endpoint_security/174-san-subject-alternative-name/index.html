핵심 인사이트 (3줄 요약)

  1. 본질: SAN (Subject Alternative Name)은 X.509 v3 인증서가 대표할 수 있는 DNS (Domain Name System) 이름, IP (Internet Protocol) 주소, 이메일, URI (Uniform Resource Identifier)를 확장 필드에 명시하는 메커니즘이다.
  2. 가치: 가상 호스팅, 로드밸런서, 멀티도메인 서비스 환경에서 한 장의 인증서로 여러 엔드포인트를 명시적으로 검증하게 해 인증서 운영 복잡도를 크게 줄인다.
  3. 판단 포인트: 현대 브라우저의 호스트 검증은 Common Name보다 SAN을 우선하며, 이름 집합이 고정적이면 SAN, 하위 도메인이 계속 늘면 와일드카드, 격리가 중요하면 별도 인증서가 더 적합하다.

Ⅰ. 개요 및 필요성

SAN (Subject Alternative Name)은 인증서의 "추가 신원 목록"이다. 과거에는 Subject의 Common Name 한 칸으로 서버 이름을 표현하는 관행이 많았지만, 한 IP 뒤에 여러 서비스가 모이는 클라우드·로드밸런서·가상 호스팅 환경에서는 이름 하나만으로 현실을 담기 어려웠다. api.example.com, admin.example.com, partner.example.net처럼 서로 다른 접속 지점을 한 서비스 게이트웨이가 처리할 때, 인증서가 하나의 이름만 대표하면 나머지는 모두 이름 불일치 오류가 된다.

SAN이 중요한 이유는 단순 편의성 때문만이 아니다. 브라우저와 TLS (Transport Layer Security) 클라이언트는 "내가 접속한 호스트가 이 인증서가 주장하는 이름 집합 안에 있는가"를 기계적으로 판정해야 한다. 즉 SAN은 사람이 읽는 설명란이 아니라, 호스트 검증의 기준 데이터다.

아래 그림은 왜 SAN이 필요해졌는지를 "하나의 게이트웨이, 여러 이름" 관점에서 보여 준다.

SAN이 없으면 서버가 안전한 키를 가지고 있어도, 클라이언트는 "접속한 이름과 인증서의 이름이 다르다"며 연결을 거부한다. 결국 SAN은 암호화의 성능 문제가 아니라, 신뢰의 범위를 정확히 적어 두는 문제다.

  • 📢 섹션 요약 비유: SAN은 건물 출입증 뒷면에 적힌 "이 사람이 출입할 수 있는 모든 출입문 목록"과 같다. 정문 하나만 적혀 있으면 지하 주차장 문에서는 막히지만, 허용된 문이 목록으로 적혀 있으면 어디서 들어와도 같은 사람으로 확인된다.

Ⅱ. 아키텍처 및 핵심 원리

SAN은 X.509 v3 확장 필드 안에 들어간다. 인증서 본문에는 Subject, 공개키, 유효기간 같은 기본 정보가 있고, SAN은 그중 "이 인증서가 대변할 수 있는 이름들"을 추가로 적는 역할을 한다. 실무에서는 CSR (Certificate Signing Request) 단계에서 SAN 목록을 선언하고, CA (Certificate Authority)가 각 이름에 대한 통제권을 검증한 뒤 인증서로 발급한다.

┌──────────────────────────────────────────────────────────────────────┐
│ TLS hostname validation with SAN                                     │
├──────────────────────────────────────────────────────────────────────┤
│ Client requests: https://api.example.com                             │
│        │                                                             │
│        ▼                                                             │
│ Server sends certificate                                             │
│   ├─ Subject CN = www.example.com        (legacy / secondary)        │
│   └─ SAN extension                                                   │
│      ├─ DNS: api.example.com                                         │
│      ├─ DNS: admin.example.com                                       │
│      ├─ DNS: *.internal.example.com                                  │
│      └─ IP : 10.10.10.5                                              │
│        │                                                             │
│ Client matcher                                                       │
│   ├─ requested host ∈ SAN list  -> continue handshake                │
│   └─ requested host ∉ SAN list  -> name mismatch error               │
└──────────────────────────────────────────────────────────────────────┘

핵심은 SAN이 "추가 정보"가 아니라 실제 매칭 테이블이라는 점이다. 특히 SNI (Server Name Indication)는 서버가 어떤 인증서를 내보낼지 고르는 힌트이고, SAN은 클라이언트가 받은 인증서가 맞는지 검증하는 근거다. 즉 SNI와 SAN은 대체 관계가 아니라, 선택 → 검증의 순서로 연결된다.

SAN 엔트리 타입표현 예시주 용도주의점
dNSNameapi.example.comHypertext Transfer Protocol Secure (HTTPS), Application Programming Interface (API), 일반 웹 서버가장 흔한 유형이며 FQDN (Fully Qualified Domain Name) 기준으로 맞춰야 한다.
iPAddress10.10.10.5DNS 없이 IP로 직접 접속하는 관리망운영 중 IP 변경 가능성이 크므로 재발급 부담을 고려해야 한다.
rfc822Nameadmin@example.comS/MIME 메일 인증서웹 서버 인증과는 별도 목적이다.
uniformResourceIdentifierspiffe://cluster/ns/app서비스 메시, 워크로드 IDURI 자체를 신원으로 쓰는 환경에서 유용하다.
wildcard entry*.example.com하위 1단계 서브도메인 다수패턴도 SAN 안에 들어가며, 범위가 넓어질수록 노출 반경도 커진다.

또 하나의 원리는 명시성이다. SAN은 "이름이 많아도 다 알아서 허용"이 아니라, 인증서가 책임질 이름을 구체적으로 열거하거나 패턴으로 한정한다. 그래서 새 호스트가 추가되면 기존 인증서가 자동으로 따라가지 않고, 필요한 경우 재발급이 발생한다. 이것이 번거로워 보여도, 반대로 말하면 허용 범위를 증명 가능한 방식으로 고정해 준다는 뜻이다.

  • 📢 섹션 요약 비유: SAN은 택배 주소록과 같다. 택배 기사에게 "아무 집이나 내 집으로 쳐 주세요"가 아니라, 배송 가능한 주소를 정확히 적어 둬야 실수 없이 배달된다.

Ⅲ. 비교 및 연결

SAN을 이해할 때 가장 자주 헷갈리는 대상은 Common Name, 와일드카드 인증서, SNI다. 셋은 비슷해 보이지만 담당하는 질문이 다르다.

구분SANCommon NameWildcardSNI

이 비교가 중요한 이유는 운영 판단이 달라지기 때문이다. 예를 들어 api.example.com, admin.example.com, billing.partner.net처럼 도메인 집합이 고정되어 있고 서로 다른 도메인까지 포함해야 하면 SAN 인증서가 적합하다. 반면 tenant1.example.com, tenant2.example.com처럼 같은 존 아래 하위 호스트가 계속 늘면 와일드카드가 편할 수 있다. 다만 와일드카드는 보통 한 단계 하위 서브도메인에만 적용되고, 범위가 넓을수록 유출 시 파급 범위가 커진다.

또한 SNI와 SAN을 혼동하면 안 된다. SNI가 없으면 서버가 틀린 인증서를 내보낼 수 있고, SAN이 없으면 클라이언트가 인증서를 받아도 이름을 검증할 수 없다. 그래서 멀티도메인 HTTPS는 흔히 SNI로 인증서 선택 → SAN으로 이름 검증의 두 단계를 함께 사용한다.

  • 📢 섹션 요약 비유: SNI는 호텔 프런트에 "몇 호실 손님인지" 알려 주는 말이고, SAN은 받은 객실 키가 정말 그 방을 열 수 있는지 확인하는 열쇠 목록이다. 방 번호를 말해도 키가 틀리면 못 들어가고, 키가 맞아도 프런트가 엉뚱한 키를 주면 역시 못 들어간다.

Ⅳ. 실무 적용 및 기술사 판단

SAN 설계의 핵심은 "몇 개를 넣을 수 있는가"보다 "어디까지 한 장으로 묶어도 되는가"다. 인증서 하나에 너무 많은 이름을 넣으면 운영은 편해지지만, 개인키 유출·오발급·재발급 시 영향 범위가 함께 커진다. 반대로 서비스마다 인증서를 지나치게 쪼개면 자동화와 갱신 비용이 늘어난다. 따라서 SAN은 편의성과 격리 수준 사이의 균형 문제다.

운영 상황권장 선택이유
로드밸런서 하나가 3~10개의 고정 FQDN을 처리SAN 인증서명시적 이름 목록 관리가 쉽고 인증서 수를 줄일 수 있다.
같은 존 아래 서브도메인이 계속 생성와일드카드 또는 와일드카드 + SAN신규 서브도메인 추가 때마다 재발급할 부담을 줄인다.

사내 서비스 메시, 워크로드 ID 기반 인증URI SAN 활용DNS가 아닌 서비스 ID를 신원으로 쓰기 좋다.
DNS 대신 IP로 직접 접속하는 관리 구간IP SAN접속 방식과 검증 기준을 일치시킨다.

실무 체크리스트

  1. CSR 생성 시 실제 접속 호스트명과 SAN 목록이 정확히 일치하는가?
  2. 공용 서비스라면 브라우저·모바일 앱·API 클라이언트가 모두 SAN 기준으로 검증하도록 되어 있는가?
  3. 새 호스트 추가 시 인증서 재발급, 배포, 롤백 절차가 자동화되어 있는가?
  4. 내부망 전용 이름이나 사설 주소는 공인 CA 대신 사설 PKI에서 관리해야 하는가?
  5. 와일드카드와 SAN을 혼용할 때 범위가 과도하게 넓어지지 않았는가?

자주 발생하는 안티패턴

  • Common Name만 넣고 SAN을 비워 둔 인증서 배포
  • 보안 성격이 다른 수십 개의 서비스명을 한 장에 과도하게 묶는 구성
  • SNI 구성은 했지만 실제 인증서 SAN 목록을 갱신하지 않아 이름 불일치를 일으키는 운영
  • IP 접속을 허용하면서 DNS SAN만 등록해 두는 불일치

기술사 답안에서는 "SAN = 멀티도메인용 필드"까지만 쓰면 아쉽다. 더 좋은 답은 **"SAN은 현대 TLS 호스트 검증의 기준 필드이며, 멀티도메인·와일드카드·서비스 ID 같은 이름 정책을 인증서에 기계적으로 인코딩하는 확장"**이라고 정리하는 것이다.

  • 📢 섹션 요약 비유: SAN 운영은 우산을 몇 명이 함께 쓸지 정하는 일과 같다. 한 우산을 너무 많이 같이 쓰면 편하지만, 우산 하나가 망가졌을 때 모두가 젖는다. 반대로 우산을 너무 많이 나누면 들고 다니는 짐이 늘어난다.

Ⅴ. 기대효과 및 결론

SAN 덕분에 현대 웹과 API 인프라는 하나의 게이트웨이, 여러 가상 호스트, 자동화된 인증서 배포를 현실적으로 운영할 수 있게 되었다. 브라우저는 SAN 목록을 기준으로 이름 일치를 판단하고, 운영팀은 인증서 수를 줄이면서도 필요한 이름 집합을 명시적으로 통제할 수 있다. 즉 SAN의 효과는 단순 절약이 아니라, 신뢰 범위의 표준화에 있다.

물론 SAN이 만능은 아니다. 이름이 많아질수록 인증서 재발급 영향 범위가 커지고, 너무 넓은 와일드카드나 과도한 멀티도메인 구성은 사고 시 blast radius를 키운다. 따라서 기억해야 할 핵심은 "SAN은 가능한 한 많이 넣는 기술"이 아니라 필요한 이름만 정확히 선언하는 최소 권한형 인증서 설계라는 점이다.

  • 📢 섹션 요약 비유: 좋은 출입증은 모든 문을 열게 만들지 않는다. 꼭 필요한 문만 열리게 해야 편의성과 안전이 함께 지켜진다.
