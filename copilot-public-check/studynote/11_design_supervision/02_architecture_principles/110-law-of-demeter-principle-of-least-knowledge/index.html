0. 핵심 인사이트

핵심: 최소 지식의 원칙은 객체가 너무 먼 내부 구조까지 알지 못하게 하여, 협력은 이웃과만 하고 내부 탐색 사슬은 숨기도록 만드는 결합도 제어 원칙이다. 비유: 회사에서 다른 부서 일을 처리할 때 담당 창구만 알면 되지, 그 부서 내부 팀 구조와 결재 라인을 모두 알아야 한다면 조직은 금방 복잡해지는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

최소 지식의 원칙 (Principle of Least Knowledge) 또는 디미터의 법칙 (Law of Demeter)은 한 객체가 너무 많은 다른 객체의 내부 구조를 알지 말아야 한다는 원칙이다. 흔히 “오직 가까운 객체와만 대화하라” 또는 “train wreck call을 피하라”라고 요약된다. 대표적 위반 형태가 a.getB().getC().doSomething() 같은 호출 사슬이다.

이 원칙이 필요한 이유는 내부 구조 탐색이 결합도를 기하급수적으로 키우기 때문이다. 클라이언트가 B와 C의 구조까지 알아야 하면, C의 변경이 B를 거쳐 A까지 전파된다. 이는 캡슐화를 깨고, 객체의 책임 경계를 흐리며, 테스트와 변경 비용을 증가시킨다.

Law of Demeter는 따라서 단순한 문법 규칙이 아니라, 메시지 중심 협력을 지향하는 객체지향 설계 원칙이다. 객체는 데이터를 꺼내와 외부에서 처리되기보다, 스스로 책임을 수행하거나 적절한 이웃 객체에 위임해야 한다. 이 점에서 Tell, Don't Ask 원칙과도 깊게 연결된다.

법칙을 기계적으로 적용하면 “점(.) 하나만 써라”로 오해되기 쉽지만, 핵심은 메서드 체이닝 자체보다 내부 구조 지식 노출이다. 예를 들어 Fluent API는 동일 객체 또는 불변 빌더를 체인하는 경우가 많아 LoD 위반으로 보지 않는다. 반면 하위 객체를 계속 꺼내는 탐색 체인은 전형적 위반이다.

3. 구조 및 원리

핵심 조건: 객체는 자신, 자신의 필드, 메서드 인자, 메서드 내부에서 생성한 객체 등 직접적인 협력 대상과만 통신해야 하며, 타 객체의 내부 객체를 연쇄적으로 탐색해 행동을 수행해서는 안 된다.

동작 순서:

  1. 협력 경계를 확인한다: 객체가 실제로 알아야 할 상대가 누구인지 정한다.
  2. 호출 사슬을 탐지한다: getA().getB().getC() 형태가 있는지 본다.
  3. 책임 위치를 재평가한다: 필요한 동작을 더 안쪽 객체가 직접 수행할 수 없는지 확인한다.
  4. 위임 메서드를 추가한다: 클라이언트가 깊은 구조를 몰라도 되게 메시지 전달 지점을 만든다.
  5. 캡슐화를 강화한다: 내부 컬렉션, 하위 객체 구조, 상세 타입 노출을 줄인다.
  6. 테스트를 협력 단위로 단순화한다: 내부 구조가 아닌 공개 계약만 검증한다.
[LoD 위반]
Order → Customer → Address → ZipCode → validate()
client가 내부 구조를 모두 앎

[LoD 적용]
Order.verifyDeliveryArea()
   └─ 내부에서 Customer/Address에 위임

클라이언트는 Order만 알면 됨

허용 가능한 대화 대상은 일반적으로 다음과 같이 정리된다. 자기 자신, 메서드 인자로 받은 객체, 자신이 직접 보유한 필드 객체, 메서드 안에서 새로 생성한 객체다. 반면 “내 친구의 친구”와 직접 대화하기 시작하면 구조 지식이 새어 나온다. 이때 필요한 것은 탐색이 아니라 적절한 메시지 위임이다.

실무에서 Law of Demeter가 중요한 이유는 DTO 체인, ORM 엔티티 그래프 탐색, UI 계층의 도메인 내부 접근에서 결합 폭발을 막기 위해서다. 특히 프레젠테이션 계층이 도메인의 하위 구조를 과도하게 탐색하기 시작하면 계층 경계가 빠르게 무너진다.

Law of Demeter는 SRP, DIP와도 연결된다. 책임이 분명한 객체는 외부가 깊게 탐색할 필요가 적고, 추상화 기반 설계는 구체 내부 구조 노출을 줄인다. 또한 Facade 패턴은 복잡한 하위 시스템을 감추는 점에서 이 원칙의 실무적 구현으로 자주 쓰인다.

5. 실무 적용 및 판단

채택 조건:

  • 호출 사슬이 길어지고 객체 내부 구조 노출이 많을 때
  • 계층 간 캡슐화 붕괴가 보일 때
  • 도메인 로직이 데이터 꺼내오기 중심으로 흘러갈 때

회피 조건:

  • 단순 DTO 조립까지 무조건 금지해 오히려 코드가 부자연스러워질 때
  • Fluent Builder처럼 의도적으로 설계된 체이닝까지 모두 위반으로 볼 때
  • 위임 메서드가 의미 없이 지나치게 많아져 인터페이스가 오염될 때

체크리스트:

  1. a.getB().getC() 같은 탐색 체인이 반복되는가?
  2. 클라이언트가 다른 객체의 내부 구조를 알아야만 일을 처리하는가?
  3. 필요한 동작을 더 안쪽 객체에 위임할 수 있는가?
  4. 계층 경계를 넘어 상세 타입이나 하위 객체를 노출하고 있는가?
  5. Fluent API와 내부 구조 탐색을 구분하고 있는가?

실무에서는 엔티티 그래프 탐색을 컨트롤러에서 직접 수행하거나, UI가 도메인 하위 객체 필드를 연쇄 접근하는 경우가 대표적 위반이다. 주문 객체에 배송 가능 여부 판단을 위임하면 호출 사슬과 결합을 동시에 줄일 수 있다.

6. 기대효과 및 결론

최소 지식의 원칙을 지키면 객체 간 결합이 줄고, 내부 구조 변경이 외부로 덜 전파되며, 메시지 중심 협력이 강화된다. 이는 테스트 단순화와 리팩토링 안전성 향상으로 이어진다. 특히 복잡한 도메인 모델에서는 구조 지식 누수를 막는 효과가 매우 크다.

하지만 이 원칙도 기계적으로 적용하면 위임 메서드만 늘어나는 “메서드 폭증”이 생길 수 있다. 따라서 핵심은 점 개수 세기가 아니라, 클라이언트가 알아야 할 지식의 최소화다. 좋은 객체는 내부를 보여주지 않고 스스로 일을 처리한다.
