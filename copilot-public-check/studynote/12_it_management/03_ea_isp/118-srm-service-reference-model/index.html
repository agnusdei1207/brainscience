0. 핵심 인사이트

핵심: SRM (Service Reference Model)의 본질은 애플리케이션 서비스를 공통 컴포넌트 관점으로 분류해 재사용과 표준화를 촉진하는 것이다.

비유: 집을 지을 때 방마다 가구를 새로 만들지 않고 표준 규격의 부품을 조합해 구성하는 모듈식 가구 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

SRM (Service Reference Model)은 애플리케이션과 서비스 기능을 공통 분류 체계로 정리하는 참조 모델이다. 동일한 업무라도 인증, 검색, 통계, 알림, 결제 같은 공통 서비스는 여러 시스템에서 반복적으로 필요하다. SRM은 이런 기능을 서비스 관점에서 구조화해 재사용 가능한 컴포넌트 후보를 찾게 한다.

SRM이 없으면 프로젝트마다 유사 기능을 다시 개발하게 되고, 유지보수와 통합 비용이 커진다. 반대로 서비스 분류와 공통 컴포넌트 기준이 있으면 공통 플랫폼, API, 공유 서비스로 전환하기 쉬워진다.

2. 구성요소

서비스 분류는 SRM의 상위 체계를 만들고, 컴포넌트 정의는 구현 단위를 구체화한다. 인터페이스 표준은 서비스 간 결합 방식을 통일하며, 재사용 정책은 프로젝트가 공통 서비스를 우선 활용하도록 유도한다. 이 네 요소가 모여 애플리케이션 표준화가 가능해진다.

3. 구조 및 원리

핵심 조건: 서비스는 업무 기능과 분리 가능한 공통 관점으로 정의되어야 하며, 인터페이스와 재사용 기준이 함께 마련되어야 한다.

SRM의 핵심은 기능을 업무 시스템 단위가 아니라 서비스 단위로 재구성하는 것이다. 이렇게 하면 서로 다른 애플리케이션에서도 공통 기능을 묶어 플랫폼화할 수 있다. 단, 서비스 경계를 너무 넓게 잡으면 재사용성이 떨어지고, 너무 세분화하면 관리 복잡도가 커진다.

동작 순서:

  1. 공통 서비스 후보 식별: 여러 시스템에서 반복되는 기능을 찾는다.
  2. 서비스 분류 체계 수립: 공통 서비스 영역과 세부 컴포넌트를 계층화한다.
  3. 인터페이스·표준 정의: 서비스 호출 규약, 데이터 계약, 운영 기준을 정한다.
  4. 재사용 적용: 신규 사업이 공통 서비스를 우선 활용하도록 가이드한다.
[업무 시스템 A] ─┐
[업무 시스템 B] ─┼─▶ [공통 서비스 분류] ─▶ [인증][검색][통계][알림]
[업무 시스템 C] ─┘                     └─ 표준 API/컴포넌트

SRM은 단순히 마이크로서비스 목록을 만드는 것이 아니다. 공통성과 재사용성을 기준으로 분류해야 하므로, 특정 프로젝트의 구현 세부사항에 매몰되면 안 된다. 또한 공통 서비스라고 해서 무조건 중앙집중화하는 것이 최선은 아니며, 성능과 독립성이 필요한 경우는 분산 배치가 더 적합할 수 있다.

4. 비교 및 연결

BRM이 업무 기능을 분류한다면 SRM은 이를 지원하는 공통 서비스 관점을 제공한다. AA 포트폴리오는 실제 시스템 배치를 설명하고, SRM은 그 안에서 재사용 가능한 서비스 경계를 정의한다. 따라서 SRM은 애플리케이션 표준화와 플랫폼 전략의 핵심 연결 고리다.

5. 실무 적용 및 판단

채택 조건:

  • 공통 플랫폼 구축, API 표준화, 서비스 재사용 확대 시
  • 중복 개발이 잦은 공통 기능이 많을 때
  • 패키지/플랫폼/공유 서비스 전략이 필요할 때

회피 조건:

  • 프로젝트별 구현 모듈을 그대로 SRM이라 부르는 경우
  • 인터페이스 표준 없이 서비스 목록만 만드는 경우
  • 업무 기능(BRM)과 서비스 기능을 혼동하는 경우

체크리스트:

  1. 공통 서비스 분류가 반복 기능을 충분히 포괄하는가?
  2. 컴포넌트 경계와 인터페이스 표준이 정의되는가?
  3. 신규 사업의 재사용 기준이 존재하는가?
  4. 플랫폼화 대상과 개별 시스템 고유 기능이 구분되는가?

전자정부 공통 인증, 메시징, 전자결재 연계 서비스는 SRM 관점으로 정의하기 적합하다. 민간에서는 고객 알림, 상품 조회, 공통 과금, API 게이트웨이 기능을 공통 서비스로 분류해 플랫폼화한다.

6. 기대효과 및 결론

SRM은 애플리케이션 기능을 서비스 자산으로 전환해 재사용과 표준화를 가능하게 한다. 이를 통해 중복 개발을 줄이고 플랫폼 전략의 기반을 마련할 수 있다. 미래에는 API 관리, 이벤트 기반 아키텍처, 서비스 카탈로그가 결합되며 SRM의 운영 가치가 더 커질 것이다.
