0. 핵심 인사이트

핵심: CPU 스케줄링의 가장 근본적인 분류 기준으로, 프로세스가 CPU를 잡았을 때 "스스로 내놓을 때까지 기다려줄 것인가(비선점)" 아니면 **"OS가 중간에 강제로 뺏을 수 있는가(선점)"**의 권력 구조 차이를 의미한다. 비유: 선점 / 비선점 스케줄링 차이은(는) 복잡한 교통을 한 번에 통제해 전체 흐름을 맞추는 신호 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

  • 개념:

    • 비선점형 스케줄링 (Non-Preemptive): 실행 중인 프로세스가 I/O를 요청하거나 스스로 종료할 때까지 CPU를 계속 독점하는 방식.
    • 선점형 스케줄링 (Preemptive): OS가 하드웨어 인터럽트를 이용해 실행 중인 프로세스의 CPU를 강제로 회수하고, 다른 우선순위가 높은 프로세스에 할당할 수 있는 방식.

  • 필요성 (독재의 종식과 반응성 확보):

    • 비선점형 방식에서는 개발자가 실수로 while(true) 무한 루프 코드를 짜면, 그 프로세스가 CPU를 영원히 쥐고 놔주지 않아서 마우스도 안 움직이고 컴퓨터 전체가 먹통(Freeze)이 된다.

    • 시간이 중요한 대화형 시스템(사용자 입력)에서는, 다른 무거운 작업이 돌고 있더라도 내 키보드 입력이 즉시 처리되어야 한다.

    • 해결책: 프로세스의 '자발적 양보'에 기대는 순진한 생각을 버리고, OS 커널이 타이머 칩(하드웨어)을 무기로 삼아 **"시간 다 됐어! 강제 하차해!"**라고 쫓아내는 선점형(강압적) 스케줄링이 필수적으로 대두되었다.

    • 비선점형: 마이크를 한 번 잡으면, 자기가 연설을 스스로 끝내고 내려오기 전까지는 아무도 마이크를 뺏을 수 없는 자유 발언대. 한 명이 10시간 떠들면 나머지 사람은 다 집에 가야 한다.

    • 선점형: 1분마다 무조건 마이크 전원을 꺼버리고 다음 사람에게 마이크를 강제로 넘기는 TV 토론. 누군가 헛소리를 길게 늘어놓아도 1분 뒤면 입이 막히므로 토론회 전체가 마비되지 않는다.

  • 발전 과정:

    1. 초기 OS (비선점): FCFS(First Come First Served), SJF(Shortest Job First). 스위칭 오버헤드가 없어 연산 효율은 좋음.
    2. 과도기 (협력적 멀티태스킹): Windows 3.1, Mac OS 9. 앱들이 스스로 yield()를 불러서 양보하게 만듦 (결국 비선점의 일종이라 잘 멈춤).
    3. 현대 OS (선점형): Windows NT, Linux, macOS. RR(Round Robin), SRTF, MLFQ. 하드웨어 인터럽트 기반의 절대 권력 통제.

2. 구성요소

스케줄러가 개입하는 4가지 상황 (결정적 차이)

프로세스의 상태 변화 중 스케줄러가 언제 개입하느냐에 따라 선점과 비선점이 나뉜다.

  1. Running $\rightarrow$ Waiting(Block) : (예: I/O 요청 시 스스로 잠듦)
  2. Running $\rightarrow$ Terminated : (예: 프로그램 정상 종료)
  3. Running $\rightarrow$ Ready : (예: 타이머 만료로 강제 쫓겨남) ★
  4. Waiting $\rightarrow$ Ready : (예: I/O가 끝난 애가 기존 실행 놈을 새치기함) ★
  • 비선점형: 1번과 2번 상황에서만 스케줄러가 동작한다. (프로세스가 '스스로' 비킬 때만 개입)
  • 선점형: 1, 2번뿐만 아니라 3번(시간 초과)과 4번(우선순위 역전) 상황에서도 OS가 개입해 강제로 CPU를 뺏는다.

선점형 스케줄링의 2가지 핵심 무기 (Timer & Interrupt)

선점(강제로 뺏기)이 성립하려면 소프트웨어(OS)의 힘만으로는 안 되고 하드웨어의 지원이 절대적으로 필요하다.

[다이어그램 해설] 초보 개발자는 "운영체제가 주기적으로 프로세스를 감시한다"고 생각하지만 틀렸다. CPU가 악성 코드를 돌리고 있을 때는 운영체제의 코드도 멈춰(휴면) 있다! 오직 외부에서 강제로 때려주는 **물리적 알람(타이머 인터럽트)**만이 멈춰있는 OS의 영혼을 CPU로 다시 불러들여 심판의 철퇴(선점)를 내리게 할 수 있다.

3. 구조 및 원리

핵심 조건: 운영체제의 해당 메커니즘은 현재 상태 정보, 자원 제약, 정책 기준이 함께 정합성을 가질 때 안정적으로 동작한다.

동작 순서:

  1. 요청 또는 이벤트 발생: 사용자 요청, 인터럽트, 시스템 호출 등으로 커널이 해당 기능을 처리할 필요가 생긴다.
  2. 현재 상태 확인: 커널은 큐, 제어 블록, 메타데이터, 자원 가용량을 확인해 실행 가능 여부와 우선순위를 판단한다.
  3. 정책 적용 및 자원 배정: 해당 주제의 핵심 정책에 따라 상태 전이, 자원 할당, 보호 검사를 수행한다.
  4. 결과 반영 및 후속 처리: 처리 결과를 시스템 상태에 기록하고 다음 인터럽트·스케줄링·복구 단계로 연결한다.

알고리즘 명칭선점 / 비선점특징 및 동작 방식

MLFQ (Multi-Level Feedback Queue)선점큐(Queue)가 여러 개. 현대 OS 스케줄링의 근간

선점형의 부작용: 문맥 교환 오버헤드와 동기화(Race Condition)

선점형이 무조건 좋은 것만은 아니다. 치명적인 두 가지 대가를 치러야 한다.

  1. Context Switch 오버헤드: 강제로 뺏고 넘겨주는 행위 자체가 레지스터 복사와 TLB 플러시를 유발하여 시스템을 느리게 만든다.
  2. Race Condition (데이터 충돌): 프로세스 A가 공유 메모리의 Count = 5를 6으로 바꾸려는 찰나(Read만 한 상태), OS가 강제로 CPU를 뺏어 프로세스 B에게 넘겼다. B가 Count를 4로 깎고 턴을 마쳤다. 다시 A가 깨어나서 원래 하던 대로 6을 써버렸다. 정답은 5가 되어야 하는데 데이터가 깨졌다. (비선점형에서는 절대 발생하지 않는 문제)

5. 실무 적용 및 판단

실무 시나리오

  1. 시나리오 — 인터럽트 처리 중의 커널 선점(Kernel Preemption) 금지로 인한 랙(Lag): 과거 구형 리눅스 서버(2.4 버전 이하)에서 커다란 파일을 디스크에서 지우고(rm) 있으면, 마우스 커서마저 안 움직이고 서버 전체가 뚝뚝 끊기는 현상.

    • 원인 분석: 유저 프로그램끼리는 "선점형(RR)"이라도, 프로그램이 시스템 콜을 호출해 **"커널 모드(Ring 0)"**로 들어간 순간, 옛날 리눅스는 그 커널 코드를 '비선점형'으로 취급했다. 즉, 커널이 파일을 지우는 무거운 작업을 하는 동안에는 다른 유저 앱이 아무리 급해도 CPU를 뺏을 수 없었다.
    • 아키텍처 대응 (Preemptible Kernel): 리눅스 2.6부터는 CONFIG_PREEMPT 기능이 도입되어, 커널 모드 안에서 코드가 돌고 있더라도 급한 인터럽트나 스레드가 나타나면 **커널 코드마저 강제로 중단시키고 선점(Kernel Preemption)**할 수 있게 진화하여 데스크탑의 부드러움을 쟁취했다.

  2. 시나리오 — 실시간(RTOS) 환경에서의 우선순위 역전 (Priority Inversion): 화성 탐사선 패스파인더에서, 우선순위가 가장 높은 1번 스레드(선점형)가, 가장 낮은 3번 스레드가 쥐고 있는 락(Lock)을 기다리며 멈춰버린 대형 사고.

    • 원인 분석: 1번이 3번의 락을 기다리는데, 중간 우선순위인 2번 스레드가 나타나서 3번 스레드의 CPU를 뺏어버렸다(선점). 3번은 CPU를 뺏겨서 락을 영원히 풀지 못하고, 1번도 영원히 멈추게 된 것이다. 선점형 스케줄링과 락(Lock)이 결합할 때 터지는 최악의 재앙이다.
    • 대응 (우선순위 상속, PIP): OS 커널이 이 상황을 감지하고, 락을 쥐고 있는 비루한 3번 스레드의 우선순위를 일시적으로 1번(최고)으로 뻥튀기(Boost)해 준다. 그러면 2번 스레드가 감히 3번을 선점하지 못하게 되고, 3번이 빨리 락을 풀고 1번을 살려내게 된다.

[다이어그램 해설] 많은 사람이 "선점형이 무조건 더 좋은 최신 기술"이라고 착각한다. 선점형은 '응답성'을 위해 'CPU 전체 성능'을 깎아 먹는 이율배반적 구조다. 빅데이터 분석이나 그래픽 렌더링 팜에서는 OS가 중간중간 끼어들어 CPU를 뺏는 선점 행위가 오히려 방해만 된다. 아키텍트는 워크로드에 맞춰 선점의 빈도(Tick Rate)를 의도적으로 낮추는 비선점 지향 튜닝을 할 줄 알아야 한다.

도입 체크리스트

  • Reentrancy (재진입성): 우리가 만든 공유 라이브러리(함수)가 선점형 환경에 안전한가? A 프로세스가 함수를 실행하다가 강제로 뺏겨서 B 프로세스가 동일한 함수에 진입(재진입)하더라도, 전역 변수가 꼬이지 않고 완벽히 지역 변수(Stack)로만 동작하도록 100% Thread-safe 하게 짜였는가 검증해야 한다.

미래 전망

  • 사용자 공간 선점 스케줄링 (User-space Preemption): Go 언어의 고루틴(Goroutine)은 초기에는 비선점형(협력적)으로 동작하여 버그 시 무한 루프에 빠졌다. 하지만 Go 1.14부터는 백그라운드의 sysmon 스레드가 너무 오래 CPU를 먹는 고루틴에 강제로 비동기 시그널(SIGURG)을 쏴서 탈취하는 '유저 스페이스 레벨의 선점형 스케줄링'을 도입하여 언어 런타임 자체의 안정성을 OS 급으로 끌어올렸다.
  • eBPF를 통한 선점 로직의 마이크로 컨트롤: 리눅스 커널의 고정된 스케줄링 정책을 벗어나, 클라우드 워크로드의 특성에 맞춰 "이 파드(Pod)는 선점하지 마, 저 컨테이너는 1ms마다 선점해"라는 초정밀 스케줄링 정책을 eBPF로 런타임에 동적 삽입하는 기술이 하이퍼스케일러들의 비밀 무기가 되고 있다.

결론

선점(Preemption)과 비선점(Non-Preemption)의 차이는 단순히 CPU를 누가 놓느냐의 차이가 아니라, "운영체제와 애플리케이션 중 누구에게 시스템의 통제 권력을 쥐여줄 것인가"에 대한 철학적 결단의 산물이다. 현대 IT 생태계는 애플리케이션의 신뢰성을 부정하고 강력한 OS의 강제 권력(선점형 타이머)을 채택함으로써, 악성코드나 버그가 시스템 전체를 무너뜨리는 것을 완벽하게 막아냈다. 비록 그 대가로 락(Lock)과 레이스 컨디션이라는 동시성의 지옥이 열렸지만, 그것이 수십억 명이 스마트폰 하나로 백 가지 앱을 동시에 돌릴 수 있게 만든 가장 위대한 기회비용이었음은 틀림없다.

Race Condition (경쟁 조건)선점형 환경에서, 공유 변수를 읽고 쓰던 중에 강제로 CPU를 뺏기면서 발생하는 데이터 오염 현상
