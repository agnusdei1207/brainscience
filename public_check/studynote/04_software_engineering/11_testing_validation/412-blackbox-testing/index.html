0. 핵심 인사이트

핵심: 해부용 메스로 속을 까보는 개발자 시점이 아니라, 자동차 엔진이 어떻게 도는지는 알 바 없고 "액셀(입력)을 밟으면 차가 100km/h로 가는가(출력)?"만 오직 겉 박스 버튼으로만 확인하는 사용자 시점의 검증이다. 2. 가치: 아무리 내부 C언어 코드 구조나 알고리즘이 완벽하게 100% 짜여 있다고 한들, 처음 고객이 원했던 요구사항 문서(명세서)와 다르게 동작한다면 무용지물이므로 이를 철저하게 잡아내는 족집게 역할을 한다. 3. 판단 포인트: 테스트를 설계할 때 소스코드를 참조해서 짠다면 그것은 반칙이다. 오직 '사용자 메뉴얼, 요구명세서, 유스케이스' 문서를 통해서만 입력 대표값, 경갓값, 논리 조합 등을 추론해 내는 기법(동등 분할 등)을 익히는 것이 핵심이다.

📝 모범 답안

1. 개요 및 필요성

소프트웨어를 테스트할 때 크게 두 개의 파벌이 존재합니다. 하나는 코드를 현미경으로 보면서 1줄 1줄 피가 흐르듯 테스트하는 화이트박스, 또 다른 하나는 아예 코드는 안 보고 겉껍질을 감싸고 작동시켜 보는 블랙박스(Black-box) 파벌입니다.

개발자가 화이트박스를 주장하며 "제 코드는 수학적으로 오류 확률이 제로입니다."라고 말해도, 고객이 "네 수학은 맞는데, 로그인 버튼을 누르니까 메인 화면으로 안 가고 회원가입 창이 뜨잖아요!"라고 화를 내는 상황이 바로 명세(Specification)의 불일치입니다. 블랙박스 테스트는 이 껍데기 박스(소프트웨어) 속 안에 기어가 들어있든 외계인이 들어있든 관심 없습니다. 오로지 **"명세서에 a라는 지폐를 넣으면 콜라가 나온다"**라고 쓰여 있으니, 정말 a를 넣어서 콜라가 나오는지 100번 눌러보고, 일부러 수표를 넣어보고, 돌멩이를 넣어봐서 뱉어내는가 확인하는 작업입니다.

  • 📢 섹션 요약 비유: 이 상자 안에 마법사가 숨어서 요리를 하는지, 로봇이 요리를 하는지는 내 알 바 아닙니다. 레시피 북(명세서)에 "10원 넣으면 핫도그 나온다"라고 적혀 있으니, 10원 넣어서 핫도그 나오는지만 입구와 출구에서 감시하는 무서운 평가단입니다.

2. 구성요소

블랙박스는 입력값을 넣어서 테스트를 해야 하는데, "비밀번호는 1~10자리 숫자"라고 할 때, 1부터 9999999999까지 수백억 번을 입력해 볼 수는 없습니다(무한 테스트의 딜레마). 따라서 블랙박스 전문가(QA)들은 이 무한한 우주의 입력값을 똑똑한 공식으로 **압축해서 대표선수만 뽑아 넣는 '기법(Techniques)'**을 발명해 냈습니다.

  1. 동등 분할 (Equivalence Partitioning)
    • 똑같은 결과를 낼 것 같은 애들을 한 반(그룹)으로 묶어서 반장 1명씩만 뽑아 테스트합니다. (예: 1~100점 합격 입력 시 50점 하나만 넣기)
  2. 경계값 분석 (Boundary Value Analysis)
    • 버그의 90%는 문지방(경계)에서 터집니다. 100점 합격 기준점일 때 어중간한 값이 아니라 딱 '99, 100, 101' 이렇게 살떨리는 절벽 값들만 조준 사격합니다.
  3. 결정 테이블 (Decision Table) 및 상태 전이 (State Transition)
    • VVIP 회원이면서 현금결제를 했는데 마일리지는 10점 이하일 때 등등... 엄청나게 꼬인 비즈니스 논리표를 2차원 매트릭스로 그려 누락되는 스위치 조합이 없게 촘촘히 밟아봅니다.
  • 📢 섹션 요약 비유: 10만 명 군인(입력값)의 키가 얼마인지 다 잴 시간이 없으니까, "소대별로 한 명씩 나와(동등 분할)", "줄 맨 앞 한 명 맨 뒤 한 명 나와봐(경계값)"라며 효율성의 극한을 뽐내는 통계적 발췌 기술입니다.

3. 구조 및 동작 원리

블랙박스 테스트가 위대하기 위해서는 전제 조건이 하나 있습니다. 박스 안에 도면이 없으니, 명세서(요구사항) 자체가 완벽하게 쓰여 있어야 합니다. "게시판에 글이 적당히 예쁘게 올라갈 것"이란 명세서로는 블랙박스 테스터가 결코 테스트를 설계할 수 없습니다. "게시판 제목은 UTF-8 100바이트 이하일 때 저장성공, 초과 시 오류 메시지 팝업"처럼 깐깐한 수학적 조건이 있어야 하죠.

그래서 블랙박스 TC(테스트 케이스) 명세표의 맨 우측에는 항상 **명세서 추적 ID (Traceability)**칸이 쌍으로 묶여 있습니다. "제가 이 테스트를 실패시킨 이유는, 요구사항 번호 REQ-023번의 3조 2항을 위배했기 때문입니다."라며 법정 증거처럼 들이밀 수 있게 만드는 것입니다.

  • 📢 섹션 요약 비유: 경찰이 범인을 체포(버그 보고)하려면 단순히 기분이 나빠서가 아니라 막무가내 건달(코드)에게 "여기 법전(명세서) 4조 1항에 침 뱉으면 벌금이라 적혀있다!"라고 확실한 문서 근거를 들이밀어 항복시키는 원동력입니다.

4. 비교 및 트레이드오프

개발팀이 단위 테스트(Unit Test)로 자신들의 코드 블록 내부를 하얗게 밝히는 화이트박스를 아무리 열심히 해도, 최종 승인(Sign-off)을 나가는 고객 인수 환경(UAT, OAT)에서는 100% 무조건 블랙박스 테스트가 지배합니다.

시스템을 조립해 만든 통합 환경이나 UI 화면 위에는 소스코드를 까볼 환경도, 콘솔 화면도 보이지 않기 때문입니다. 그래서 실무에서는 보통 개발자 티타임이나 슬랙에서는 블랙박스와 화이트박스가 섞여서 일하지만, 마지막 골키퍼인 독립된 품질보증(QA) 부서의 모니터 앞에서는 절대적으로 화면 UI 지향적이고 로그 결과 확인 중심인 블랙박스 테스트가 유일무이한 최종 무기로 군림합니다.

  • 📢 섹션 요약 비유: 요리사(개발자)는 국물 내부 염도를 시약으로 재어보고 재료 분자(소스코드)를 연구하며 화이트박스 검사를 하지만, 최종 음식 평론가(QA와 블랙박스)는 그냥 입에 넣고 "오, 짜네. 점수 0점." 하고 겉껍질의 맛으로만 냉혹하게 평가해 버리는 분업의 묘미입니다.

5. 실무 적용 및 최적화 기법

코드 내부 로직에 눈감아버리는 블랙박스(명세 기반) 테스트의 철학은, 숲을 보지 못하고 나무의 잔가지(코드 최적화)에 집착하던 개발자들에게 "고객이 원했던 원래 모습이라는 게 무엇인가"를 강력하게 환기해 줍니다. 내부 로직이 아무리 현란해도 출력물이 틀리면 쓰레기다라는 진리를 바탕으로, 사용자 관점의 가치를 사수하고 기획 의도와 구현물 간의 간극을 좁히는 테스트 공학의 굳건한 우뇌(사용자 감성, 결과 지향)로 자리 잡고 있습니다.

  • 📢 섹션 요약 비유: 시계 속 톱니바퀴 1만 개가 기름칠 쫙쫙 되어 완벽하게 돌고 있다고 시계 장인이 아무리 우겨도, 겉면 바늘이 아침 9시인데 밤 9시를 가리키면 손님에겐 그냥 고장 난 시계(버그)라는 잔인하고 명쾌한 팩트 체크 폭행입니다.

👶 어린이를 위한 3줄 비유 설명

  1. 마술 상자가 하나 있는데, 그 속에서 비둘기가 나오는지 로봇 팔이 나오는지는 꽉 잠겨서 까맣고 전혀 안 보여요.
  2. 하지만 설명서에 "파란 동전을 넣으면 막대 사탕이 나온다"라고 적혀 있으니까, 속은 신경 안 쓰고 밖에서 내가 파란 동전을 진짜 넣어서 사탕이 나오는지만 확인해요.
  3. 속 설계도를 보지 않고, 밖에서 입력과 결과만 맞는지 100번 눌러보며 설명서대로 잘되는지 체크하는 깐깐한 시어머니 같은 검사법이에요!
