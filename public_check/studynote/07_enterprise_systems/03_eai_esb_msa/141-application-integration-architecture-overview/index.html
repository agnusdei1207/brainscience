0. 핵심 인사이트

핵심: 애플리케이션 통합 아키텍처의 본질은 개별 시스템을 많이 연결하는 것이 아니라, 이기종 시스템 사이의 데이터·기능·프로세스 흐름을 통제 가능한 연결 구조로 재설계하는 데 있다. 비유: 통합 아키텍처는 건물마다 제각각 깔린 임시 전선을 정리해, 중앙 배전 규칙과 표준 전압을 갖춘 전력망으로 바꾸는 작업에 가깝다.

📝 모범 답안

1. 개요 및 필요성

기업 정보시스템은 ERP(Enterprise Resource Planning), CRM(Customer Relationship Management), SCM(Supply Chain Management), 그룹웨어, 레거시 메인프레임처럼 서로 다른 기술과 데이터 모델 위에서 개별 최적화되어 발전해 왔다. 문제는 업무가 부서별 시스템 경계를 넘을 때 발생한다. 주문은 영업 시스템에서 발생하지만 재고는 물류 시스템이 알고, 매출 인식은 회계 시스템이 처리하며, 고객 알림은 채널 시스템이 담당한다. 시스템이 분리될수록 업무는 오히려 연결되어야 한다.

애플리케이션 통합 아키텍처는 이 연결을 임시 인터페이스의 집합이 아니라 설계 가능한 구조로 바꾸기 위해 등장했다. 초기에는 빠른 개발을 위해 점대점(Point-to-Point)으로 직접 연동했지만, 시스템 수가 늘면서 연결 수가 폭증하고 변경 영향 분석이 불가능해졌다. 이후 중앙 Hub, 메시지 브로커(Message Broker), ESB(Enterprise Service Bus), API 중심 구조, MSA(Microservice Architecture)와 이벤트 기반 통합으로 진화했다.

통합 아키텍처가 없다면 데이터 중복 입력, 상태 불일치, 장애 전파, 인터페이스 난립, 운영 책임 불명확이 동시에 발생한다. 따라서 통합은 단순 연결 기술이 아니라 기업 운영 복잡도를 제어하는 구조적 장치다.

2. 구성요소

구성요소역할핵심 포인트
업무 시스템(Provider/Consumer)데이터를 생산·소비하거나 기능을 호출통합 대상은 애플리케이션 자체가 아니라 그 경계와 계약
인터페이스 계약메시지 형식, API 명세, 이벤트 스키마 정의기술보다 계약 안정성이 장기 유지보수성에 더 중요
어댑터(Adapter)시스템별 프로토콜·포맷 차이 흡수레거시 연계에서는 어댑터 품질이 통합 성공을 좌우
중재 계층(Mediation)라우팅, 변환, 검증, 보안 적용Hub·Broker·ESB·Gateway가 이 역할을 수행
전송 채널HTTP, MQ, 파일, DB 링크, 이벤트 버스 제공동기·비동기 선택이 결합도와 복원력에 직접 영향
운영·관제추적, 재처리, 모니터링, SLA 관리통합은 개발보다 운영 통제가 더 중요
거버넌스표준 데이터 모델, 버전, 보안 정책 관리통합이 많아질수록 기술보다 통제 규칙이 우선

이 요소들은 독립적으로 존재하지 않는다. 업무 시스템은 자신의 내부 구조를 노출하지 않고 계약을 통해 외부와 연결되고, 어댑터는 시스템 고유 포맷을 통합 가능한 형식으로 바꾼다. 중재 계층은 흐름을 제어하며, 전송 채널은 응답 시간과 장애 격리 수준을 결정한다. 마지막으로 운영·거버넌스가 없으면 통합은 구현 직후부터 다시 스파게티 구조로 회귀한다.

3. 구조 및 원리

핵심 조건: 통합 아키텍처는 이기종 시스템 차이를 흡수하면서도 결합도를 낮추고, 메시지 흐름의 책임 주체와 장애 전파 범위를 명확히 분리해야 한다. 또한 업무 중요도에 따라 실시간성, 일관성, 재처리 가능성 사이의 균형을 선택해야 한다.

동작 순서:

  1. 업무 시스템이 이벤트 발생 또는 서비스 호출 필요를 감지한다.
  2. 원천 시스템 포맷을 어댑터가 표준 메시지·API 요청 형태로 변환한다.
  3. 중재 계층이 수신자를 결정하고, 필요한 검증·라우팅·보안 정책을 적용한다.
  4. 전송 채널이 메시지를 대상 시스템 또는 구독자에게 전달한다.
  5. 대상 시스템은 자신의 내부 모델로 다시 변환하여 처리한다.
  6. 결과는 동기 응답, 비동기 이벤트, 재처리 큐, 감사 로그 형태로 운영 계층에 남는다.

핵심은 연결의 수를 줄이는 것만이 아니다. 더 중요한 것은 변화의 방향을 통제하는 것이다. 점대점 구조에서는 시스템 A의 변경이 B, C, D의 인터페이스 수정으로 확산된다. 반면 표준 계약과 중재 계층을 두면 변화는 어댑터 또는 계약 버전에 국한된다. 따라서 통합 아키텍처는 기술 통합이라기보다 변경 파급을 제어하는 구조라고 보는 편이 정확하다.

또한 실시간 통합과 배치 통합의 선택은 구조 원리에 큰 차이를 만든다. 실시간 API는 즉시성이 높지만 가용성 의존성이 커지고, 비동기 메시지는 지연이 있으나 복원력과 확장성이 높다. 현대 아키텍처는 이 둘을 혼합하여 조회는 API, 상태 전파는 이벤트, 대량 정합성 확보는 ETL로 분리하는 방향으로 설계한다.

이 비교에서 중요한 점은 신구 아키텍처의 우열이 아니라 적용 맥락이다. 예를 들어 ETL 중심 데이터 적재는 여전히 중앙형 구조가 유리하고, 대외 채널 확장은 API Gateway가 더 적합하다. 또 메시지 브로커는 ESB를 완전히 대체하는 개념이 아니라, 통합 백본의 분산화된 한 구현으로 볼 수 있다. 따라서 통합 아키텍처는 단일 정답이 아니라 업무 흐름별 조합 문제다.

5. 실무 적용 및 판단

채택 판단은 '우리 회사가 최신 아키텍처를 쓰는가'가 아니라 '어떤 흐름에 어떤 결합 방식을 허용할 것인가'에서 출발해야 한다.

  • 채택 조건
    • 시스템 수가 많고 기술 스택이 이질적일 때
    • 인터페이스 변경 빈도가 높아 영향 통제가 중요할 때
    • 재처리, 감사 추적, 장애 격리가 중요한 업무일 때
    • 데이터 통합, 기능 호출, 프로세스 통합을 분리 설계해야 할 때
  • 회피 또는 축소 조건
    • 시스템 수가 적고 구조가 단순할 때
    • 중앙 미들웨어가 오히려 비용과 복잡도를 키울 때
    • 실시간성과 지연 허용치가 업무별로 명확하지 않을 때

실무 체크리스트:

  • 표준 메시지 모델 또는 API 명세가 존재하는가?
  • 동기 호출 실패 시 대체 흐름과 재시도 정책이 정의되어 있는가?
  • 인터페이스 버전 변경 시 하위 호환 전략이 있는가?
  • 통합 실패를 추적할 관측 지표와 감사 로그가 준비되어 있는가?
  • 통합을 데이터, 애플리케이션, 프로세스 관점으로 분리해 설계했는가?

대표 사례로는 SAP PI/PO 기반 EAI, IBM Integration Bus와 Mule ESB 기반 SOA, Kafka·REST API·iPaaS(Integration Platform as a Service)를 조합한 클라우드 통합 구조가 있다. 최근에는 내부 시스템은 이벤트 기반, 외부 채널은 API 중심, 분석계는 ETL/ELT 중심으로 다층 혼합 설계하는 경우가 많다.

6. 기대효과 및 결론

애플리케이션 통합 아키텍처의 기대효과는 연결 수 감소 그 자체보다, 변경 통제·운영 가시성·업무 자동화·재사용성 향상에 있다. 통합 구조가 잘 설계되면 신규 시스템 도입 시 전체 인터페이스를 다시 짜지 않고도 확장할 수 있으며, 장애 발생 시 실패 지점을 빠르게 격리하고 복구할 수 있다.

다만 어떤 형태든 통합 계층은 또 하나의 복잡도를 만든다. 표준이 약하면 통합층은 금세 누더기가 되고, 표준이 지나치게 강하면 변화 대응이 느려진다. 결국 좋은 통합 아키텍처는 모든 연결을 한 기술로 통일하는 구조가 아니라, 업무 특성에 따라 적절한 결합 방식과 운영 규율을 분리하는 구조다. 전통적 EAI에서 현대 이벤트 기반 구조로의 발전은 기술 교체가 아니라 통합 책임의 분산과 계약 중심 설계의 강화라고 정리할 수 있다.
