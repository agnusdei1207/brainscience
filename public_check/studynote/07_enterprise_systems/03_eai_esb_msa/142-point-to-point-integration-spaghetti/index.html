0. 핵심 인사이트

핵심: P2P(Point-to-Point) 통합은 가장 빠르게 시작할 수 있지만, 시스템 수가 늘어날수록 인터페이스가 기하급수적으로 증가해 변경과 장애가 전체 구조를 얽어매는 스파게티 구조를 만든다. 비유: 처음에는 두 방을 전선 하나로 연결하면 되지만, 방이 늘어날수록 모든 방 사이에 각자 전선을 따로 깔아 건물 전체가 얽혀 버리는 상황과 같다.

📝 모범 답안

1. 개요 및 필요성

점대점 통합은 시스템 A가 시스템 B를 직접 호출하거나 파일을 주고받는 식의 1:1 연결 구조다. 초기 구축에서는 별도 미들웨어 없이도 빠르게 구현할 수 있고, 시스템 수가 매우 적다면 가장 단순한 방식이기도 하다. 그래서 많은 기업에서 첫 번째 통합은 대부분 P2P로 시작한다.

문제는 이 단순함이 규모 확장에 취약하다는 점이다. 시스템이 n개일 때 상호 연동 인터페이스 수는 일반적으로 n(n-1)/2 수준까지 증가한다. 방향이 서로 다르거나 포맷 변환 어댑터가 별개라면 실제 관리 대상은 이보다 더 많아진다. 결국 하나의 시스템 변경이 다수 연결에 파급되고, 장애 원인 추적도 어려워진다.

따라서 P2P는 '나쁜 구조'라기보다 적용 범위가 매우 제한된 구조다. 소규모·단기 통합에서는 합리적이지만, 기업 전사 통합의 기본 구조로 삼기에는 유지보수성과 운영성이 너무 낮다.

2. 구성요소

구성요소역할핵심 포인트
송신 시스템데이터를 보내거나 기능 호출상대 시스템 주소와 계약을 직접 알아야 함
수신 시스템요청 수신 및 처리호출자별 인터페이스 차이를 흡수해야 할 수 있음
개별 인터페이스파일, DB 링크, API, 소켓 등 직접 연결인터페이스마다 규칙이 달라 표준화가 어려움
포맷 변환 로직송신·수신 시스템 내부 또는 중간 스크립트에 존재재사용보다 복제가 많아짐
예외 처리호출 실패, 타임아웃, 재시도 처리시스템별로 제각각 구현되는 경우가 많음
운영 문서연결 대상, 주기, 담당자 관리문서가 실제 구조를 못 따라가면 운영 리스크 급증

P2P의 핵심 문제는 구성요소가 적어서가 아니라, 각 연결이 독립적으로 진화한다는 데 있다. 즉 모든 인터페이스가 작은 시스템처럼 행동한다. 포맷, 인증, 재시도, 예외 처리, 스케줄이 연결별로 달라지기 때문에, 전체 관점에서 보면 표준이 없는 작은 통합들이 누적되어 복잡도가 폭증한다.

3. 구조 및 원리

핵심 조건: P2P는 통합 대상 수가 적고 변경 주기가 낮아야 하며, 인터페이스별 계약을 사람이 추적 가능한 범위 안에 둘 수 있어야 한다. 시스템 수가 늘거나 데이터 모델 변화가 잦아지면 구조적 한계가 급격히 드러난다.

동작 순서:

  1. 송신 시스템이 특정 수신 시스템의 주소와 인터페이스 계약을 직접 참조한다.
  2. 송신 측 또는 별도 스크립트가 수신 시스템이 이해할 수 있는 포맷으로 데이터를 변환한다.
  3. 직접 호출 또는 파일 전송을 수행한다.
  4. 수신 시스템이 처리 결과를 응답하거나 후속 파일을 생성한다.
  5. 실패 시 각 연결별 재시도·보정 로직이 별도로 수행된다.
P2P 연결 구조

[A] <------> [B]
 | \          |
 |  \         |
 |   \        |
 v    v       v
[C] <------> [D]

연결 수 예시
n = 4  -> 4*3/2 = 6
n = 10 -> 10*9/2 = 45
n = 20 -> 20*19/2 = 190

이 구조가 위험한 이유는 연결 수 자체보다 변경 영향의 비가시성에 있다. 예를 들어 고객 코드 체계가 변경되면 ERP와 직접 연결된 CRM, 물류, 정산, DW(Data Warehouse) 적재 스크립트를 모두 찾아 수정해야 한다. 그러나 실제 운영에서는 이런 연결이 문서화되지 않은 경우가 많아, 일부만 수정되어 데이터 불일치가 발생한다.

또한 장애는 연쇄적으로 전파된다. 동기 호출 방식에서는 수신 시스템 장애가 송신 시스템의 타임아웃으로 이어지고, 다시 상위 업무 흐름 정지로 확산된다. 비동기 파일 기반이라 해도 파일 누락, 스케줄 충돌, 중복 적재 문제가 인터페이스마다 개별적으로 발생한다. 즉 P2P는 연결을 빠르게 만들지만, 통합 운영의 복잡도를 구조적으로 외부화한다.

4. 비교 및 연결

비교 항목P2PHub-and-SpokeESB/Message Broker

연결 수 증가 대응매우 취약개선됨우수

P2P는 중앙 미들웨어 도입 전 단계로 자주 등장하지만, 완전히 사라지는 구조는 아니다. 소규모 SaaS 연동, 일회성 마이그레이션, 개발 환경 임시 연결에는 여전히 유효하다. 다만 기업 핵심 업무 흐름의 기본 패턴으로 채택하면 향후 EAI나 ESB 도입 비용이 더 커지는 경우가 많다. 즉 P2P는 '출발점으로는 가능하지만 종착점으로는 위험한 구조'로 이해해야 한다.

5. 실무 적용 및 판단

적합한 경우:

  • 통합 대상이 2~3개 수준이고 수명 주기가 짧을 때
  • PoC(Proof of Concept)나 임시 데이터 이관처럼 빠른 연결이 중요할 때
  • 복잡한 중앙 미들웨어보다 직접 API 호출이 더 단순할 때

피해야 하는 경우:

  • 시스템 추가 가능성이 높을 때
  • 인터페이스 변경이 잦거나 조직이 여러 팀으로 나뉘어 있을 때
  • 운영 추적, 감사 로그, 재처리가 중요한 업무일 때

실무 체크리스트:

  • 현재 연결 수와 1년 후 예상 연결 수를 계산했는가?
  • 인터페이스 목록·담당자·재처리 절차가 문서화되어 있는가?
  • 공통 데이터 코드 변경 시 영향 시스템을 식별할 수 있는가?
  • 동기 호출 실패가 상위 서비스 장애로 이어지지 않도록 차단 장치가 있는가?

소규모 스타트업의 내부 백오피스 연동처럼 변화 범위가 좁다면 P2P는 효율적이다. 반면 금융·제조처럼 조직과 시스템이 많은 환경에서는 짧은 성공이 장기적 부채로 바뀌는 대표 사례가 된다.

6. 기대효과 및 결론

P2P의 장점은 단순성과 빠른 구현이다. 별도 플랫폼 투자 없이도 연동을 시작할 수 있고, 개발자가 구조를 직관적으로 이해하기 쉽다. 그러나 그 장점은 대상 수가 적을 때만 유지된다. 규모가 커지면 인터페이스 증식, 중복 로직, 장애 전파, 문서 불일치가 동시에 발생해 전체 통합 비용이 오히려 폭증한다.

결론적으로 P2P는 소규모 문제에는 정답일 수 있지만, 대규모 통합의 기본 전략이 될 수는 없다. 시험 답안에서는 'P2P는 단순하지만 n(n-1)/2 복잡도로 인해 스파게티 구조가 되고, 이 한계를 해결하기 위해 EAI Hub와 ESB가 등장했다'는 인과를 명확히 연결하는 것이 중요하다.
