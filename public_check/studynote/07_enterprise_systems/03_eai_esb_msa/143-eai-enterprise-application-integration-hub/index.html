0. 핵심 인사이트

핵심: EAI(Enterprise Application Integration)의 허브 방식은 각 시스템을 중앙 통합 허브에만 연결하게 하여, 개별 시스템 간 직접 결합을 중앙의 변환·라우팅 규칙으로 치환하는 구조다. 비유: 모든 항공편을 도시별 직항으로 연결하는 대신, 허브 공항을 통해 환승시키는 방식과 같다. 노선 수는 줄지만 허브의 성능과 안정성이 전체 품질을 좌우한다.

📝 모범 답안

1. 개요 및 필요성

EAI는 기업 내부의 이기종 애플리케이션을 통합하기 위한 전통적 접근이다. 그중 허브 방식은 P2P의 인터페이스 난립 문제를 해결하기 위해 등장했다. 개별 시스템은 더 이상 서로를 직접 알 필요가 없고, 중앙 허브가 메시지 변환, 라우팅, 오케스트레이션을 담당한다.

이 방식이 필요한 이유는 기업 시스템이 기능적으로는 연결되어 있으나 기술적으로는 분절되어 있기 때문이다. ERP, 인사, 생산, 회계, 물류 시스템은 같은 주문 흐름을 공유하지만, 데이터 코드 체계와 인터페이스 방식은 모두 다르다. 허브가 없다면 새 시스템이 들어올 때마다 기존 모든 시스템과 연결을 추가해야 한다.

EAI 허브는 이러한 복잡도를 중앙 집중적으로 수용한다. 즉 각 시스템의 복잡도를 허브로 모아 전체 네트워크 복잡도를 줄인다. 이는 운영 통제와 표준화 측면에서 큰 장점이 있지만, 동시에 허브가 기업 통합의 병목이 되는 구조적 특성도 만든다.

2. 구성요소

구성요소역할핵심 포인트

이 구조에서 중요한 것은 어댑터와 정규 모델(Canonical Data Model)의 조합이다. 어댑터는 시스템 고유 프로토콜을 허브 내부 표준으로 연결하고, 허브는 이를 공통 모델에 맞춰 해석한다. 따라서 새 시스템 추가 시 기존 모든 시스템을 수정하는 대신, 새 어댑터 하나와 허브 매핑 규칙만 정의하면 된다.

3. 구조 및 원리

핵심 조건: EAI 허브는 중앙에서 변환 규칙과 경로를 통제할 수 있어야 하며, 각 시스템이 허브와의 계약만 지키도록 구조를 단순화해야 한다. 이때 허브 내부에는 표준 데이터 모델과 강한 운영 통제 체계가 필요하다.

동작 순서:

  1. 원천 시스템이 허브 어댑터로 데이터를 보낸다.
  2. 어댑터가 시스템 고유 포맷을 허브 입력 형식으로 캡슐화한다.
  3. 허브가 메시지를 Canonical Data Model로 정규화한다.
  4. 라우팅 규칙이 대상 시스템과 전달 순서를 결정한다.
  5. 대상 어댑터가 각 시스템 고유 포맷으로 재변환하여 전달한다.
  6. 처리 결과와 오류 정보는 허브 관제 계층에 집중된다.

허브 방식의 핵심 논리는 연결 수를 줄이는 대신 변환 책임을 집중시키는 데 있다. P2P에서는 A와 B, A와 C, B와 C가 각각 변환 규칙을 가진다. 허브에서는 A→표준, 표준→B만 정의하면 되므로 시스템별 책임 경계가 명확해진다. 그러나 변환과 라우팅이 모두 허브에 쌓이면 허브 성능, 장애 복구, 배포 통제가 통합 전체의 품질을 결정하게 된다.

따라서 EAI 허브는 기술 구조이면서 동시에 운영 구조다. 허브에 들어오는 모든 메시지를 추적·재처리·감사할 수 있다는 점은 강점이지만, 반대로 허브가 조직의 승인 병목이 되어 변화 속도를 늦출 수 있다.

EAI 허브는 ESB의 전 단계이자 기반 개념으로 이해할 수 있다. ESB도 변환과 라우팅을 수행하지만, 서비스 계약과 개방형 표준을 더 적극적으로 활용하고 분산형 구성을 취할 수 있다. 반면 EAI 허브는 기업 내부 데이터 통합, 레거시 연결, 중앙 운영 통제에 더 강점을 가진다.

5. 실무 적용 및 판단

적합한 경우:

  • 레거시 시스템이 많고 프로토콜 이질성이 큰 경우
  • 전사 공통 데이터 표준을 중앙에서 통제해야 하는 경우
  • 운영 관제와 감사 추적을 중앙 집중형으로 수행해야 하는 경우

주의할 점:

  • 허브가 단일 장애점(SPOF)이 되지 않도록 이중화·클러스터링이 필요하다.
  • 허브 규칙이 비대해지면 변경 요청이 모두 통합팀으로 몰려 병목이 된다.
  • Canonical Data Model이 과도하게 추상화되면 오히려 변화 수용성이 떨어질 수 있다.

실무 체크리스트:

  • 핵심 업무코드 표준이 허브 내부에서 통일되어 있는가?
  • 신규 시스템 추가 시 기존 매핑에 영향이 없는가?
  • 허브 장애 시 우회 또는 재처리 전략이 있는가?
  • 운영 조직이 메시지 추적·재전송·보정 권한을 갖고 있는가?

대표 사례로는 TIBCO, IBM WebSphere 계열 통합 플랫폼, SAP PI/PO 등이 있다. 이들은 전통적 전사 통합 환경에서 매우 강력했지만, 클라우드와 MSA 확산 이후에는 API 관리와 이벤트 기반 통합으로 일부 역할이 분산되고 있다.

6. 기대효과 및 결론

EAI 허브는 시스템 간 직접 결합을 제거하고, 통합 규칙을 중앙에서 관리 가능하게 만든다는 점에서 기업 통합의 중요한 전환점이다. 인터페이스 수를 줄이고, 운영 관측성을 높이며, 신규 시스템 도입 시 통합 비용을 예측 가능하게 만든다.

그러나 그 효과는 허브 품질에 집중된다. 허브 설계가 과도하게 비대해지면 중앙 통제의 장점이 중앙 병목의 단점으로 바뀐다. 따라서 EAI 허브는 '모든 것을 중앙이 해결하는 만능 구조'가 아니라, 표준화와 운영 통제의 이점을 얻는 대신 병목과 확장성 문제를 감수하는 아키텍처라는 균형 잡힌 이해가 필요하다.
