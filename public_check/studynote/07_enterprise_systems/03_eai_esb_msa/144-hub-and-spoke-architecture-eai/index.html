0. 핵심 인사이트

핵심: Hub-and-Spoke 아키텍처는 중앙 Hub가 통합 규칙을 수행하고, 각 Spoke가 시스템별 연결 특성을 흡수함으로써 연결 복잡도를 구조적으로 줄이는 EAI의 대표 구현 방식이다. 비유: 자전거 바퀴에서 중심 축이 회전을 통제하고, 각 살(Spoke)이 외곽 림과 연결되듯이 중앙 통제와 개별 접속을 분리한 구조다.

📝 모범 답안

1. 개요 및 필요성

Hub-and-Spoke는 EAI를 가장 직관적으로 설명하는 아키텍처다. 기업 내부 시스템은 기술 스택과 데이터 형식이 모두 다르므로, 모든 시스템 사이를 직접 연결하면 금세 복잡도가 통제 불가능한 수준으로 증가한다. 이때 중앙 Hub에만 연결하게 만들면 전체 연결 수를 줄이고 통합 정책을 한곳에서 관리할 수 있다.

이 구조가 필요한 이유는 통합의 본질이 단순 전달이 아니라 차이의 흡수에 있기 때문이다. 예를 들어 ERP는 코드값 중심, CRM은 고객 중심, 물류는 이벤트 중심 모델을 사용한다. Hub-and-Spoke 구조는 이런 차이를 Hub 내부의 정규 모델과 변환 로직으로 모아 시스템 간 직접 협상을 제거한다.

즉 Hub-and-Spoke는 '모든 시스템을 중앙에 묶는다'는 단순한 구조가 아니라, 통합 책임을 중앙 Hub와 시스템별 Spoke로 명확히 분할하는 설계다.

요소 간 상호작용은 분명하다. Spoke는 '연결의 복잡도'를 맡고, Hub는 '통합의 복잡도'를 맡는다. 이 분할 덕분에 개별 시스템은 Hub 계약만 따르면 되고, Hub는 기업 표준을 중심으로 전체 흐름을 제어할 수 있다. 다만 Hub와 Rule Repository가 비대해지면 중앙 집중의 부작용도 함께 커진다.

3. 구조 및 원리

핵심 조건: Hub-and-Spoke는 Hub 내부 표준이 안정적이어야 하며, Spoke가 시스템 변화의 충격을 흡수해야 한다. 또한 Hub는 변환·라우팅을 중앙화하되, 처리량과 가용성을 확보할 수 있어야 한다.

동작 순서:

  1. 각 시스템은 자신의 Spoke Adapter를 통해 Hub에 접속한다.
  2. Spoke는 원천 시스템의 포맷과 프로토콜을 수신해 Hub 표준 형식으로 변환한다.
  3. Hub는 메시지를 Canonical Model로 해석하고, Rule Repository를 조회한다.
  4. Hub가 목적지, 전달 순서, 필요 변환을 결정한다.
  5. 대상 Spoke가 목적 시스템 포맷으로 메시지를 재구성하여 전달한다.
  6. 실패 메시지는 Queue 또는 Error Store로 이동해 재처리한다.
Hub-and-Spoke 구조

[System A]--Spoke A--\
[System B]--Spoke B---\
[System C]--Spoke C----> [Hub]
[System D]--Spoke D---/    |
                           +--> [Canonical Model]
                           +--> [Routing Rules]
                           +--> [Transform Engine]
                           +--> [Queue / Error Store]

이 구조의 중요한 원리는 변환 지점의 고정이다. P2P에서는 시스템 쌍마다 변환이 일어나지만, Hub-and-Spoke에서는 Spoke에서 Hub 표준으로, 다시 Hub 표준에서 목적 시스템 형식으로만 변환한다. 그 결과 신규 시스템 추가 시 기존 모든 시스템에 영향을 주지 않는다.

그러나 이 장점은 Hub 설계 품질에 달려 있다. Canonical Model이 현실 데이터를 제대로 표현하지 못하면 Spoke가 비정상적으로 복잡해지고, Hub 규칙이 지나치게 많아지면 중앙 변경 병목이 발생한다. 따라서 Hub-and-Spoke는 연결 구조를 단순화하는 대신, 표준 모델 설계의 중요성을 극대화하는 구조다.

Hub-and-Spoke는 메시지 브로커보다 더 강한 중앙 통제를 제공하고, ESB보다 구현 개념이 단순하다. 반면 분산성과 자율성은 낮다. 따라서 조직이 중앙 통합팀 중심으로 운영되는지, 서비스 팀 자율성을 중시하는지에 따라 적합성이 달라진다.

5. 실무 적용 및 판단

적합한 경우:

  • 전사 공통 코드와 데이터 체계가 중요할 때
  • 레거시 시스템이 많아 중앙 어댑터 관리가 필요한 경우
  • 통합 운영 조직이 별도로 존재하고 승인 절차가 강한 경우

주의 사항:

  • Hub 이중화, 스케일아웃, 큐 기반 완충이 설계되어야 한다.
  • Spoke 수가 많아질수록 어댑터 생명주기 관리가 중요해진다.
  • 허브에 업무 로직까지 과도하게 넣으면 통합층이 새로운 모놀리식이 된다.

실무 체크리스트:

  • Spoke별 소유 조직과 변경 책임이 명확한가?
  • Canonical Model이 실제 업무 용어와 맞는가?
  • Hub 장애 시 처리 중 메시지의 유실 방지 전략이 있는가?
  • 통합 로직과 업무 로직의 경계가 구분되는가?

금융·제조·공공기관처럼 레거시 비중이 큰 조직에서는 여전히 유효하다. 다만 클라우드 네이티브 환경에서는 중앙 Hub를 최소화하고 API, Broker, Event Bus로 역할을 분리하는 방향이 늘고 있다.

6. 기대효과 및 결론

Hub-and-Spoke의 가장 큰 효과는 연결 구조를 예측 가능하게 만든다는 점이다. 시스템이 늘어나도 각 시스템은 Hub 하나와만 연결하면 되므로 확장 시 구조적 혼란이 줄어든다. 또한 중앙 관제를 통해 오류 추적과 보정이 쉬워진다.

하지만 중앙 집중의 비용 역시 분명하다. Hub가 성능 병목, 승인 병목, 기술 병목이 될 수 있으며, 표준 모델이 잘못 설계되면 오히려 전체 변화가 느려진다. 따라서 Hub-and-Spoke는 스파게티 구조를 정리하는 데 매우 효과적이지만, 장기적으로는 ESB나 이벤트 기반 구조로 기능을 재분배할 필요가 있는 과도기적 중심 구조로 이해하는 것이 적절하다.
