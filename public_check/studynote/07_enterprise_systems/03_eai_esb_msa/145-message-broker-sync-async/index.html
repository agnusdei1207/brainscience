0. 핵심 인사이트

핵심: 메시지 브로커(Message Broker)는 송신자와 수신자 사이에 전달 책임을 분리해, 동기 호출의 즉시성 한계와 비동기 처리의 복원력 장점을 선택적으로 활용할 수 있게 하는 통합의 완충 계층이다. 비유: 직접 통화는 상대가 받아야 대화가 성립하지만, 브로커는 우체국처럼 메시지를 맡아 두었다가 적절한 방식으로 배달해 주는 구조다.

📝 모범 답안

1. 개요 및 필요성

기업 통합에서 가장 먼저 부딪히는 문제는 '바로 응답이 필요한가, 아니면 나중에 처리해도 되는가'이다. 동기(Synchronous) 호출은 요청-응답이 즉시 이어져 사용자 경험이 직관적이지만, 상대 시스템 가용성에 강하게 의존한다. 반면 비동기(Asynchronous) 통합은 응답을 기다리지 않고 메시지를 맡긴 뒤 후속 처리를 분리할 수 있어 확장성과 복원력이 높다.

메시지 브로커는 이 비동기 통합을 실현하는 핵심 인프라다. 생산자(Producer)는 브로커에 메시지만 맡기고, 소비자(Consumer)는 자신의 속도에 맞게 처리한다. 이를 통해 피크 트래픽 흡수, 장애 격리, 재처리, 순서 제어가 가능해진다.

현대 통합 구조에서는 동기와 비동기를 대립적으로 보지 않는다. 조회·승인처럼 즉시 응답이 필요한 업무는 동기 API가 적합하고, 주문 후속 처리·정산·알림·이벤트 전파는 비동기 메시지가 적합하다. 메시지 브로커는 이 둘 사이의 역할 분리를 가능하게 한다.

2. 구성요소

구성요소역할핵심 포인트
Producer메시지를 생성해 브로커로 전송수신자 상태를 직접 알 필요가 없음

이 구성요소는 단순 전달을 넘어서 처리 책임을 분산한다. Producer는 메시지 생성 책임만 지고, 브로커는 전달과 저장 책임을 지며, Consumer는 업무 처리 책임을 진다. 이 분리 덕분에 송신자와 수신자의 처리 속도, 배포 시점, 장애 상태가 서로 직접 얽히지 않는다.

3. 구조 및 원리

핵심 조건: 메시지 브로커는 생산자와 소비자의 시간적 결합을 끊어야 하며, 최소 1회 이상 전달, 중복 처리 허용, 순서 보장 범위 같은 메시징 계약이 사전에 정의되어 있어야 한다.

동작 순서:

  1. Producer가 메시지를 생성하고 브로커에 게시한다.
  2. 브로커는 메시지를 큐 또는 토픽에 저장하고 전달 대상을 관리한다.
  3. Consumer는 자신의 처리 속도에 맞게 메시지를 가져오거나 푸시받는다.
  4. 처리 성공 시 Ack를, 실패 시 Nack 또는 재시도 요청을 보낸다.
  5. 반복 실패 메시지는 DLQ(Dead Letter Queue)로 분리된다.
  6. 필요 시 후속 이벤트를 다시 브로커에 게시해 연쇄 비동기 흐름을 만든다.
동기 vs 비동기 구조 비교

동기 호출
[Client] ---> [Service B]
   |              |
   +---- wait ----+
   (B 장애 시 A도 지연/실패)

비동기 브로커
[Producer] --> [Broker Queue/Topic] --> [Consumer]
                   |        |
                   |        +--> Retry / DLQ
                   +--> Persistence / Ordering

브로커 기반 비동기 통합의 핵심 원리는 시간적 분리와 전달 책임 분리다. 동기 API는 요청 시점에 양쪽 시스템이 동시에 준비되어 있어야 하지만, 브로커는 메시지를 안전하게 저장함으로써 수신자 지연을 흡수한다. 이로 인해 장애 격리, 버퍼링, 병렬 처리라는 장점이 생긴다.

반면 비동기는 즉시 일관성을 약화시킨다. 메시지는 결국 처리되더라도, 현재 시점에는 아직 반영되지 않았을 수 있다. 따라서 실무에서는 멱등성(Idempotency), 중복 소비 방지 키, 재시도 정책, 순서 보장 단위를 반드시 함께 설계해야 한다. 브로커는 만능 해법이 아니라 운영 규율이 필수인 전달 메커니즘이다.

4. 비교 및 연결

항목동기 API메시지 브로커
응답 방식즉시 요청-응답비동기 전달 후 후속 처리
결합도상대 가용성에 의존시간적 결합 완화
장애 전파큼작음
사용자 체감빠른 결과 확인 가능결과 확인 방식 추가 설계 필요
대표 기술REST, gRPCRabbitMQ, ActiveMQ, Kafka, SQS

또한 브로커 내부에서도 MQ형과 로그형이 구분된다. RabbitMQ는 복잡한 라우팅과 큐 중심 처리에 강하고, Kafka는 대량 이벤트 스트림과 순차 로그 처리에 강하다. 따라서 브로커 선택은 '비동기냐 아니냐'보다 전달 패턴과 처리량 특성에 따라 결정해야 한다.

5. 실무 적용 및 판단

적합한 경우:

  • 주문 후속 처리, 알림, 정산, 이벤트 전파처럼 지연 허용이 가능한 업무
  • 수신자 일시 장애를 격리해야 하는 업무
  • 생산자와 소비자의 처리량 차이가 큰 경우
  • 멀티 소비자 배포가 필요한 경우

주의할 점:

  • 소비자가 멱등하게 구현되지 않으면 중복 처리 문제가 생긴다.
  • DLQ는 만들기만 하고 운영하지 않으면 장애 은닉 수단이 된다.
  • 브로커를 도입해도 조회성 업무까지 모두 비동기로 만들면 사용성 저하가 발생한다.

실무 체크리스트:

  • 적어도 한 번(at-least-once)과 정확히 한 번(exactly-once) 중 어떤 전달 보장을 요구하는가?
  • 메시지 키와 순서 보장 단위가 정의되어 있는가?
  • 재시도 횟수, 지수 백오프, DLQ 운영 절차가 있는가?
  • 소비자 장애 시 처리 지연을 어떤 SLA로 허용하는가?

전자상거래에서는 주문 생성은 동기 API로 받고, 재고 차감·결제 완료 알림·추천 시스템 업데이트는 비동기 이벤트로 분리하는 패턴이 대표적이다. 금융권에서는 핵심 거래 승인 자체는 동기식이더라도, 감사 로그와 후속 통계는 비동기 브로커로 분리하는 경우가 많다.

6. 기대효과 및 결론

메시지 브로커를 도입하면 생산자와 소비자를 느슨하게 결합하고, 트래픽 스파이크와 일시 장애를 흡수하며, 다수 시스템으로 이벤트를 확산할 수 있다. 이는 현대 분산 시스템의 확장성과 복원력에 매우 중요한 기반이다.

하지만 비동기 구조는 눈에 보이지 않는 복잡도를 만든다. 처리 지연, 중복 소비, 순서 역전, 최종 일관성 문제를 이해하지 못하면 브로커는 오히려 디버깅을 어렵게 만든다. 따라서 핵심은 브로커 도입 자체가 아니라, 어떤 업무를 동기로 남기고 어떤 업무를 비동기로 분리할지에 대한 명확한 경계 설정이다.
