0. 핵심 인사이트

핵심: 엔터프라이즈 통합은 한 가지 기술로 해결되지 않으며, 데이터는 ETL/ELT로, 애플리케이션 기능은 API·메시지로, 업무 흐름은 BPM(Business Process Management)으로 다뤄야 전체 운영이 유기적으로 연결된다. 비유: 같은 도시라도 상수도는 배관으로, 자동차는 도로로, 행정 절차는 행정 체계로 관리하듯이 통합도 대상에 따라 다른 구조가 필요하다.

📝 모범 답안

1. 개요 및 필요성

기업 통합을 논할 때 가장 흔한 오류는 모든 문제를 하나의 미들웨어로 해결하려는 것이다. 그러나 통합 대상은 본질적으로 다르다. 분석을 위해 데이터를 모으는 문제, 시스템 기능을 실시간 호출하는 문제, 사람과 시스템이 함께 움직이는 업무 절차를 관리하는 문제는 서로 성격이 다르다.

이 차이를 구분하기 위해 통합은 보통 데이터 통합, 애플리케이션 통합, 프로세스 통합으로 나눈다. 데이터 통합은 주로 ETL(Extract-Transform-Load)이나 ELT(Extract-Load-Transform)로 구현되고, 애플리케이션 통합은 API(Application Programming Interface), 메시지, ESB를 사용하며, 프로세스 통합은 BPM을 통해 업무 단계와 승인 흐름을 관리한다.

이 구분이 중요한 이유는 각각의 성공 기준이 다르기 때문이다. 데이터 통합은 정확성과 적재 주기, 애플리케이션 통합은 응답성과 결합도, 프로세스 통합은 업무 가시성과 통제 가능성이 핵심이다. 이를 혼동하면 잘못된 기술 선택이 발생한다.

2. 구성요소

통합 유형주요 기술역할핵심 포인트
데이터 통합ETL, ELT, CDC(Change Data Capture)데이터 수집·정제·적재분석과 정합성 중심
애플리케이션 통합API, MQ, ESB, Event Bus시스템 기능 호출·상태 전달실시간성·결합도 관리 중심
프로세스 통합BPM, Workflow Engine, Rule Engine사람·시스템·규칙의 흐름 관리업무 통제와 추적 중심
공통 거버넌스메타데이터, 표준 코드, 보안 정책유형 간 기준 통일기술보다 운영 표준이 중요

이 세 계층은 독립적이지만 현실에서는 상호 보완적이다. 예를 들어 주문 접수는 API로 받고, 주문 데이터는 ETL/CDC로 분석계에 적재하며, 승인과 정산 절차는 BPM으로 관리할 수 있다. 즉 하나의 업무는 여러 통합 계층을 동시에 사용한다.

3. 구조 및 원리

핵심 조건: 통합 대상을 데이터, 기능, 프로세스로 분리해 설계해야 하며, 각 계층의 일관성 요구 수준과 응답 시간 요구 수준을 구분해야 한다. 데이터 적재는 배치·정합성이, 애플리케이션 통합은 즉시성·격리가, 프로세스 통합은 상태 관리와 추적성이 핵심 조건이다.

동작 순서:

  1. 운영 시스템에서 업무 이벤트나 데이터 변경이 발생한다.
  2. 실시간 기능 호출이 필요하면 API 또는 메시지 기반 애플리케이션 통합이 수행된다.
  3. 누적 데이터는 ETL/ELT 또는 CDC를 통해 분석 저장소로 이동한다.
  4. 사람의 승인, 예외 처리, 단계별 규정 준수가 필요하면 BPM이 프로세스 상태를 관리한다.
  5. 각 계층의 결과는 모니터링과 메타데이터 체계로 연결되어 전체 업무 가시성을 형성한다.
통합 3계층 구조

[Operational Systems]
      |
      +--> [API / MQ / ESB] ---------> 실시간 기능 통합
      |
      +--> [ETL / ELT / CDC] --------> 데이터 통합 / DW, Lake
      |
      +--> [BPM / Workflow Engine] --> 승인, 예외, 프로세스 상태 관리

ETL은 원천 데이터의 정제와 적재를 통해 분석 가능성을 확보한다. 반면 API와 메시지는 운영 시스템 간 직접 상호작용을 담당한다. BPM은 그 위에서 '누가 언제 어떤 순서로 처리해야 하는가'를 통제한다. 따라서 세 가지는 경쟁 관계가 아니라 서로 다른 레벨의 문제를 다루는 계층적 도구다.

예를 들어 구매 승인 업무를 생각하면, 신청 등록은 API, 승인 대기 상태와 결재 라우팅은 BPM, 누적 구매 실적 집계는 ETL이 맡는다. 이때 BPM이 데이터 적재를 대체할 수 없고, ETL이 승인 절차를 관리할 수도 없다. 이 구분이 실무 설계의 핵심이다.

4. 비교 및 연결

항목ETL/ELTAPI/MessageBPM
통합 대상데이터애플리케이션 기능·이벤트업무 절차
시간 특성배치 또는 준실시간실시간 또는 비동기상태 기반 지속 흐름
핵심 성공 기준정합성, 적재 성능응답성, 결합도, 복원력추적성, 규정 준수, 책임 분리
대표 산출물DW, Data Mart, Lake서비스 호출, 이벤트 전파프로세스 인스턴스, 승인 이력

이 비교는 기술 선택을 구조화한다. 대량 데이터를 야간에 적재해야 하는 문제를 API로 풀면 비효율적이고, 고객 조회 같은 실시간 호출을 ETL로 처리하면 요구사항을 충족하지 못한다. 또한 사람 승인 절차를 단순 API 체인으로 구현하면 예외 처리와 상태 추적이 어려워진다.

5. 실무 적용 및 판단

적용 기준:

  • ETL/ELT: 분석, 리포팅, 통합 저장소 구축이 목적일 때
  • API/Message: 운영 시스템 간 실시간 연동이나 이벤트 전달이 목적일 때
  • BPM: 승인, 예외 분기, 사람 개입, SLA 추적이 중요할 때

실무 체크리스트:

  • 이 요구사항의 본질이 데이터 이동인지, 기능 호출인지, 절차 관리인지 구분했는가?
  • 데이터 정합성과 실시간성 중 무엇이 우선인가?
  • 사람 승인, 규정 준수, 예외 라우팅이 필요한가?
  • 운영과 분석 계층을 혼동하고 있지 않은가?

실제 기업 사례에서 주문 서비스는 API와 이벤트로 운영되고, DW 적재는 CDC/ETL로 수행되며, 클레임 처리 프로세스는 BPM 엔진으로 관리된다. 최근에는 iPaaS가 이 세 영역을 통합적으로 지원하기도 하지만, 내부 구조는 여전히 이 세 관점을 분리해 관리한다.

6. 기대효과 및 결론

통합을 데이터·애플리케이션·프로세스 수준으로 구분하면 문제에 맞는 기술을 선택할 수 있고, 각 계층의 성공 기준도 명확해진다. 이는 과도한 미들웨어 의존이나 부적절한 기술 남용을 방지하는 효과가 있다.

결론적으로 엔터프라이즈 통합은 단일 제품이 아니라 역할 분리의 설계 문제다. ETL은 정보를 모으고, API/메시지는 시스템을 연결하며, BPM은 업무 절차를 통제한다. 이 세 가지를 혼합하되 혼동하지 않는 것이 실무적 정답이다.
