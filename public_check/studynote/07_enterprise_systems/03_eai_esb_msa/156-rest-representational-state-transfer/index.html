0. 핵심 인사이트

핵심: REST (Representational State Transfer)는 네트워크 호출을 “함수 실행”이 아니라 “자원의 상태를 표준 인터페이스로 전이시키는 행위”로 재정의함으로써, 웹의 확장성과 독립 진화를 가능하게 한 아키텍처 스타일이다. 비유: REST는 자유 형식 전화 지시가 아니라, 주소와 표준 동작만으로 누구나 같은 의미를 이해하는 국제 물류 송장 체계에 가깝다.

📝 모범 답안

1. 개요 및 필요성

REST는 Roy Fielding이 2000년 박사 논문에서 제시한 웹 아키텍처 스타일이다. 핵심은 HTTP를 단순 전송 채널로 쓰는 것이 아니라, 웹이 원래 가진 URI (Uniform Resource Identifier), 메서드, 상태 코드, 캐시, 계층 구조를 그대로 활용해 분산 시스템을 설계하는 데 있다.

REST가 등장한 배경에는 RPC (Remote Procedure Call)·SOAP (Simple Object Access Protocol) 계열 인터페이스의 한계가 있었다. 초기 웹 서비스는 “서버의 어떤 함수를 호출할 것인가”에 초점을 두었고, 그 결과 URI는 단순 진입점이 되고 실제 의미는 메시지 바디나 WSDL (Web Services Description Language) 문서에 숨어 버렸다. 이 방식은 도구 의존성과 계약 복잡도를 높였고, 웹 인프라가 이미 제공하는 캐시·프록시·브라우저 친화성을 충분히 활용하지 못했다.

REST는 이 문제를 “웹답게 설계하라”는 방향으로 뒤집었다. 자원은 URI로 식별하고, 행위는 HTTP 메서드로 표현하며, 결과는 표현(Representation)으로 주고받는다. 이렇게 하면 클라이언트와 서버는 구체 구현보다 인터페이스 의미에 의존하게 되고, 대규모 분산 환경에서도 결합도를 낮춘 채 진화할 수 있다.

2. 구성요소

요소역할핵심 포인트
자원 (Resource)시스템이 노출하는 대상 식별/users/42, /orders/1001처럼 명사 중심으로 표현
URI자원의 위치·식별자 제공동사가 아니라 자원 구조를 드러내야 함
표현 (Representation)자원의 현재 상태 전달JSON, XML, HAL 등으로 직렬화
HTTP 메서드자원에 대한 의도 전달GET, POST, PUT, PATCH, DELETE 의미 보존
상태 코드처리 결과의 표준화200, 201, 204, 400, 404, 409, 500 등
헤더/캐시 메타데이터부가 제어 정보 전달ETag, Cache-Control, Location, Authorization
제약 조건REST다움을 결정Client-Server, Stateless, Cacheable, Uniform Interface, Layered System

이 요소들은 서로 독립적이지 않다. URI가 자원을 분명히 드러내야 메서드 의미가 살아나고, 메서드 의미가 표준화되어야 상태 코드와 캐시가 일관되게 동작한다. 결국 REST의 품질은 개별 요소의 나열이 아니라 자원 식별 + 표준 동작 + 자기 서술적 메시지가 함께 맞물릴 때 확보된다.

3. 구조 및 원리

핵심 조건: 자원은 URI로 식별되고, 행위는 HTTP 의미론을 따라야 하며, 각 요청은 서버가 추가 문맥 없이 처리할 수 있을 만큼 자기 완결적이어야 한다.

REST의 본질은 “서버 함수 호출”이 아니라 “자원 상태 전이”다. 클라이언트는 특정 자원의 현재 상태를 요청하거나, 새로운 표현을 보내 서버 상태를 바꾸고, 서버는 그 결과를 다시 표현으로 반환한다. 여기서 중요한 점은 클라이언트와 서버가 상태를 공유하지 않고 인터페이스만 공유한다는 점이다.

동작 순서:

  1. 자원 식별: 클라이언트는 /orders/1001처럼 관심 대상을 URI로 지정한다. URI가 안정적일수록 클라이언트는 내부 구현이 아닌 자원 모델에 의존한다.
  2. 행위 선언: 조회면 GET, 생성이면 POST, 전체 교체면 PUT, 부분 수정이면 PATCH, 삭제면 DELETE를 사용한다. 이 단계가 REST와 단순 HTTP 터널링을 가르는 분기점이다.
  3. 표현 전달: 요청 바디에는 자원의 원하는 상태나 입력 값이 JSON 등의 형태로 담긴다. 서버는 이를 도메인 모델에 반영한다.
  4. 상태 전이 수행: 서버는 비즈니스 규칙을 검증하고 저장소 상태를 변경한다. 이때 변경된 것은 “메시지”가 아니라 “서버 쪽 자원 상태”다.
  5. 표현과 메타데이터 반환: 서버는 결과 자원의 표현, 상태 코드, 캐시 정보, 후속 접근 위치(Location 헤더 등)를 돌려준다.
  6. 계층적 중개 허용: 중간 프록시·게이트웨이·캐시가 요청 의미를 이해하고도 본질을 훼손하지 않아야 한다. 이것이 웹 규모 확장을 가능하게 한다.
Client
  │  GET /orders/1001
  │  Accept: application/json
  ▼
[ REST Interface ]
  │  URI로 자원 식별
  │  메서드로 의도 해석
  ▼
[ Order Service ]
  │  도메인 규칙 검증
  ▼
[ Order Store ]
  │
  └── 상태 조회/변경

응답
HTTP/1.1 200 OK
ETag: "v12"
Cache-Control: max-age=30
{
  "orderId": 1001,
  "status": "PAID",
  "items": [...]
}

REST 제약은 단순 교과서 암기가 아니라 성능과 진화 가능성의 근거다. Stateless는 수평 확장을 쉽게 만들고, Cacheable은 반복 조회 비용을 줄이며, Uniform Interface는 다양한 클라이언트와 중간 계층이 공통 규칙으로 상호작용하게 만든다. 반대로 URI에 동사를 섞거나 모든 요청을 POST 하나로 처리하면, REST가 제공하는 인프라 이점을 스스로 포기하는 셈이 된다.

4. 비교 및 연결

항목RESTSOAP/RPCGraphQLgRPC
모델 중심자원 중심함수/오퍼레이션 중심질의 중심서비스 메서드 중심
전송 의미 활용HTTP 의미론 적극 활용HTTP를 주로 터널로 사용대개 POST 단일 엔드포인트HTTP/2 위 바이너리 RPC
캐시 친화성높음낮음별도 전략 필요낮음
인간 가독성높음XML 계약 의존스키마 기반낮음
강점범용성, 웹 친화성엄격 계약, WS-*과/부족 조회 최소화고성능 내부 통신

REST는 모든 문제의 정답이 아니다. 복잡한 조합 조회는 GraphQL이 더 적합할 수 있고, 초저지연 내부 통신은 gRPC가 유리하다. 그러나 공개 API, CRUD 중심 서비스, 브라우저·모바일·외부 파트너까지 포괄하는 생태계에서는 REST의 단순성과 호환성이 여전히 강력하다.

Richardson Maturity Model과 연결하면, 실무에서 REST라고 부르는 대부분은 Level 2까지 만족하는 API다. Level 3의 HATEOAS까지 구현해야 이론적으로는 가장 완전한 REST에 가깝지만, 실제 제품에서는 비용 대비 효익을 따져 선택적으로 적용한다.

5. 실무 적용 및 판단

채택 조건

  • 공개 API 또는 다수 외부 소비자를 상대하는 경우
  • CRUD 성격이 강하고 자원 모델이 비교적 명확한 경우
  • HTTP 캐시, CDN, 프록시, 브라우저 친화성이 중요한 경우
  • 서비스 독립 배포와 느슨한 계약이 필요한 경우

회피 또는 보완 조건

  • 초당 수십만 건의 저지연 내부 호출이 핵심인 경우 → gRPC 검토
  • 화면별 조합 조회가 지나치게 다양해 과조회/과소조회가 심한 경우 → BFF 또는 GraphQL 병행
  • 장기 실행 워크플로와 상태 전이가 핵심인 경우 → 이벤트 기반 설계·하이퍼미디어·상태머신 설계를 함께 검토

체크리스트:

  1. URI가 자원을 표현하는가, 아니면 동작을 노출하는가?
  2. GET 요청이 서버 상태를 바꾸지 않는가?
  3. POST/PUT/PATCH/DELETE의 의미가 일관적인가?
  4. 상태 코드를 비즈니스 오류에 맞게 사용하는가?
  5. 캐시 가능 조회에 ETag·Cache-Control을 적용했는가?
  6. 인증은 헤더 기반으로 독립 처리 가능한가?

실무 사례로는 GitHub API, Stripe API, Kubernetes API의 상당 부분이 REST적 설계 원칙을 따른다. 다만 내부 마이크로서비스 간에는 REST만 쓰지 않고, 외부에는 REST·내부에는 gRPC를 혼합하는 경우가 흔하다.

6. 기대효과 및 결론

REST를 올바르게 적용하면 인터페이스 이해 비용이 낮아지고, HTTP 생태계 전체의 이점을 활용할 수 있으며, 클라이언트와 서버가 비교적 독립적으로 발전한다. 특히 대규모 인터넷 서비스에서 중요한 캐시, 프록시, 로드밸런서, API 게이트웨이와의 궁합이 좋다.

그러나 REST는 “예쁜 URI 규칙”이 아니라 제약 조건의 조합이다. 무상태성 없이 세션에 의존하거나, Uniform Interface 없이 POST 만능 API로 설계하면 이름만 REST일 뿐 실제 효과는 줄어든다. 결론적으로 REST는 웹 규모 확장을 전제로 한 인터페이스 설계 철학이며, 자원 중심 사고를 팀 전체가 공유할 때 가장 큰 가치를 낸다.
