0. 핵심 인사이트

핵심: Richardson Maturity Model은 “HTTP를 썼다”와 “REST답게 설계했다”를 구분하기 위해, 자원 분리·HTTP 의미론·하이퍼미디어 적용 정도를 단계별로 판별하는 평가 프레임이다. 비유: 같은 도로를 달려도 오토바이, 승용차, 자율주행차의 규칙 준수 수준이 다르듯, API도 REST를 사용하는 깊이에 따라 성숙도가 달라진다.

📝 모범 답안

1. 개요 및 필요성

Richardson Maturity Model (RMM)은 Leonard Richardson이 제시한 REST API 성숙도 평가 모델로, API가 REST 제약을 어느 수준까지 수용했는지를 Level 0부터 Level 3까지 네 단계로 설명한다.

이 모델이 필요한 이유는 “HTTP/JSON이면 REST”라는 오해가 매우 흔하기 때문이다. 실제로는 단일 URI에 POST만 쓰는 RPC 스타일 API도 HTTP 위에서 동작할 수 있다. 그러나 이것은 REST의 자원 중심 설계, 메서드 의미론, 하이퍼미디어 기반 상태 전이를 충분히 활용하지 못한다. RMM은 이러한 혼동을 정리하고, 설계를 개선할 수 있는 방향성을 제공한다.

또한 RMM은 절대적 시험 채점표라기보다 아키텍처 토론 도구에 가깝다. 팀은 이 모델을 이용해 현재 API가 어느 수준인지, 다음 개선이 무엇인지, Level 3까지 갈 실익이 있는지를 합리적으로 판단할 수 있다.

2. 구성요소

수준핵심 특징얻는 이점
Level 0단일 URI, 보통 POST 하나, 액션은 바디에 포함단순 구현, 레거시 호환
Level 1자원별 URI 분리자원 식별 가능, 경계 명확화
Level 2HTTP 메서드·상태 코드 의미 활용표준 인프라 활용, 캐시·모니터링 향상
Level 3HATEOAS (Hypermedia As The Engine Of Application State) 적용클라이언트-서버 결합도 추가 완화

이 네 단계는 상호 배타적 아키텍처가 아니라 점진적 누적 관계다. 즉 Level 2는 Level 1의 자원 분리를 포함하고, Level 3은 Level 2의 HTTP 의미 활용을 전제로 한다. 따라서 상위 단계로 갈수록 REST 제약을 더 많이 반영한 설계가 된다.

3. 구조 및 원리

핵심 조건: REST 성숙도는 단순 기술 스택이 아니라, 자원 식별 → 표준 메서드 활용 → 하이퍼미디어 기반 상태 전이의 누적 적용 정도로 판단해야 한다.

RMM의 핵심은 HTTP를 몇 개 썼는지가 아니라, API가 웹의 인터페이스 원리를 얼마나 내재화했는지 보는 데 있다. Level 0에서는 HTTP가 사실상 터널이다. Level 1에서는 비로소 자원 개념이 생긴다. Level 2에서는 표준 메서드와 상태 코드가 살아나고, Level 3에서는 응답이 다음 가능한 행동을 스스로 안내한다.

동작 순서:

  1. Level 0 - 단일 진입점: 모든 작업이 /api 같은 하나의 엔드포인트로 들어온다. 서버는 바디의 action 값을 해석해 내부 분기를 수행한다.
  2. Level 1 - 자원 분리: /users/10, /orders/22처럼 관심 대상을 URI로 구분한다. 이로써 API 구조가 도메인 구조를 반영하기 시작한다.
  3. Level 2 - HTTP 의미론 채택: GET은 조회, POST는 생성, PUT/PATCH는 수정, DELETE는 삭제를 표현한다. 상태 코드도 200/201/404/409처럼 표준화된다.
  4. Level 3 - 하이퍼미디어 적용: 응답 안에 self, cancel, pay 같은 링크가 포함되어 클라이언트가 다음 전이를 서버가 제공한 링크로 따라간다.
  5. 설계 판단: 실무에서는 Level 2가 비용 대비 효과가 가장 크며, Level 3은 워크플로 지향 시스템이나 장수명 공개 API에서 선택적으로 검토한다.
Level 3  ─ HATEOAS
          응답이 다음 행동을 안내
          ▲
Level 2  ─ HTTP Verbs + Status Codes
          표준 의미론 활용
          ▲
Level 1  ─ Resources
          URI가 자원을 식별
          ▲
Level 0  ─ RPC over HTTP
          HTTP는 단순 터널

중요한 점은 Level이 높다고 무조건 더 좋은 것은 아니라는 사실이다. 예를 들어 모바일 앱과 백오피스가 내부적으로만 사용하는 API라면 Level 2로도 충분할 수 있다. 반대로 여러 소비자가 장기간 이용하는 공개 워크플로 API라면 Level 3의 링크 기반 상태 전이가 버전 진화에 유리할 수 있다. RMM은 성숙도 순위를 매기는 도구이면서 동시에 비용-효익 분석 틀이다.

RMM은 REST와 SOA, RPC, GraphQL을 경쟁 관계로만 보지 않게 해 준다. 예를 들어 GraphQL은 RMM 잣대로 Level 2/3을 바로 대입하기 어렵다. 그것은 다른 질의 모델이기 때문이다. 즉 RMM은 REST 내부의 성숙도 모델이지, 모든 API 스타일의 우열표는 아니다.

또한 HATEOAS가 포함된 Level 3은 브라우저 기반 HTML 웹과 매우 유사하다. 브라우저는 링크를 따라 상태를 전이한다. REST가 웹에서 나왔다는 사실을 고려하면, Level 3은 웹 고유 철학을 가장 많이 반영한 단계라고 볼 수 있다.

5. 실무 적용 및 판단

권장 판단 기준

  • 사내 시스템 간 단순 연동: 최소 Level 1 이상 확보
  • 외부 공개 API·일반적인 제품 API: Level 2를 기본선으로 채택
  • 상태 전이 중심 워크플로·오래 유지될 공개 플랫폼: Level 3 선택 검토

체크리스트:

  1. 단일 URI에 액션 이름을 넣어 POST만 호출하고 있지 않은가?
  2. URI가 자원을 중심으로 모델링되어 있는가?
  3. HTTP 메서드와 상태 코드가 표준 의미대로 사용되는가?
  4. 클라이언트가 다음 URI를 전부 하드코딩해야 하는가?
  5. 응답이 현재 상태에서 가능한 다음 행동을 안내할 필요가 있는가?

실무적으로는 대부분의 조직이 Level 2를 목표로 한다. 이유는 명확하다. Level 2만으로도 캐시, 프록시, API 모니터링, 개발자 경험 개선 효과가 크기 때문이다. 반면 Level 3은 응답 형식과 클라이언트 구현 복잡도가 증가해, 모든 팀이 감당할 필요는 없다.

6. 기대효과 및 결론

RMM을 적용하면 “이 API가 왜 REST답지 않은가”를 감정이 아니라 구조적으로 설명할 수 있다. 또한 개선 우선순위를 정할 수 있어, 무조건적인 재설계보다 단계적 리팩터링이 가능하다.

결론적으로 RMM의 핵심 가치는 Level 3 찬양에 있지 않다. 오히려 현재 수준을 정확히 인식하고, 필요한 수준까지만 설계 성숙도를 끌어올리는 판단력에 있다. 기술사 답안 관점에서는 Level 2가 산업 표준, Level 3이 이론적으로 가장 REST에 가깝다는 점을 함께 서술하는 것이 균형 잡힌 결론이다.
