0. 핵심 인사이트

핵심: Level 0은 HTTP를 자원 지향 인터페이스가 아니라 원격 함수 호출을 전달하는 운반 수단으로만 사용하는 단계로, REST의 외형을 빌렸지만 웹의 의미론은 거의 활용하지 못한다. 비유: Level 0은 우편함 주소를 하나만 두고 모든 업무를 “이 편지로 무엇을 해 달라”는 쪽지에 써서 보내는 콜센터형 시스템과 같다.

📝 모범 답안

1. 개요 및 필요성

Level 0은 Richardson Maturity Model의 최하위 단계로, 흔히 RPC over HTTP 또는 The Swamp of POX (Plain Old XML)라고 부른다. 이 단계에서는 HTTP가 단순 터널 역할만 하며, 대부분의 요청이 단일 URI와 단일 POST 메서드로 처리된다.

이 방식은 REST 원칙과는 거리가 멀지만, 역사적으로는 의미가 있었다. SOAP, XML-RPC, 초기 사내 통합 API는 복잡한 함수 호출을 방화벽 친화적인 HTTP로 전달하기 위해 이 방식을 선택했다. 즉 Level 0은 “잘못된 설계”라기보다, 자원 중심 설계로 넘어가기 전의 과도기이자 레거시 인터페이스의 흔한 출발점이다.

문제는 시스템 규모가 커질수록 액션 이름, 에러 처리, 캐시 정책, 문서 의존성이 모두 메시지 바디에 숨어 버린다는 점이다. 이때 HTTP 자체가 제공하는 표준 의미를 활용할 수 없게 된다.

2. 구성요소

이 구조에서는 URI와 메서드가 업무 의미를 충분히 설명하지 못하므로, 클라이언트와 서버는 메시지 본문 규칙에 강하게 결합된다. 따라서 계약이 바뀌면 소비자 전체가 동시에 수정되어야 하는 경우가 많다.

3. 구조 및 원리

핵심 조건: 단일 엔드포인트가 존재하고, 요청의 실제 의도는 HTTP 메서드가 아니라 바디 내부의 액션 값과 파라미터 조합으로 해석된다.

Level 0의 메커니즘은 단순하다. 클라이언트는 하나의 엔드포인트로 메시지를 보내고, 서버는 그 안의 action 또는 오퍼레이션 이름을 읽어 내부 핸들러를 선택한다. 즉 네트워크 인터페이스는 하나지만, 애플리케이션 내부에는 사실상 많은 함수가 숨어 있는 셈이다.

동작 순서:

  1. 단일 URI 선택: 클라이언트는 /hospitalService 같은 공용 엔드포인트로 요청을 보낸다.
  2. POST 전송: 조회·수정·삭제 여부와 무관하게 대부분 POST를 사용한다. 이는 HTTP 메서드 의미를 사실상 포기한 것이다.
  3. 바디에 액션 기술: 예를 들어 {"action":"cancelAppointment","id":"A-9"}처럼 실제 동작을 메시지 안에 기술한다.
  4. 서버 라우팅 분기: 서버는 URI가 아니라 액션 필드를 기준으로 내부 메서드에 라우팅한다.
  5. 응답 본문 해석: 종종 HTTP 상태 코드는 200이고, 실제 성공·실패는 응답 JSON/XML 안의 코드로 판단한다.
Client
  │ POST /service
  │
  │ {
  │   "action": "deleteUser",
  │   "userId": 42
  │ }
  ▼
[ Single Endpoint Router ]
  ├─ action=createUser  → create()
  ├─ action=deleteUser  → delete()
  └─ action=getUser     → get()
  ▼
Response Body
  {
    "resultCode": "OK"
  }

이 구조는 중앙 라우터 하나로 다양한 작업을 처리할 수 있어 구현이 단순해 보인다. 그러나 캐시 프록시는 어떤 요청이 조회인지 알 수 없고, 모니터링 시스템도 어떤 도메인 작업이 실패했는지 HTTP 수준에서 파악하기 어렵다. 결국 의미를 모두 애플리케이션 레이어에 숨기는 설계다.

Level 0은 SOAP 기반 기업 연동, 일부 레거시 사내 API, 단순 게이트웨이 프록시에서 아직도 볼 수 있다. 특히 오퍼레이션 중심 계약이 강한 조직에서는 REST로 명목 전환만 하고 실제 설계는 Level 0에 머무는 경우가 흔하다.

REST 관점에서 가장 큰 문제는 자원 모델이 보이지 않는다는 점이다. 자원 경계가 드러나지 않으면 URI 설계, HTTP 의미론, HATEOAS 같은 상위 수준 논의로 나아가기 어렵다.

5. 실무 적용 및 판단

허용될 수 있는 경우

  • 외부 공개가 아닌 폐쇄형 레거시 연동
  • SOAP/XML-RPC 계약을 장기간 유지해야 하는 경우
  • 자원 모델보다 오퍼레이션 계약이 우선인 특수 인터페이스

지양해야 하는 경우

  • 공개 API 또는 다수 소비자가 사용하는 플랫폼 API
  • 캐시, CDN, HTTP 모니터링, 표준 오류 처리 활용이 필요한 경우
  • 장기적으로 자원 중심 설계로 진화해야 하는 경우

개선 체크리스트:

  1. 단일 엔드포인트에 숨어 있는 주요 업무 객체를 추출할 수 있는가?
  2. 액션 이름을 자원 + 메서드로 재모델링할 수 있는가?
  3. 성공/실패를 HTTP 상태 코드로 끌어올릴 수 있는가?
  4. 조회 API를 GET으로 분리하면 캐시 이득이 생기는가?

Level 0은 종착지가 아니라 출발점이다. 리팩터링 시에는 먼저 자원 식별(Level 1), 그다음 메서드 의미 부여(Level 2) 순서로 개선하는 것이 현실적이다.

6. 기대효과 및 결론

Level 0은 단순성과 레거시 호환성이라는 장점이 있으나, API 규모가 커질수록 문서 의존성과 강결합이 급격히 심화된다. HTTP의 강점을 거의 쓰지 못하므로 웹 친화성과 운영 효율이 떨어진다.

결론적으로 Level 0은 “HTTP 위 RPC”를 설명하는 유용한 개념이며, 현대 RESTful 설계의 기준선은 아니다. 기술사 답안에서는 Level 0을 레거시·과도기 단계로 규정하고, 개선 방향을 함께 제시하는 것이 적절하다.
