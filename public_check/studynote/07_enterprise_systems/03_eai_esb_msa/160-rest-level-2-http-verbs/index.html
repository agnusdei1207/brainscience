0. 핵심 인사이트

핵심: Level 2는 자원 URI 위에 HTTP 메서드와 상태 코드의 표준 의미를 얹어, 웹 인프라가 API 의도를 이해하도록 만드는 단계이며 실무에서 가장 널리 채택되는 REST 기준선이다. 비유: Level 2는 같은 창구를 쓰더라도 조회용, 접수용, 정정용, 폐기용 서식을 구분해 공무원이 종이만 보고도 처리 의도를 즉시 아는 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

Level 2는 Richardson Maturity Model에서 가장 실용적인 핵심 단계다. Level 1에서 자원을 URI로 분리했다면, Level 2에서는 이제 그 자원에 대한 행위를 HTTP 메서드의 의미에 맞게 표현한다.

이 단계가 중요한 이유는 웹의 표준 메커니즘이 본격적으로 살아나기 때문이다. GET은 조회, POST는 생성, PUT/PATCH는 수정, DELETE는 삭제라는 의미를 지니고, 상태 코드는 200·201·204·400·404·409처럼 결과를 표준화한다. 이때부터 캐시, 프록시, 로깅, 모니터링, API 문서화가 훨씬 자연스럽게 작동한다.

실무에서 “RESTful API”라고 할 때 대부분은 Level 2를 만족하는 API를 의미한다. Level 3의 HATEOAS는 선택적이지만, Level 2는 사실상 산업 표준에 가깝다.

2. 구성요소

요소역할핵심 포인트
GET자원 조회안전성(Safe), 멱등성(Idempotent) 보장
POST자원 생성 또는 비멱등 처리새 자원 생성, 명령 실행에 사용
PUT자원 전체 교체멱등성 보장
PATCH자원 부분 수정변경 필드만 전송
DELETE자원 삭제멱등성 있는 삭제 의미
상태 코드결과 표준화200, 201, 204, 400, 404, 409, 500 등
헤더추가 제어Location, ETag, If-Match, Cache-Control

이 구성요소는 단순 문법이 아니라 계약의 의미 체계다. 예를 들어 GET을 조회로만 쓰면 캐시와 CDN이 이를 안전하게 최적화할 수 있고, PUT을 멱등하게 설계하면 재시도 로직이 안전해진다. 반대로 조회를 POST로 처리하면 이런 이점이 사라진다.

3. 구조 및 원리

핵심 조건: 동일 자원 URI에 대해 HTTP 메서드가 행위 의미를 구분해야 하며, 응답은 상태 코드와 헤더를 포함한 HTTP 의미론 전체로 결과를 표현해야 한다.

Level 2의 본질은 “행위를 메시지 바디가 아니라 프로토콜 자체로 표현한다”는 데 있다. 즉 API 설계자가 업무 의미를 HTTP 표준에 정렬함으로써, 클라이언트와 중간 인프라가 별도 문서 없이도 기본 동작을 이해할 수 있게 만든다.

동작 순서:

  1. 자원 URI 선택: /users 또는 /users/42처럼 자원 경로를 결정한다.
  2. 메서드로 의도 표현: 목록 조회면 GET /users, 생성이면 POST /users, 수정이면 PUT/PATCH /users/42, 삭제면 DELETE /users/42를 사용한다.
  3. 요청 제약 적용: PUT은 전체 표현, PATCH는 변경 필드만 보내는 등 메서드별 입력 의미를 맞춘다.
  4. 서버 처리: 서버는 메서드와 URI 조합에 따라 동일 자원에 대한 서로 다른 의미를 수행한다.
  5. HTTP 결과 표준화: 생성 성공 시 201 Created와 Location 헤더를 반환하고, 자원 부재는 404, 충돌은 409로 표현한다.
  6. 인프라 활용: GET은 캐시, PUT/DELETE는 재시도·멱등 제어, 상태 코드는 모니터링과 알림 체계에 직접 연결된다.
/users            GET     → 사용자 목록 조회
/users            POST    → 사용자 생성
/users/42         GET     → 42번 사용자 조회
/users/42         PUT     → 42번 사용자 전체 교체
/users/42         PATCH   → 42번 사용자 일부 수정
/users/42         DELETE  → 42번 사용자 삭제

          ┌──────── URI: /users/42 ────────┐
GET    ──▶│ read                           │
PUT    ──▶│ replace                        │
PATCH  ──▶│ partial update                 │
DELETE ──▶│ remove                         │
          └────────────────────────────────┘

멱등성과 안전성은 Level 2 이해에서 핵심이다. GET은 여러 번 호출해도 서버 상태를 바꾸지 않아야 하며, PUT/DELETE는 여러 번 호출해도 최종 상태가 같아야 한다. 이 속성은 재시도, 장애 복구, 캐시, 동시성 제어 전략의 기반이 된다.

4. 비교 및 연결

항목Level 1Level 2Level 3
자원 URI있음있음있음
메서드 의미약함강함강함
상태 코드 활용제한적적극적적극적
하이퍼미디어없음없음있음
실무 채택도과도기매우 높음제한적

Level 2는 REST와 HTTP 운영 생태계를 가장 잘 연결해 준다. API Gateway 정책, CDN 캐시, 브라우저 동작, APM 로그, 장애 분석이 모두 HTTP 의미론에 기대기 때문이다. 따라서 REST 설계 논의에서 Level 2는 단순 이론이 아니라 운영 효율의 분기점이다.

반면 복잡한 UI 조합 조회에서는 Level 2만으로는 엔드포인트 수가 늘어나거나 응답 형태가 프런트 요구와 맞지 않을 수 있다. 이 경우 BFF, GraphQL, Aggregation 패턴을 병행한다.

5. 실무 적용 및 판단

채택 권장

  • 외부 공개 API
  • 웹/모바일/파트너 API
  • 표준화된 모니터링·보안·캐시 인프라를 활용해야 하는 경우

주의 사항

  • GET에서 상태 변경을 수행하지 말 것
  • POST를 만능 메서드로 남용하지 말 것
  • PUT과 PATCH의 의미를 혼동하지 말 것
  • 200 OK 안에 에러 메시지만 넣고 끝내지 말 것

체크리스트:

  1. 조회 요청이 정말로 안전한가?
  2. 생성 성공 시 201과 Location을 반환하는가?
  3. 수정 API에 멱등성 요구가 있는가?
  4. 동시 수정 충돌을 ETag/If-Match로 제어할 필요가 있는가?
  5. 삭제 API의 반복 호출 시 결과 의미가 일관적인가?

대표 사례로 대부분의 SaaS 공개 API, OpenAPI 기반 기업 API, Kubernetes 리소스 API가 Level 2 특성을 강하게 가진다.

6. 기대효과 및 결론

Level 2를 달성하면 API의 의미가 URI와 메서드, 상태 코드 수준에서 표준화되어 팀 간 해석 차이가 줄어든다. 운영 측면에서는 캐시, 프록시, 보안 장비, 모니터링 체계가 API 의미를 더 잘 이해하게 된다.

결론적으로 Level 2는 REST 성숙도 중 가장 현실적이면서도 효과가 큰 단계다. 기술사 답안에서는 “실무 표준”이라는 표현과 함께, 안전성·멱등성·상태 코드 활용의 의미를 연결해 서술하는 것이 핵심이다.
