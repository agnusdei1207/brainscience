0. 핵심 인사이트

핵심: Level 3은 응답이 단순 데이터가 아니라 다음 가능한 상태 전이를 스스로 안내하도록 만들어, 클라이언트가 URI를 하드코딩하지 않고도 애플리케이션 흐름을 따라가게 하는 단계다. 비유: Level 3은 목적지 주소만 알려주는 지도보다, 현재 위치에서 갈 수 있는 다음 길을 표지판으로 계속 갱신해 주는 내비게이션에 가깝다.

📝 모범 답안

1. 개요 및 필요성

Level 3은 Richardson Maturity Model의 최상위 단계로, HATEOAS (Hypermedia As The Engine Of Application State)를 적용한 REST 설계를 의미한다. 여기서 핵심은 클라이언트가 API 문서에 적힌 URI를 전부 외워서 호출하는 것이 아니라, 서버가 응답 안에 포함한 링크를 따라 상태를 전이한다는 점이다.

이 개념은 REST의 본질인 “애플리케이션 상태 전이”를 가장 충실히 구현한다. 브라우저가 HTML 문서 속 링크를 따라 이동하듯, API 클라이언트도 현재 자원 표현 안에 담긴 링크를 사용해 다음 동작을 결정한다.

필요성은 결합도 완화에 있다. URI 구조가 바뀌더라도 rel=pay, rel=cancel 같은 의미 관계가 유지되면 클라이언트는 세부 경로를 덜 하드코딩하게 된다. 특히 상태 전이 규칙이 중요한 워크플로 API에서 유효하다.

Level 3에서 중요한 것은 링크의 존재 자체보다 상태 의존성이다. 예를 들어 주문이 CREATED 상태일 때는 pay, cancel 링크가 보이지만, SHIPPED 상태가 되면 track 링크가 나타나고 cancel은 사라질 수 있다. 즉 링크는 단순 문서 편의 기능이 아니라 상태머신의 외부 표현이다.

3. 구조 및 원리

핵심 조건: 응답은 현재 자원 데이터뿐 아니라, 현재 상태에서 허용되는 다음 상태 전이와 그 링크 관계를 함께 제공해야 한다.

Level 3의 원리는 클라이언트가 URI 구조를 미리 안다고 가정하지 않는 것이다. 서버는 자원의 현재 상태를 알고 있으므로, 어떤 전이가 가능한지도 가장 정확하게 안다. 따라서 서버는 응답 안에 현재 상태에서 유효한 링크만 제공하고, 클라이언트는 이를 따라 동작한다.

동작 순서:

  1. 초기 진입점 접근: 클라이언트가 루트 또는 시작 자원에 접근한다.
  2. 현재 상태 표현 수신: 서버는 자원 데이터와 함께 링크 목록을 반환한다.
  3. 링크 관계 해석: 클라이언트는 rel 값을 읽어 가능한 다음 행동을 파악한다.
  4. 상태 전이 수행: 필요한 링크를 따라가 다음 요청을 보낸다.
  5. 새 상태에 맞는 링크 재수신: 서버는 전이 결과에 따라 새로운 링크 집합을 제공한다.
  6. 워크플로 진행: 클라이언트는 계속해서 서버가 허용한 경로 안에서만 이동한다.
GET /orders/1001

{
  "orderId": 1001,
  "status": "CREATED",
  "_links": {
    "self":   {"href": "/orders/1001"},
    "pay":    {"href": "/orders/1001/payment"},
    "cancel": {"href": "/orders/1001/cancel"}
  }
}

CREATED ──pay────▶ PAID ──ship────▶ SHIPPED
   │
   └─cancel──────▶ CANCELED

이 구조의 장점은 URI보다 관계 의미에 계약이 실린다는 점이다. 클라이언트가 /orders/1001/payment라는 문자열을 직접 조합하지 않아도 되므로, 서버는 내부 경로 구조를 더 유연하게 조정할 수 있다. 다만 클라이언트 구현과 문서, 테스트 방식이 복잡해지므로 모든 시스템에 필요한 것은 아니다.

4. 비교 및 연결

항목Level 2Level 3
URI 하드코딩많음상대적으로 적음

클라이언트 복잡도상대적으로 낮음높음

적합 영역일반 CRUD API워크플로·장수명 공개 API

Level 3은 HTML 웹과 가장 닮아 있다. 브라우저는 미리 모든 URL을 코드에 박아 넣지 않아도, HTML 문서 안의 링크와 폼을 따라 탐색한다. REST가 웹의 아키텍처 원리를 일반화한 것이라면, Level 3은 그 철학을 API에 가장 충실하게 옮긴 형태다.

반면 모바일 앱이나 SPA (Single Page Application)처럼 클라이언트가 이미 명확한 화면 흐름을 갖고 있을 경우, Level 3의 이점보다 구현 비용이 더 클 수 있다. 그래서 실무 다수는 Level 2에 머문다.

5. 실무 적용 및 판단

적합한 경우

  • 주문, 승인, 티켓, 워크플로처럼 상태 전이가 중요한 도메인
  • 장기간 버전 호환성이 중요한 공개 플랫폼 API
  • 다양한 제3자 소비자가 API를 탐색적으로 사용해야 하는 경우

부담이 큰 경우

  • 단순 CRUD 위주의 내부 API
  • 클라이언트가 URI를 이미 강하게 통제하는 사내 서비스
  • 링크 해석 규약을 도입·교육할 비용이 부족한 조직

체크리스트:

  1. 현재 상태에 따라 다음 가능한 행동이 달라지는가?
  2. URI 구조 변경 가능성이 높고 장기 호환이 중요한가?
  3. 클라이언트가 링크 관계(rel)를 이해할 수 있는가?
  4. HAL/JSON:API/Siren 같은 미디어 타입 규약이 필요한가?
  5. 링크가 단순 참고 정보가 아니라 실제 상태 전이를 제어하는가?

실무에서는 HAL 기반 링크 추가, 결제/승인 API의 상태 전이 링크, 루트 엔드포인트 탐색 API 형태로 제한적으로 적용하는 경우가 많다.

6. 기대효과 및 결론

Level 3을 적용하면 클라이언트는 서버가 제공한 상태 전이 규칙 안에서 동작하므로, URI 구조와 워크플로 변경에 대한 결합도가 낮아질 수 있다. 특히 장수명 공개 API나 상태기계가 중요한 도메인에서 의미가 크다.

그러나 도입 비용은 분명하다. 응답 형식, 테스트, 클라이언트 구현, 문서 체계가 모두 복잡해진다. 따라서 결론적으로 Level 3은 “REST의 이상형”이지만, 모든 API의 의무는 아니다. 업무 특성과 소비자 다양성을 고려한 선택적 도입이 합리적이다.
