0. 핵심 인사이트

핵심: 무상태성은 서버가 클라이언트의 이전 요청 문맥을 기억하지 않도록 강제해, 어떤 서버 인스턴스라도 동일 요청을 독립 처리할 수 있게 만드는 REST의 확장성 핵심 제약이다. 비유: 무상태성은 창구 직원이 고객 얼굴을 기억하는 대신, 고객이 올 때마다 필요한 서류를 완비해서 제출하게 만드는 제도와 같다.

📝 모범 답안

1. 개요 및 필요성

Statelessness는 REST의 핵심 제약 중 하나로, 서버가 클라이언트의 세션 상태를 애플리케이션 메모리에 유지하지 않는다는 원칙이다. 즉 각 요청은 그 자체로 처리에 필요한 모든 정보를 포함해야 하며, 서버는 이전 요청을 기억하지 않아도 동일하게 응답할 수 있어야 한다.

이 원칙이 중요한 이유는 분산 환경의 확장성과 장애 복원력 때문이다. 서버가 사용자별 세션을 메모리에 쥐고 있으면 특정 사용자는 특정 서버에 묶이는 세션 어피니티(Session Affinity)가 생기고, 수평 확장과 장애 전환이 어려워진다. 반대로 무상태 서버는 로드밸런서 뒤에 인스턴스를 자유롭게 늘리고 줄일 수 있다.

REST가 웹 규모를 지향하는 이유를 생각하면 무상태성은 선택이 아니라 기반이다. 대규모 인터넷 서비스에서 수백만 사용자 문맥을 애플리케이션 메모리에 저장하는 방식은 운영상 병목이 되기 쉽다.

여기서 오해하면 안 되는 점은 “상태가 전혀 없어야 한다”가 아니라, 서버 메모리에 클라이언트 대화 상태를 들고 있지 말라는 뜻이라는 점이다. 비즈니스 데이터는 당연히 DB에 존재할 수 있고, 장바구니나 주문 상태도 저장소에 유지된다. 다만 특정 WAS 인스턴스만 알고 있는 세션 문맥이 없어야 한다.

3. 구조 및 원리

핵심 조건: 각 요청은 인증·입력·대상 식별 정보를 스스로 포함해야 하며, 서버 인스턴스는 이전 대화 문맥 없이도 같은 결과를 낼 수 있어야 한다.

무상태성의 핵심 원리는 애플리케이션 서버를 계산 노드로 단순화하는 데 있다. 서버는 요청을 받아 필요한 외부 저장소를 조회하고 결과를 반환한 뒤, 해당 클라이언트에 대한 메모리 문맥을 남기지 않는다. 따라서 다음 요청은 어떤 서버로 가도 상관없다.

동작 순서:

  1. 클라이언트 준비: 클라이언트는 액세스 토큰, 요청 파라미터, 대상 URI를 포함해 요청을 구성한다.
  2. 로드밸런싱: 요청은 임의의 서버 인스턴스로 분산된다.
  3. 서버 독립 처리: 서버는 토큰을 검증하고 필요한 데이터를 DB/캐시에서 조회한다.
  4. 응답 반환 후 문맥 폐기: 처리 결과를 반환한 뒤 해당 사용자의 세션 상태를 애플리케이션 메모리에 보존하지 않는다.
  5. 다음 요청 재분산: 다음 요청은 다른 인스턴스로 가더라도 동일 규칙으로 처리된다.
Client
  │ Authorization: Bearer <token>
  │ GET /orders/1001
  ▼
[ Load Balancer ]
  ├──▶ App-1
  ├──▶ App-2
  └──▶ App-3
          │
          ├── token 검증
          ├── DB / Cache 조회
          └── 응답 후 사용자 문맥 미보관

공유 상태는 외부 저장소에만 존재

무상태성은 수평 확장에 유리하지만, 요청마다 인증 정보와 문맥을 반복 전달해야 하므로 네트워크 비용이 약간 증가할 수 있다. 또한 완전한 무상태 설계라도 멱등하지 않은 POST 요청의 중복 처리, 분산 트랜잭션, 장기 워크플로 관리 문제는 별도로 다루어야 한다.

4. 비교 및 연결

확장성세션 복제 비용 증가인스턴스 증설 용이
요청 크기작을 수 있음토큰·메타데이터 포함으로 다소 증가

무상태성은 API Gateway, JWT 인증, Microservices Architecture, Service Discovery와 밀접하게 연결된다. 특히 MSA에서 개별 서비스가 서버 세션에 강하게 의존하면 자동 확장과 장애 복구 이점이 크게 줄어든다.

또한 무상태성은 캐시와도 궁합이 좋다. GET 요청이 사용자 세션에 의존하지 않고 요청만으로 결정되면, 중간 캐시 계층이 훨씬 안전하게 응답을 재사용할 수 있다.

5. 실무 적용 및 판단

권장 상황

  • 로드밸런서 뒤 다중 서버 운영
  • 클라우드 오토스케일링 환경
  • API 중심 서비스, 모바일/웹 다중 클라이언트 지원

주의 상황

  • 서버 메모리에 장바구니·인증 세션을 직접 들고 있는 설계
  • 요청 재시도 시 중복 처리 방어가 없는 비멱등 API
  • 토큰만으로 처리하기 어려운 장기 대화형 상태 기계

체크리스트:

  1. 요청 하나만 보고 처리 가능한가?
  2. 특정 인스턴스에 사용자 세션이 묶이지 않는가?
  3. 인증 정보가 헤더 또는 표준 메커니즘으로 전달되는가?
  4. 서버가 죽어도 다른 서버가 동일 요청을 처리할 수 있는가?
  5. 필요한 상태는 외부 저장소에 일관되게 보존되는가?

실무에서는 세션 쿠키를 완전히 없애기보다, 세션 정보를 중앙 저장소에 두고 애플리케이션 서버는 무상태로 유지하는 절충도 자주 사용한다. 중요한 것은 “어느 서버가 요청을 받든 처리 가능해야 한다”는 운영 목표다.

6. 기대효과 및 결론

무상태성을 확보하면 서버 증설·축소, 장애 전환, 배포, 캐시 적용이 쉬워진다. 특히 API 트래픽이 급변하는 클라우드 환경에서 운영 자동화를 가능하게 하는 핵심 조건이 된다.

반면 모든 문맥을 요청에 담는 비용과, 장기 워크플로 관리의 복잡성은 여전히 존재한다. 따라서 무상태성은 만능이 아니라 확장성을 위한 설계 원칙으로 이해해야 한다. 결론적으로 REST에서 무상태성은 선택 사항이 아니라, 웹 규모 아키텍처를 가능하게 하는 필수 전제다.
