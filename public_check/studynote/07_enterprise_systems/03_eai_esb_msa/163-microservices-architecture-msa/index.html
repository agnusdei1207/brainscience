0. 핵심 인사이트

핵심: MSA는 거대한 단일 애플리케이션을 비즈니스 기능별로 분해해, 각 서비스가 자체 코드·배포·데이터를 독립적으로 소유하도록 함으로써 변화 속도와 확장 유연성을 확보하는 아키텍처다. 비유: MSA는 모든 부서를 하나의 초대형 건물에 몰아넣는 대신, 업무별 전문 팀이 독립 건물을 쓰되 표준 도로와 규칙으로 협업하는 도시형 구조에 가깝다.

📝 모범 답안

1. 개요 및 필요성

Microservices Architecture는 애플리케이션을 하나의 거대한 배포 단위로 유지하지 않고, 비즈니스 기능별로 잘게 분해된 독립 서비스들의 집합으로 설계하는 방식이다. 각 서비스는 자체 코드베이스, 독립 배포 파이프라인, 전용 데이터 저장소를 가질 수 있으며, 일반적으로 HTTP API나 메시징으로 상호작용한다.

MSA가 등장한 배경은 대형 모놀리식 시스템의 한계다. 기능이 늘어날수록 빌드 시간이 길어지고, 작은 변경도 전체 배포를 유발하며, 일부 기능만 확장하고 싶어도 애플리케이션 전체를 복제해야 한다. 또한 팀 규모가 커지면 하나의 코드베이스에 대한 충돌과 조정 비용이 급격히 증가한다.

클라우드, 컨테이너, DevOps, 자동화 배포 문화가 확산되면서 MSA는 이러한 문제를 해결하는 현실적 대안으로 부상했다. 단, 단순 분할만으로 해결되지 않으며 데이터 경계, 운영 플랫폼, 관측성까지 함께 성숙해야 한다.

이 구성요소는 서로 보완적이다. 서비스만 잘게 쪼개고 데이터베이스를 공유하면 독립성이 약해지고, 배포만 분리하고 관측성을 갖추지 않으면 장애 분석이 더 어려워진다. 따라서 MSA는 단일 기술이 아니라 조직·플랫폼·데이터 설계의 묶음이다.

3. 구조 및 원리

핵심 조건: 서비스 경계는 비즈니스 도메인 기준으로 분해되어야 하며, 각 서비스는 독립 배포 가능성과 데이터 소유권을 가져야 하고, 서비스 간 통신 실패를 전제로 한 복원력 설계가 필요하다.

MSA의 핵심 원리는 “독립성”이다. 독립적으로 개발·배포·확장할 수 있으려면 서비스 경계가 명확해야 하고, 다른 서비스의 내부 테이블이나 코드에 직접 의존하지 않아야 한다. 이 때문에 Database per Service, API 계약, 비동기 이벤트, 관측성 체계가 중요해진다.

동작 순서:

  1. 도메인 분해: 주문, 결제, 배송, 재고 등 비즈니스 역량별로 서비스를 나눈다.
  2. 독립 저장소 부여: 각 서비스가 자신의 데이터 모델과 저장소를 소유한다.
  3. 서비스 간 통신: 동기 호출은 REST/gRPC, 느슨한 연계는 이벤트/메시지로 처리한다.
  4. 독립 배포: 특정 서비스만 변경·배포·롤백할 수 있다.
  5. 분산 운영 관리: API Gateway, Service Discovery, Circuit Breaker, Tracing을 통해 복잡도를 제어한다.
  6. 최종 일관성 수용: 단일 DB 트랜잭션이 어려우므로 Saga 등 보상 메커니즘을 사용한다.
[ Client ]
    │
    ▼
[ API Gateway ]
    │
    ├──▶ [ Order Service ] ───▶ [ Order DB ]
    │          │
    │          ├── sync call ─▶ [ Payment Service ] ─▶ [ Payment DB ]
    │          │
    │          └── event ─────▶ [ Shipping Service ] ─▶ [ Shipping DB ]
    │
    └──▶ [ User Service ] ───▶ [ User DB ]

이 구조는 배포와 확장에 유리하지만, 네트워크 실패, 부분 장애, 데이터 정합성 문제를 새로 가져온다. 즉 모놀리식에서 코드 내부 호출이던 것이 네트워크 호출로 바뀌는 순간, 지연·재시도·서킷 브레이커·분산 추적이 설계의 일부가 된다.

4. 비교 및 연결

항목모놀리식MSASOA
배포 단위하나다수의 독립 서비스서비스 다수이나 전사 통합 성격 강함

난점규모 확대 시 병목운영 복잡도, 분산 정합성중앙 버스 복잡도

MSA는 SOA와 친연성이 있지만 동일하지 않다. SOA가 전사 시스템 통합과 재사용에 더 초점을 둔다면, MSA는 제품 단위 애플리케이션의 독립 배포와 팀 자율성에 더 초점을 둔다.

또한 MSA는 API Gateway, BFF, Service Discovery, Circuit Breaker, Saga, Observability 패턴과 강하게 연결된다. 이들은 선택 기능이 아니라 실질적으로 MSA 운영을 가능하게 하는 기반 패턴들이다.

5. 실무 적용 및 판단

적합한 경우

  • 도메인이 크고 변화 속도가 빠른 제품
  • 팀이 여러 개로 나뉘어 독립 릴리스가 필요한 경우
  • 기능별 트래픽 편차가 커 선택적 확장이 중요한 경우
  • 클라우드·컨테이너·자동화 배포 기반이 성숙한 경우

부적합하거나 시기상조인 경우

  • 소규모 팀이 하나의 단순 제품을 개발하는 초기 단계
  • 강한 일관성과 단순 운영이 절대적으로 중요한 경우
  • 테스트, 배포, 모니터링 자동화가 없는 조직

체크리스트:

  1. 서비스 경계가 기술 레이어가 아니라 도메인 기준인가?
  2. 서비스 간 DB 직접 조회를 금지할 수 있는가?
  3. 장애 추적용 로그·메트릭·트레이싱이 준비되었는가?
  4. 배포 자동화와 롤백 전략이 서비스별로 존재하는가?
  5. 분산 트랜잭션 대신 보상 로직을 수용할 수 있는가?

실무 사례로 Netflix, Amazon, Uber, Coupang 등 대규모 서비스 기업이 MSA를 채택하지만, 동시에 많은 조직이 모듈러 모놀리스에서 출발해 점진적으로 일부 도메인만 분리하는 전략을 택한다.

6. 기대효과 및 결론

MSA의 기대효과는 변화 속도, 선택적 확장, 팀 자율성 향상이다. 특정 서비스만 빠르게 배포하거나, 결제 서비스만 증설하거나, 서비스별로 적합한 기술을 선택할 수 있다.

그러나 운영 복잡도, 네트워크 실패, 데이터 일관성 저하, 플랫폼 비용 증가라는 대가를 치른다. 따라서 결론적으로 MSA는 “크게 만들기 위한 기본값”이 아니라, 규모와 변화 속도가 충분히 클 때 복잡성을 감수하고 얻는 아키텍처 이득이다. 기술사 답안에서는 장점과 함께 분산 시스템 난제를 반드시 병기해야 균형이 맞다.
