0. 핵심 인사이트

핵심: 모놀리식 아키텍처는 하나의 코드베이스와 배포 단위 안에 화면·비즈니스 로직·데이터 접근을 함께 묶어, 단순성과 강한 일관성을 얻는 대신 규모가 커질수록 변경과 확장이 무거워지는 구조다. 비유: 모놀리식은 모든 기능이 한 몸으로 움직이는 대형 기계라서 초반에는 제어가 쉽지만, 나중에는 작은 부품 하나를 갈아도 전체 설비를 멈춰야 하는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

Monolithic Architecture는 애플리케이션의 주요 기능이 하나의 실행 단위와 코드베이스에 통합된 전통적 구조다. 사용자 인터페이스, 비즈니스 로직, 데이터 접근 계층이 하나의 프로젝트 안에서 함께 개발·빌드·배포되는 경우가 많으며, 일반적으로 하나의 데이터베이스를 공유한다.

이 구조가 오랫동안 표준이었던 이유는 단순성 때문이다. 개발자는 한 저장소에서 전체 흐름을 따라갈 수 있고, 함수 호출은 네트워크가 아니라 프로세스 내부 메서드 호출이므로 성능과 디버깅이 유리하다. 데이터도 단일 트랜잭션으로 관리하기 쉽다.

문제는 제품과 조직이 성장할수록 나타난다. 작은 변경도 전체 시스템 배포를 요구하고, 특정 기능만 따로 확장하기 어렵고, 여러 팀이 같은 코드베이스에 몰리며 결합도가 높아진다. 따라서 모놀리식은 초기에는 효율적이지만, 규모가 커질수록 구조적 제약이 드러난다.

2. 구성요소

요소역할핵심 포인트
단일 코드베이스전체 기능 구현팀이 하나의 저장소와 빌드 체계를 공유
단일 배포 산출물일괄 배포JAR/WAR, 단일 컨테이너 이미지 등
계층 구조UI/Service/DAO 분리논리 계층은 있어도 물리적으로는 한 배포 단위
공유 데이터베이스데이터 일관성 확보단일 트랜잭션이 쉬움
중앙 빌드 파이프라인전체 빌드·테스트 수행작은 변경도 전체 검증 필요

모놀리식은 단일 구조라는 이유로 무조건 나쁜 것이 아니다. 내부적으로 모듈화가 잘 된 모놀리식은 상당히 긴 수명을 가진다. 핵심은 “물리적으로 하나”라는 사실과 “논리적으로 잘 분리되어 있는가”를 구분하는 데 있다.

3. 구조 및 원리

핵심 조건: 애플리케이션의 주요 기능이 하나의 프로세스와 배포 단위 안에서 동작하며, 내부 상호작용은 네트워크가 아니라 메서드 호출과 공유 트랜잭션으로 처리된다.

모놀리식의 원리는 모든 기능을 하나의 애플리케이션 경계 안에서 처리하는 것이다. 사용자의 요청은 단일 웹 애플리케이션에 들어와, 내부 계층을 따라 비즈니스 로직을 실행하고, 공유 데이터베이스에 접근한 뒤 응답을 반환한다.

동작 순서:

  1. 사용자 요청 유입: 브라우저나 앱의 요청이 단일 애플리케이션으로 들어온다.
  2. 컨트롤러/화면 처리: 프레젠테이션 계층이 요청을 해석한다.
  3. 비즈니스 로직 수행: 주문, 결제, 회원 등 여러 모듈이 같은 프로세스 내부에서 메서드 호출로 협력한다.
  4. 공유 DB 트랜잭션 처리: 하나의 트랜잭션 경계 안에서 여러 테이블을 일관되게 갱신한다.
  5. 단일 산출물 배포: 변경이 있으면 보통 전체 애플리케이션을 다시 빌드·배포한다.
Client
  │
  ▼
[ Monolith Application ]
  ├── Presentation Layer
  ├── Business Layer
  │     ├── Order Module
  │     ├── Payment Module
  │     └── User Module
  └── Data Access Layer
           │
           ▼
      [ Shared DB ]

이 구조의 장점은 강한 일관성과 낮은 분산 복잡도다. 하지만 기능이 늘어날수록 모듈 간 의존성이 코드 수준에서 얽히고, 특정 모듈만 별도로 배포·확장하기가 어렵다. 결국 “초기 생산성”과 “장기 변화 비용”의 균형이 모놀리식 판단의 핵심이 된다.

4. 비교 및 연결

항목모놀리식모듈러 모놀리스MSA
배포 단위하나하나다수
내부 결합도높아지기 쉬움논리적 분리 강화물리적 분리
트랜잭션단일 DB에 유리단일 DB에 유리분산 정합성 문제
운영 복잡도낮음낮음~중간높음
독립 확장어려움어려움용이

모놀리식은 MSA의 반대말로 자주 쓰이지만, 실제로는 “잘 구조화된 모듈러 모놀리스”가 나쁜 분산 시스템보다 훨씬 낫다. 따라서 MSA 전환 판단은 단순 유행이 아니라, 현재 모놀리식이 실제 병목이 되었는지를 근거로 해야 한다.

또한 모놀리식에서 MSA로 갈 때는 Strangler Fig Pattern처럼 점진 분해 전략이 중요하다. 한 번에 전면 전환하면 기능 누락과 운영 리스크가 커진다.

5. 실무 적용 및 판단

적합한 경우

  • 소규모 팀, 초기 제품, 제한된 도메인 복잡도
  • 강한 트랜잭션 일관성이 핵심인 업무
  • 운영 인력과 플랫폼 역량이 제한된 조직

부적합해지는 신호

  • 작은 변경도 전체 빌드·배포를 유발함
  • 특정 기능만 확장해야 하는데 전체를 늘려야 함
  • 팀 간 코드 충돌과 배포 조정 비용이 급증함
  • 장애 영향 범위가 너무 넓음

체크리스트:

  1. 현재 문제는 아키텍처가 아니라 모듈화 부족 아닌가?
  2. 독립 배포가 실제로 필요한 팀 구조인가?
  3. 단일 DB 트랜잭션이 중요한 도메인인가?
  4. 운영 자동화 없이 MSA로 가면 더 나빠지지 않는가?
  5. 모듈러 모놀리스로 먼저 개선할 여지는 없는가?

실무적으로 많은 성공적인 서비스가 상당 기간 모놀리식으로 성장한다. 핵심은 모놀리식을 부정하는 것이 아니라, 성장 단계에 맞는 구조로 이해하는 것이다.

6. 기대효과 및 결론

모놀리식은 개발 단순성, 테스트 용이성, 강한 데이터 일관성 측면에서 여전히 강력하다. 특히 초기 단계에서는 복잡한 분산 인프라 없이 빠른 기능 개발이 가능하다.

하지만 규모가 커질수록 빌드, 배포, 확장, 팀 자율성 면에서 한계가 누적된다. 결론적으로 모놀리식은 낡은 구조가 아니라 단순성과 일관성을 우선하는 합리적 출발점이며, 한계가 명확해질 때 점진적으로 모듈화 또는 서비스 분해를 검토하는 것이 바람직하다.
