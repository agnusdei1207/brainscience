0. 핵심 인사이트

핵심: API Gateway는 다수의 내부 서비스를 외부에 하나의 진입점으로 노출하면서, 라우팅·인증·정책·집계를 중앙에서 처리해 클라이언트와 서비스 간 결합을 줄이는 엣지 계층이다. 비유: API Gateway는 건물 각 부서로 손님을 직접 보내지 않고, 로비 데스크가 신원 확인과 안내를 먼저 처리한 뒤 적절한 부서로 연결하는 접수 시스템과 같다.

📝 모범 답안

1. 개요 및 필요성

API Gateway는 마이크로서비스 환경에서 외부 클라이언트와 내부 서비스 사이에 위치하는 단일 진입점이다. 클라이언트는 내부 서비스의 실제 위치나 분산 구조를 알 필요 없이 Gateway만 호출하고, Gateway가 요청을 적절한 서비스로 라우팅한다.

이 계층이 필요한 이유는 MSA의 외부 노출 복잡도 때문이다. 서비스가 수십 개로 분해되면 모바일 앱과 웹 클라이언트가 각 서비스의 주소, 인증 방식, 버전, 장애 처리 규칙을 모두 알아야 하는데 이는 현실적으로 유지보수 비용이 높다. Gateway는 이 복잡성을 한 번 감싸는 역할을 한다.

또한 인증·인가, 속도 제한, 로깅, 헤더 변환, 응답 집계 같은 공통 정책을 각 서비스마다 중복 구현하지 않고 중앙에서 처리할 수 있다는 점도 큰 이유다.

API Gateway는 단순 프록시보다 넓은 역할을 가진다. 단순 L4/L7 로드밸런서가 트래픽 분산에 초점을 둔다면, Gateway는 API 의미를 이해하고 정책을 적용하는 애플리케이션 엣지 계층이다. 다만 이 때문에 비즈니스 로직까지 Gateway에 넣으면 곧바로 비대화 문제가 발생한다.

3. 구조 및 원리

핵심 조건: 외부 요청의 진입점은 단일화하되, 공통 횡단 관심사는 Gateway에 모으고 도메인 비즈니스 로직은 백엔드 서비스에 남겨야 한다.

API Gateway의 원리는 “외부 복잡성 흡수, 내부 서비스 보호”다. 클라이언트는 하나의 엔드포인트만 보며, Gateway는 내부 서비스 구조 변화와 정책 집행을 대신 감당한다. 이때 Gateway가 할 일과 하지 말아야 할 일을 명확히 구분하는 것이 중요하다.

동작 순서:

  1. 요청 수신: 클라이언트가 단일 도메인(예: api.company.com)으로 요청한다.
  2. 선행 정책 수행: 인증, 권한, 속도 제한, 기본 검증, 로깅을 적용한다.
  3. 대상 서비스 결정: 경로와 메타데이터를 기준으로 내부 서비스 또는 BFF로 라우팅한다.
  4. 필요 시 집계: 한 화면에 필요한 여러 서비스 데이터를 병렬 호출해 조합할 수 있다.
  5. 응답 반환: 내부 구조를 숨긴 채 외부 계약 형태로 결과를 반환한다.
  6. 관측 데이터 기록: 추적 ID, 메트릭, 에러 로그를 남겨 운영 가시성을 높인다.
Client
  │  https://api.company.com/orders/1001
  ▼
[ API Gateway ]
  ├── AuthN/AuthZ
  ├── Rate Limit
  ├── Routing
  ├── Aggregation
  └── Logging/Tracing
      │
      ├──▶ Order Service
      ├──▶ Payment Service
      └──▶ User Service

Gateway는 매우 유용하지만 만능 계층은 아니다. 인증, 정책, 조합 정도는 적절하나, 주문 계산 규칙이나 결제 승인 로직까지 Gateway에 넣으면 서비스 분해 효과가 무너진다. 즉 Gateway는 스마트해야 하지만 도메인 두뇌가 되어서는 안 된다.

4. 비교 및 연결

항목Load BalancerAPI GatewayBFF
주목적트래픽 분산단일 진입점 + 정책 + 라우팅특정 프런트엔드 맞춤 백엔드
계층네트워크/전송 중심API 엣지 계층채널 특화 응용 계층

API Gateway는 Service Discovery, OAuth2, WAF, BFF, Circuit Breaker와 밀접하게 연결된다. 특히 Gateway가 모든 트래픽을 받으므로 고가용성, 스케일아웃, 장애 격리가 필수다.

또한 BFF와의 관계를 구분해야 한다. Gateway는 공통 진입점이고, BFF는 채널별 맞춤 조합 계층이다. 둘은 대체 관계가 아니라 계층적 조합 관계인 경우가 많다.

5. 실무 적용 및 판단

적합한 경우

  • 외부에 노출되는 마이크로서비스가 많을 때
  • 공통 인증·보안·속도 제한 정책이 필요할 때
  • 모바일/웹/파트너 등 다양한 소비자를 지원할 때

주의할 점

  • Gateway에 비즈니스 로직 집중 금지
  • 단일 장애점 방지를 위한 다중 인스턴스 구성 필요
  • 과도한 응답 집계는 지연 증가와 병목을 유발할 수 있음

체크리스트:

  1. 공통 정책이 서비스마다 중복 구현되고 있는가?
  2. 외부 클라이언트가 내부 서비스 구조를 너무 많이 알고 있는가?
  3. Gateway 이중화와 스케일아웃 구성이 준비되었는가?
  4. 서비스 발견·인증·트레이싱과의 연계가 마련되었는가?
  5. BFF와 역할이 명확히 구분되어 있는가?

대표 제품으로는 Kong, NGINX, Spring Cloud Gateway, Apigee, AWS API Gateway가 있다. Kubernetes 환경에서는 Ingress/Gateway API와 조합하여 사용하기도 한다.

6. 기대효과 및 결론

API Gateway를 도입하면 외부 계약이 단순해지고, 공통 정책의 중복 구현이 줄며, 내부 서비스의 위치와 구조를 숨길 수 있다. 이는 보안, 운영, 클라이언트 경험 모두에 이점을 준다.

반면 중앙 병목과 비대화 위험이 존재하므로, 역할 범위를 엄격히 관리해야 한다. 결론적으로 API Gateway는 MSA의 필수 진입 관리 계층이지만, 도메인 로직을 흡수하는 초대형 허브가 되어서는 안 된다.
