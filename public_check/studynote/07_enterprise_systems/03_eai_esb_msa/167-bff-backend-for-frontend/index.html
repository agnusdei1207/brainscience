0. 핵심 인사이트

핵심: BFF는 모든 클라이언트가 하나의 범용 백엔드를 공유할 때 생기는 응답 과잉·변경 병목을 줄이기 위해, 프런트엔드 채널별로 최적화된 전용 백엔드 계층을 두는 패턴이다. 비유: BFF는 같은 식재료 창고를 쓰더라도 모바일, 웹, 키오스크가 각자 필요한 분량과 포장을 다르게 받아 가도록 전용 조리대를 따로 두는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

BFF (Backend For Frontend)는 모바일 앱, 웹, 관리자 콘솔, 스마트 TV처럼 서로 다른 사용자 채널마다 전용 백엔드 계층을 두는 아키텍처 패턴이다. 공통 백엔드 서비스를 그대로 노출하면 각 채널의 화면 구조와 성능 요구가 달라 과조회(over-fetching), 과소조회(under-fetching), API 변경 병목이 발생하기 쉽다.

예를 들어 모바일은 작은 화면과 느린 네트워크를 고려해 최소 데이터만 원하지만, 웹은 한 화면에서 더 많은 조합 데이터를 필요로 할 수 있다. 하나의 범용 API가 이 둘을 동시에 만족시키려 하면 필연적으로 복잡해진다.

BFF는 이러한 문제를 해결하기 위해 “채널 특화 조합 계층”을 도입한다. 프런트엔드 팀은 자신이 담당하는 사용자 경험에 맞게 응답 구조를 빠르게 조정할 수 있고, 백엔드 공통 서비스는 보다 안정적인 도메인 API에 집중할 수 있다.

2. 구성요소

요소역할핵심 포인트
채널별 BFF모바일/Web/Admin 전용 계층채널 요구사항 반영

BFF의 핵심은 “전용성”이다. 공통 Gateway가 모든 소비자를 한 번에 만족시키려는 반면, BFF는 특정 클라이언트 경험을 위해 과감히 응답을 조정한다. 따라서 도메인 로직은 공통 서비스에 남기고, BFF는 조합·형태 변환·화면 최적화에 집중해야 한다.

3. 구조 및 원리

핵심 조건: 채널별 UX 요구가 유의미하게 다를 때, 공통 도메인 API와 화면 조합 책임을 분리하고, 각 BFF는 특정 프런트엔드의 응답 계약만 책임져야 한다.

BFF의 원리는 프런트엔드와 백엔드의 경계를 “도메인 서비스”와 “채널 적합화 계층”으로 한 번 더 나누는 것이다. 이렇게 하면 공통 서비스는 제품 핵심 로직을 안정적으로 유지하고, 채널 팀은 화면 요구 변화에 민첩하게 대응할 수 있다.

동작 순서:

  1. 클라이언트 진입: 모바일 앱, 웹, 관리자 콘솔이 각각 자신에게 대응되는 BFF를 호출한다.
  2. 채널 맥락 반영: BFF는 화면 단위 요구사항, 인증 방식, 네트워크 제약을 고려한다.
  3. 공통 서비스 병렬 호출: 필요한 주문·상품·리뷰·사용자 서비스를 조합한다.
  4. 응답 최적화: 모바일은 필드 축소, 웹은 추가 메타데이터 포함 등 채널 맞춤 응답을 반환한다.
  5. 독립 진화: 특정 채널 UI 변경이 다른 채널 API 계약에 직접 충돌하지 않게 된다.
Mobile App ──▶ [ Mobile BFF ] ──┬──▶ Product Service
                                ├──▶ Review Service
Web App    ──▶ [ Web BFF ] ─────┤
                                └──▶ Order Service
Admin      ──▶ [ Admin BFF ] ───┘

이 구조는 채널별 최적화에 매우 유리하지만, BFF가 너무 많아지면 중복 로직이 늘 수 있다. 따라서 어떤 로직이 채널 특화인지, 어떤 로직이 공통 도메인인지 경계를 엄격히 관리해야 한다.

BFF와 GraphQL은 경쟁 관계일 수도, 조합 관계일 수도 있다. 예를 들어 모바일 BFF 내부에서 GraphQL을 사용해 백엔드 조합을 단순화할 수 있다. 또한 공통 API Gateway 앞단 뒤에 여러 BFF를 배치하는 구조도 흔하다.

5. 실무 적용 및 판단

적합한 경우

  • 모바일/웹/관리자 등 채널별 요구가 크게 다를 때
  • 프런트엔드 팀이 빠른 화면 실험과 출시가 필요할 때
  • 공통 API가 비대해져 변경 협의 비용이 커졌을 때

주의할 점

  • BFF마다 도메인 로직 복제 금지
  • 채널 수가 적고 요구 차이가 작다면 과설계 가능
  • 버전 관리와 소유 조직이 명확하지 않으면 중복과 혼란 증가

체크리스트:

  1. 채널 간 응답 요구 차이가 충분히 큰가?
  2. 공통 API 변경이 실제 병목이 되고 있는가?
  3. BFF가 도메인 규칙이 아니라 조합 책임에 집중하는가?
  4. 공통 인증·정책은 Gateway와 역할 분리되어 있는가?
  5. BFF 팀과 공통 서비스 팀의 소유권이 명확한가?

실무 사례로는 모바일 전용 BFF, 관리자 화면 전용 BFF, 파트너 포털 전용 BFF가 흔하다. 대형 서비스는 채널별 배포 주기를 분리하기 위해 BFF를 적극 활용한다.

6. 기대효과 및 결론

BFF를 도입하면 채널별 최적화와 프런트엔드 개발 속도가 향상되고, 범용 API를 둘러싼 조직 병목을 줄일 수 있다. 특히 화면 중심 요구가 빠르게 변하는 서비스에서 효과가 크다.

반면 무분별한 BFF 증식은 중복과 운영 비용을 키울 수 있다. 결론적으로 BFF는 “모든 곳에 쓰는 패턴”이 아니라, 채널 간 요구 차이가 충분할 때 API 계약을 채널 단위로 분리하는 전략적 패턴이다.
