0. 핵심 인사이트

핵심: 서비스 디스커버리는 동적으로 생성·소멸하는 서비스 인스턴스의 위치를 자동 등록·조회하게 만들어, 분산 시스템이 하드코딩된 IP 없이도 서로를 찾도록 하는 핵심 인프라다. 비유: 서비스 디스커버리는 이사를 자주 가는 가게들의 최신 주소를 실시간으로 갱신해 두는 전자 주소록과 같다.

📝 모범 답안

1. 개요 및 필요성

Service Discovery는 분산 시스템에서 서비스 인스턴스의 네트워크 위치(IP, Port, DNS 이름)를 동적으로 등록하고 조회하는 메커니즘이다. 컨테이너, 오토스케일링, 무중단 배포가 일반화된 환경에서는 서비스 인스턴스가 자주 생성·종료되므로, 고정 IP 설정만으로는 통신을 유지하기 어렵다.

전통적인 정적 설정 방식에서는 payment.service=10.0.0.15 같은 값을 환경 설정에 넣어 사용했다. 하지만 MSA와 Kubernetes 환경에서는 인스턴스 수와 주소가 계속 바뀌므로 이런 방식이 곧바로 깨진다. 이 문제를 해결하기 위해 등장한 것이 서비스 디스커버리다.

즉 서비스 디스커버리는 단순한 편의 기능이 아니라, 동적 인프라에서 서비스 간 연결을 가능하게 하는 기본 운영 메커니즘이다.

2. 구성요소

요소역할핵심 포인트
Service Registry인스턴스 목록 저장Eureka, Consul, etcd, Kubernetes API
Provider Registration서비스 등록시작 시 자신의 주소와 메타데이터 등록
Heartbeat / Health Check생존 상태 확인죽은 인스턴스 제거
Consumer Lookup호출 대상 조회클라이언트 또는 프록시가 조회
Load Balancing인스턴스 선택Round Robin, Least Connections 등
DNS / Virtual IP조회 결과 노출 방식이름 기반 접근 단순화

핵심은 “등록”과 “정리”가 모두 자동화되어야 한다는 점이다. 인스턴스가 살아났을 때 등록만 되고 죽었을 때 제거되지 않으면, 호출자는 곧바로 죽은 엔드포인트로 요청을 보내게 된다. 따라서 Health Check와 TTL 관리가 매우 중요하다.

3. 구조 및 원리

핵심 조건: 서비스 인스턴스는 자신의 위치를 자동 등록해야 하고, 레지스트리는 건강하지 않은 인스턴스를 제거해야 하며, 호출자는 조회 결과를 기반으로 살아 있는 대상에게 요청을 보내야 한다.

서비스 디스커버리의 원리는 주소 결정을 실행 시점으로 미루는 것이다. 배포 시점에 IP를 박아 넣는 대신, 요청 직전 또는 주기적으로 최신 인스턴스 목록을 조회해 사용한다. 이 덕분에 오토스케일링과 롤링 업데이트가 가능해진다.

동작 순서:

  1. 인스턴스 기동: 새로운 서비스 인스턴스가 시작된다.
  2. 레지스트리 등록: 인스턴스는 자신의 주소, 포트, 메타데이터를 등록한다.
  3. 헬스체크 유지: 주기적 heartbeat 또는 active check로 정상 여부를 알린다.
  4. 소비자 조회: 클라이언트나 프록시가 레지스트리에서 사용 가능한 인스턴스를 조회한다.
  5. 대상 선택 및 호출: 조회 결과 중 하나를 선택해 요청을 보낸다.
  6. 장애 인스턴스 제거: heartbeat 실패나 헬스체크 실패 시 레지스트리가 목록에서 제거한다.
[ Service Instance ]
      │ register / heartbeat
      ▼
[ Service Registry ]
      ▲                 │ lookup
      │                 ▼
  health remove    [ Consumer / Gateway ]
                           │
                           └──▶ healthy instance 호출

이 구조 덕분에 서비스 주소 변경은 애플리케이션 코드 수정이 아니라 런타임 인프라 이벤트로 처리된다. 하지만 레지스트리 자체의 가용성과 일관성이 중요해지며, 캐시된 목록이 오래되면 stale endpoint 문제가 생길 수 있다.

4. 비교 및 연결

항목정적 설정Service Discovery
주소 관리수동자동
확장성낮음높음
무중단 배포 대응어려움용이
운영 복잡도초기 단순레지스트리 운영 필요
장애 대응느림상대적으로 빠름

Service Discovery는 API Gateway, Load Balancer, Service Mesh, Kubernetes Service와 강하게 연결된다. 특히 Kubernetes는 내장 DNS와 Service 추상화로 많은 디스커버리 기능을 플랫폼 레벨에서 제공한다.

또한 Client-side Discovery와 Server-side Discovery는 “누가 조회할 것인가”를 나눈 패턴이며, Service Discovery의 구현 방식 차이로 이해해야 한다.

5. 실무 적용 및 판단

적합한 경우

  • 컨테이너·오토스케일링 환경
  • 서비스 인스턴스가 빈번히 늘고 줄어드는 경우
  • 롤링 배포, 카나리 배포를 자주 수행하는 경우

주의할 점

  • 레지스트리 가용성 확보 필요
  • 헬스체크 지연으로 죽은 인스턴스가 남지 않게 해야 함
  • 캐시 정책이 너무 길면 stale endpoint 문제 발생

체크리스트:

  1. 인스턴스 등록/해제가 자동화되어 있는가?
  2. 헬스체크와 제거 정책이 적절한가?
  3. 호출자가 조회 결과를 얼마나 오래 캐시하는가?
  4. 레지스트리 장애 시 대체 경로가 있는가?
  5. Kubernetes/DNS 기반 기능으로 충분한지, 별도 레지스트리가 필요한지 판단했는가?

실무 제품으로는 Netflix Eureka, HashiCorp Consul, ZooKeeper, etcd가 대표적이며, Kubernetes에서는 Service + CoreDNS가 사실상 표준 역할을 수행한다.

6. 기대효과 및 결론

서비스 디스커버리를 도입하면 정적 주소 의존성이 제거되고, 오토스케일링과 롤링 업데이트를 자연스럽게 운영할 수 있다. 이는 클라우드 네이티브 아키텍처의 핵심 전제다.

그러나 레지스트리의 가용성, 헬스체크 정확성, 조회 캐시 정책을 잘못 설계하면 오히려 연결 실패가 늘 수 있다. 결론적으로 Service Discovery는 MSA의 부가 기능이 아니라, 동적 인프라를 실질적으로 작동시키는 연결 기반 기술이다.
