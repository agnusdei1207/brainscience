0. 핵심 인사이트

핵심: 폴백(Fallback)은 장애를 숨기는 장식이 아니라, 실패를 허용 가능한 수준의 서비스 열화(Graceful Degradation)로 바꾸어 전체 사용자 여정을 끊기지 않게 만드는 복원력 제어 장치다. 비유: 고속철이 멈췄을 때 모든 승객을 역에 묶어두는 대신, 우회 버스를 즉시 투입해 목적지 도착 수준은 낮아져도 이동 자체는 이어가게 만드는 운영 전략과 같다.

📝 모범 답안

1. 개요 및 필요성

폴백은 원 서비스가 실패했을 때 예외를 그대로 전파하지 않고, 미리 정의한 대체 응답을 반환하여 사용자 경험과 상위 서비스의 안정성을 지키는 패턴이다. 마이크로서비스 아키텍처(MSA)에서는 하나의 요청이 여러 하위 서비스 호출에 의존하므로, 비핵심 기능 하나의 장애가 전체 요청 실패로 확대되기 쉽다. 특히 추천, 랭킹, 리뷰, 환율, 외부 연동 정보처럼 "없으면 불편하지만 없다고 핵심 거래가 멈춰서는 안 되는" 기능은 폴백 설계 여부가 서비스 품질을 크게 좌우한다.

폴백이 필요한 이유는 단순히 에러 화면을 줄이기 위해서가 아니다. 첫째, 상위 서비스가 장애 상황에서 대기와 재시도로 자원을 고갈시키지 않도록 해야 한다. 둘째, 사용자에게 완전 실패 대신 제한된 기능을 제공하면 이탈률을 낮출 수 있다. 셋째, 운영 관점에서는 장애 범위를 격리하고 우선순위가 높은 핵심 기능에 자원을 집중할 수 있다. 즉 폴백은 장애를 없애는 기술이 아니라, 장애의 사업적 충격을 제어하는 기술이다.

2. 구성요소

구성요소역할핵심 포인트
실패 감지기타임아웃, 예외, 서킷 브레이커 OPEN 상태를 감지폴백은 반드시 명확한 실패 조건 위에서만 동작해야 한다
폴백 정책어떤 대체 응답을 줄지 정의기본값, 캐시, 스텁 응답, 기능 비활성화 등으로 세분화
대체 데이터 소스캐시, 마지막 정상값, 정적 구성값데이터 신선도와 정확도 한계를 함께 관리해야 한다
응답 변환 계층폴백 결과를 API 계약에 맞게 반환클라이언트 계약을 깨지 않아야 한다
관측성 계층폴백 발생률, 원인, 지속시간을 수집성공처럼 보이는 숨은 실패를 드러내야 한다

폴백은 보통 서킷 브레이커, 타임아웃, 재시도 정책과 함께 배치된다. 실패 감지기가 먼저 비정상 상황을 판단하고, 폴백 정책이 어떤 수준까지 기능을 낮출지 결정하며, 대체 데이터 소스가 실제 응답 재료를 제공한다. 이때 응답 변환 계층은 원래 API 스키마를 유지해 클라이언트가 추가 오류 처리 없이 동작하도록 하고, 관측성 계층은 "정상 응답처럼 보이는 비정상 상태"를 운영자에게 노출한다.

3. 구조 및 원리

핵심 조건: 폴백은 핵심 거래 무결성을 침해하지 않는 읽기 중심 기능에 우선 적용해야 하며, 대체 응답의 허용 오차·신선도·책임 범위를 사전에 정의해야 한다.

동작 순서:

  1. 클라이언트 요청이 상위 서비스에 도달하면 상위 서비스는 하위 서비스 호출 전에 타임아웃과 실패 임계치를 설정한다.
  2. 하위 서비스가 지연되거나 예외를 반환하면 실패 감지기가 이를 포착하고, 서킷 브레이커가 열려 있다면 실제 호출 자체를 생략한다.
  3. 상위 서비스는 폴백 정책 테이블을 조회해 해당 기능이 "캐시 반환", "기본 메시지 반환", "기능 숨김", "부분 성공 처리" 중 어느 전략을 따르는지 결정한다.
  4. 대체 데이터 소스에서 마지막 정상값이나 미리 준비된 기본값을 읽어 응답 계약에 맞게 변환한다.
  5. 응답 헤더나 메타데이터에 degraded 상태를 기록하고, 메트릭과 로그에 폴백 발생 사실을 남긴다.
  6. 운영자는 폴백 비율이 임계치를 넘는지 감시하고, 장기화되면 장애 대응을 수행한다.
[Client]
   |
   v
[API Service]

   +--> call downstream -----------------------------+
   |                                                 |

   |                           \                          |                      /
   +----------------------------\-------------------------+---------------------/
                                 v
                      [Degraded but Contract-safe Response]

이 구조의 핵심은 "실패를 성공처럼 위장하는 것"이 아니라 "실패를 통제된 결과로 변환하는 것"이다. 따라서 폴백은 항상 제한 조건을 가져야 한다. 예를 들어 추천 목록은 빈 목록으로 대체해도 되지만, 결제 승인 결과를 "성공으로 가정"하는 폴백은 치명적이다. 또한 캐시 기반 폴백은 오래된 데이터를 노출할 수 있으므로, 허용 가능한 신선도(Time To Live)와 사용자 고지 방식이 함께 정의되어야 한다. 결국 폴백의 품질은 대체 응답 자체보다도, 어디까지 허용하고 어디서 절대 금지할지를 구분하는 경계 설계에서 결정된다.

4. 비교 및 연결

항목폴백재시도 (Retry)서킷 브레이커 (Circuit Breaker)
목적실패 시 대체 응답 제공일시적 오류 재호출반복 실패 시 호출 차단
사용 시점실패가 이미 발생했을 때실패 직후실패율 임계치 초과 시
장점사용자 경험 유지, 부분 기능 제공일시 장애 복구 가능자원 고갈과 연쇄 장애 방지
주의점잘못 쓰면 데이터 왜곡과도하면 부하 증폭차단 후 복구 판단 필요

폴백은 서킷 브레이커와 경쟁 관계가 아니라 보완 관계다. 서킷 브레이커가 "더 이상 호출하지 말자"를 결정하면, 폴백이 "그 대신 무엇을 돌려줄 것인가"를 담당한다. 또한 캐시, BFF (Backend for Frontend), CQRS (Command Query Responsibility Segregation) 읽기 모델과도 자주 연결된다. 읽기 전용 복제본이나 사전 계산된 뷰가 있으면 폴백 품질이 높아지기 때문이다. 반대로 강한 일관성이 필요한 명령 처리 영역에서는 폴백보다 명시적 실패와 재시도가 더 적절하다.

5. 실무 적용 및 판단

채택이 적합한 영역은 상품 상세, 추천, 공지, 리뷰, 통계, 외부 환율/날씨 정보처럼 읽기 중심이면서 사용자 경험 영향은 크지만 정합성 위험은 상대적으로 낮은 기능이다. 예를 들어 전자상거래에서 추천 서비스가 장애 나면 "추천 상품 없음"을 반환하더라도 주문 기능은 계속 수행되어야 한다. 반면 결제 승인, 재고 차감, 인증 토큰 발급처럼 잘못된 기본값이 비즈니스 손실이나 보안 사고로 이어지는 기능에는 폴백을 매우 제한적으로 사용해야 한다.

실무 체크리스트는 다음과 같다.

  • 대체 응답이 비즈니스적으로 허용 가능한가?
  • 캐시 데이터의 최대 허용 지연 시간은 얼마인가?
  • 폴백 응답과 정상 응답을 운영자가 구분할 수 있는가?
  • 폴백이 장기화될 때 자동 복구 대신 장애 은폐만 하고 있지 않은가?
  • 핵심 쓰기 기능에 위험한 "가짜 성공"을 반환하지 않는가?

대표 구현으로는 Resilience4j, Spring Cloud CircuitBreaker, Envoy 기반 서비스 메시의 로컬 응답 정책 등이 활용된다. 다만 도구보다 중요한 것은 정책이다. 폴백이 많을수록 시스템이 안정적인 것이 아니라, "어떤 실패를 어떤 품질로 축소할 것인지"를 세밀하게 정의한 시스템이 성숙한 것이다.

6. 기대효과 및 결론

폴백의 가장 큰 효과는 전체 실패를 부분 실패로 축소한다는 점이다. 이를 통해 사용자 경험을 방어하고, 상위 서비스의 쓰레드·커넥션 점유를 줄이며, 장애 전파를 완화할 수 있다. 또한 운영자는 핵심 기능과 부가 기능의 우선순위를 명확히 구분하게 되어, 시스템 복원력 설계를 비즈니스 가치와 연결할 수 있다.

그러나 폴백은 만능 해법이 아니다. 과도한 폴백은 장애를 늦게 발견하게 만들고, 오래된 데이터 노출이나 "조용한 오류"를 만들 수 있다. 따라서 폴백은 항상 관측성, 사용자 고지, 만료 정책과 함께 설계되어야 하며, 핵심 쓰기 트랜잭션에는 엄격한 금지선이 필요하다. 결론적으로 폴백은 "서비스를 정상처럼 보이게 하는 미봉책"이 아니라, 허용 가능한 열화 수준을 미리 설계하는 복원력 아키텍처의 핵심 구성이다.
