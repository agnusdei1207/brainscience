0. 핵심 인사이트

핵심: 폴리글랏 퍼시스턴스(Polyglot Persistence)는 모든 데이터를 하나의 데이터베이스 규칙에 억지로 맞추지 않고, 도메인별 접근 패턴과 일관성 요구에 맞는 저장 엔진을 선택해 시스템 전체 최적화를 달성하는 아키텍처 원칙이다. 비유: 모든 화물을 같은 창고에 넣는 대신, 냉동식품은 냉동창고에, 귀중품은 금고에, 대량 박스는 자동화 물류창고에 배치해 보관 특성에 맞게 운영하는 물류 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

폴리글랏 퍼시스턴스는 하나의 시스템 안에서 관계형 데이터베이스 관리 시스템(RDBMS), 키-값 저장소(Key-Value Store), 문서 데이터베이스(Document DB), 그래프 데이터베이스(Graph DB), 시계열 데이터베이스(Time-series DB) 등을 혼합해 사용하는 설계 방식이다. 전통적 모놀리식 환경에서는 표준화와 운영 단순성을 위해 단일 RDBMS를 선호했지만, MSA에서는 서비스마다 데이터 모델과 접근 패턴이 크게 달라 단일 저장소가 오히려 병목이 되기 쉽다.

예를 들어 주문·결제는 강한 트랜잭션과 정합성이 중요하므로 RDBMS가 적합하고, 세션이나 캐시는 초저지연 접근이 중요하므로 Redis가 유리하다. 추천 관계나 네트워크 분석은 그래프 탐색이 중요해 Neo4j 계열이 효율적이며, 대량 이벤트 로그는 확장성과 쓰기 처리량이 높은 컬럼 패밀리 DB나 로그 저장소가 맞을 수 있다. 즉 폴리글랏 퍼시스턴스는 "DB를 다양하게 써 보자"가 아니라, 데이터의 의미와 질의를 기준으로 저장 기술을 분리하는 전략이다.

2. 구성요소

구성요소역할핵심 포인트
도메인 서비스데이터 소유와 사용 책임 보유저장소 선택 기준은 서비스 경계와 도메인 요구다
저장 엔진RDBMS, NoSQL, Graph, Cache 등정합성·확장성·질의 패턴에 따라 선택
데이터 접근 계층저장소별 API와 모델 캡슐화다른 서비스가 내부 스키마를 직접 알지 않게 해야 한다
데이터 동기화 메커니즘이벤트, CDC (Change Data Capture), ETL이종 저장소 간 읽기 모델·분석 모델을 구축
운영 표준백업, 모니터링, 보안, 스키마 관리기술 다양성이 운영 혼란으로 번지지 않게 통제

핵심은 저장소가 다양해져도 무질서해지지 않도록 경계를 명확히 하는 것이다. 각 서비스는 자신이 선택한 저장소를 직접 소유하고, 외부 서비스는 API나 이벤트를 통해서만 접근해야 한다. 이때 공통 운영 표준이 없으면 기술 다양성은 곧 장애 다양성으로 바뀐다. 따라서 폴리글랏 퍼시스턴스는 저장 기술 선택의 자유와 플랫폼 차원의 표준화를 동시에 요구한다.

3. 구조 및 원리

핵심 조건: 저장소 선택은 유행이 아니라 데이터 모델, 질의 패턴, 일관성 수준, 장애 복구 방식, 운영 역량을 기준으로 정당화되어야 하며, 서비스 경계 밖 직접 접근은 금지해야 한다.

동작 순서:

  1. 도메인 분해를 통해 서비스 경계를 정하고, 각 서비스가 처리하는 데이터의 쓰기 패턴·조회 패턴·정합성 요구를 분석한다.
  2. 주문, 결제처럼 ACID (Atomicity, Consistency, Isolation, Durability)가 중요한 영역은 RDBMS를, 캐시/세션은 인메모리 저장소를, 연결 관계 분석은 그래프 DB를 선택한다.
  3. 각 서비스는 자신의 저장소 스키마와 접근 API를 캡슐화하고, 외부 서비스와는 이벤트나 API 계약으로만 연동한다.
  4. 교차 서비스 조회가 필요하면 운영 DB를 직접 조인하지 않고, 이벤트 기반 읽기 모델이나 데이터 파이프라인으로 별도 뷰를 구성한다.
  5. 운영 단계에서는 저장소별 백업, 장애 복구, 보안, 모니터링, 스키마 진화를 표준화해 기술 다양성에 따른 복잡도를 통제한다.

이 원리의 핵심은 "데이터를 저장하는 기술"보다 "데이터를 소유하는 주체"를 먼저 확정하는 데 있다. 서비스가 독립적으로 배포되고 진화하려면 저장소까지 함께 캡슐화되어야 한다. 또한 이종 저장소는 동일한 트랜잭션 모델을 제공하지 않으므로, 시스템 차원에서는 최종 일관성(Eventual Consistency)과 비동기 동기화를 받아들여야 한다. 따라서 폴리글랏 퍼시스턴스는 성능 최적화 수단이면서 동시에 데이터 통합 전략의 재설계를 요구하는 아키텍처다.

4. 비교 및 연결

항목단일 RDBMS 중심폴리글랏 퍼시스턴스
장점운영 단순성, 기술 표준화도메인별 최적 성능, 확장 유연성
단점특정 질의·규모에서 비효율운영 복잡도, 기술 스택 증가
정합성중앙 집중 관리 용이서비스 간 최종 일관성 고려 필요
적합 환경비교적 균질한 업무 시스템접근 패턴이 다양한 대규모 MSA

이 개념은 Database per Service와 자주 함께 등장한다. 다만 둘은 같은 말이 아니다. Database per Service는 "데이터 소유권 분리"에 초점이 있고, 폴리글랏 퍼시스턴스는 "저장 기술 최적화"에 초점이 있다. 즉 모든 서비스가 각자 PostgreSQL을 써도 Database per Service는 성립하지만 폴리글랏 퍼시스턴스는 아니다. 반대로 한 팀이 여러 저장소를 쓰더라도 서비스 경계가 불명확하면 아키텍처 이점이 약해진다.

5. 실무 적용 및 판단

실무에서는 무조건 많은 DB를 도입하는 것이 아니라, 단일 저장소가 분명한 비효율을 일으킬 때 단계적으로 확장하는 것이 바람직하다. 예를 들어 전자상거래 플랫폼에서 주문·결제는 PostgreSQL, 세션/장바구니는 Redis, 상품 검색은 Elasticsearch/OpenSearch, 추천 그래프는 Neo4j, 로그 분석은 Kafka+ClickHouse 조합으로 분리할 수 있다. 이때 핵심 성공 요인은 "서비스가 각자 알아서 선택"하는 것이 아니라, 플랫폼 팀이 승인 기준과 운영 표준을 제공하는 것이다.

판단 체크리스트는 다음과 같다.

  • 이 데이터는 현재 저장소에서 구조적으로 비효율적인가?
  • 새로운 저장소가 질의·성능 이점을 명확히 제공하는가?
  • 운영팀이 해당 기술의 백업·복구·보안 역량을 보유하는가?
  • 서비스 경계가 분명하여 직접 조인 요구를 차단할 수 있는가?
  • 이종 저장소 간 최종 일관성을 감수할 수 있는가?

6. 기대효과 및 결론

폴리글랏 퍼시스턴스의 기대효과는 서비스별 성능 최적화, 확장성 향상, 도메인 특화 모델링 가능성에 있다. 각 서비스는 자신에게 맞는 저장 모델을 선택함으로써 불필요한 데이터 변환과 비효율적 인덱싱을 줄일 수 있다. 또한 특정 저장소의 장애나 확장 이슈가 전체 시스템의 일괄 병목으로 번지는 위험도 완화된다.

반면 운영 복잡도, 데이터 통합 난이도, 인력 역량 분산이라는 비용이 분명히 존재한다. 따라서 이 패턴은 기술 다양성 자체를 목표로 삼아서는 안 되며, 서비스 경계와 운영 표준이 성숙한 조직에서 선택적으로 도입해야 한다. 결론적으로 폴리글랏 퍼시스턴스는 "여러 DB를 쓰는 것"이 아니라, 도메인 책임과 데이터 특성에 따라 저장 전략을 설계하는 MSA 데이터 아키텍처의 심화 단계다.

7. 발전 흐름도

단일 RDBMS 표준화
   -> 서비스별 스키마 분리
      -> Database per Service 정착
         -> 도메인별 저장소 최적화
            -> 이벤트 기반 읽기 모델/분석 저장소 분리
               -> 플랫폼 표준 하의 Polyglot Persistence 운영
