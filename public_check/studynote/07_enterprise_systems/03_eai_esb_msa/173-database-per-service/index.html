0. 핵심 인사이트

핵심: Database per Service는 데이터 저장소를 나누는 기술이 아니라, 각 서비스가 자신의 데이터 모델과 변경 책임을 독점하도록 만들어 서비스 경계를 실제로 강제하는 아키텍처 규율이다. 비유: 각 부서가 공용 금고를 함께 쓰면 누구 책임인지 흐려지지만, 부서별 금고와 승인 절차를 분리하면 권한과 책임 경계가 분명해지는 조직 운영과 같다.

📝 모범 답안

1. 개요 및 필요성

Database per Service는 MSA에서 각 서비스가 자신만의 데이터 저장소를 소유하고, 다른 서비스는 그 저장소에 직접 접근하지 못하도록 제한하는 패턴이다. 여기서 저장소는 물리적으로 완전히 분리된 데이터베이스일 수도 있고, 동일 인스턴스 내 독립 스키마나 계정일 수도 있다. 중요한 것은 물리 분리보다도 논리적 소유권과 접근 통제다.

이 원칙이 필요한 이유는 서비스 경계를 코드만으로는 지키기 어렵기 때문이다. 주문 서비스가 결제 DB를 직접 조회해 조인하기 시작하면, 배포는 분리되어 있어도 실제 데이터 의존성은 모놀리식처럼 얽히게 된다. 그러면 스키마 변경이 연쇄 장애를 만들고, 서비스 독립 배포가 어려워지며, 데이터 정합성 책임도 불분명해진다. 따라서 MSA에서 진정한 자율성을 확보하려면 API뿐 아니라 데이터 계층까지 캡슐화해야 한다.

2. 구성요소

구성요소역할핵심 포인트
서비스 경계데이터 소유 주체 정의도메인 책임과 저장소 책임이 일치해야 한다
전용 저장소서비스가 독점적으로 읽고 쓰는 DB물리 분리보다 독점 접근이 본질
접근 제어다른 서비스의 직접 SQL 접근 차단계정, 네트워크, 권한 정책으로 강제
API/이벤트 계약외부와 데이터 교환 수단데이터 공유는 조회가 아니라 계약 기반 통신으로 수행
읽기 모델/복제본교차 서비스 조회 대응직접 조인 대신 CQRS, 이벤트, CDC로 구성

구성요소 간 핵심 관계는 "소유-노출-소비" 구조다. 서비스는 전용 저장소를 소유하고, 외부에는 API나 이벤트만 노출하며, 다른 서비스는 그 계약을 소비한다. 이때 운영상 불편함 때문에 직접 DB 조회를 허용하면, 모든 원칙이 한 번에 무너진다. 따라서 Database per Service는 기술 선택이 아니라 조직 차원의 강제 규칙이어야 한다.

3. 구조 및 원리

핵심 조건: 각 서비스는 자신의 데이터만 직접 변경할 수 있어야 하며, 서비스 간 데이터 결합은 SQL 조인이 아니라 API 호출·이벤트 발행·읽기 모델 동기화로 해결해야 한다.

동작 순서:

  1. 도메인 분해를 통해 주문, 결제, 재고처럼 서비스 경계를 정의하고 각 경계에 데이터 소유권을 부여한다.
  2. 각 서비스는 독립된 DB 혹은 스키마를 사용하고, 다른 서비스 계정의 직접 접속 권한을 차단한다.
  3. 한 서비스가 다른 서비스의 데이터가 필요하면 해당 서비스의 API를 호출하거나, 구독 중인 이벤트를 통해 로컬 읽기 모델을 갱신한다.
  4. 서비스 내부에서는 로컬 트랜잭션으로 강한 정합성을 유지하고, 서비스 간에는 비동기 동기화 또는 SAGA (Saga Pattern)로 최종 일관성을 맞춘다.
  5. 스키마 변경은 외부 DB 소비자를 고려할 필요 없이 해당 서비스 계약 범위 안에서 통제된다.
[Order Service] ----API/Event----> [Payment Service]
      |                                 |
      v                                 v
 [Order DB]                         [Payment DB]
      ^                                 ^
      |                                 |
 direct SQL forbidden             direct SQL forbidden

[Reporting Service]
      ^
      |
 read model built from events / CDC

이 구조가 중요한 이유는 서비스 자율성이 코드 레벨이 아니라 데이터 레벨에서 검증되기 때문이다. 서비스가 자신의 스키마를 마음대로 진화할 수 있으려면 외부 소비자가 내부 테이블 구조를 몰라야 한다. 또한 트랜잭션 경계도 서비스 내부로 축소되어, 분산 2단계 커밋(2PC) 같은 무거운 메커니즘 대신 로컬 ACID와 비동기 조정을 사용할 수 있다. 결국 Database per Service는 MSA에서 독립 배포, 독립 확장, 독립 진화의 전제조건이다.

4. 비교 및 연결

항목공유 데이터베이스Database per Service
데이터 접근여러 서비스가 같은 테이블 접근서비스 소유 저장소만 직접 접근
장점초기 개발과 조인 조회가 쉬움경계 명확, 독립 배포·스키마 진화 용이
단점강결합, 변경 파급 큼교차 조회 구현 복잡, 최종 일관성 필요
트랜잭션중앙 DB에서 쉽게 처리서비스 간 분산 트랜잭션 문제 등장

이 패턴은 Polyglot Persistence와 자주 결합되지만 동일하지 않다. Database per Service는 "소유권 분리"이고, Polyglot Persistence는 "저장 기술 최적화"다. 또한 CQRS, Transactional Outbox, Saga Pattern과도 강하게 연결된다. 서비스 간 직접 조인을 포기하면 읽기 모델 분리와 이벤트 기반 동기화가 자연스럽게 뒤따르기 때문이다.

5. 실무 적용 및 판단

실무에서 가장 큰 난점은 교차 서비스 조회 요구다. 예를 들어 주문 화면에 결제 상태, 배송 상태, 고객 등급을 함께 보여주려면 과거에는 단일 SQL 조인으로 해결했지만, 이제는 API 조합, BFF (Backend for Frontend), CQRS 읽기 모델, 데이터 제품화 같은 대안을 선택해야 한다. 따라서 Database per Service는 단순한 저장소 분리보다 조회 아키텍처 재설계를 동반한다.

적용 체크리스트는 다음과 같다.

  • 서비스별 데이터 소유권과 수정 권한이 명확한가?
  • 다른 서비스의 DB 직접 접근을 네트워크·권한 정책으로 차단했는가?
  • 교차 서비스 조회를 위한 읽기 모델 또는 API 조합 전략이 있는가?
  • 서비스 간 정합성은 Saga, 이벤트, Outbox 등으로 관리하는가?
  • 운영 조직이 스키마 책임과 장애 책임을 서비스 단위로 관리하는가?

6. 기대효과 및 결론

이 패턴의 효과는 서비스 경계를 실제로 강제한다는 데 있다. 각 팀은 자신의 데이터 모델을 자율적으로 변경할 수 있고, 특정 서비스의 스키마 수정이 다른 서비스 배포를 즉시 요구하지 않는다. 또한 장애와 성능 문제도 서비스 단위로 국소화되어 독립 확장과 운영 책임 분리가 용이하다.

그러나 그 대가로 교차 조회 복잡도, 분산 정합성 문제, 데이터 중복 저장이 발생한다. 따라서 Database per Service는 단순히 DB를 나누는 기술이 아니라, "공유 조인을 포기하고 계약 기반 협력을 수용하는가"에 대한 조직적 선택이다. MSA가 데이터 계층까지 분해될 때 비로소 아키텍처적 의미를 갖는다는 점에서, 이 패턴은 MSA의 핵심 기준선이라 할 수 있다.
