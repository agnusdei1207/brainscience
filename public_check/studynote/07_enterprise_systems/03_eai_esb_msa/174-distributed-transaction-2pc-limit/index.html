0. 핵심 인사이트

핵심: 2PC (Two-Phase Commit)는 여러 자원을 하나의 원자적 트랜잭션으로 묶으려는 강한 정합성 기법이지만, 분산 환경에서는 잠금 유지와 코디네이터 의존성 때문에 장애 시 가용성을 크게 희생하는 구조적 한계를 갖는다. 비유: 여러 부서가 동시에 결재해야 문서가 효력을 갖는 제도에서, 최종 승인자 한 명이 연락 두절되면 나머지 부서는 모두 결재 대기 상태로 멈춰 서는 조직 운영과 같다.

📝 모범 답안

1. 개요 및 필요성

분산 트랜잭션은 서로 다른 데이터베이스나 서비스에 걸친 작업을 하나의 원자적 단위처럼 보장하려는 시도다. 전통적 엔터프라이즈 환경에서는 분산 트랜잭션을 위해 XA와 2PC가 널리 논의되었다. 2PC는 코디네이터가 각 참여자에게 준비 여부를 묻고, 모두 준비되면 최종 커밋을 지시함으로써 전체 성공 또는 전체 실패를 맞추는 방식이다.

문제는 MSA와 클라우드 환경에서 이 모델이 잘 맞지 않는다는 점이다. 서비스마다 서로 다른 저장소와 네트워크 지연, 독립 배포 주기, 장애 패턴을 가지는 환경에서는 글로벌 락과 중앙 조정이 곧 병목이 된다. 특히 일시 장애가 흔한 환경에서는 "잠시 느린 참여자" 하나가 전체 트랜잭션을 오래 붙잡아 시스템 처리량을 크게 떨어뜨린다. 그래서 현대 MSA에서는 2PC의 강한 정합성보다, 로컬 트랜잭션과 최종 일관성을 조합하는 패턴이 더 널리 채택된다.

2. 구성요소

구성요소역할핵심 포인트
코디네이터전역 트랜잭션 진행 관리준비/커밋 결정의 단일 기준점
참여자 (Participant)각 자원 관리자(DB, 메시지 시스템 등)prepare 이후 결정 대기 상태가 생긴다
Prepare 로그참여자가 커밋 가능 상태를 기록장애 복구 시 불확실 상태 해소 근거
Commit/Abort 메시지최종 결과 전파네트워크 단절 시 전달 지연이 치명적
락 및 자원 점유중간 상태 일관성 유지대기 시간이 길수록 가용성 저하

2PC는 코디네이터 중심으로 작동한다. 참여자는 prepare 단계에서 로컬 변경을 커밋 직전 상태까지 진행한 뒤, 외부에 노출하지 않은 채 락을 유지하며 최종 결정을 기다린다. 이 구조는 일관성 측면에서는 강력하지만, 참여자와 코디네이터 모두가 안정적으로 살아 있다는 가정 위에 서 있다.

3. 구조 및 원리

핵심 조건: 모든 참여 자원이 2PC/XA를 지원해야 하고, prepare 이후 락 유지에 따른 지연을 감수할 수 있어야 하며, 코디네이터 장애 시 불확실 상태를 허용하지 않는 운영 체계가 필요하다.

동작 순서:

  1. 애플리케이션이 전역 트랜잭션을 시작하면 코디네이터가 모든 참여자를 등록한다.
  2. 1단계(Prepare)에서 코디네이터는 각 참여자에게 "커밋 가능한가"를 질의한다.
  3. 참여자는 로컬 변경을 디스크에 기록하고, 실제 커밋은 하지 않은 채 락을 유지하며 YES/NO를 응답한다.
  4. 모든 참여자가 YES를 보내면 코디네이터는 2단계(Commit)에서 전체 커밋을 지시한다. 하나라도 NO면 전체 Abort를 지시한다.
  5. 문제는 prepare 후 commit 명령이 오기 전까지 참여자가 중간 상태로 묶인다는 점이며, 코디네이터나 네트워크가 장애 나면 이 대기 상태가 길어진다.
Coordinator            Participant A            Participant B
    |                        |                        |
    |---- PREPARE ---------->|                        |
    |------------------------|---- PREPARE --------->|
    |                        |                        |
    |<--- YES (lock held) ---|                        |
    |<-----------------------|<--- YES (lock held) --|
    |                        |                        |
    |---- COMMIT ----------->|                        |
    |------------------------|---- COMMIT ---------->|
    |                        |                        |
    v                        v                        v
 global success        release lock, commit    release lock, commit

 * if coordinator fails after PREPARE, participants remain in uncertain wait state

2PC의 한계는 단순한 성능 저하가 아니라 구조적 블로킹이다. 참여자는 prepare 이후 독자적으로 커밋도 롤백도 결정하기 어렵다. 즉 일부 노드가 멈추면 전체 시스템이 "정합성을 위해 기다리는 상태"에 빠진다. CAP 관점에서도 네트워크 분할이 발생했을 때 가용성보다 일관성에 치우친 선택을 강제한다. 또한 MSA에서는 메시지 브로커, 캐시, 외부 SaaS 등 2PC를 지원하지 않는 자원이 많아, 이질적 시스템을 모두 전역 트랜잭션에 넣기도 어렵다.

4. 비교 및 연결

항목2PCSaga Pattern
일관성강한 원자성최종 일관성
장애 시 특성블로킹, 가용성 저하보상 트랜잭션 필요
성능글로벌 조정 오버헤드 큼로컬 트랜잭션 중심으로 상대적 유연
적용 대상XA 가능한 동질적 자원독립 서비스·이질적 자원 환경

2PC는 전통적 엔터프라이즈의 강한 정합성 요구에 적합할 수 있지만, 현대 MSA에서는 DB per Service, 비동기 메시징, 다중 저장소 구성이 일반적이어서 적용 범위가 크게 줄었다. 이때 Transactional Outbox는 DB 커밋과 메시지 발행 문제를 로컬 트랜잭션으로 축소하고, Saga는 서비스 간 정합성을 보상 방식으로 해결한다. 즉 현대 패턴들은 "글로벌 트랜잭션을 잘 구현"하려 하기보다 "글로벌 트랜잭션이 필요 없도록 재설계"하는 방향에 가깝다.

5. 실무 적용 및 판단

실무에서 2PC를 회피하는 대표 이유는 다음과 같다. 첫째, 네트워크 지연과 장애가 잦은 클라우드 환경에서는 블로킹 비용이 크다. 둘째, 서비스별 독립 배포와 이질적 저장소 조합이 많아 XA 지원 전제가 깨진다. 셋째, 락 유지 시간이 길어지면 처리량과 응답 시간이 급격히 악화된다. 넷째, 장애 복구 절차가 복잡해 운영 부담이 증가한다.

다만 금융 핵심 원장처럼 극단적으로 강한 정합성이 필요하고, 참여 자원이 제한적이며, 인프라가 안정적으로 통제되는 환경에서는 일부 제한적 활용 여지가 있다. 판단 체크리스트는 다음과 같다.

  • 모든 참여 자원이 2PC를 지원하는가?
  • prepare 동안 락 유지와 처리량 저하를 감당할 수 있는가?
  • 네트워크 분할과 코디네이터 장애를 운영적으로 제어할 수 있는가?
  • 보상 트랜잭션보다 글로벌 원자성이 정말 더 중요한가?
  • 외부 시스템까지 포함한 엔드투엔드 정합성을 2PC로 실제 보장할 수 있는가?

6. 기대효과 및 결론

2PC는 이론적으로 강한 원자성을 제공하지만, 분산 환경에서는 높은 가용성과 유연한 확장을 요구하는 현대 시스템과 충돌한다. 특히 서비스 경계가 세분화되고 네트워크가 불안정할수록, 글로벌 잠금과 중앙 조정은 병목이 된다. 따라서 MSA에서 2PC를 배제하는 이유는 구현이 어려워서가 아니라, 그 대가가 아키텍처 목표와 맞지 않기 때문이다.

결론적으로 2PC는 "정합성을 얻기 위한 고전적 해법"이지만, 오늘날의 선택지는 2PC를 정교하게 쓰는 것보다 정합성 모델 자체를 재설계하는 방향에 있다. 로컬 ACID, Outbox, Saga, 읽기 모델 분리 같은 패턴이 널리 채택되는 이유도 여기에 있다. 즉 2PC의 한계를 이해하는 것은 단순히 배제 이유를 아는 데 그치지 않고, MSA가 왜 최종 일관성을 전략적으로 수용하는지를 이해하는 출발점이다.

7. 발전 흐름도
