0. 핵심 인사이트

핵심: Choreography Saga는 중앙 지휘자 없이 각 서비스가 이벤트를 발행·구독하며 자신의 다음 행동을 결정하도록 만들어, 분산 워크플로우를 느슨한 결합으로 운영하는 Saga 구현 방식이다. 비유: 지휘자가 없는 재즈 합주에서 각 연주자가 앞선 연주의 신호를 듣고 자기 파트를 이어가되, 전체 흐름은 악보 규칙과 합의된 큐에 의해 맞춰지는 공연과 같다.

📝 모범 답안

1. 개요 및 필요성

Choreography Saga는 Saga Pattern의 구현 방식 중 하나로, 별도의 중앙 오케스트레이터 없이 서비스들이 이벤트 기반으로 협업하는 구조다. 각 서비스는 자신이 수행해야 할 로컬 트랜잭션을 완료한 뒤 결과 이벤트를 발행하고, 다른 서비스는 자신과 관련된 이벤트를 구독해 후속 작업을 수행한다. 실패 시에도 동일하게 보상 이벤트를 발행하여 이미 완료된 서비스들이 자율적으로 원복 절차를 실행한다.

이 방식이 필요한 이유는 중앙 제어기를 두지 않아도 되는 높은 분산성과 서비스 자율성 때문이다. 도메인이 비교적 단순하고 참여 서비스 수가 적당하며, 이벤트 중심 설계가 잘 정착된 조직에서는 중앙 워크플로우 엔진 없이도 유연하게 프로세스를 확장할 수 있다. 특히 새로운 참여자를 기존 흐름에 느슨하게 연결할 수 있어 확장성이 높다.

이 구조에서 각 서비스는 동시에 producer와 consumer가 된다. 즉 주문 서비스는 OrderPlaced 이벤트를 발행하면서 PaymentFailed 같은 이벤트를 소비할 수 있고, 결제 서비스는 OrderPlaced를 소비하고 PaymentApproved 또는 PaymentFailed를 다시 발행한다. 따라서 이벤트 계약, 스키마 버전, 상관관계 ID가 전체 흐름을 연결하는 핵심 인프라가 된다.

3. 구조 및 원리

핵심 조건: 이벤트 계약이 명확해야 하고, 참여 서비스 수와 의존 관계가 추적 가능한 수준이어야 하며, 중복 이벤트·재전달·순서 지연을 견디는 멱등 처리와 관측성 체계가 필수다.

동작 순서:

  1. 시작 서비스가 첫 로컬 트랜잭션을 완료하고 도메인 이벤트를 브로커에 발행한다.
  2. 후속 서비스는 자신이 관심 있는 이벤트를 구독해 로컬 트랜잭션을 수행한다.
  3. 성공 시 다음 단계 이벤트를 발행하고, 실패 시 보상 이벤트를 발행한다.
  4. 앞 단계 서비스들은 보상 이벤트를 수신해 취소·환불·원복을 수행한다.
  5. 모든 단계가 이벤트 체인으로 연결되며, 상태 추적은 분산 로그·트레이싱·상태 저장소를 통해 보완한다.
Order Service        Broker          Payment Service      Inventory Service
     |                 |                    |                    |
     |--OrderPlaced--->|                    |                    |
     |                 |--OrderPlaced-----> |                    |
     |                 |                    |--PaymentApproved-> |
     |                 |<--PaymentFailed--- |                    |
     |<-PaymentFailed--|                    |                    |
     |--OrderCancelled>|                    |                    |

No central controller:
services react to events they subscribe to.

Choreography의 장점은 결합도를 낮춘다는 데 있다. 특정 단계가 추가되어도 기존 중앙 흐름 정의를 수정하지 않고 이벤트 구독자만 늘리면 될 수 있다. 그러나 흐름이 복잡해질수록 "누가 누구의 다음 단계인가"가 코드와 이벤트 토픽에 분산되어 파악이 어려워진다. 특히 예외 경로가 많고 규칙이 자주 바뀌는 업무에서는 이벤트 폭증과 숨은 의존성이 생기기 쉬우므로, 적합한 복잡도 한계를 넘으면 오히려 운영 난이도가 급증한다.

4. 비교 및 연결

결합도낮음오케스트레이터 중심 결합
가시성낮아지기 쉬움흐름 가시성 높음
적합도단순·확장형 이벤트 도메인복잡·규칙 많은 프로세스

Choreography는 Event-Driven Architecture와 가장 자연스럽게 맞물린다. 반면 API 중심 조직이나 강한 프로세스 통제가 필요한 금융·업무 승인 절차에서는 Orchestration이 더 적합할 수 있다. 또한 Transactional Outbox를 함께 사용하면 이벤트 발행 신뢰성을 높일 수 있고, CQRS와 결합하면 이벤트 기반 읽기 모델 구성도 용이하다.

5. 실무 적용 및 판단

실무에서는 주문 생성 후 알림 발송, 포인트 적립, 감사 로그 기록처럼 "주 흐름에 느슨하게 붙는 후속 작업"에서 큰 장점을 보인다. 또한 독립 팀이 각자 이벤트를 구독해 기능을 확장하기 쉬워 조직 자율성과도 잘 맞는다. 다만 결제-재고-배송처럼 실패 경로와 예외 조건이 많은 핵심 거래 흐름에서는 추적성과 변경 통제가 어려워질 수 있다.

판단 체크리스트는 다음과 같다.

  • 전체 참여 서비스 수와 이벤트 흐름을 한눈에 추적할 수 있는가?
  • 이벤트 명세와 버전 관리 체계가 성숙했는가?
  • 재처리·중복 수신·순서 지연에 대한 멱등 설계가 되어 있는가?
  • 업무 규칙 변경이 잦아 중앙 통제가 필요한가, 아니면 느슨한 확장이 더 중요한가?
  • 분산 추적, dead-letter queue, 운영 대시보드가 준비되어 있는가?

6. 기대효과 및 결론

Choreography Saga의 효과는 느슨한 결합, 높은 확장성, 자율적 서비스 진화에 있다. 새로운 소비자를 추가하기 쉽고, 중앙 엔진이 없어 단일 병목을 줄일 수 있다. 이벤트 중심 조직에서는 업무 흐름을 자연스럽게 도메인 이벤트로 표현할 수 있어 아키텍처 일관성도 높아진다.

반면 흐름 가시성 부족, 디버깅 난이도, 숨은 의존성 증가가 큰 한계다. 따라서 Choreography는 "중앙 제어를 피하는 만능 해법"이 아니라, 참여자 수와 규칙 복잡도가 적절한 도메인에서 강점을 발휘하는 선택지다. 결론적으로 이 방식은 자율성과 단순 이벤트 협업에 강하지만, 복잡도가 높아질수록 Orchestration으로 전환하거나 하이브리드 모델을 검토해야 한다.

7. 발전 흐름도

로컬 이벤트 알림
