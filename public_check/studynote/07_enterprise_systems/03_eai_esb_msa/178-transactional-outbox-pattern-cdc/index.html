0. 핵심 인사이트

핵심: Transactional Outbox는 비즈니스 데이터 저장과 외부 메시지 발행을 하나의 로컬 데이터베이스 트랜잭션으로 묶어, dual write 문제를 제거하고 결국 메시지가 반드시 나가도록 만드는 신뢰성 패턴이다. 비유: 공식 접수 문서와 발송 대장을 한 자리에서 동시에 기록해 두고, 우편실이 발송 대장만 보고 누락 없이 우편을 보내는 행정 절차와 같다.

📝 모범 답안

1. 개요 및 필요성

MSA에서 가장 흔한 실패 중 하나는 dual write 문제다. 예를 들어 주문 서비스가 주문 정보를 DB에 저장한 뒤 Kafka에 OrderCreated 이벤트를 발행하려 할 때, DB 커밋은 성공했지만 메시지 발행이 실패하면 다른 서비스는 주문 생성 사실을 알지 못한다. 반대로 메시지는 발행되었는데 DB 반영이 실패하면 소비자는 존재하지 않는 주문을 처리하게 된다. 서로 다른 두 시스템(DB와 브로커)에 대한 쓰기를 완벽하게 동시에 맞추기는 어렵다.

Transactional Outbox는 이 문제를 해결하기 위해 비즈니스 테이블 변경과 아웃박스(Outbox) 테이블 기록을 하나의 로컬 트랜잭션으로 처리한다. 즉 애플리케이션은 브로커에 직접 즉시 발행하지 않고, 먼저 DB 안에 "발행할 메시지"를 안전하게 저장한다. 이후 별도 릴레이 프로세스나 CDC가 Outbox를 읽어 브로커로 전달한다. 이로써 "DB에 반영되었지만 이벤트는 유실"되는 상황을 제거할 수 있다.

핵심은 애플리케이션이 메시지 브로커를 신뢰 경계 밖으로 밀어내고, 먼저 로컬 DB라는 강한 일관성 영역 안에 "보낼 사실"을 고정한다는 점이다. 이후 릴레이는 Outbox를 기준으로 재시도할 수 있으므로, 메시지 발행 경로가 일시 실패해도 복구 가능하다. 따라서 Outbox는 원자성을 제공하는 동시에, 비동기 재전송의 근거 데이터를 제공한다.

3. 구조 및 원리

핵심 조건: 비즈니스 변경과 Outbox 기록이 반드시 동일한 로컬 트랜잭션 안에 있어야 하며, 릴레이는 순서·재시도·중복 발행을 고려해 동작해야 하고, 소비자는 멱등 처리해야 한다.

동작 순서:

  1. 애플리케이션은 주문 생성 같은 비즈니스 변경과 함께 Outbox 테이블에 이벤트 레코드를 INSERT한다.
  2. 두 작업은 하나의 DB 트랜잭션으로 커밋된다. 따라서 비즈니스 데이터와 발행 예정 이벤트는 항상 함께 존재하거나 함께 사라진다.
  3. 별도 Poller 또는 CDC 도구(Debezium 등)가 Outbox의 미발행 레코드를 읽는다.
  4. 릴레이는 이벤트를 브로커에 발행한 뒤, 성공 여부를 표시하거나 삭제 플래그를 기록한다.
  5. 소비자는 이벤트 ID 기반 중복 제거를 수행하며, 장애 시 릴레이는 재시도한다.
[Application]
    |
    |  local transaction
    v
+---------------------------+
| DB                        |
|  - Business Table         |
|  - Outbox Table           |
+---------------------------+
    |
    | poll / CDC
    v
[Relay / Debezium] ---> [Kafka / Broker] ---> [Consumers]
                                 |
                                 +--> duplicate possible, so consumers must be idempotent

이 패턴은 2PC 없이도 "DB 변경 사실이 결국 메시지로 전파된다"는 보장을 만든다. 다만 정확히 한 번(Exactly-once)을 자동으로 얻는 것은 아니다. 릴레이가 브로커에 발행한 뒤 상태 표시 전에 죽으면 재기동 후 같은 메시지를 다시 보낼 수 있으므로, 시스템 전체는 보통 적어도 한 번 전달을 전제로 설계한다. 따라서 Outbox의 본질은 발행 유실 방지이지, 중복 제거까지 단독 해결하는 것이 아니다. 이 때문에 소비자 멱등성, 이벤트 키 설계, 정렬 키 관리가 함께 필요하다.

4. 비교 및 연결

항목Dual Write 직접 처리Transactional Outbox
DB-메시지 원자성보장 어려움로컬 트랜잭션으로 보강
장애 복구발행 누락 추적 어려움Outbox를 근거로 재시도 가능
구현 복잡도표면상 단순릴레이·정리 작업 필요
메시지 중복상황 따라 발생여전히 가능, 멱등성 필요

Outbox는 Saga, CQRS, Event-Driven Architecture의 핵심 기반 패턴이다. Saga 단계 이벤트를 안전하게 내보내야 할 때, 읽기 모델 동기화를 위한 도메인 이벤트를 발행할 때 특히 자주 사용된다. 또한 Event Sourcing과는 다르다. Event Sourcing은 이벤트 자체가 시스템의 원천 데이터이고, Outbox는 비즈니스 상태 변경 사실을 외부에 알리기 위한 전달 신뢰성 패턴이다.

5. 실무 적용 및 판단

실무에서는 주문 생성 후 결제 서비스에 알림, 결제 완료 후 배송 서비스에 알림, 회원 가입 후 CRM 동기화 같은 시나리오에 널리 사용된다. 구현 방식은 크게 두 가지다. Polling Publisher는 애플리케이션이나 별도 워커가 주기적으로 Outbox를 읽는 방식으로 구현이 단순하다. CDC 기반은 DB 변경 로그를 읽어 브로커에 전달하므로 지연이 짧고 확장성이 좋지만, 인프라 운영 난도가 높다.

체크리스트는 다음과 같다.

  • 비즈니스 변경과 Outbox INSERT가 같은 트랜잭션으로 묶였는가?
  • 이벤트 ID, aggregate ID, 발생 시각 등 재처리에 필요한 메타데이터가 있는가?
  • 소비자가 중복 메시지를 안전하게 처리하는가?
  • Outbox 정리 정책(보관 기간, 아카이브, 파티셔닝)이 있는가?
  • 순서 보장이 필요한 경우 aggregate 단위 ordering 전략이 있는가?

6. 기대효과 및 결론

Transactional Outbox의 효과는 메시지 유실 위험을 크게 줄이고, DB 변경과 이벤트 전파 사이의 단절을 해소한다는 데 있다. 이를 통해 서비스 간 비동기 협업의 신뢰성이 높아지고, Saga나 CQRS 같은 상위 패턴도 안정적으로 구현할 수 있다. 또한 장애 복구 시 Outbox를 기준으로 재전송 여부를 판단할 수 있어 운영 단서가 명확해진다.

반면 Outbox 테이블 관리, 릴레이 운영, 중복 메시지 처리라는 추가 복잡성이 생긴다. 따라서 이 패턴은 단순히 메시지를 보내는 기술이 아니라, 분산 시스템에서 "사실의 기록"과 "사실의 전파"를 분리해 신뢰성을 확보하는 설계 원칙으로 이해해야 한다. 결론적으로 Outbox는 MSA에서 데이터 변경과 이벤트 발행을 가장 현실적으로 접합하는 표준 패턴이다.
