0. 핵심 인사이트

핵심: CQRS는 쓰기와 읽기가 동일한 모델일 필요가 없다는 전제에서 출발해, 상태 변경 책임과 조회 최적화 책임을 분리함으로써 복잡한 도메인과 대규모 읽기 부하를 동시에 다루는 패턴이다. 비유: 회계 원장과 경영 대시보드를 같은 형식으로 만들지 않고, 원장은 엄격한 입력 규칙으로 관리하되 대시보드는 보기 좋게 재가공해 제공하는 정보 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

CQRS는 Command Query Responsibility Segregation의 약자로, 시스템의 상태를 변경하는 명령(Command)과 데이터를 읽는 질의(Query)의 모델·저장소·인터페이스를 분리하는 아키텍처 패턴이다. 전통적인 CRUD 모델에서는 하나의 도메인 모델과 하나의 DB 스키마가 쓰기와 읽기를 동시에 담당한다. 그러나 복잡한 비즈니스 규칙이 적용되는 쓰기 경로와, 화면별 조합 조회·검색·통계가 필요한 읽기 경로는 요구 특성이 크게 다르다.

MSA에서 Database per Service가 정착되면 이 차이는 더 커진다. 여러 서비스 데이터를 묶어 보여주는 조회는 직접 조인이 어려워지고, 화면별 응답 구조가 서비스 내부 도메인 모델과 맞지 않는 경우가 많다. CQRS는 이 문제를 해결하기 위해 쓰기 모델은 도메인 무결성과 명령 검증에 집중시키고, 읽기 모델은 조회 성능과 화면 친화적 구조에 맞춰 별도로 설계한다.

2. 구성요소

구성요소역할핵심 포인트
Command 모델생성·수정·삭제 규칙 처리검증, 도메인 로직, 트랜잭션 중심
Query 모델조회용 데이터 구조 제공조인 결과, 문서형 뷰, 검색 인덱스 등 자유로운 형태
Write 저장소정합성 중심 저장소보통 정규화된 모델과 로컬 트랜잭션 사용
Read 저장소조회 최적화 저장소비정규화, 캐시, 검색 엔진, 문서 DB 가능
동기화 메커니즘이벤트, CDC, projection읽기 모델 최신화와 재구축 전략 필요

CQRS의 핵심은 단순히 API를 나누는 데 있지 않다. Command 쪽은 불변 조건과 도메인 규칙을 엄격히 유지하고, Query 쪽은 사용자 화면·검색·통계의 요구에 맞게 자유롭게 재구성한다. 이 둘을 연결하는 동기화 메커니즘이 없으면 읽기 모델은 금방 낡은 복사본이 되므로, 이벤트 기반 projection 설계가 실질적 핵심이 된다.

3. 구조 및 원리

핵심 조건: 쓰기 모델은 도메인 무결성에 집중하고, 읽기 모델은 조회 패턴에 맞게 자유롭게 최적화해야 하며, 읽기 지연과 재구축 가능성을 감수하는 최종 일관성 전략이 필요하다.

동작 순서:

  1. 클라이언트의 변경 요청은 Command API로 들어와 검증, 권한 확인, 도메인 규칙 적용 후 write 저장소에 커밋된다.
  2. 쓰기 성공 후 도메인 이벤트 또는 변경 로그가 발행된다.
  3. Projection 프로세스가 이벤트를 읽어 read 저장소를 갱신한다.
  4. 조회 요청은 Query API를 통해 read 저장소에서 즉시 응답한다.
  5. 필요 시 read 모델은 전체 이벤트나 변경 로그를 재생해 재구축할 수 있다.
            Commands                               Queries
[Client] --------------> [Command API]        [Client] -------------> [Query API]
                               |                                           |
                               v                                           v
                        [Write Model / DB]                         [Read Model / DB]
                               |
                               | domain events / CDC
                               v
                         [Projection Updater]
                               |
                               +------------------------------------------->

이 구조는 읽기와 쓰기의 비대칭성을 적극 활용한다. 예를 들어 주문 생성은 여러 검증과 트랜잭션을 거쳐야 하지만, 주문 목록 조회는 사용자 기준으로 비정규화된 문서 한 건이면 충분할 수 있다. CQRS는 이러한 차이를 하나의 모델에 억지로 담지 않고, 각각에 맞는 모델을 허용한다. 다만 그 결과 읽기 모델은 즉시 최신이 아닐 수 있으므로, 사용자에게 "처리 중" 상태를 보여주거나 약간의 지연을 감수하는 UX 설계가 동반되어야 한다.

4. 비교 및 연결

항목전통적 CRUDCQRS
모델읽기/쓰기 단일 모델읽기와 쓰기 분리
장점단순성조회 최적화와 도메인 복잡성 대응
단점복잡한 조회·도메인에 비효율동기화와 운영 복잡도 증가
정합성단일 DB에서는 즉시성 높음보통 읽기 측 최종 일관성 수용

CQRS는 Event Sourcing과 자주 함께 언급되지만 필수 결합은 아니다. Event Sourcing 없이도 Outbox, CDC, ETL을 이용해 read 모델을 동기화할 수 있다. 또한 API Gateway, BFF와 결합하면 클라이언트별 최적화된 조회 모델을 제공하기 좋다. 반면 단순 CRUD 시스템에는 과도한 설계가 될 수 있다.

5. 실무 적용 및 판단

실무에서 CQRS는 읽기 부하가 매우 크거나, 조회 화면이 복잡한 조인·집계를 요구하거나, 쓰기 도메인 규칙이 복잡해 하나의 모델로 관리하기 어려울 때 효과적이다. 전자상거래의 주문 대시보드, 금융 거래 내역 조회, 검색·추천 시스템, 관리자 통합 모니터링 등이 대표 사례다. 특히 MSA에서 여러 서비스 이벤트를 조합해 조회용 문서를 만드는 방식이 흔하다.

판단 체크리스트는 다음과 같다.

  • 읽기와 쓰기의 성격 차이가 충분히 큰가?
  • 읽기 모델의 지연 업데이트를 비즈니스적으로 허용할 수 있는가?
  • Projection 실패·재처리·재구축을 운영할 수 있는가?
  • 화면·검색·통계 요구가 단일 정규화 모델에서 비효율적인가?
  • 팀이 모델 분리 복잡도를 감당할 수 있는가?

6. 기대효과 및 결론

CQRS의 기대효과는 도메인 무결성과 조회 성능을 각각 독립적으로 최적화할 수 있다는 데 있다. 쓰기 쪽은 규칙과 트랜잭션에 집중하고, 읽기 쪽은 사용자 요구에 맞는 데이터 모양으로 빠르게 응답할 수 있다. 또한 확장성 측면에서도 읽기와 쓰기를 서로 다른 저장소·스케일링 전략으로 운영할 수 있다.

그러나 모델 두 벌과 동기화 파이프라인을 운영해야 하므로 복잡성이 커진다. 읽기 지연, Projection 장애, 데이터 중복 저장도 감수해야 한다. 따라서 CQRS는 "고급스럽기 때문에" 도입하는 패턴이 아니라, 단일 모델이 읽기와 쓰기 요구를 동시에 만족시키지 못할 때 선택하는 구조적 해법이다. 결론적으로 CQRS는 MSA에서 조회 복잡도와 도메인 복잡도를 분리 관리하는 핵심 패턴이다.

7. 발전 흐름도

단일 CRUD 모델
   -> 읽기/쓰기 요구 비대칭 증가
      -> API 분리
         -> CQRS 도입
            -> 이벤트 기반 projection 고도화
               -> Event Sourcing / Search / Analytics와 결합
