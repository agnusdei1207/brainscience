0. 핵심 인사이트

핵심: Event Sourcing은 현재 상태를 덮어쓰는 대신 상태를 만들어 낸 모든 사건을 순서대로 저장하여, 데이터의 진실 원천을 "최종 값"이 아니라 "변화의 역사"로 바꾸는 아키텍처다. 비유: 최종 잔액만 적는 통장이 아니라 입금·출금 내역 전체를 남겨 언제든 현재 잔액과 과거 상태를 다시 계산할 수 있는 회계 장부와 같다.

📝 모범 답안

1. 개요 및 필요성

전통적인 CRUD 시스템은 현재 상태만 저장하는 경우가 많다. 예를 들어 주문 상태를 CREATED에서 PAID로 바꾸면 이전 상태는 사라지고 마지막 값만 남는다. 이 방식은 단순하지만, 왜 현재 상태가 되었는지의 맥락, 과거 특정 시점 상태, 상태 전이 규칙 검증, 재처리나 감사 추적에는 한계가 있다. Event Sourcing은 이러한 문제를 해결하기 위해 상태 변경을 유발한 이벤트를 불변(Immutable) 로그로 저장한다.

즉 시스템의 원천 데이터는 "주문 생성", "결제 승인", "배송 시작" 같은 이벤트이며, 현재 상태는 이 이벤트들을 순서대로 적용한 결과로 계산된다. 이 모델은 감사·재현·시간여행(Time Travel) 조회에 강하며, CQRS와 결합하면 읽기 모델을 여러 형태로 재구축할 수 있다. 특히 금융, 주문 처리, 워크플로우, 감사가 중요한 도메인에서 큰 가치가 있다.

Event Sourcing에서는 Aggregate가 매우 중요하다. Aggregate는 단순 테이블 행이 아니라, 특정 ID의 이벤트 스트림을 재생해 현재 상태를 만들고 새 명령을 검증하는 도메인 경계다. Snapshot은 성능 최적화 수단이며, 이벤트 스키마 버전 관리는 장기 보존 로그의 유지 가능성을 좌우한다.

3. 구조 및 원리

핵심 조건: 이벤트는 불변이어야 하고, Aggregate 단위의 순서가 보장되어야 하며, 과거 이벤트를 재생해도 같은 결과가 나오도록 버전 관리와 멱등적 Projection이 설계되어야 한다.

동작 순서:

  1. 명령이 들어오면 시스템은 해당 Aggregate의 이벤트 스트림을 읽어 현재 상태를 재구성한다.
  2. 재구성된 상태에 도메인 규칙을 적용해 명령의 유효성을 검증한다.
  3. 유효하면 새로운 이벤트를 생성해 이벤트 저장소에 append한다.
  4. Projection 프로세스가 새 이벤트를 읽어 조회 모델, 검색 인덱스, 캐시 등을 갱신한다.
  5. 재생 비용이 커지면 주기적으로 Snapshot을 저장해 이후 로딩 비용을 줄인다.
[Command]
   |
   v
[Aggregate] --load events--> [Event Store]
   |                             |
   | validate & create event     | append-only
   v                             v
[new Event] ----------------> [Immutable Log]
                                  |
                                  +--> [Projection / Read Model]
                                  +--> [Snapshot Builder]

이 구조의 본질은 "상태는 계산 결과"라는 점이다. 따라서 이벤트 설계가 곧 데이터 모델 설계가 된다. 이벤트는 과거 사실을 표현해야 하므로 의미가 명확해야 하고, 한번 저장되면 수정하기보다 새 정정 이벤트를 추가하는 방식이 일반적이다. 또한 시간이 지날수록 이벤트 스키마가 진화하므로, upcasting·versioning·migration 전략이 매우 중요하다. Event Sourcing은 강력하지만, 이벤트 설계를 잘못하면 오히려 장기 유지보수 비용이 커질 수 있다.

4. 비교 및 연결

항목CRUD 중심 저장Event Sourcing
저장 대상현재 상태상태를 만든 이벤트 이력
감사 추적별도 로그 필요기본적으로 내장
상태 재현제한적특정 시점 재구성 가능
복잡도낮음이벤트 설계·재생·버전 관리 복잡

Event Sourcing은 CQRS와 자주 결합된다. 이벤트 저장소를 write 측 원천으로 사용하고, projection으로 read 모델을 구성하면 자연스러운 조합이 된다. 그러나 둘은 독립 개념이다. CQRS만 쓰고 현재 상태 저장을 유지할 수도 있고, Event Sourcing을 쓰되 단순 조회 모델을 둘 수도 있다. 또한 Transactional Outbox와는 목적이 다르다. Outbox는 외부 통신 신뢰성, Event Sourcing은 상태 원천 모델의 전환에 초점이 있다.

5. 실무 적용 및 판단

실무 적용에 적합한 영역은 감사 추적이 중요하고 상태 전이 이력이 비즈니스적으로 큰 의미를 갖는 도메인이다. 주문 이력, 계좌 거래, 보험 청구, 워크플로우 엔진, 규정 준수 시스템 등이 대표적이다. 반대로 단순 CRUD 관리 화면이나 이력 가치가 낮은 마스터 데이터에는 과도한 설계가 될 수 있다.

판단 체크리스트는 다음과 같다.

  • 상태 변화의 이력이 비즈니스적으로 중요한가?
  • 과거 시점 재현, 감사, 재계산 요구가 실제로 존재하는가?
  • 이벤트 스키마 버전 관리와 장기 보존을 운영할 역량이 있는가?
  • Projection 재구축과 Snapshot 전략을 설계할 수 있는가?
  • 팀이 "현재 값"이 아니라 "사건의 역사"로 사고할 준비가 되어 있는가?

6. 기대효과 및 결론

Event Sourcing의 효과는 완전한 감사 추적, 상태 재현 가능성, 다중 읽기 모델 재구축, 도메인 이벤트 중심 설계에 있다. 데이터가 왜 현재 상태가 되었는지 설명 가능해지고, 새로운 분석 요구가 생겨도 과거 이벤트로부터 다시 모델을 만들 수 있다. 이는 변화가 많은 비즈니스와 규제 환경에서 큰 장점이다.

그러나 이벤트 설계 난이도, 스키마 진화, 저장량 증가, 디버깅 방식의 변화라는 비용이 따른다. 따라서 Event Sourcing은 모든 시스템의 기본값이 아니라, 역사 자체가 자산인 도메인에서 강력한 선택지다. 결론적으로 이 패턴은 데이터 저장 방식을 바꾸는 기술이 아니라, 시스템의 진실 원천을 "현재 상태"에서 "변화의 서사"로 전환하는 아키텍처적 발상이다.
