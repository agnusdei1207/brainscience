0. 핵심 인사이트

핵심: Service Mesh는 서비스 내부 코드가 아니라 인프라 계층의 프록시 네트워크에서 서비스 간 통신 정책, 보안, 관측성을 일관되게 적용해 MSA 운영 복잡도를 낮추는 구조다. 비유: 각 차량 운전자가 제멋대로 규칙을 구현하는 대신, 도로 관제 시스템이 신호·통행 규칙·CCTV를 중앙에서 관리해 전체 교통 흐름을 통제하는 도시 인프라와 같다.

📝 모범 답안

1. 개요 및 필요성

서비스 메시(Service Mesh)는 마이크로서비스 간 동서(East-West) 트래픽을 전용 프록시 계층으로 처리하여, 재시도, 타임아웃, 로드밸런싱, 상호 TLS (mTLS), 인증서 배포, 정책 적용, 트레이싱 수집 등을 애플리케이션 코드 바깥에서 통일적으로 수행하는 아키텍처다. 대표 구현으로 Istio와 Linkerd가 널리 알려져 있다.

이 개념이 필요한 이유는 서비스 수가 늘어날수록 네트워크 관련 공통 기능을 각 언어·프레임워크 코드에 중복 구현하기 어렵기 때문이다. 예를 들어 Java 서비스는 Resilience4j를 쓰고, Go 서비스는 직접 구현하고, Node 서비스는 다른 라이브러리를 쓰면 정책 일관성과 운영 가시성이 깨진다. 서비스 메시는 이를 인프라 계층으로 끌어올려 언어 독립적으로 제어하려는 시도다. 즉 공통 통신 기능을 애플리케이션 관심사에서 분리하는 것이 본질이다.

서비스 메시의 구조는 제어와 데이터의 분리다. 컨트롤 플레인은 정책과 인증서를 관리하지만 실제 요청 패킷은 데이터 플레인 프록시들이 처리한다. 이 덕분에 애플리케이션 코드는 비교적 단순하게 유지하면서도, 운영자는 프록시 계층에서 전체 통신 정책을 조정할 수 있다.

3. 구조 및 원리

핵심 조건: 모든 서비스 트래픽이 메시 프록시를 경유해야 하며, 서비스 아이덴티티와 인증서 체계가 통일되어야 하고, 네트워크 정책 운영을 애플리케이션 팀과 플랫폼 팀이 분담할 수 있어야 한다.

동작 순서:

  1. 서비스가 배포되면 각 Pod 또는 노드에 프록시가 함께 배치되고, 컨트롤 플레인으로부터 라우팅·보안 정책을 수신한다.
  2. 서비스 A가 서비스 B를 호출하면 애플리케이션이 직접 B와 통신하는 대신 로컬 프록시로 요청을 보낸다.
  3. 프록시는 mTLS 인증, 서비스 발견, 로드밸런싱, 재시도, timeout 정책을 적용한 뒤 상대 프록시에 전달한다.
  4. 상대 프록시는 요청을 검증하고 서비스 B에 전달한다.
  5. 양쪽 프록시는 호출 메트릭과 트레이스를 수집해 관측성 시스템으로 보낸다.
+------------------+      mTLS / routing / retry      +------------------+
| Pod A            | <--------------------------------> | Pod B            |
|  App A           |                                    |  App B           |
|  Sidecar Proxy   |                                    |  Sidecar Proxy   |
+------------------+                                    +------------------+
         ^                                                        ^
         |                                                        |
         +---------------- Control Plane --------------------------+
                    policy / cert / telemetry configuration

이 구조의 장점은 공통 네트워크 기능의 일관성이다. 카나리 배포, A/B 테스트, 장애 주입, mTLS, 인증 정책을 서비스 코드 수정 없이 적용할 수 있다. 그러나 프록시 홉이 늘어나므로 지연과 자원 사용량이 증가하며, 메시 자체가 복잡한 운영 대상이 된다. 따라서 서비스 메시는 단순한 서비스 수십 개 규모에서 항상 필요한 것은 아니며, 조직의 플랫폼 역량이 뒷받침되어야 한다.

4. 비교 및 연결

항목API GatewayService Mesh
주 대상 트래픽북-남(North-South)동-서(East-West)
위치외부 진입점서비스 간 내부 통신 계층
기능인증, 라우팅, 외부 공개 APImTLS, 재시도, 정책, 내부 관측성
관계대체 아님상호 보완적

Service Mesh는 Sidecar Pattern 위에서 많이 구현되지만, 반드시 사이드카만 쓰는 것은 아니다. 최근에는 ambient mesh처럼 프록시 배치 방식을 바꾸는 흐름도 있다. 또한 Circuit Breaker, Retry, Distributed Tracing, Zero Trust Network와 긴밀히 연결된다. Istio는 기능이 풍부하고, Linkerd는 상대적으로 단순성과 경량성을 강조한다는 차이가 자주 비교 포인트가 된다.

5. 실무 적용 및 판단

실무에서 메시가 빛나는 환경은 다음과 같다. 서비스 수가 많고 다언어 스택이 공존하며, 보안과 정책 통제가 중요하고, 카나리 배포·트래픽 분할·mTLS·세밀한 추적이 필요한 조직이다. Kubernetes 기반 대규모 플랫폼에서 특히 효과가 크다. 반면 서비스 수가 적고, 공통 기능을 애플리케이션 라이브러리 수준에서 충분히 관리할 수 있다면 메시 운영 복잡도가 더 큰 비용이 될 수 있다.

체크리스트는 다음과 같다.

  • 서비스 수와 팀 수가 공통 통신 정책의 중앙 관리가 필요할 정도로 많은가?
  • mTLS, 정책 기반 접근 제어, 트래픽 분할 요구가 강한가?
  • 프록시 리소스 비용과 운영 복잡도를 감당할 수 있는가?
  • 플랫폼 팀이 컨트롤 플레인과 관측성 스택을 운영할 수 있는가?
  • API Gateway와 역할 경계를 명확히 구분했는가?

6. 기대효과 및 결론

서비스 메시의 기대효과는 코드 중복 제거, 보안 표준화, 통신 정책의 중앙 일관성, 풍부한 관측성에 있다. 애플리케이션 팀은 비즈니스 로직에 집중하고, 플랫폼 팀은 네트워크 운영을 공통 계층에서 관리할 수 있다. 대규모 MSA에서는 이 분리가 상당한 운영 효율을 만든다.

그러나 메시는 또 하나의 분산 시스템을 도입하는 것이므로, 학습 비용과 장애 면적도 함께 증가한다. 따라서 무조건 도입하기보다 조직 규모, 보안 요구, 운영 성숙도를 기준으로 판단해야 한다. 결론적으로 서비스 메시의 본질은 "프록시를 많이 두는 것"이 아니라, 서비스 간 통신을 애플리케이션 코드에서 분리해 플랫폼 차원에서 통제 가능한 자원으로 만드는 데 있다.

7. 발전 흐름도
