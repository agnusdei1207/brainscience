0. 핵심 인사이트

핵심: 분산 추적은 마이크로서비스 요청을 하나의 Trace로 묶어, 어느 구간에서 지연·오류·재시도가 발생했는지를 서비스 경계를 넘어서 설명 가능한 형태로 복원하는 관측성 체계다. 비유: 국제 특송 화물에 단일 운송장 번호를 붙여 공항·세관·물류창고를 거치는 모든 이동 이력을 한 화면에서 추적하는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

분산 추적(Distributed Tracing)은 단일 요청이 API Gateway, 인증, 주문, 결제, 재고, 알림처럼 여러 서비스와 메시지 브로커를 통과할 때 그 전체 흐름을 하나의 실행 맥락으로 묶어 분석하는 기술이다. 모놀리식 환경에서는 애플리케이션 로그와 스택 트레이스만으로 병목을 찾을 수 있었지만, 마이크로서비스 환경에서는 동일한 사용자 요청이 수십 개 프로세스와 노드를 거치므로 로그만으로는 인과 관계를 재구성하기 어렵다.

로그는 사건의 내용을 남기고, 메트릭은 집계된 건강 상태를 보여주지만, "어떤 호출 체인이 왜 느려졌는가"라는 질문에는 추적이 필요하다. 특히 동기 호출과 비동기 메시징이 혼재한 구조에서는 Trace ID가 없으면 각 서비스 로그가 서로 다른 사건처럼 보인다. 이때 장애 원인 분석은 팀 간 추정과 책임 공방으로 변질되기 쉽다.

따라서 분산 추적의 필요성은 단순 모니터링을 넘어선다. 첫째, 호출 경로별 지연 시간 분해가 가능해져 병목 지점을 객관적으로 찾을 수 있다. 둘째, 재시도·타임아웃·서킷 브레이커가 실제로 어떤 경로에서 작동했는지 확인할 수 있다. 셋째, 배포 이후 성능 회귀(regression)를 서비스 단위가 아니라 사용자 요청 단위로 추적할 수 있다. 결국 분산 추적은 MSA 운영에서 "관측 가능한 인과 사슬"을 만드는 기반이다.

구성요소는 계층적으로 맞물린다. 애플리케이션은 계측을 통해 Span을 만들고, Context Propagation으로 하위 서비스에 Trace를 이어 준다. Collector는 다양한 언어 런타임에서 발생한 Span을 공통 형식으로 모으고, 저장소와 UI는 이를 검색 가능한 실행 그래프로 복원한다. Sampling은 이 전체 파이프라인의 비용과 정확도를 동시에 좌우한다.

3. 구조 및 원리

핵심 조건: 모든 서비스가 동일한 Trace Context 규약을 사용해야 하며, Span 시작·종료 시점이 일관되어야 하고, 샘플링 정책은 전체 경로를 끊지 않는 방식으로 설계되어야 한다.

동작 순서:

  1. 진입점(API Gateway, Ingress, Edge Proxy)에서 새로운 Trace를 생성하거나 기존 traceparent 헤더를 수용한다.
  2. 첫 서비스는 현재 요청을 대표하는 Root Span을 만들고, 인증·DB 질의·외부 API 호출 같은 하위 작업마다 Child Span을 생성한다.
  3. 다운스트림 호출 시 Trace ID와 Parent Span ID를 HTTP 헤더, gRPC metadata, 메시지 헤더에 포함하여 전달한다.
  4. 각 서비스는 자신의 처리 시간을 독립 Span으로 기록하고, 오류·태그·이벤트 로그를 Span 속성으로 남긴다.
  5. Collector는 Span을 수집해 Trace 단위로 조합하며, UI는 시간축 기준으로 Gantt 형태의 호출 경로를 복원한다.
  6. 운영자는 특정 Trace에서 임계 경로(critical path), 오류 전파, 비정상 재시도, N+1 호출 패턴을 식별한다.
[Client]
   |
   v
[API Gateway] -- Root Span --> [Order Service] -- Child Span --> [Payment Service]
                                   |                                   |
                                   +--> [Inventory Service]            +--> [PG API]
                                   |
                                   +--> [Kafka Produce] ---> [Notification Consumer]

Trace ID = T-12345
Spans    = gateway, order, inventory, payment, pg-call, kafka-produce, notify-consume

분산 추적의 핵심은 "시간 정보가 있는 호출 그래프"를 만드는 데 있다. 로그는 문장 단위로 남지만 Span은 시작 시각, 종료 시각, 상위 Span, 상태 코드를 포함하므로 서비스 간 인과 관계를 구조적으로 표현한다. 이 때문에 동일한 평균 응답 시간이라도 어떤 호출이 임계 경로인지, 병렬 호출 중 어느 가지가 느린지 판단할 수 있다.

Zipkin과 Jaeger는 모두 이 모델을 구현하지만 접근 방식에 차이가 있다. Zipkin은 구조가 단순하고 빠르게 도입하기 쉬우며, Jaeger는 Agent-Collector-Query 아키텍처와 적응형 샘플링, 서비스 의존성 분석에 강점이 있다. 최근에는 OpenTelemetry가 계측 표준 역할을 하면서 수집 대상은 OTel로 통일하고, 백엔드는 Zipkin·Jaeger·Tempo 등으로 선택하는 방식이 일반적이다.

실무에서는 비동기 구간이 가장 까다롭다. HTTP 체인에서는 부모-자식 관계가 명확하지만, Kafka나 RabbitMQ에서는 생산과 소비가 시간적으로 분리되므로 메시지 헤더에 Trace Context를 넣고 "producer span"과 "consumer span"을 연결해야 한다. 또한 샘플링으로 인해 상위 Span은 있는데 하위 Span이 없는 단절 Trace가 생기면 분석 가치가 급격히 떨어진다. 따라서 오류 요청, 고지연 요청, 특정 테넌트 요청은 우선적으로 보존하는 tail-based sampling이 유리하다.

분산 추적은 로그나 메트릭을 대체하지 않는다. 로그는 세부 오류 메시지를, 메트릭은 시스템 건강 상태를, 추적은 요청 수준의 인과 관계를 제공한다. 따라서 세 신호를 상호 연계하는 Observability 삼각 구성이 중요하다. 또한 서비스 메시(Service Mesh)와 결합하면 애플리케이션 수정 없이 네트워크 레벨 Span을 수집할 수 있지만, 애플리케이션 내부 로직까지 보려면 코드 계측이 여전히 필요하다.

5. 실무 적용 및 판단

채택이 적합한 경우는 서비스 수가 증가하여 장애 분석 시간이 길어지는 조직, 외부 API 의존도가 높아 타임아웃 원인 분석이 중요한 조직, 그리고 SLA/SLO 기반 운영이 필요한 조직이다. 반대로 단일 애플리케이션이나 호출 경로가 매우 단순한 시스템에서는 계측 비용이 과할 수 있다.

실무 체크리스트는 다음과 같다.

  • 모든 서비스에 OpenTelemetry SDK 또는 자동 계측 에이전트를 일관되게 배포했는가
  • HTTP, gRPC, 메시지 브로커 모두에서 Trace Context를 전달하는가
  • Span 이름 규칙, 서비스 이름 규칙, 태그 키 규칙이 통일되었는가
  • 개인정보와 비밀값을 Span attribute에 기록하지 않도록 필터링했는가
  • 샘플링 정책이 오류 요청과 장기 지연 요청을 우선 보존하는가

대표 사례로는 Kubernetes 환경에서 OpenTelemetry Collector를 DaemonSet 또는 Gateway 모드로 두고, 백엔드로 Jaeger나 Tempo를 사용하는 구성이 많다. Zipkin은 간결한 도입과 학습 비용 측면에서 강점이 있고, Jaeger는 대규모 운영과 적응형 샘플링에서 강점을 보인다.

6. 기대효과 및 결론

분산 추적의 직접 효과는 장애 분석 시간 단축과 성능 병목의 정밀한 식별이다. 그러나 더 본질적인 효과는 서비스 경계를 넘는 공통 운영 언어를 만든다는 점이다. 어느 팀의 잘못인지가 아니라, 어떤 Trace 경로가 지연을 만들었는지로 대화가 바뀌기 때문이다.

다만 모든 Span을 무한정 수집하면 비용과 저장량이 급증하고, 계측이 불완전하면 잘못된 결론을 낼 수 있다. 따라서 추적은 도구 도입 자체보다 계측 표준화, 샘플링 설계, 로그·메트릭 연계까지 포함한 운영 체계로 접근해야 한다. 결론적으로 분산 추적은 MSA의 선택 사항이 아니라, 복잡성을 감당하기 위한 기본 관측성 인프라다.
