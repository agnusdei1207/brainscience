0. 핵심 인사이트

핵심: ACL은 레거시 시스템과 신규 도메인 사이에서 데이터 구조와 용어 체계를 번역해, 외부 모델의 왜곡이 내부 도메인 설계를 오염시키지 않도록 보호하는 경계 계층이다. 비유: 외교 현장에서 통역관이 단어만 옮기는 것이 아니라, 서로 다른 제도와 맥락의 의미 차이를 조정해 오해를 막는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

신규 시스템이 레거시 시스템과 통합될 때 가장 흔한 실패는 기술 연동이 아니라 개념 오염이다. 예를 들어 레거시의 고객 개념이 계약자·수익자·사용자를 뒤섞은 구조인데, 신규 서비스가 그 값을 그대로 받아 쓰면 신규 도메인의 모델링 기준도 모호해진다. 이때 표면적으로는 연동이 빠르게 끝난 것처럼 보여도, 시간이 지날수록 신규 코드가 레거시의 데이터 왜곡과 예외 규칙을 그대로 흡수하게 된다.

도메인 주도 설계(Domain-Driven Design, DDD)에서 ACL은 이러한 오염을 차단하기 위해 사용된다. 신규 도메인은 자신만의 용어와 규칙을 유지하고, 외부 세계와의 차이는 경계에서 번역한다. 즉 ACL의 목적은 단순 포맷 변환이 아니라 "의미의 분리"다.

이 패턴이 필요한 이유는 세 가지다. 첫째, 레거시 통합이 불가피한 상황에서 신규 모델의 수명을 지킨다. 둘째, 외부 시스템 교체 시 영향 범위를 ACL 내부로 국한한다. 셋째, 서비스 분해와 현대화 과정에서 점진적 독립을 가능하게 한다. 따라서 ACL은 레거시와 연결하기 위한 임시 어댑터가 아니라, 경계 품질을 결정하는 전략적 계층이다.

ACL은 보통 Facade와 Translator를 중심으로 구성된다. 신규 서비스는 레거시 API나 테이블 구조를 직접 알지 않고, ACL이 제공하는 표준 계약만 사용한다. 이 구조 덕분에 레거시 변경은 ACL 내부 변환 로직만 수정하면 되고, 신규 도메인 모델은 안정적으로 유지된다.

3. 구조 및 원리

핵심 조건: 신규 도메인의 용어와 모델이 먼저 정의되어 있어야 하며, 외부 시스템 의존성은 ACL로 단일화되어야 하고, 번역 규칙은 명시적·테스트 가능해야 한다.

동작 순서:

  1. 신규 서비스는 자신의 도메인 언어로 ACL에 요청을 보낸다.
  2. ACL은 요청을 레거시 시스템이 이해하는 포맷과 프로토콜로 변환한다.
  3. 레거시 시스템의 응답, 코드값, 오류 형식을 ACL이 수신한다.
  4. ACL은 외부 의미를 내부 도메인 모델로 재구성하고, 필요한 보정 규칙을 적용한다.
  5. 신규 서비스는 레거시 세부사항을 모른 채 정제된 결과만 사용한다.
  6. 외부 시스템이 바뀌면 ACL 내부 어댑터와 변환 규칙만 교체한다.
[New Service Domain]
        |
        v
   [ACL Facade]
   /     |      \
[Mapper][Policy][Adapter]
        |         \
        |        [Legacy API / DB / MQ]
        |
  Canonical Model Returned

ACL의 본질은 방화벽이 아니라 번역 엔진이다. 예를 들어 레거시의 CUST_TP=7이 신규 시스템에서는 CorporateCustomer를 의미할 수 있다. 이때 ACL이 없다면 신규 서비스는 7이라는 외부 코드 체계를 직접 알아야 한다. 이런 지식이 여러 서비스에 퍼지면 외부 모델이 내부 모델을 잠식한다. ACL은 이 의존성을 한 곳에 모아 의미를 재정의한다.

구현 형태는 전용 마이크로서비스, 라이브러리, 또는 Integration Layer로 다양하다. 외부 변화가 잦고 여러 신규 서비스가 같은 레거시를 참조한다면 독립 서비스형 ACL이 유리하다. 반면 호출 지연이 민감하고 사용 범위가 좁다면 라이브러리형도 가능하다. 중요한 것은 형태보다 의존성 방향이다. 신규 도메인이 외부 모델을 모르게 하는 단방향 의존성이 유지되어야 한다.

ACL은 Adapter보다 한 단계 상위 개념이다. Adapter가 인터페이스 호환성에 집중한다면, ACL은 도메인 의미 체계를 분리하는 데 집중한다. 또한 스트랭글러 피그 패턴과 자주 함께 사용된다. 레거시 기능을 점진 전환할 때 ACL이 없으면 신규 서비스가 레거시 규칙을 그대로 흡수하게 되어, 겉으로는 분리되었지만 본질적으로는 여전히 레거시에 묶인 상태가 된다.

5. 실무 적용 및 판단

ACL이 적합한 상황은 레거시 시스템의 용어 체계와 데이터 품질이 신규 서비스와 크게 다른 경우, 외부 시스템이 자주 변하거나 교체될 가능성이 있는 경우, 그리고 장기적으로 신규 도메인의 독립 운영을 목표로 하는 경우다. 반대로 단순 조회형 통합이나 수명이 짧은 임시 연계에서는 과도한 계층이 될 수 있다.

실무 체크리스트는 다음과 같다.

  • 신규 도메인의 핵심 엔티티와 용어가 레거시와 독립적으로 정의되었는가
  • 외부 코드값, 상태값, 오류 코드를 ACL 내부에서만 해석하는가
  • 변환 규칙이 테스트 데이터와 회귀 테스트로 보호되는가
  • ACL 내부 로직이 비대해져 또 다른 레거시가 되지 않도록 책임을 제한했는가
  • 추후 레거시 제거 시 ACL도 함께 축소·폐기할 계획이 있는가

대표 구현으로는 레거시 SOAP 서비스를 신규 REST/gRPC 계약으로 감싸는 방식, 레거시 DB의 조인 결과를 도메인별 Canonical API로 재구성하는 방식, 또는 메인프레임 전문을 현대적 이벤트 계약으로 변환하는 방식이 있다.

6. 기대효과 및 결론

ACL을 적용하면 신규 서비스는 외부 시스템 변경에 덜 흔들리고, 설계 언어를 장기적으로 유지할 수 있다. 이는 개발 생산성뿐 아니라 조직 차원의 의사소통 품질에도 직접 기여한다. 동일한 도메인 언어를 유지할 수 있기 때문이다.

하지만 ACL이 만능은 아니다. 번역 규칙이 많아질수록 성능 지연과 복잡도가 증가하고, 잘못 설계하면 모든 예외 처리와 보정 로직이 ACL에 몰려 거대한 통합 계층이 된다. 따라서 ACL은 "모든 외부 연동에 일괄 적용"하는 기술이 아니라, 도메인 오염 위험이 큰 경계에 선택적으로 적용해야 한다. 결론적으로 ACL은 레거시와 공존하면서도 신규 시스템의 순수성을 보존하기 위한 핵심 보호막이다.
