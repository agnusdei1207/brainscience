0. 핵심 인사이트

핵심: 멀티 테넌트 데이터베이스 아키텍처는 하나의 SaaS 플랫폼이 여러 고객 조직의 데이터를 공용 인프라 위에서 처리하되, 보안·성능·복구 단위는 테넌트 기준으로 분리하도록 설계하는 데이터 격리 전략이다. 비유: 같은 건물과 설비를 공유하더라도 출입 카드, 전기 계량, 방음, 비상 복구 계획은 세대별로 분리된 고층 오피스 빌딩 운영과 같다.

📝 모범 답안

1. 개요 및 필요성

SaaS(Software as a Service)는 고객사마다 별도 시스템을 운영하는 방식보다, 공용 플랫폼 위에 다수 고객을 수용해야 원가 경쟁력이 생긴다. 그러나 공용 인프라를 사용한다고 해서 데이터까지 뒤섞이면 안 된다. 한 고객의 조회 조건 누락, 백업 복구 실수, 과도한 부하가 다른 고객에게 곧바로 영향을 주면 SaaS 비즈니스의 신뢰 기반이 무너진다.

따라서 멀티 테넌시의 핵심 과제는 두 가지 상충 목표를 동시에 만족하는 것이다. 첫째, 인프라·운영·배포 측면에서는 최대한 공유해 효율을 높여야 한다. 둘째, 보안·성능·복구·과금 측면에서는 고객별 독립성을 보장해야 한다. 이 균형을 어떻게 잡느냐에 따라 Database per Tenant, Schema per Tenant, Shared Schema 같은 패턴이 갈린다.

이 아키텍처가 필요한 이유는 단순 비용 절감이 아니다. 고객 수가 늘수록 배포 자동화, 스키마 변경, 모니터링, 과금, 규제 준수까지 모두 테넌트 단위로 관리되어야 하기 때문이다. 결국 멀티 테넌트 DB 설계는 데이터 저장 방식이 아니라 SaaS 운영 모델 전체를 결정하는 아키텍처 선택이다.

이 구성요소는 인증부터 백업까지 전 구간에 걸친다. 요청이 들어오면 먼저 테넌트를 식별하고, 해당 테넌트의 격리 모델에 따라 DB 연결과 접근 정책이 달라진다. 이후 성능 제어, 과금, 감사, 복구 체계 역시 동일한 테넌트 식별자를 기준으로 작동해야 한다.

3. 구조 및 원리

핵심 조건: 모든 데이터 접근 경로에서 테넌트 식별자가 강제되어야 하며, 격리 수준은 보안 요구·운영 비용·복구 단위를 함께 고려해 선택해야 한다.

동작 순서:

  1. 사용자가 로그인하거나 API를 호출하면 Tenant Resolver가 테넌트 ID를 확정한다.
  2. 애플리케이션은 테넌트 정책에 따라 전용 DB, 전용 스키마, 또는 공유 테이블 중 대상 저장소를 선택한다.
  3. 데이터 접근 계층은 쿼리 생성 시 테넌트 조건을 자동 주입하거나 DB 정책으로 강제한다.
  4. 성능 모니터링은 테넌트별 쿼리량, 저장량, 지연 시간을 집계해 노이즈 네이버를 감지한다.
  5. 백업과 복구는 격리 모델에 맞춰 전체 인스턴스, 스키마, 또는 테넌트 데이터 세트 단위로 수행한다.
  6. 고객 규모나 규제 등급이 높아지면 공유형에서 전용형으로 승격하는 경로를 마련한다.
[Request]
   |
   v
[Tenant Resolver] --> tenant = ACME
   |
   v
[Routing Policy]
   |---- Gold  -> [Dedicated DB]
   |---- Standard -> [Shared DB / Schema per Tenant]
   |---- Basic -> [Shared Schema + tenant_id]

모든 조회/쓰기 조건은 tenant 경계를 강제해야 한다.

세 가지 대표 모델은 비용과 격리 수준의 교환 관계에 있다. Database per Tenant는 복구와 규제 대응이 유리하지만 운영 비용이 높다. Schema per Tenant는 논리적 분리와 공용 인프라의 균형을 취할 수 있지만 스키마 수가 많아지면 운영이 복잡해진다. Shared Schema는 효율이 가장 높지만, 쿼리 누락과 성능 간섭 위험이 커서 애플리케이션과 DB 양쪽에서 강력한 안전장치가 필요하다.

실무에서 가장 위험한 부분은 행 수준 공유 모델이다. 개발자가 WHERE tenant_id = ?를 빠뜨리는 순간 데이터 유출이 발생할 수 있기 때문이다. 따라서 PostgreSQL Row-Level Security, ORM 전역 필터, 저장 프로시저, 데이터 접근 래퍼 등 다중 방어층을 두는 것이 바람직하다. 또한 백업도 동일하게 설계해야 한다. 저장은 공유하더라도 복구는 테넌트 단위로 요구되는 경우가 많으므로, 논리 백업과 메타데이터 카탈로그를 함께 관리해야 한다.

4. 비교 및 연결

모델장점한계적합 상황
Database per Tenant최고 수준 격리, 개별 복구 용이비용·운영 복잡도 큼금융, 공공, 대형 엔터프라이즈

Shared Schema비용 효율과 확장성 우수데이터 유출·성능 간섭 위험대량 소형 고객 SaaS

멀티 테넌시는 단순한 DB 구조가 아니라 인증, 캐시, 검색 인덱스, 로그, 분석 파이프라인까지 함께 설계해야 한다. 예를 들어 검색 엔진 인덱스나 객체 스토리지 키도 테넌트 경계를 반영하지 않으면 DB만 분리해도 보안 사고가 발생할 수 있다. 또한 데이터 메시나 도메인 분리와 연결될 때는 테넌트 경계와 도메인 경계가 충돌하지 않는지도 검토해야 한다.

5. 실무 적용 및 판단

초기 SaaS는 Shared Schema로 시작해도 되지만, 다음 조건이 보이면 상위 격리 모델을 검토해야 한다. 고객별 보안 규정이 상이한가, 개별 복구 요구가 빈번한가, 특정 고객 트래픽이 다른 고객을 방해하는가, 커스텀 스키마 요구가 많은가가 판단 기준이다.

실무 체크리스트는 다음과 같다.

  • 인증 토큰에서 테넌트 식별이 일관되게 추출되는가
  • DB, 캐시, 검색, 파일 저장소 모두 동일한 테넌트 경계를 적용하는가
  • 공유형 모델이라면 Row-Level Security나 강제 필터가 적용되는가
  • 백업·복구를 테넌트 단위로 수행할 수 있는가
  • 고객 성장에 따라 전용 DB로 승격하는 경로가 자동화되어 있는가

실무에서는 흔히 "기본 공유형 + 프리미엄 전용형"의 혼합 모델을 쓴다. 대부분 고객은 Shared Schema에 수용하고, 규제·대용량 고객만 전용 DB로 이동시키는 방식이다. 이는 비용 효율과 엔터프라이즈 수요를 함께 충족시키는 현실적 전략이다.

6. 기대효과 및 결론

멀티 테넌트 DB 아키텍처의 효과는 단순 자원 절감에 그치지 않는다. 운영 자동화, 일괄 배포, 기능 출시 속도, 고객 확장성이 함께 개선된다. 특히 스키마 진화와 공통 기능 배포를 중앙에서 통제할 수 있다는 점은 SaaS 사업의 핵심 경쟁력이다.

그러나 공유도가 높아질수록 격리 사고의 파급 범위도 커진다. 따라서 비용 절감만 보고 가장 공유도가 높은 모델을 택하는 것은 위험하다. 보안 등급, 고객 규모, 복구 SLA, 데이터 주권 요건을 기준으로 적정 격리 수준을 선택해야 한다. 결론적으로 멀티 테넌트 아키텍처의 핵심은 "얼마나 많이 공유할 것인가"가 아니라 "무엇을 공유하고 무엇은 반드시 분리할 것인가"를 명확히 정의하는 데 있다.
