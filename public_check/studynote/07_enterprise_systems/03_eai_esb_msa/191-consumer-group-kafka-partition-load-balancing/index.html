0. 핵심 인사이트

핵심: 컨슈머 그룹은 Kafka 토픽의 파티션을 여러 소비자 인스턴스에 분배해 중복 처리 없이 병렬 소비를 가능하게 하는 논리적 협업 단위다. 비유: 한 창고의 여러 작업 구역을 팀원들에게 나누어 맡기되, 같은 구역을 두 사람이 동시에 담당하지 않도록 반장과 출입표가 관리되는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

Kafka는 대용량 메시지를 빠르게 적재할 수 있지만, 실제 병목은 메시지 소비 애플리케이션에서 자주 발생한다. 소비 로직에는 DB 저장, 외부 API 호출, 파일 생성 같은 상대적으로 느린 작업이 포함되므로 단일 컨슈머로는 처리량을 따라가기 어렵다. 이때 단순히 컨슈머 인스턴스를 복제하면 같은 메시지를 여러 인스턴스가 중복 처리할 수 있다.

컨슈머 그룹은 이 문제를 해결하기 위해 등장했다. 동일 그룹에 속한 컨슈머들은 하나의 논리적 소비자처럼 동작하며, 각 파티션은 그룹 내 정확히 한 컨슈머에 할당된다. 그 결과 병렬성을 확보하면서도 같은 그룹 내부에서는 중복 처리를 피할 수 있다.

이 메커니즘은 Kafka 확장 전략의 핵심이다. 생산자 확장은 브로커와 파티션 수로 해결하지만, 소비자 확장은 컨슈머 그룹과 파티션 수의 조합으로 결정된다. 따라서 컨슈머 그룹을 이해하는 것은 Kafka 운영의 기본 전제다.

2. 구성요소

구성요소역할핵심 포인트
Topic메시지 논리 채널여러 파티션으로 분할 가능
Partition병렬성의 최소 단위순서는 파티션 내부에서만 보장

핵심 관계는 단순하다. 파티션 수가 병렬성의 상한을 정하고, 그룹 내 컨슈머 수는 실제 병렬 소비 인스턴스 수를 정한다. 컨슈머가 파티션보다 많으면 남는 컨슈머는 유휴 상태가 되고, 파티션이 많으면 일부 컨슈머가 여러 파티션을 담당한다.

3. 구조 및 원리

핵심 조건: 같은 그룹 안에서는 하나의 파티션을 동시에 하나의 컨슈머만 읽어야 하며, 메시지 순서 보장은 파티션 내부에 한정되고, 오프셋 커밋 전략이 처리 의미론을 결정한다.

동작 순서:

  1. 컨슈머 인스턴스들이 동일한 Group ID로 브로커에 참여한다.
  2. Group Coordinator가 현재 멤버 수와 파티션 수를 기준으로 할당 계획을 계산한다.
  3. 각 컨슈머는 자신에게 배정된 파티션만 poll() 하여 메시지를 읽는다.
  4. 비즈니스 처리 후 성공 지점에 따라 오프셋을 커밋한다.
  5. 컨슈머 장애, 스케일 아웃, 스케일 인이 발생하면 Rebalance가 실행되어 파티션이 재배치된다.
  6. 새 컨슈머는 마지막 커밋 오프셋 이후부터 처리를 이어받는다.
Topic: orders
Partitions: P0, P1, P2, P3

Consumer Group G1
  C1 -> P0, P1
  C2 -> P2
  C3 -> P3

Consumer Group G2
  A1 -> P0, P1, P2, P3   (독립 구독)

컨슈머 그룹의 중요한 성질은 "그룹 간 독립성"이다. 같은 토픽이라도 다른 Group ID를 사용하면 서로 다른 구독자로 간주되어 동일 메시지를 각자 읽을 수 있다. 따라서 주문 토픽을 정산 그룹과 분석 그룹이 동시에 소비하는 구조가 가능하다. 반면 같은 그룹 내에서는 파티션 독점 규칙 때문에 중복이 없다.

오프셋 커밋 전략은 처리 의미를 결정한다. 선커밋 후처리는 장애 시 메시지 손실 위험이 있고, 후커밋은 중복 재처리 가능성이 있다. Kafka는 기본적으로 at-least-once 처리에 가깝기 때문에, 소비자는 멱등성을 확보하는 쪽이 일반적이다. 또한 긴 처리 시간을 가진 컨슈머는 Rebalance 시 세션 타임아웃으로 탈락할 수 있으므로, heartbeat와 cooperative rebalance 설정을 함께 고려해야 한다.

4. 비교 및 연결

항목같은 그룹 내 컨슈머 추가파티션 수 증가새로운 그룹 추가
목적동일 업무 병렬 처리병렬성 상한 확대독립적 추가 소비
효과현재 파티션 범위 내 부하 분산처리량 잠재력 증가동일 메시지 재활용
한계파티션 수 이상 확장 불가데이터 재분배 비용 발생중복 처리 아닌 별도 구독

컨슈머 그룹은 Queue의 Worker Pool과 유사하지만, Kafka는 로그 기반 저장소이므로 그룹별로 독립 오프셋을 유지한다는 점이 다르다. 또한 EDA와 결합하면 한 토픽을 여러 그룹이 서로 다른 목적의 파이프라인으로 재활용할 수 있다.

5. 실무 적용 및 판단

컨슈머 그룹 설계에서 가장 먼저 결정할 것은 파티션 수다. 예상 최대 처리량, 키 기반 순서 요구, 소비자 수 상한을 고려해 미리 설계해야 한다. 파티션을 너무 적게 만들면 확장 여지가 사라지고, 너무 많이 만들면 브로커와 컨슈머 메타데이터 비용이 증가한다.

실무 체크리스트는 다음과 같다.

  • 키 기반 순서가 필요한 업무는 동일 키가 같은 파티션으로 가는가
  • 최대 소비자 수보다 충분한 파티션 수를 확보했는가
  • 오프셋 커밋 시점이 비즈니스 처리 완료와 일치하는가
  • Rebalance 동안 처리 중복과 중단 시간을 허용 가능한 수준으로 설계했는가
  • Lag 모니터링과 재처리 절차가 마련되어 있는가

대표 사례는 주문 승인 이벤트를 같은 그룹의 다수 워커가 병렬 처리하는 구조, 그리고 같은 토픽을 다른 그룹이 각각 정산·알림·분석 용도로 소비하는 구조다. 이때 그룹 개념을 잘못 이해하면 중복 메일 발송이나 데이터 누락 같은 치명적 문제가 발생한다.

6. 기대효과 및 결론

컨슈머 그룹의 효과는 수평 확장, 장애 복구, 중복 없는 병렬 처리다. 특히 인스턴스 장애 시 파티션을 다른 컨슈머가 이어받을 수 있어 고가용성 측면에서도 중요하다.

하지만 컨슈머 그룹만 늘린다고 무한 확장이 가능한 것은 아니다. 파티션 수가 병렬성 한계를 정하고, 순서 보장 요구가 강할수록 키 분배 자유도는 줄어든다. 또한 Rebalance는 운영 중단과 지연을 유발할 수 있으므로 설계 초기부터 고려해야 한다. 결론적으로 Kafka 확장의 본질은 "컨슈머 수"가 아니라 "파티션 전략과 그룹 전략의 조합"에 있다.
