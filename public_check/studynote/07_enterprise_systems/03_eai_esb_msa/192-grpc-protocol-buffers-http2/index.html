0. 핵심 인사이트

핵심: gRPC는 인터페이스를 Protocol Buffers로 엄격하게 정의하고, HTTP/2 위에서 바이너리 직렬화와 스트리밍을 사용해 서비스 간 고성능·강타입 통신을 구현하는 현대적 RPC 프레임워크다. 비유: 자유 형식 편지 대신 정해진 양식의 전자 문서를 전용 고속 전송선으로 주고받아 해석 오류와 운송 지연을 동시에 줄이는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

REST와 JSON은 개방성과 인간 친화성 덕분에 외부 API에 널리 쓰인다. 그러나 내부 서비스 간 통신에서는 사람이 읽기 쉬운 형식이 항상 최적은 아니다. 동일한 필드를 반복하는 텍스트 기반 메시지는 네트워크 효율이 떨어지고, 직렬화·역직렬화 비용도 높다. 또한 동기 요청-응답 중심 구조에서는 양방향 스트리밍이나 다중 요청 병렬화가 불편하다.

gRPC는 이러한 한계를 해결하기 위해 등장했다. 먼저 .proto 파일에 서비스 메서드와 메시지 구조를 정의하고, 이를 기반으로 클라이언트와 서버 코드를 자동 생성한다. 통신 시에는 Protocol Buffers(Protobuf)의 바이너리 포맷을 사용해 메시지를 작고 빠르게 처리하고, 전송 계층으로는 HTTP/2를 사용해 멀티플렉싱과 스트리밍을 지원한다.

따라서 gRPC의 필요성은 단순 속도 향상에만 있지 않다. 계약 기반 개발, 다중 언어 코드 생성, 명확한 에러 모델, deadline 전파, 양방향 스트리밍까지 포함한 서비스 간 통신 표준화를 가능하게 한다는 점이 핵심이다.

구성요소는 계약 중심으로 결합된다. .proto가 바뀌면 생성 코드, 배포 호환성, 클라이언트 업데이트 전략이 함께 영향을 받는다. 따라서 gRPC의 운영 핵심은 런타임 자체보다 계약 진화 규칙과 호환성 관리에 있다.

3. 구조 및 원리

핵심 조건: 서비스 계약은 먼저 IDL로 정의되어야 하며, Protobuf 필드 번호는 안정적으로 관리되어야 하고, HTTP/2 연결 재사용과 deadline 전파를 전제로 설계해야 한다.

동작 순서:

  1. 설계자는 .proto 파일에 메시지 구조와 RPC 메서드를 정의한다.
  2. 코드 생성기로 서버 골격과 클라이언트 Stub를 생성한다.
  3. 클라이언트는 Channel을 통해 서버에 HTTP/2 연결을 맺고, Stub 메서드를 호출한다.
  4. 요청 객체는 Protobuf 바이너리로 직렬화되어 HTTP/2 Stream 위로 전송된다.
  5. 서버는 메서드를 실행한 뒤 응답 메시지를 다시 Protobuf로 직렬화해 반환한다.
  6. 스트리밍 RPC의 경우 하나의 연결 위에서 여러 메시지를 연속 전송하며, Metadata와 Deadline은 호출 전반에 함께 전파된다.

gRPC가 빠른 이유는 두 계층의 결합 때문이다. Protobuf는 필드 이름 대신 번호 기반 인코딩을 사용해 메시지를 작게 만들고, HTTP/2는 하나의 TCP 연결에서 다수 스트림을 동시에 처리한다. 그 결과 REST/HTTP/1.1에서 흔한 연결 오버헤드와 헤더 중복을 줄일 수 있다.

그러나 gRPC는 호환성 규칙을 지키지 않으면 오히려 운영 위험이 커진다. 필드 번호를 재사용하거나 필수 의미의 필드를 무리하게 바꾸면 구버전 클라이언트와 충돌한다. 또한 브라우저는 순수 gRPC를 직접 사용하기 어렵기 때문에 gRPC-Web이나 API Gateway의 transcoding이 필요할 수 있다. 따라서 내부 서비스 간 통신에는 매우 강력하지만, 외부 공개 API에서는 REST와 병행하는 경우가 많다.

gRPC는 OpenAPI와도 연결된다. OpenAPI가 HTTP API 문서와 계약 관리에 강하다면, gRPC는 서비스 간 호출 계약과 코드 생성에 강하다. 또한 Distributed Tracing과 결합할 때는 Metadata에 Trace Context를 전파하고, Service Mesh 환경에서는 mTLS와 정책 제어를 함께 적용할 수 있다.

5. 실무 적용 및 판단

gRPC는 내부 마이크로서비스 간 고빈도 호출, 다중 언어 백엔드, 스트리밍 데이터 전송, 엄격한 계약 관리가 필요한 시스템에 적합하다. 반대로 브라우저 직접 호출, 외부 파트너 공개 API, 캐시 친화적 리소스 조회 중심 인터페이스에는 REST가 더 적합할 수 있다.

실무 체크리스트는 다음과 같다.

  • .proto 변경 시 하위 호환 규칙을 팀 표준으로 관리하는가
  • 필드 번호 재사용 금지, reserved 처리 원칙이 있는가
  • Deadline, retry, circuit breaker 정책이 공통 Interceptor로 관리되는가
  • 브라우저나 외부 API가 필요하면 gRPC-Web 또는 REST Gateway를 병행하는가
  • tracing, auth, observability metadata를 전파하는가

대표 사례는 서비스 메시 내부의 주문-결제-재고 통신, 모바일 백엔드와 실시간 피드 스트리밍, ML 추론 서버 호출 등이다. 특히 낮은 지연과 계약 일관성이 중요한 내부망에서 효과가 크다.

6. 기대효과 및 결론

gRPC의 효과는 낮은 직렬화 비용, 계약 기반 개발, 코드 생성에 따른 생산성, 스트리밍 통신 지원이다. 또한 다중 언어 조직에서 서버와 클라이언트 간 인터페이스 오해를 크게 줄인다.

반면 브라우저 친화성이 낮고, Protobuf 호환성 규칙을 잘못 다루면 운영 문제가 발생한다. 따라서 gRPC는 "REST의 완전한 대체"가 아니라, 내부 고성능 통신에 최적화된 선택지로 보는 것이 맞다. 결론적으로 gRPC는 MSA 내부 통신에서 성능과 계약 일관성을 동시에 요구할 때 가장 강력한 표준 중 하나다.
