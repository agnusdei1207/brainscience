0. 핵심 인사이트

핵심: 웹훅은 이벤트 발생 시 제공자가 소비자의 미리 등록된 URL로 HTTP 요청을 보내는 역방향 통지 방식으로, 폴링 비용 없이 외부 시스템과 비동기 연동을 실현한다. 비유: 우편함을 수시로 열어보는 대신, 배달원이 도착 즉시 초인종을 눌러 알려 주는 구조와 같다.

📝 모범 답안

1. 개요 및 필요성

외부 시스템의 상태 변화를 실시간에 가깝게 알고 싶을 때 가장 단순한 방법은 Polling이다. 그러나 결제 완료, Git Push, 주문 배송 상태처럼 드물게 발생하는 이벤트를 확인하려고 수초마다 API를 호출하면 네트워크 비용과 서버 부하가 커지고, 응답 지연은 폴링 주기에 묶인다.

웹훅(Webhook)은 이 문제를 "알림 등록"으로 바꾼다. 소비자는 자신의 콜백 URL을 제공자 시스템에 등록해 두고, 이벤트가 발생하면 제공자가 그 URL로 POST 요청을 보낸다. 따라서 소비자는 반복 조회를 하지 않아도 되고, 제공자는 의미 있는 상태 변화가 있을 때만 통지하면 된다.

웹훅이 중요한 이유는 SaaS 통합의 기본 단위이기 때문이다. 결제 게이트웨이, Git 플랫폼, 협업 도구, 마케팅 플랫폼 대부분이 웹훅을 통해 외부 시스템과 사건을 연결한다. 즉 웹훅은 "작은 HTTP 콜백"처럼 보이지만, 실제로는 기업 간 느슨한 비동기 통합의 핵심 메커니즘이다.

웹훅 구조에서 가장 중요한 관계는 "수신 즉시 확인, 후속 처리는 비동기"다. 제공자는 빠른 응답을 기대하므로, 수신 측이 웹훅 엔드포인트에서 무거운 비즈니스 로직을 직접 수행하면 재시도 폭증과 중복 처리 문제가 생긴다.

3. 구조 및 원리

핵심 조건: 수신 측 URL은 외부에서 접근 가능해야 하며, 요청 진위를 검증해야 하고, 중복 전송과 순서 역전을 전제로 멱등 처리를 설계해야 한다.

동작 순서:

  1. 소비자 시스템이 제공자 플랫폼에 이벤트 종류와 콜백 URL을 등록한다.
  2. 제공자 측에서 지정 이벤트가 발생하면 페이로드를 생성하고 서명 정보를 부여한다.
  3. 제공자는 등록된 URL로 HTTP POST 요청을 전송한다.
  4. 수신 시스템은 서명을 검증하고, Event ID 기준으로 중복 여부를 확인한다.
  5. 유효한 요청이면 빠르게 2xx 응답을 반환하고, 실제 업무 처리는 내부 큐나 워커로 넘긴다.
  6. 제공자는 2xx를 받지 못하면 재시도 정책에 따라 재전송하며, 장기 실패는 운영 경보로 전환한다.
[Provider SaaS]
    |
    | POST /webhook/orders
    | Header: Signature, Delivery-ID
    v
[Webhook Receiver] --> [Verify Signature] --> [Dedup Store]
        |                                      |
        +---- 200 OK 빠른 응답 ---------------+
        |
        v
   [Internal Queue / Worker] --> [Business Processing]

웹훅의 본질은 HTTP Push지만, 실제 운영 난점은 신뢰성이다. 인터넷 경로의 일시 실패, 수신 서버 배포 중단, 서명 키 회전, 순서 뒤바뀜이 모두 빈번하게 발생한다. 따라서 "웹훅을 받는다"는 것은 단순 엔드포인트 구현이 아니라, 재시도·멱등성·보안·관측성을 갖춘 수신 플랫폼을 운영한다는 뜻이다.

또한 제공자마다 전달 보장 수준이 다르다. 어떤 시스템은 순서를 보장하지 않고, 어떤 시스템은 최대 N회만 재시도한다. 그러므로 소비자는 제공자 문서를 신뢰하기보다, 스스로 중복 허용·순서 무관 설계를 택하는 편이 안전하다. 필요하면 웹훅은 알림 트리거로만 쓰고, 상세 데이터는 후속 API 조회로 보강한다.

웹훅은 EDA와도 연결된다. 웹훅은 인터넷 경계의 이벤트 전달 수단이고, 내부 시스템에서는 이를 메시지 브로커로 다시 게시해 표준 이벤트 파이프라인으로 연결하는 경우가 많다. 또한 AsyncAPI는 이러한 웹훅 계약을 문서화하는 데 활용될 수 있다.

5. 실무 적용 및 판단

웹훅은 외부 플랫폼 사건을 즉시 받아야 하고, 수신 시스템이 공개 URL과 검증 체계를 가질 수 있을 때 적합하다. 반대로 내부 방화벽 정책상 외부 수신이 어렵거나, 제공자가 웹훅을 지원하지 않으면 폴링이나 중계 서비스가 필요하다.

실무 체크리스트는 다음과 같다.

  • HMAC 또는 서명 기반 진위 검증을 구현했는가
  • Event ID 기반 멱등성 저장소를 두었는가
  • 수신 엔드포인트가 빠르게 2xx를 반환하고 후속 처리를 비동기화하는가
  • 제공자 재시도 정책과 타임아웃 값을 파악했는가
  • 운영 대시보드에서 전달 성공률과 재시도 상태를 볼 수 있는가

대표 사례로는 GitHub Push 이벤트를 받아 CI 파이프라인을 시작하는 구조, 결제 완료 웹훅으로 주문 상태를 확정하는 구조, 전자서명 완료 웹훅으로 계약 저장소를 갱신하는 구조가 대표적이다.

6. 기대효과 및 결론

웹훅의 효과는 폴링 비용 제거, 지연 감소, 외부 플랫폼과의 느슨한 비동기 통합 실현이다. 특히 이벤트가 드물고 즉시성이 중요한 업무에서 큰 효율을 낸다.

그러나 공개 엔드포인트 운영, 서명 검증, 중복 처리, 재시도 운영은 결코 가볍지 않다. 따라서 웹훅은 "간단한 HTTP 호출"로 보지 말고, 외부 이벤트 수신 채널로서의 신뢰성 요구사항을 갖춘 아키텍처로 다뤄야 한다. 결론적으로 웹훅은 SaaS 통합의 표준적 출입구지만, 안전한 수신 설계가 전제되어야 한다.
