0. 핵심 인사이트

핵심: EDI와 VAN 기반 B2B 연동은 기업 간 문서를 표준 전자 포맷으로 변환하고, 전달·인증·추적 체계를 갖춘 통신망을 통해 자동 교환함으로써 공급망 거래를 시스템 대 시스템으로 연결하는 구조다. 비유: 서로 다른 나라 기업이 각자 언어로 계약서를 보내지 않고, 국제 표준 양식과 인증된 교환소를 통해 서류를 주고받는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

기업 내부 애플리케이션 통합(EAI)과 달리 B2B 통합은 회사 경계를 넘는다. 거래처마다 ERP, 코드 체계, 보안 정책, 통신 방식이 다르므로 단순 API 호출만으로는 안정적인 대량 거래 문서 교환이 어렵다. 특히 발주서, 출하통지서, 세금계산서, 송장 같은 문서는 법적·회계적 증빙 성격을 가지므로, 전달 실패나 중복 처리의 비용이 크다.

EDI(Electronic Data Interchange)는 이러한 문제를 해결하기 위해 문서 구조를 표준화했다. UN/EDIFACT, ANSI X12 같은 포맷은 특정 거래 문서의 필드와 세그먼트 구조를 정의해, 서로 다른 기업 시스템이 동일 문서를 기계적으로 해석할 수 있게 한다. VAN(Value Added Network)은 이러한 문서를 안전하게 중계·추적하는 상업용 네트워크 서비스 역할을 해 왔다.

오늘날 API와 Web EDI가 확산되었지만, 제조·유통·물류·무역 분야에서는 여전히 EDI/VAN이 중요한 이유가 있다. 거래처가 많고, 규격과 합의가 길게 유지되며, 전달 확인과 감사 추적이 중요하기 때문이다. 따라서 EDI/VAN은 구식 기술이 아니라, 기업 간 대규모 거래 자동화의 역사적·실무적 기반이다.

구성요소의 핵심은 "표준 문서"와 "거래처별 매핑"이 동시에 필요하다는 점이다. 표준이 있어도 코드값, 선택 필드, 필수 여부는 거래처 계약에 따라 달라진다. 그래서 EDI 프로젝트는 단순 네트워크 연결보다 매핑과 운영 대사에 더 많은 노력이 들어간다.

3. 구조 및 원리

핵심 조건: 내부 업무 데이터와 외부 표준 문서 간 매핑이 정확해야 하며, 거래처별 버전·코드셋 관리와 전달 확인 체계가 반드시 존재해야 한다.

동작 순서:

  1. 내부 ERP에서 발주·출하·청구 같은 업무 이벤트가 발생한다.
  2. EDI Translator가 내부 레코드를 거래처 합의에 맞는 EDIFACT/X12 문서로 변환한다.
  3. 문서는 VAN 또는 AS2/전용 게이트웨이를 통해 상대 기업으로 전송된다.
  4. 상대방 게이트웨이 또는 Translator가 문서를 수신해 자사 포맷으로 역변환한다.
  5. 수신 성공 여부는 기능 확인 메시지(ACK)로 회신된다.
  6. 운영 시스템은 송신 건수, 수신 ACK, 업무 반영 건수를 대사해 누락과 오류를 검출한다.
[ERP]
  |
  v
[EDI Translator] -- EDIFACT/X12 --> [VAN / AS2] --> [Partner Gateway]
  ^                                                        |
  |----------------------- ACK / CONTRL / 997 -------------+

EDI의 핵심은 표준 포맷 그 자체보다 "정형화된 계약된 문서 교환"에 있다. 예를 들어 발주서 한 장이 단순 파일 전송이 아니라, 문서 구조 검증, 파트너 식별, 보안 채널, 수신 확인, 업무 반영 대사까지 포함하는 프로세스로 관리된다. 이 때문에 거래량이 많을수록 수작업 이메일이나 파일 업로드 방식보다 훨씬 높은 신뢰성과 생산성을 제공한다.

현대 환경에서는 VAN 의존이 줄고 AS2, SFTP, API 기반 교환이 늘어났지만, 본질은 그대로다. 즉 내부 시스템 포맷을 외부 거래 표준으로 바꾸고, 전달과 확인을 자동화하는 구조가 핵심이다. 많은 기업은 여전히 EDI 허브를 두고 내부적으로는 API/이벤트 기반으로 연결해 현대화한다.

대상기업 간 정형 거래 문서실시간 서비스 호출기업 내부 시스템 연계

EDI는 API의 이전 단계가 아니라 목적이 다른 통합 방식이다. API는 실시간 질의·명령에 적합하고, EDI는 거래 문서의 대량·반복·감사 가능 교환에 강하다. 실제 현장에서는 두 방식이 공존하며, EDI 게이트웨이가 내부 API 또는 ESB와 연결되는 구조가 흔하다.

5. 실무 적용 및 판단

EDI/VAN은 거래처가 많고 문서 표준이 산업 차원에서 이미 자리 잡은 경우, 감사 추적과 전달 확인이 중요한 경우, 그리고 거래 건수가 커서 수작업이 불가능한 경우에 적합하다. 반대로 실시간 상호작용이 중요한 SaaS형 연동이나 가벼운 파트너 통합에는 API가 더 적합하다.

실무 체크리스트는 다음과 같다.

  • 거래처별 문서 버전, 필수 필드, 코드셋이 계약서로 관리되는가
  • 변환 실패와 ACK 미수신을 운영에서 즉시 감지할 수 있는가
  • 내부 ERP 변경이 EDI 매핑에 미치는 영향을 통제하는가
  • 송수신 건수와 업무 반영 건수를 대사하는 프로세스가 있는가
  • 장기적으로 API/Web EDI와 병행할 통합 로드맵이 있는가

대표 사례는 제조업 발주/납품, 대형 유통사의 공급사 주문 및 ASN(Advance Shipping Notice) 통합, 물류사와의 운송 송장 교환 등이다. 이 영역에서는 여전히 EDI가 핵심 기반으로 쓰인다.

6. 기대효과 및 결론

EDI/VAN 기반 통합의 효과는 거래 문서 처리의 자동화, 오입력 감소, 공급망 리드타임 단축, 대사 가능성 향상이다. 특히 거래량이 큰 산업에서는 사람 중심 문서 처리에서 발생하는 비용을 획기적으로 줄인다.

그러나 파트너 온보딩과 매핑 유지보수 비용이 크고, 표준 문서라도 실제로는 파트너별 변형이 존재한다. 따라서 EDI는 도입보다 운영이 더 중요하다. 결론적으로 EDI/VAN은 현대 API 시대에도 여전히 유효한 B2B 통합 기반이며, 내부 현대화 기술과 연결해 점진적으로 진화시켜야 한다.
