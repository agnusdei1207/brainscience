0. 핵심 인사이트

핵심: 서버리스 아키텍처는 애플리케이션 로직을 짧은 함수와 관리형 백엔드 서비스로 분해하여, 인프라 운영보다 이벤트 처리와 비즈니스 가치 구현에 집중하게 하는 클라우드 실행 모델이다. 비유: 자체 발전소와 창고를 짓는 대신, 전기·물류·보안을 공공 인프라로 사용하고 필요한 순간에만 작업자를 호출해 업무를 처리하는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

전통적인 애플리케이션 운영에서는 서버 프로비저닝, OS 패치, WAS 튜닝, 스케일링, 장애 대응 같은 인프라 업무가 상당한 비중을 차지했다. 그러나 많은 서비스의 실제 요구는 고정 서버를 계속 운영하는 것이 아니라, 특정 요청이나 이벤트가 왔을 때 짧은 로직을 실행하고 인증·스토리지·메시징 같은 공통 기능을 안정적으로 사용하는 것이다.

서버리스 아키텍처는 이러한 필요에서 등장했다. Backend as a Service(BaaS)는 인증, 데이터베이스, 파일 저장, 메시징, 알림 같은 공통 기능을 관리형 API로 제공하고, Function as a Service(FaaS)는 사용자 정의 코드를 이벤트 단위로 실행한다. 개발자는 서버 인스턴스를 직접 관리하지 않고도 애플리케이션을 조립할 수 있다.

이 모델이 필요한 이유는 세 가지다. 첫째, 변동성 큰 트래픽에서 비용 효율이 좋다. 둘째, 소규모 팀이 빠르게 기능을 출시할 수 있다. 셋째, 이벤트 중심 통합과 잘 맞는다. 따라서 서버리스는 단순 운영 절감이 아니라, 클라우드 네이티브 방식으로 아키텍처를 재구성하는 접근이다.

2. 구성요소

구성요소역할핵심 포인트

서버리스는 단일 제품이 아니라 조합형 아키텍처다. API Gateway가 요청을 받고, FaaS가 로직을 수행하며, BaaS가 상태와 공통 기능을 맡는다. 운영의 중심은 서버가 아니라 이벤트, 권한, 함수 간 흐름으로 이동한다.

3. 구조 및 원리

핵심 조건: 함수는 짧고 무상태(stateless)해야 하며, 상태는 외부 관리형 서비스에 저장해야 하고, 권한과 콜드 스타트 영향을 고려해 이벤트 구동 방식으로 설계해야 한다.

동작 순서:

  1. 사용자 요청 또는 외부 이벤트가 API Gateway, Queue, Storage 이벤트 등으로 유입된다.
  2. 플랫폼이 해당 이벤트에 연결된 함수를 자동으로 기동한다.
  3. 함수는 필요한 인증 정보와 설정을 읽고, 관리형 DB·스토리지·메시징 서비스와 상호작용한다.
  4. 결과를 즉시 응답하거나, 후속 이벤트를 발행해 다른 함수 체인으로 넘긴다.
  5. 플랫폼은 부하에 따라 함수 인스턴스를 자동 확장하고, 사용량 기반으로 과금한다.
  6. 로그와 메트릭은 중앙 관측 체계로 수집되어 성능·오류를 추적한다.
[Client / Event]
      |
      v
 [API Gateway / Trigger]
      |
      v
    [FaaS]
   /   |    \
[Auth][DB][Storage]
      |
      +--> [Queue / Event Bus] --> [Other Functions]

서버리스의 핵심 원리는 실행 환경의 추상화다. 개발자는 프로세스 수, 서버 크기, OS 패치 주기를 직접 다루지 않고, 함수 코드와 이벤트 연결만 정의한다. 이 때문에 운영 효율은 높아지지만, 실행 시간 제한, 콜드 스타트, VPC 연결 지연, 상태 외부화 같은 새로운 제약을 받아들여야 한다.

또한 BaaS 의존도가 높아질수록 특정 클라우드에 종속될 수 있다. 예를 들어 인증·스토리지·NoSQL·이벤트 규칙이 특정 CSP 서비스에 깊게 묶이면 이식성이 떨어진다. 따라서 전략적으로는 빠른 출시와 벤더 종속 사이의 균형을 판단해야 한다. 엔터프라이즈 환경에서는 공통 보안·감사·배포 정책을 함수 단위로 강제하는 거버넌스도 중요하다.

서버리스는 EDA와 잘 결합된다. 큐나 이벤트 버스를 통해 함수 체인을 구성하면 고도로 느슨한 결합이 가능하다. 반면 장시간 실행 트랜잭션, 대규모 메모리 상태 유지, 낮은 지연이 절대적인 워크로드는 컨테이너 기반이 더 적합할 수 있다.

5. 실무 적용 및 판단

서버리스는 초기 제품 개발, 이벤트 처리 파이프라인, 배치 작업, 파일 변환, 통합 허브, 갑작스러운 트래픽 변동이 큰 서비스에 적합하다. 반대로 상시 고부하 장기 실행 서비스나 특수 런타임 제어가 필요한 경우에는 한계가 있다.

실무 체크리스트는 다음과 같다.

  • 함수가 무상태이며 짧은 실행 시간으로 분해 가능한가
  • 민감 정보와 권한이 함수별 최소 범위로 분리되는가
  • 콜드 스타트와 동시성 제한이 SLA에 부합하는가
  • 공통 로깅, 추적, 배포, 롤백 체계가 있는가
  • 특정 BaaS 의존에 대한 장기 전략이 있는가

대표 사례로는 이미지 업로드 후 리사이징, 주문 이벤트 후 후속 알림 처리, 모바일 앱 백엔드, 문서 승인 워크플로우 자동화 등이 있다. 이런 업무는 서버리스의 이벤트 중심성과 잘 맞는다.

6. 기대효과 및 결론

서버리스의 기대효과는 출시 속도 향상, 운영 부담 감소, 탄력적 확장, 사용량 기반 비용 최적화다. 특히 작은 팀이 공통 인프라보다 비즈니스 로직에 집중할 수 있다는 점이 크다.

그러나 서버가 사라진 것이 아니라 관리 책임의 위치가 바뀐 것에 불과하다. 권한, 이벤트 흐름, 비용 폭증, 관측성, 벤더 종속은 여전히 관리 대상이다. 따라서 서버리스는 단순 비용 절감 기법이 아니라, 애플리케이션 경계를 이벤트와 관리형 서비스 중심으로 재설계하는 전략으로 이해해야 한다.
