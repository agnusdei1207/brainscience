0. 핵심 인사이트

핵심: ELT는 원천 데이터를 먼저 저장소에 적재해 보존하고, 변환은 저장소 내부의 대규모 연산 능력으로 수행함으로써 데이터 유연성과 확장성을 얻는 현대 데이터 플랫폼 방식이다. 비유: 재료를 조리실 밖에서 미리 다 손질하는 대신, 대형 중앙 주방에 먼저 모아 두고 주문 목적에 따라 그 안에서 빠르게 조리하는 구조와 같다.

📝 모범 답안

1. 개요 및 필요성

ELT (Extract, Load, Transform)는 데이터를 먼저 대상 저장소에 적재한 뒤, 그 안에서 SQL이나 모델링 도구를 이용해 변환하는 방식이다. 전통적 ETL이 적재 전 변환을 중시했다면, ELT는 클라우드 데이터 웨어하우스와 데이터 레이크의 저장·연산 확장성을 활용해 원시 데이터 보존과 반복 재가공을 가능하게 한다.

ELT가 부상한 이유는 데이터 양과 형식의 폭발적 증가 때문이다. 로그, 이벤트, SaaS 데이터, 반정형 JSON, IoT 스트림은 미리 모든 규칙을 확정하기 어렵다. 또한 클라우드 DW는 대규모 병렬 처리와 저장/연산 분리를 제공하므로, 중간 ETL 서버보다 대상 저장소 내부에서 변환하는 편이 더 경제적일 수 있다. ELT는 이런 기술 환경 변화를 반영한 방식이다.

ELT에서 저장소는 단순 보관소가 아니라 변환 엔진 자체다. 따라서 스키마 설계, 권한 관리, 비용 통제, 워크로드 분리가 모두 중요해진다. 특히 raw → staging → curated 계층을 명확히 두지 않으면 원시 데이터와 공식 지표가 뒤섞이기 쉽다.

3. 구조 및 원리

핵심 조건: ELT는 원시 데이터의 보존, 저장소 내부 연산의 확장성, 변환 로직의 버전관리, 비용 제어를 함께 만족해야 한다.

[Source Systems / SaaS / Logs]
            |
            v
+-------------------------+
| Load to Raw Storage     |
| cloud object / raw zone |
+------------+------------+
             |
             v
+-------------------------+
| Warehouse / Lake Engine |
| SQL, dbt, push-down     |
+------------+------------+
             |
      +------+------+
      |             |
      v             v
[Curated Model]  [BI / ML / API]

동작 순서:

  1. 원천 데이터를 가능한 한 손실 없이 raw 영역에 적재한다. 이 단계에서는 속도와 보존성이 우선이며, 최소한의 기술 메타데이터만 부여한다.
  2. 저장소 내부에서 표준화, deduplication, join, window 연산, SCD 처리 등을 수행해 staging/clean 계층을 만든다.
  3. 비즈니스 정의가 반영된 curated 모델과 데이터 마트를 생성한다. 이때 dbt 같은 도구를 활용하면 모델 간 의존성, 테스트, 문서화가 쉬워진다.
  4. BI, 머신러닝, API 서비스는 curated 계층을 사용한다. raw 계층은 원본 보존과 실험적 분석에 남겨 둔다.
  5. 필요 시 저장/연산 자원을 분리해 변환 시점에만 compute를 확장한다. ELT의 경제성은 이 탄력성에서 나온다.

ELT의 강점은 원시 데이터가 남기 때문에 규칙이 바뀌어도 재변환이 가능하다는 점이다. 반면 단점은 저장소 내부에 품질이 검증되지 않은 데이터가 들어오므로 권한과 계층 분리가 약하면 잘못된 데이터가 바로 소비될 위험이 있다는 점이다. 따라서 ELT는 자유로움만큼 강한 거버넌스를 요구한다.

4. 비교 및 연결

ELT는 Data Lake, Lakehouse, dbt, Reverse ETL과도 긴밀히 연결된다. 데이터 레이크의 원시 보존 특성과, DW의 구조화된 분석 모델을 하나의 플랫폼 안에서 연결하는 중심 방식이기 때문이다. 특히 medallion 구조에서 bronze/raw → silver/clean → gold/business 계층은 ELT 사고방식과 매우 유사하다.

5. 실무 적용 및 판단

채택 조건은 클라우드 기반 저장소를 사용하고, 원시 데이터 보존 가치가 높으며, 데이터 모델 변경이 잦고, 분석 민첩성이 중요한 경우다. 회피 조건은 대상 저장소 연산 비용이 과도하거나, 미정제 데이터의 저장 자체가 규제로 제한되는 경우다.

실무 체크리스트:

  • raw/staging/curated 계층이 분리되어 있는가
  • 변환 SQL과 모델이 버전관리되는가
  • 저장소 내부 연산 비용 모니터링이 되는가
  • 공식 지표는 curated만 사용하도록 통제되는가
  • 재처리와 데이터 테스트가 자동화되어 있는가

대표 도구와 플랫폼으로 Snowflake, BigQuery, Databricks, Redshift, dbt, Fivetran, Airbyte가 자주 사용된다. 특히 SaaS 기반 분석 조직에서 빠른 적재 후 SQL 모델링을 반복하는 패턴에 강하다.

6. 기대효과 및 결론

ELT는 데이터 유연성, 재처리 가능성, 확장성을 높여 현대 데이터 플랫폼의 기본 방식으로 자리 잡았다. 그러나 '먼저 쌓고 나중에 정리'한다는 특성상, 계층 분리와 품질 통제가 약하면 데이터 늪으로 쉽게 전락한다. 따라서 ELT의 성공 조건은 강력한 저장소 성능이 아니라, raw와 공식 데이터의 경계를 지키는 설계와 운영 규율이다.
