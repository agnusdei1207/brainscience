0. 핵심 인사이트

핵심: 서로게이트 키 (Surrogate Key)는 비즈니스 의미를 식별자에서 제거해, 차원 이력과 다중 원천 통합을 안정적으로 유지하게 만드는 데이터 웨어하우스 (Data Warehouse) 내부 전용 키다. 비유: 여러 나라 언어로 적힌 서류를 하나의 접수번호 체계로 재분류하는 민원센터와 같다. 📝 모범 답안

1. 개요 및 필요성

서로게이트 키는 데이터 웨어하우스에서 차원 테이블의 기본키로 사용하는 인공 식별자다. 자연키(Natural Key) 또는 비즈니스 키(Business Key)는 고객번호, 제품코드처럼 현업 의미를 가지지만, 원천 시스템 변경·중복·재사용의 영향을 직접 받는다. 반면 서로게이트 키는 DW 내부에서만 생성·관리되므로 분석 모델이 원천 시스템의 불안정성으로부터 분리된다.

이 키가 필요한 첫 번째 이유는 통합이다. 기업은 ERP, CRM, 전자상거래, 제휴사 시스템처럼 서로 다른 식별 체계를 동시에 운영한다. 동일 고객이라도 시스템마다 다른 키를 가질 수 있으므로, DW는 이를 하나의 분석 관점으로 묶어야 한다. 둘째는 이력 관리다. SCD Type 2에서 동일한 비즈니스 키가 여러 버전의 차원 행으로 존재하려면, 각 버전을 구별할 별도 식별자가 필요하다. 셋째는 성능과 안정성이다. 대규모 팩트 테이블은 문자열이나 복합키보다 정수형 인조키를 외래키로 가질 때 저장 효율과 조인 성능이 좋아진다.

결국 서로게이트 키는 단순한 번호 부여가 아니라, 분석 모델을 원천 업무 시스템으로부터 절연시키는 설계 장치다. 이를 사용하지 않으면 원천 키 변경, 중복, 이력 버전 충돌이 곧바로 DW의 참조 무결성 문제로 이어진다.

구성요소는 분리되어 있지만 실제로는 하나의 흐름으로 작동한다. 원천 데이터가 들어오면 먼저 BK 기준으로 기존 차원 행을 조회한다. 이때 변경이 없으면 기존 SK를 재사용하고, Type 2 변경이면 기존 버전을 만료 처리한 뒤 새 SK를 발급한다. 팩트 적재는 반드시 이 룩업 결과를 참조해야 하므로, 서로게이트 키는 차원 설계와 ETL 제어를 동시에 묶는 축이다.

또한 예외 키는 실무에서 중요하다. 고객 차원을 아직 찾지 못했더라도 팩트 적재를 중단하지 않기 위해 0=Unknown, -1=Not Applicable 같은 예약값을 두는 경우가 많다. 이는 분석 품질과 배치 안정성을 동시에 확보하기 위한 운영 장치다.

3. 구조 및 원리

핵심 조건: SK는 DW 내부에서만 유일해야 하며, BK는 별도 컬럼으로 반드시 보존되어야 하고, SCD Type 2에서는 동일 BK의 각 버전마다 서로 다른 SK가 부여되어야 한다.

동작 순서:

  1. 원천 레코드 수신: 고객번호, 제품코드 등 BK를 가진 원천 데이터를 적재 후보로 받는다.
  2. 차원 룩업 수행: BK와 현재 버전 조건으로 기존 차원 행을 탐색한다. 이 단계가 잘못되면 팩트가 틀린 차원 버전을 참조한다.
  3. 변경 유형 판정: 신규 BK인지, 단순 Type 1 갱신인지, Type 2 이력 생성인지 판단한다. 서로게이트 키 정책은 이 판정 결과에 따라 달라진다.
  4. SK 재사용 또는 신규 발급: 동일 버전이면 기존 SK를 사용하고, 새 버전이면 새 SK를 생성한다.
  5. 팩트 외래키 연결: 최종적으로 팩트 테이블은 BK가 아니라 SK를 참조한다. 그래서 과거 거래는 당시의 차원 버전에 고정된다.
원천 시스템                차원 테이블(DW)                     팩트 테이블
───────────               ─────────────────────────          ───────────────
customer_id=C-001   ──▶   sk=101, bk=C-001, tier=Silver     sale_id=1, cust_sk=101
(2023 거래)                start=2023-01-01, end=2024-03-14

customer_id=C-001   ──▶   sk=205, bk=C-001, tier=Gold       sale_id=2, cust_sk=205
(2024 변경 후)             start=2024-03-15, end=9999-12-31

핵심: 동일 BK라도 버전이 다르면 SK가 달라진다.

이 구조가 중요한 이유는 팩트의 시점 정합성 때문이다. 2023년 매출이 Silver 고객 시점에 발생했다면, 나중에 고객이 Gold가 되어도 기존 팩트는 cust_sk=101을 유지해야 한다. 만약 BK를 직접 팩트 외래키로 쓴다면, 차원 변경 시 과거와 현재가 뒤섞여 분석이 왜곡된다.

추가로 설계 시 주의할 점은 두 가지다. 첫째, SK만 남기고 BK를 지우면 원천 추적이 불가능해진다. 둘째, 분산 환경에서 SK 발급 충돌이 발생하지 않도록 시퀀스, ID 서비스, 테이블 포맷의 트랜잭션 보장 등 발급 전략을 명확히 해야 한다.

서로게이트 키는 SCD, 스타 스키마, 팩트-차원 분리와 밀접하게 연결된다. 특히 SCD Type 2는 같은 고객의 다른 시간 버전을 독립 행으로 보존해야 하므로 SK가 거의 필수적이다. 반면 운영계 OLTP는 보통 현재 상태 중심이므로 BK를 기본키로 유지해도 문제가 적다. 따라서 SK는 모든 데이터 모델의 일반 원칙이라기보다, 분석용 데이터 모델의 특수 해법으로 이해해야 한다.

5. 실무 적용 및 판단

채택 조건:

  • 다중 원천 통합으로 동일 엔터티의 키 체계가 다를 때
  • 차원 이력 관리가 필요할 때
  • 수억 건 이상 팩트-차원 조인 성능을 안정적으로 확보해야 할 때

회피 또는 주의 조건:

  • 운영계 트랜잭션 DB에서 불필요하게 인조키를 남발해 업무 의미를 숨기는 경우
  • BK를 보존하지 않아 원천 추적이 끊기는 경우
  • ETL 룩업 로직 없이 SK만 생성해 중복 차원 행이 양산되는 경우

체크리스트:

  1. BK를 별도 컬럼과 유니크 규칙으로 관리하는가?
  2. Type 2 대상 속성과 Type 1 대상 속성을 구분했는가?
  3. Unknown SK 정책을 정의했는가?
  4. SK 발급이 재처리 시에도 중복 없이 재현 가능한가?
  5. 팩트 적재 시점에 올바른 차원 버전을 조회하는가?

실무 사례로는 고객 차원, 제품 차원, 조직 차원처럼 시간이 지나며 속성이 바뀌는 엔터티에서 가장 자주 사용된다. Kimball 방식의 DW, Snowflake/Redshift 기반 차원 모델, 대다수 상용 ETL 도구의 차원 룩업 컴포넌트가 모두 이 전제를 따른다.

6. 기대효과 및 결론

서로게이트 키를 도입하면 DW는 원천 시스템의 식별 정책 변화로부터 독립성을 얻고, 이력 보존과 통합 분석의 기반을 확보한다. 특히 SCD Type 2와 결합될 때 과거 사실과 당시 차원 상태를 정확히 연결할 수 있으므로, 시점 기반 분석의 신뢰도가 크게 향상된다.

다만 이 키는 만능이 아니다. BK 보존, 룩업 정확성, 재처리 일관성, 예외 키 정책이 함께 갖춰지지 않으면 오히려 의미 없는 숫자만 많은 테이블이 된다. 따라서 결론적으로 서로게이트 키는 단독 기술이 아니라 차원 모델링·이력 관리·ETL 제어가 결합된 설계 원칙으로 이해해야 한다.
