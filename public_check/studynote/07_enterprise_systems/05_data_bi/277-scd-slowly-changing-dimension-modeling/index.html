0. 핵심 인사이트

핵심: SCD (Slowly Changing Dimension)는 차원 속성의 변화 자체보다, 그 변화를 분석에서 어떤 시간 의미로 보존할지를 결정하는 모델링 규칙이다. 비유: 사람의 주소 변경을 현재 주소만 볼지, 전입·전출 이력을 모두 남길지 정하는 주민기록 관리 방식과 같다. 📝 모범 답안

1. 개요 및 필요성

데이터 웨어하우스의 차원(Dimension)은 제품, 고객, 조직, 지역처럼 사실(Fact)을 해석하는 기준 축이다. 문제는 이 축이 완전히 고정되어 있지 않다는 점이다. 고객 등급은 바뀌고, 조직은 개편되며, 제품 분류도 재정의된다. 이런 변화는 운영계 관점에서는 단순 업데이트일 수 있지만, 분석계에서는 과거 사실을 어떤 차원 상태와 연결할 것인가라는 시간 문제를 만든다. 이 문제를 해결하는 대표적 모델링 규칙이 SCD다.

SCD가 필요한 이유는 시점 정합성 때문이다. 예를 들어 2023년에 Silver 고객이었던 사람이 2024년에 Gold로 승급했다면, 2023년 매출을 Gold 고객 매출로 해석하면 잘못된 분석이 된다. 반대로 오타 수정이나 명칭 표준화는 굳이 이력을 남기지 않고 현재 값으로 일괄 정정하는 편이 더 적절하다. 즉 차원 변화는 모두 같은 방식으로 다루면 안 되고, 속성의 의미와 분석 목적에 따라 모델링 전략을 달리해야 한다.

따라서 SCD는 단순한 저장 기법이 아니라, 무엇을 역사로 볼 것인가에 대한 비즈니스 해석 규칙이다. DW 설계에서 이 판단이 틀리면 성능보다 먼저 의미가 무너진다.

SCD의 핵심은 차원 자체가 아니라 속성 단위의 정책 설정이다. 하나의 고객 차원 안에서도 이름 오타는 Type 1, 고객 등급은 Type 2, 직전 등급 비교용 컬럼은 Type 3로 혼용될 수 있다. 따라서 실무에서는 차원별 SCD보다 속성별 SCD 정책표가 더 중요하다.

또한 SCD는 ETL/ELT와 분리해서 생각할 수 없다. 변경 감지(Change Detection), 현재 버전 판정, 이력 만료 처리, 새 버전 삽입, 팩트 적재 시점의 SK 연결이 한 세트로 운영되어야 한다.

3. 구조 및 원리

핵심 조건: 차원 속성은 변경 빈도가 아니라 분석 의미를 기준으로 분류해야 하며, 이력이 필요한 속성은 사실 데이터가 발생한 시점과 올바르게 연결될 수 있어야 한다.

동작 순서:

  1. 변경 감지: 원천 데이터와 현재 차원 상태를 비교해 무엇이 달라졌는지 파악한다.
  2. 속성 정책 판정: 변경된 속성이 Type 1 대상인지, Type 2 대상인지, Type 3 대상인지 결정한다.
  3. 차원 갱신 수행: Type 1은 덮어쓰기, Type 2는 기존 행 만료 후 새 행 삽입, Type 3은 이전 값 컬럼 이동을 수행한다.
  4. 버전 연결 보장: Type 2의 경우 새 서로게이트 키를 생성해 팩트가 해당 시점 버전을 참조하게 한다.
  5. 분석 규칙 검증: 현재값 조회, 특정 시점 조회, 직전 비교 조회가 의도한 결과를 내는지 확인한다.
원천 변경 발생
    ↓
[변경 감지]
    ↓
┌───────────────┬───────────────┬───────────────┐
│ Type 1        │ Type 2        │ Type 3        │
│ 현재값 교체    │ 새 버전 생성    │ 이전값 컬럼 보존 │
└───────────────┴───────────────┴───────────────┘
    ↓                ↓                 ↓
현재 기준 분석      시점 기준 분석       직전 비교 분석

이 구조에서 가장 중요한 차이는 과거 사실을 재해석할 것인가, 당시 맥락을 유지할 것인가다. Type 1은 과거 사실도 현재 차원으로 재해석한다. Type 2는 당시 맥락을 보존한다. Type 3은 현재와 직전 맥락만 동시에 보여준다. 따라서 SCD 선택은 저장 공간의 문제가 아니라 분석 의미의 선택이다.

경계 조건도 명확하다. 법적 감사, 고객 동의 이력, 조직 개편 전후 비교처럼 시점이 중요한 속성은 Type 2를 우선 검토해야 한다. 반면 명백한 입력 오류 수정에 Type 2를 적용하면 불필요한 이력만 늘어난다.

SCD는 서로게이트 키, 스타 스키마, OLAP 분석과 연결된다. 특히 Type 2는 팩트가 당시 차원 버전을 정확히 참조해야 하므로 SK 설계가 핵심이다. 또 데이터 카탈로그와 데이터 거버넌스 측면에서는 각 속성이 어떤 SCD 정책을 따르는지 메타데이터로 명시해야 분석자 해석 충돌을 막을 수 있다.

5. 실무 적용 및 판단

채택 기준은 다음과 같다.

  • Type 1: 잘못된 코드 수정, 주소 오타 보정, 표준 명칭 통일
  • Type 2: 고객 등급, 조직 소속, 상품 분류, 법적 동의 이력
  • Type 3: 전/현 비교가 핵심이고 전체 이력은 중요하지 않은 경우

실무 체크리스트:

  1. 속성별로 이력 필요 여부를 업무 부서와 합의했는가?
  2. Type 2 대상 속성에 대해 유효기간과 current flag 규칙을 정의했는가?
  3. 팩트 적재 시 올바른 차원 버전을 조회하는 로직이 있는가?
  4. 현재 기준 보고서와 과거 기준 보고서의 의미 차이를 사용자에게 설명했는가?
  5. SCD 정책이 카탈로그나 모델 문서에 명시되어 있는가?

실제 프로젝트에서는 하나의 차원에 단일 유형만 적용하기보다 혼합 전략이 일반적이다. 예를 들어 고객 차원에서 이름·이메일은 Type 1, 등급·마케팅 동의는 Type 2, 직전 등급 비교 컬럼은 Type 3로 함께 설계할 수 있다.

6. 기대효과 및 결론

SCD를 올바르게 적용하면 DW는 단순한 현재 상태 저장소가 아니라 시간에 따라 변하는 비즈니스 맥락을 해석하는 분석 플랫폼이 된다. 이력 보존이 필요한 영역에서는 정확한 시점 분석을 가능하게 하고, 불필요한 영역에서는 간단한 모델을 유지해 성능과 운영 복잡도를 통제할 수 있다.

반대로 SCD 정책이 불명확하면 같은 지표도 보고서마다 다른 의미로 계산될 수 있다. 따라서 결론적으로 SCD의 본질은 차원 변경을 어떻게 저장할 것인가가 아니라 과거 사실을 어떤 의미 체계로 해석할 것인가를 명시하는 설계 규칙이다.
