0. 핵심 인사이트

핵심: SCD Type 1은 차원 속성의 변경을 현재 진실로 재정의하여 과거 값을 덮어쓰는 방식이며, 역사 보존보다 정합한 현재 상태가 더 중요할 때 선택한다. 비유: 오타가 있는 명단을 새 종이로 추가하지 않고 기존 명단을 바로 고쳐 쓰는 행정 정정과 같다. 📝 모범 답안

1. 개요 및 필요성

SCD Type 1은 가장 단순한 차원 변경 처리 방식이다. 속성값이 바뀌면 기존 행을 직접 UPDATE하고 이전 값은 남기지 않는다. 따라서 차원 테이블에는 항상 최신 상태만 존재한다. 이 방식은 이력 관리가 불필요하거나, 과거 값 자체가 잘못된 데이터였을 때 가장 적합하다.

Type 1이 필요한 대표 상황은 데이터 오류 수정이다. 고객 이름 오탈자, 잘못 입력된 우편번호, 표준 코드로의 일괄 변환처럼 과거 값의 보존이 오히려 분석 품질을 떨어뜨리는 경우가 있다. 이런 데이터는 변경이라기보다 정정에 가깝기 때문에, 과거까지 포함해 일관된 현재 값으로 바꾸는 것이 맞다.

하지만 이 방식은 과거 사실도 현재 차원 속성으로 재해석하게 만든다. 따라서 고객 등급, 조직 소속, 법적 동의 이력처럼 시점 의미가 중요한 속성에 적용하면 심각한 분석 왜곡이 생긴다. Type 1은 단순해서 편리하지만, 적용 범위를 잘못 잡으면 DW의 역사성이 사라진다.

Type 1은 구조적으로 단순하다. 기존 차원 행을 그대로 유지한 채 컬럼 값만 바꾸므로 서로게이트 키도 그대로 유지된다. 팩트 테이블이 참조하는 외래키도 변하지 않기 때문에 ETL 구현이 쉽고 저장 공간 부담이 없다.

다만 실무에서는 이력은 버리지 않지만 DW 모델에는 남기지 않는 절충도 사용한다. 예를 들어 차원은 Type 1로 운영하되, 변경 로그 테이블이나 운영 감사 로그를 별도로 저장해 추적성을 확보할 수 있다. 이는 분석 모델의 단순성과 운영 감사 요구를 동시에 만족시키기 위한 방식이다.

3. 구조 및 원리

핵심 조건: 변경 대상 속성의 과거 값이 분석 의미를 가지지 않아야 하며, 과거 사실이 현재 값으로 재해석되어도 업무적으로 허용되어야 한다.

동작 순서:

  1. 원천 변경 탐지: 스테이징 데이터와 현재 차원 행을 비교한다.
  2. Type 1 대상 여부 확인: 변경 속성이 오타 수정, 연락처 변경, 표준화 대상인지 판별한다.
  3. 기존 행 UPDATE: 기존 SK를 유지한 채 컬럼 값을 새 값으로 덮어쓴다.
  4. 후속 팩트 참조 유지: 팩트는 동일 SK를 계속 참조하므로 추가 조정이 필요 없다.
  5. 분석 의미 검증: 과거 지표가 현재 값으로 보이는 것이 허용되는지 점검한다.
변경 전 차원
sk=10, bk=C-001, email=old@mail.com

원천 변경
email=old@mail.com → new@mail.com

Type 1 처리
UPDATE dim_customer
   SET email='new@mail.com'
 WHERE sk=10;

변경 후 차원
sk=10, bk=C-001, email=new@mail.com

핵심: 행은 그대로, 값만 교체된다.

이 메커니즘의 본질은 시간을 저장하지 않는다는 데 있다. 그래서 과거 매출 팩트가 모두 동일한 sk=10을 참조하고 있다면, 조회 시점에는 과거 매출도 new@mail.com과 연결된다. 연락처나 오탈자처럼 현재 기준이 더 중요할 때는 문제가 없지만, 등급·소속·가격처럼 당시 맥락이 중요한 속성이라면 부적절하다.

추가로 주의할 점은 대량 UPDATE 시 배치 락, 인덱스 통계, 변경 추적의 부재다. Type 1은 단순하지만, 그 단순함 때문에 잘못 적용되면 영향 범위가 넓다.

Type 1은 Type 2의 대체재가 아니라 적용 대상이 다른 별도 전략이다. 실무 차원 모델은 보통 Type 1과 Type 2를 혼합한다. 예를 들어 고객 등급은 Type 2로 관리하되 이메일은 Type 1로 덮어쓴다. 즉 차원 전체가 Type 1이 아니라 일부 속성이 Type 1인 경우가 흔하다.

5. 실무 적용 및 판단

적합한 사례:

  • 오타·중복·표준 코드 정정
  • 이메일, 휴대전화, 단순 주소처럼 현재 값만 의미 있는 속성
  • 과거 상태보다 최신 상태 기준의 운영 보고가 중요한 경우

부적합한 사례:

  • 고객 등급, 조직 이력, 상품 분류, 법적 동의 기록
  • 감사·규제 대응을 위해 변경 이력이 필요한 속성
  • 과거 분석을 당시 맥락으로 해석해야 하는 KPI

체크리스트:

  1. 이 변경이 새로운 사실이 아니라 정정인가?
  2. 과거 팩트가 현재 값으로 보이더라도 문제 없는가?
  3. 별도 감사 로그가 필요한가?
  4. Type 2와 혼용될 때 속성 경계를 명확히 했는가?
  5. 대량 UPDATE 이후 통계/인덱스 관리 계획이 있는가?

6. 기대효과 및 결론

Type 1의 가장 큰 장점은 단순성이다. 행 수 증가가 없고, 쿼리가 쉽고, 팩트 외래키를 다시 계산할 필요도 없다. 따라서 이력이 불필요한 속성에 대해서는 운영 비용 대비 효과가 매우 높다.

그러나 이 방식은 한 번 덮어쓴 과거를 되살릴 수 없다. 따라서 결론적으로 Type 1은 쉬운 방식이 아니라 현재 진실만을 공식 기록으로 채택하는 명시적 정책으로 보아야 한다. 그 정책이 맞는 속성에만 제한적으로 적용할 때 비로소 올바른 모델이 된다.
