0. 핵심 인사이트

핵심: SCD Type 2는 차원 속성 변화가 새로운 역사적 상태라는 전제 아래, 기존 버전을 닫고 새 버전을 추가해 시간축 위의 맥락을 보존하는 방식이다. 비유: 주민등록상 주소 변경 때 옛 주소를 지우지 않고 전입·전출 일자를 남겨 모든 거주 이력을 연표로 보존하는 것과 같다. 📝 모범 답안

1. 개요 및 필요성

SCD Type 2는 DW 차원 이력 관리의 표준에 가깝다. 속성이 변경되면 기존 행을 만료시키고, 변경된 값으로 새 행을 INSERT한다. 이때 각 버전은 서로 다른 서로게이트 키를 가지며, effective_start_date, effective_end_date, is_current 같은 컬럼으로 유효 기간을 표현한다.

이 방식이 필요한 이유는 과거 사실이 당시 차원 상태와 정확히 연결되어야 하기 때문이다. 고객 등급이 Silver에서 Gold로 바뀌었다면, 과거 구매는 Silver 시점 매출로 남아야 한다. 조직 개편도 마찬가지다. 2023년 실적을 2024년 조직도로 재해석하면 책임 부서가 달라져 지표가 왜곡된다. Type 2는 이런 문제를 방지한다.

또한 금융, 통신, 공공, 헬스케어처럼 규제와 감사가 중요한 산업에서는 변경 이력 자체가 법적 증적이 된다. 그래서 Type 2는 단순한 분석 편의가 아니라, 시간에 따른 데이터 책임성을 확보하는 구조라고 볼 수 있다.

Type 2는 단순히 행을 하나 더 넣는 구조가 아니다. 같은 BK에 대해 시간순으로 버전 체인을 만든다. 그래서 기존 행을 닫는 작업과 새 행을 여는 작업이 항상 함께 수행되어야 한다. 이 둘이 분리되면 같은 BK에 현재 행이 두 개 생기거나, 유효기간이 겹치거나 비는 문제가 발생한다.

또한 팩트 적재 시에는 BK가 아닌 SK를 찾아 연결해야 한다. 즉 Type 2는 차원 적재 로직과 팩트 적재 로직이 강하게 연결되는 모델이다.

3. 구조 및 원리

핵심 조건: 동일 BK에 대해 현재 버전은 하나만 존재해야 하며, 버전 간 유효기간이 겹치지 않아야 하고, 사실 데이터는 발생 시점에 유효한 SK와 연결되어야 한다.

동작 순서:

  1. 현재 버전 조회: BK와 is_current=Y 조건으로 현재 차원 행을 찾는다.
  2. 변경 여부 판정: Type 2 대상 속성이 달라졌는지 비교한다.
  3. 기존 행 만료: 기존 행의 종료일을 변경 전일로 수정하고 현재 플래그를 내린다.
  4. 새 버전 삽입: 새 SK를 발급하고 변경된 속성값과 시작일을 넣어 새 행을 생성한다.
  5. 팩트 연결: 거래 발생 시점 기준으로 유효한 SK를 팩트 외래키에 기록한다.
변경 전
sk=100, bk=C-001, tier=Silver, start=2023-01-01, end=9999-12-31, current=Y

변경 발생(2024-03-15)
Silver → Gold

처리 후
sk=100, bk=C-001, tier=Silver, start=2023-01-01, end=2024-03-14, current=N
sk=205, bk=C-001, tier=Gold,   start=2024-03-15, end=9999-12-31, current=Y

팩트 연결
2024-02-10 sale → cust_sk=100
2024-04-01 sale → cust_sk=205

이 메커니즘의 핵심은 시간을 키로 모델링한다는 점이다. Type 1이 값을 교체하는 구조라면, Type 2는 차원에 시간 축을 추가한다. 그래서 쿼리 시 is_current=Y를 넣지 않으면 중복 집계가 발생할 수 있고, 특정 시점 조회는 날짜 구간 조건이 필요하다. 즉 저장 구조가 풍부해진 만큼 질의 규칙도 엄격해진다.

실무적으로는 유효기간 겹침 방지, 재처리(idempotent) 보장, late arriving dimension 처리도 중요하다. 특히 지연 도착 데이터가 발생하면 과거 날짜에 맞는 차원 버전을 추가로 삽입해야 하므로 단순 최신 행 업데이트만으로는 부족하다.

Type 2는 서로게이트 키, 팩트 시점 연결, 데이터 거버넌스와 직결된다. 또한 최근 레이크하우스의 Time Travel 기능과 개념적으로 유사하지만, 둘은 다른 층위다. Time Travel은 테이블 상태의 시간 복원이고, Type 2는 비즈니스 엔터티 속성의 역사 모델링이다. 따라서 기술이 발전해도 Type 2의 의미적 필요성은 유지된다.

5. 실무 적용 및 판단

적합한 사례:

  • 고객 등급, 멤버십 상태, 조직 소속
  • 상품 카테고리, 가격 정책 버전
  • 마케팅 수신 동의, 리스크 등급 등 감사 필요 속성

주의 사항:

  • 현재행 뷰를 별도로 제공하지 않으면 사용자 쿼리 오류가 잦다.
  • 이력 행이 빠르게 증가하므로 파티셔닝, 압축, 아카이빙 전략이 필요하다.
  • Type 1 속성과 Type 2 속성을 섞을 때 어느 컬럼이 새 버전 생성을 유발하는지 명확히 해야 한다.

체크리스트:

  1. 현재 행 유일성 제약을 두었는가?
  2. 유효기간 겹침 검증을 자동화했는가?
  3. 팩트 적재가 시점 기준 SK 룩업을 수행하는가?
  4. late arriving data 처리 절차가 있는가?
  5. 사용자용 현재행 뷰와 이력행 뷰를 분리 제공하는가?

6. 기대효과 및 결론

Type 2의 가장 큰 효과는 DW가 현재 상태 요약본이 아니라 시간에 따른 비즈니스 기억이 되게 만든다는 점이다. 코호트 분석, 전환 분석, 조직개편 영향 분석, 규제 감사 대응 등 대부분의 고급 분석은 이 능력에 의존한다.

물론 저장 공간과 구현 복잡도는 증가한다. 그러나 시간 의미가 중요한 속성에 대해 Type 2를 생략하면, 단순히 정보가 부족한 것이 아니라 잘못된 분석을 하게 된다. 따라서 결론적으로 Type 2는 비용이 큰 선택이 아니라 시점 진실을 보존하기 위한 필수 모델링 규칙이다.
