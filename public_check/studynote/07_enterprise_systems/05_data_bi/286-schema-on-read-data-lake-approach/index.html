0. 핵심 인사이트

핵심: Schema on Read는 데이터를 먼저 보존하고, 읽는 순간 목적에 맞는 의미 체계를 씌우는 유연한 해석 모델이다. 비유: 같은 창고의 재료를 한 번은 한식, 또 한 번은 양식 레시피로 다르게 꺼내 쓰는 방식과 같다. 📝 모범 답안

1. 개요 및 필요성

Schema on Read는 데이터를 저장할 때 엄격한 구조를 강제하지 않고, 조회·분석 시점에 필요한 스키마를 적용하는 방식이다. 이는 데이터 레이크의 기본 철학으로, 미래 활용 방식이 불확실한 데이터를 우선 보존하고 나중에 해석하는 데 적합하다.

이 방식이 필요한 이유는 현대 데이터의 다양성 때문이다. 로그, JSON 이벤트, XML, 문서, 센서 데이터처럼 구조가 가변적인 데이터는 전통적인 고정 스키마 테이블로 표현하기 어렵다. 또한 수집 시점에는 어떤 분석이 필요할지 알 수 없는 경우가 많기 때문에, 사전 변환을 강제하면 오히려 미래 활용 가능성을 줄일 수 있다.

따라서 Schema on Read는 유연성과 실험성을 극대화한다. 하지만 오류와 품질 문제를 읽는 시점까지 미루기 때문에, 단순히 편한 방식이 아니라 책임이 뒤로 이동한 방식이라고 보는 것이 정확하다.

2. 구성요소

Schema on Read는 스키마가 없다가 아니라 스키마 적용 시점이 늦다는 뜻이다. 그래서 외부 테이블 정의, 뷰, 쿼리 파서, 카탈로그가 실제 핵심 구성요소가 된다. 저장과 해석이 분리되므로 같은 원시 파일도 서로 다른 목적으로 여러 스키마로 읽을 수 있다.

예를 들어 클릭 이벤트 JSON을 마케팅팀은 채널·캠페인 기준으로 읽고, 상품팀은 상품·가격 기준으로 읽을 수 있다. 이 유연성이 Schema on Read의 가장 큰 강점이다.

3. 구조 및 원리

핵심 조건: 데이터는 원시 형태로 보존하되, 읽는 시점에 적용하는 스키마가 메타데이터로 관리되어야 하며, 런타임 파싱 오류를 흡수할 품질·캐스팅 전략이 있어야 한다.

동작 순서:

  1. 원시 데이터 저장: 소스 데이터를 최소 변형 상태로 레이크에 적재한다.
  2. 메타데이터 등록: 파일 포맷, 경로, 추정 스키마를 카탈로그에 기록한다.
  3. 읽기용 스키마 정의: 외부 테이블, 뷰, DataFrame 스키마를 정의한다.
  4. 런타임 해석: 쿼리 시 파서가 파일을 읽어 정의한 타입으로 변환한다.
  5. 오류 처리/정제: 캐스팅 실패, 누락 필드, 신규 필드를 처리하고 필요하면 정제 결과를 저장한다.
원시 JSON/CSV 파일 저장
          ↓
   Catalog에 위치/포맷 등록
          ↓
외부 테이블 또는 View 정의
          ↓
쿼리 실행 시 파싱/캐스팅
          ↓
분석 결과 또는 Curated 데이터 생성

이 구조의 핵심은 저장과 해석의 분리다. Schema on Write에서는 오류가 적재 전에 드러나지만, Schema on Read에서는 런타임에 발견될 수 있다. 따라서 TRY_CAST, 기본값 처리, 스키마 진화 대응, 품질 검사 자동화가 중요하다.

또한 스키마 진화에 유리하다. 새 컬럼이 추가되더라도 과거 파일을 그대로 둔 채 읽기 스키마만 확장하면 된다. 그러나 형식 불일치가 누적되면 운영 부담이 커지므로, Raw Zone과 Curated Zone의 역할을 분명히 해야 한다.

4. 비교 및 연결

항목Schema on ReadSchema on Write
스키마 적용 시점읽을 때저장할 때
저장 유연성높음낮음
쿼리 성능상대적으로 낮음높음
오류 발견늦음빠름

Schema on Read는 데이터 레이크와 결합해 강한 유연성을 제공하고, Schema on Write는 DW와 결합해 강한 정합성을 제공한다. 최근 레이크하우스는 두 방식을 절충하여 원시 저장은 유연하게 하면서도 정제 영역에서는 스키마 강제와 품질 검증을 강화한다.

5. 실무 적용 및 판단

적합한 상황:

  • 탐색적 분석, 데이터 과학 실험
  • 가변 스키마 이벤트 처리
  • 원본 장기 보존이 필요한 환경

주의할 점:

  • 런타임 오류가 사용자 분석 시점에 터질 수 있음
  • 카탈로그 없이는 같은 파일을 누가 어떤 스키마로 읽는지 관리 불가
  • 스캔 비용이 큰 서버리스 쿼리에서는 파티셔닝과 포맷 최적화가 필수

체크리스트:

  1. 카탈로그와 외부 테이블 정의가 관리되는가?
  2. TRY_CAST, NULL 처리 등 런타임 예외 전략이 있는가?
  3. 자주 쓰는 쿼리는 Curated Zone으로 승격되는가?
  4. 스키마 진화 규칙을 정의했는가?
  5. 민감 데이터의 읽기 권한이 통제되는가?

6. 기대효과 및 결론

Schema on Read는 사전 모델링 비용을 줄이고, 미래 요구에 대한 적응력을 높이며, 비정형 데이터 활용 가능성을 크게 넓힌다. 특히 원본 데이터를 다양한 목적에 맞춰 재해석할 수 있다는 점이 큰 장점이다.

그러나 유연성은 항상 책임 이연을 동반한다. 따라서 결론적으로 Schema on Read는 스키마가 필요 없는 방식이 아니라 스키마 적용을 늦추는 대신 메타데이터, 품질, 읽기 규칙 관리 능력을 더 요구하는 방식이다.
