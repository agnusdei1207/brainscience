0. 핵심 인사이트

핵심: Schema on Write는 데이터를 쓰기 전에 구조와 품질을 강제해, 저장소 안의 데이터가 곧바로 분석 가능한 신뢰 자산이 되도록 만드는 방식이다. 비유: 창고에 물건을 넣기 전에 분류·검수·라벨링을 끝내고 진열하는 체계와 같다. 📝 모범 답안

1. 개요 및 필요성

Schema on Write는 데이터를 저장할 때 미리 정의된 스키마와 제약조건을 적용하는 방식이다. 관계형 데이터베이스(RDBMS)와 전통적인 데이터 웨어하우스가 대표적 사례다. 컬럼 타입, NULL 허용 여부, 기본키·외래키, 체크 조건 등을 사전에 정의하고, 데이터를 적재하기 전에 변환·검증한다.

이 방식이 필요한 이유는 정합성과 성능 때문이다. 공식 보고, 재무 집계, 규제 대응처럼 수치의 일관성이 중요한 영역에서는 저장 시점부터 잘못된 데이터를 차단해야 한다. 또한 구조가 명확할수록 인덱스, 컬럼 저장, 통계 정보, 파티셔닝 최적화가 가능해 쿼리 성능도 높아진다.

Schema on Write는 유연성은 낮지만, 그 대신 한 번 들어온 데이터는 믿고 쓸 수 있다는 신뢰를 만든다. 그래서 DW에서 KPI, 매출, 수량, 고객 등 공식 지표는 여전히 이 접근법이 중심이다.

2. 구성요소

요소역할핵심 포인트
스키마 정의(DDL)구조 선언테이블, 컬럼, 타입, 제약조건 정의
ETL/ELT 정제적재 전 변환코드 표준화, 형 변환, 룩업
무결성 제약품질 강제PK, FK, NOT NULL, CHECK

Schema on Write는 저장 전 단계가 핵심이다. 즉 ETL에서 원천 데이터를 목적 스키마에 맞게 정제해야 하며, 이 과정에서 오류 데이터는 격리하거나 재처리 대상에 넣는다. 따라서 저장소의 품질은 적재 파이프라인의 품질과 직결된다.

또한 구조를 강제하는 만큼 스키마 변경도 통제해야 한다. 새로운 컬럼을 추가하거나 타입을 바꾸는 일은 단순한 개발 작업이 아니라, 보고서·ETL·API에 영향을 주는 계약 변경이다.

3. 구조 및 원리

핵심 조건: 데이터는 저장 전에 목적 스키마와 품질 규칙을 충족해야 하며, 적재 실패를 허용하더라도 저장소 내부의 정합성은 반드시 보장해야 한다.

동작 순서:

  1. 목적 스키마 설계: 비즈니스 지표와 질의 패턴에 맞게 테이블 구조를 정의한다.
  2. 원천 데이터 추출: 운영계에서 데이터를 가져온다.
  3. 변환·검증: 타입 변환, 코드 매핑, 키 룩업, 제약조건 검사를 수행한다.
  4. 오류 격리: 스키마 위반 데이터는 오류 영역으로 분리한다.
  5. 적재 및 최적화: 검증 통과 데이터만 DW/RDB에 적재하고 통계·인덱스를 갱신한다.
원천 데이터
    ↓
[Transform & Validate]
  - 타입 변환
  - 제약조건 검사
  - 키 룩업
  - 품질 규칙 검증
    ↓            ↘
적재 성공         오류 격리
    ↓
[DW / RDB]
  - 신뢰 가능한 공식 데이터

이 메커니즘의 핵심은 오류 발견 시점이 빠르다는 점이다. 데이터가 잘못되면 저장 전에 실패하므로, 사용자가 보고서를 보는 단계에서 뒤늦게 문제를 발견할 가능성이 낮다. 대신 적재 비용과 개발 복잡도는 증가한다.

또한 Schema on Write는 질의 성능과 밀접하다. 컬럼 타입이 명확하고 정규화 또는 스타 스키마가 설계되어 있으면 엔진이 집계 계획을 효율적으로 세울 수 있다. 그래서 정형 BI와 공식 KPI 환경에서 여전히 강력하다.

Schema on Write는 ETL, DW, SCD, 데이터 품질 관리와 강하게 연결된다. 특히 공식 보고 데이터셋은 정의와 품질이 고정되어야 하므로 이 접근을 취한다. 반면 Data Lake는 Schema on Read를 사용해 유연성을 확보하고, 정제 영역에서 다시 Schema on Write 성격을 도입하기도 한다.

5. 실무 적용 및 판단

적합한 상황:

  • 재무, 회계, 공식 KPI, 규제 보고
  • 자주 반복되는 정형 분석과 고속 집계
  • 데이터 품질 오류를 사전에 차단해야 하는 환경

주의 사항:

  • 요구사항이 자주 바뀌는 영역에서는 스키마 변경 비용이 큼
  • 비정형 데이터에는 변환 비용이 과도할 수 있음
  • 과도한 사전 모델링은 데이터 활용 속도를 늦출 수 있음

체크리스트:

  1. 공식 지표 정의가 안정적인가?
  2. 적재 전 변환 규칙이 충분히 명시되어 있는가?
  3. 오류 데이터 격리/재처리 경로가 있는가?
  4. 스키마 변경 시 영향 분석 체계가 있는가?
  5. 보고서와 쿼리가 이 스키마를 기준으로 표준화되는가?

6. 기대효과 및 결론

Schema on Write는 저장소에 들어온 데이터 자체를 신뢰 가능한 공식 데이터로 만든다. 이는 보고서 정합성, 빠른 질의 성능, 규제 대응, 운영 안정성 측면에서 큰 장점이다. 특히 조직이 공식 숫자를 하나로 관리해야 할 때 강력하다.

그러나 모든 데이터를 이 방식으로만 처리하면 민첩성을 잃는다. 따라서 결론적으로 Schema on Write는 구식 방식이 아니라 정확성과 성능이 우선되는 영역에서 여전히 가장 강력한 데이터 계약 모델로 이해해야 한다.
