0. 핵심 인사이트

핵심: 데이터 레이크하우스는 레이크의 유연한 저장 위에 웨어하우스의 트랜잭션·거버넌스·성능 규율을 얹어, 한 플랫폼에서 BI와 ML을 함께 돌리려는 아키텍처다. 비유: 넓은 창고에 정교한 서가·재고관리·출납 시스템을 결합한 스마트 물류센터와 같다. 📝 모범 답안

1. 개요 및 필요성

전통 데이터 아키텍처에서는 Data Lake와 Data Warehouse가 분리되어 운영되었다. 레이크는 원시 데이터 보존과 ML 실험에 강하고, 웨어하우스는 정형 BI와 고성능 SQL에 강했다. 그러나 이중 저장과 이중 파이프라인은 비용, 지연, 데이터 불일치 문제를 키웠다. 이를 해결하기 위해 등장한 개념이 데이터 레이크하우스다.

레이크하우스는 오브젝트 스토리지의 저비용 확장성을 유지하면서도, 오픈 테이블 포맷과 메타데이터 계층을 통해 ACID 트랜잭션, 스키마 진화, Time Travel, 병행 쓰기 제어를 제공한다. 대표 기술로 Delta Lake, Apache Iceberg, Apache Hudi가 있다.

즉 레이크하우스의 목적은 레이크를 더 좋은 레이크로 만드는 것이 아니라, BI와 ML이 서로 다른 복사본을 보지 않도록 단일 데이터 기반을 만드는 데 있다. 이 점이 핵심 필요성이다.

2. 구성요소

요소역할핵심 포인트

레이크하우스의 특징은 저장과 계산의 분리 위에 테이블 의미 계층을 더했다는 점이다. 파일만 저장하던 레이크에 테이블 버전, 삭제/병합, 스키마 변경, 시간여행 개념이 들어오면서 웨어하우스적 성격이 생겼다.

이 구조는 다양한 엔진이 같은 데이터를 공유하게 해준다. BI 엔진은 SQL로 읽고, 데이터 엔지니어는 ETL을 수행하며, ML 플랫폼은 같은 테이블을 학습 데이터로 사용한다. 즉 복제 대신 공유가 중심이 된다.

3. 구조 및 원리

핵심 조건: 스토리지와 컴퓨팅은 분리하되, 파일 수준이 아니라 테이블 수준의 메타데이터와 트랜잭션 일관성을 보장해야 하며, 여러 엔진이 동일한 데이터 정의를 공유해야 한다.

동작 순서:

  1. 원시 데이터 적재: 오브젝트 스토리지에 배치·스트리밍 데이터를 저장한다.
  2. 테이블 포맷 적용: Delta/Iceberg/Hudi가 파일 목록과 버전 정보를 관리한다.
  3. 트랜잭션 및 스키마 제어: 병행 쓰기, MERGE, UPDATE, DELETE, 스키마 진화를 통제한다.
  4. 카탈로그 등록: 테이블 정의, 권한, 메타데이터를 중앙화한다.
  5. 다중 엔진 소비: BI는 SQL, 엔지니어링은 ETL, ML은 학습 파이프라인으로 동일 테이블을 사용한다.
오브젝트 스토리지
        ↓
[오픈 테이블 포맷]
  - ACID
  - 버전 관리
  - 스키마 진화
        ↓
[카탈로그/권한]
        ↓
┌──────────────┬──────────────┬──────────────┐
│ BI/SQL       │ ETL/Streaming│ ML/AI        │
└──────────────┴──────────────┴──────────────┘

핵심 원리는 파일 묶음을 단순 데이터가 아니라 트랜잭션 가능한 테이블로 다루는 것이다. 예를 들어 MERGE INTO를 수행할 때 관련 파일 집합과 메타데이터 스냅샷이 함께 갱신되어야 일관성이 유지된다. 이것이 레이크와 웨어하우스의 결정적 차이다.

또한 Time Travel은 과거 테이블 스냅샷을 조회하게 해주므로 재현성과 감사에 유리하다. 다만 이것은 SCD Type 2와는 다르게 데이터셋 버전 관리 기능이며, 비즈니스 차원 이력 모델을 자동 대체하지는 않는다.

레이크하우스는 레이크와 웨어하우스의 단순 평균이 아니다. 레이크의 확장성과 웨어하우스의 관리성을 결합하지만, 엔진 호환성, 카탈로그 일원화, 파일 최적화, 메타데이터 관리가 추가 과제가 된다. 따라서 기술 선택만으로 완성되지 않으며 운영 역량이 중요하다.

5. 실무 적용 및 판단

적합한 상황:

  • BI와 ML이 동일한 원천 데이터를 공유해야 할 때
  • 레이크와 DW 이중 적재 비용이 큰 환경
  • 클라우드 오브젝트 스토리지 기반 플랫폼을 표준화하려는 조직

주의 사항:

  • 소규모·단순 BI만 필요하면 전통 DW가 더 간단할 수 있음
  • 엔진별 포맷 호환성과 카탈로그 통합을 검증해야 함
  • 파일 소형화, 파티션 설계, 메타데이터 압축 등 운영 최적화가 필수

체크리스트:

  1. 어떤 오픈 테이블 포맷을 표준으로 삼을 것인가?
  2. 카탈로그와 권한 관리를 중앙화했는가?
  3. BI/ETL/ML 엔진이 동일 테이블 정의를 공유하는가?
  4. 배치·스트리밍 병행 쓰기 시 일관성이 보장되는가?
  5. 레이크하우스와 기존 DW의 역할 분담이 명확한가?

6. 기대효과 및 결론

레이크하우스는 데이터 복제를 줄이고, BI와 ML 사이의 지연과 불일치를 감소시키며, 원시 데이터의 유연성과 공식 분석 데이터의 관리성을 동시에 노린다. 이는 데이터 플랫폼 복잡도와 비용을 구조적으로 줄일 수 있다.

하지만 모든 문제를 한 번에 해결하는 만능 구조는 아니다. 포맷 선택, 메타데이터 운영, 성능 튜닝, 거버넌스 체계가 뒷받침되지 않으면 오히려 복잡성이 증가한다. 따라서 결론적으로 레이크하우스의 본질은 새로운 저장소가 아니라 공유 가능한 단일 데이터 기반 위에 트랜잭션과 거버넌스를 부여하는 통합 데이터 운영 모델이다.
