0. 핵심 인사이트

핵심: 스토리지와 컴퓨팅의 분리는 데이터를 오래 보관하는 문제와 데이터를 빠르게 계산하는 문제를 서로 다른 계층으로 나누어 각각 독립적으로 확장하게 만드는 클라우드 데이터 아키텍처의 핵심 원리다. 비유: 물건을 보관하는 창고와 작업하는 공장을 분리해, 물건이 늘면 창고만 넓히고 주문이 몰리면 작업 인력만 늘리는 방식과 같다.

📝 모범 답안

1. 개요 및 필요성

전통적인 데이터베이스와 초기 하둡 계열 시스템은 데이터가 저장된 노드에서 계산을 수행하는 결합형 구조를 많이 사용했다. 이 방식은 데이터 지역성(Data Locality) 측면에서 유리했지만, 스토리지 수요와 컴퓨팅 수요가 동시에 증가하지 않는 현실적 워크로드에서는 비효율이 컸다. 데이터는 계속 늘어나는데 계산은 특정 시간대에만 집중되는 경우가 대표적이다.

클라우드 환경에서는 고내구성 오브젝트 스토리지와 고속 네트워크가 보편화되면서 굳이 데이터를 계산 노드 로컬 디스크에 묶어둘 필요가 줄어들었다. 이에 따라 데이터를 중앙의 공유 저장소에 두고, 컴퓨팅 노드는 필요할 때 생성·확장·중지하는 방식이 가능해졌다.

이 분리 원리는 비용 구조를 바꾼다. 저장은 저렴한 계층에 장기 보관하고, 계산은 필요할 때만 강력한 자원을 사용한다. 결과적으로 데이터 웨어하우스, 레이크하우스, 서버리스 분석, 피처 스토어, 실시간 질의 엔진 등 현대 데이터 플랫폼 대부분이 이 원리를 전제로 설계된다.

실무적으로는 공유 스토리지가 단순 저장소가 아니라 "단일 진실 공급원 (SSOT: Single Source of Truth)" 역할을 한다. 반면 컴퓨팅 노드는 영속 데이터 소유자가 아니라 실행 자원일 뿐이므로, 워크로드별로 여러 클러스터를 병행 운영할 수 있다. 이때 메타데이터 서비스가 없다면 어느 파일이 최신인지, 어떤 스냅샷을 읽어야 하는지 제어할 수 없으므로 분리 구조는 성립하지 않는다.

3. 구조 및 원리

핵심 조건: 공유 스토리지는 내구성과 일관성을 제공하고, 컴퓨팅 계층은 무상태로 동작하며, 메타데이터 계층이 파일 버전·트랜잭션·통계를 관리해야 한다. 또한 네트워크 대역폭과 캐시 전략이 충분하지 않으면 분리의 장점이 성능 병목으로 상쇄된다.

동작 순서:

  1. 데이터 영속 저장: 원천 데이터와 변환 결과를 오브젝트 스토리지 또는 분산 스토리지에 저장한다. 저장 계층은 비용과 내구성에 최적화된다.
  2. 메타데이터 등록: 파일 목록, 파티션, 통계, 스냅샷 버전을 메타데이터 서비스에 기록한다. 실제 읽기 대상은 이 메타데이터가 결정한다.
  3. 컴퓨팅 자원 할당: 질의나 배치 작업이 들어오면 작업 성격에 맞는 컴퓨팅 클러스터를 할당한다. 같은 데이터를 여러 컴퓨팅 풀이 동시에 읽어도 저장 복제가 필요 없다.
  4. 원격 읽기 + 캐시 활용: 필요한 데이터 블록만 원격 저장소에서 읽고, 자주 접근되는 데이터는 로컬 캐시에 보관해 반복 I/O를 줄인다.
  5. 결과 저장 및 회수: 계산 결과를 다시 공유 스토리지에 기록하고, 컴퓨팅 자원은 종료하거나 축소한다. 데이터는 남고 계산 자원만 사라진다.

이 구조가 중요한 이유는 확장 단위가 달라지기 때문이다. 결합형 구조에서는 저장량 증가가 곧 서버 증설을 의미하지만, 분리형 구조에서는 스토리지만 확장하면 된다. 반대로 일시적인 쿼리 폭증은 데이터 이동 없이 계산 자원만 늘리면 된다. 이 독립성 때문에 비용 최적화와 멀티 워크로드 격리가 가능해진다.

다만 모든 상황에서 무조건 유리한 것은 아니다. 네트워크가 약하거나, 극도로 낮은 지연의 로컬 디스크 접근이 필요한 워크로드, 혹은 데이터와 계산이 항상 같은 비율로 증가하는 경우에는 결합형 구조가 단순하고 효율적일 수 있다.

이 원리는 Snowflake, BigQuery, Redshift RA3, Databricks, Apache Iceberg/Delta Lake 기반 레이크하우스와 직접 연결된다. 즉 분리는 단일 제품 기능이 아니라 현대 분석 시스템의 공통 토대다. 반면 데이터 지역성을 강조하는 일부 NoSQL, HPC, 로컬 SSD 기반 검색 시스템은 여전히 결합형 구조를 선호한다.

5. 실무 적용 및 판단

분리형 아키텍처는 데이터 증가 속도와 연산 증가 속도가 다를 때 가장 큰 효과를 낸다. 예를 들어 원천 데이터는 꾸준히 누적되지만, 월말·분기말에만 대량 계산이 발생하는 분석 시스템은 분리형이 매우 유리하다. 또한 BI, 데이터 과학, ETL을 서로 독립된 컴퓨팅 풀로 운영해야 하는 경우에도 효과가 크다.

실무 체크리스트:

  • 데이터 저장량과 계산 수요가 서로 다른 속도로 증가하는가?
  • 워크로드별 성능 격리가 필요한가?
  • 오브젝트 스토리지와 네트워크 성능이 요구 수준을 만족하는가?
  • 캐시, 프루닝, 파일 포맷 최적화 전략이 준비되어 있는가?
  • 메타데이터 서비스의 일관성과 장애 대응 설계가 충분한가?

대표 안티패턴은 모든 연산을 원격 스토리지에서 그대로 처리하면서 캐시·파일 포맷·파티셔닝 설계를 무시하는 것이다. 분리형 구조는 하드웨어 마법이 아니라, 메타데이터와 데이터 배치 전략이 뒷받침되어야 성능을 얻는다.

6. 기대효과 및 결론

스토리지와 컴퓨팅의 분리는 데이터 플랫폼을 탄력적 자원 조합으로 바꾼다. 장기 보관 비용을 낮추고, 동시성 처리와 워크로드 격리를 쉽게 만들며, 서버리스나 멀티 클러스터 같은 운영 모델을 가능하게 한다.

그러나 분리 자체가 목적이 되어서는 안 된다. 메타데이터 일관성, 파일 단위 최적화, 네트워크 설계, 캐시 정책을 함께 갖추지 못하면 분리는 단순한 원격 I/O 비용 증가로 끝난다.

결론적으로 이 개념은 클라우드 데이터 아키텍처의 가장 중요한 구조 원리 중 하나이며, 비용 효율성과 유연성의 근본 배경을 설명하는 키워드다. 제품 기능보다 먼저 이 원리를 이해해야 클라우드 DW와 레이크하우스의 차이를 올바르게 해석할 수 있다.
