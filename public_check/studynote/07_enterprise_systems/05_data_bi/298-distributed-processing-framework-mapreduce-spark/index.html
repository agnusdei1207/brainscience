0. 핵심 인사이트

핵심: 분산 처리 프레임워크는 거대한 데이터를 여러 노드에 나누어 병렬 계산함으로써 단일 서버의 한계를 넘어서는 계산 모델이며, MapReduce는 디스크 중심 안정성, Spark는 메모리 중심 범용성을 대표한다. 비유: 한 사람이 모든 짐을 나르는 대신 여러 작업자가 구역을 나눠 옮기고 마지막에 결과만 합치는 대규모 물류 작업과 같다.

📝 모범 답안

1. 개요 및 필요성

빅데이터 문제의 본질은 저장보다 계산이다. 데이터가 테라바이트(TB)를 넘어 페타바이트(PB)로 늘어나면, 단일 서버의 CPU·메모리·디스크 대역폭은 금세 한계에 도달한다. 이를 해결하기 위해 데이터를 여러 노드에 분산 저장하고, 계산도 각 노드가 병렬 수행한 뒤 결과를 합치는 분산 처리 모델이 등장했다.

MapReduce는 이 모델을 단순하고 강건한 형태로 정형화했다. 입력을 맵(Map) 단계에서 분할 처리하고, 셔플(Shuffle)로 같은 키를 모은 뒤, 리듀스(Reduce)에서 집계하는 방식이다. 이후 Spark는 중간 결과를 메모리에 유지하고 DAG (Directed Acyclic Graph) 기반 실행 엔진을 도입해 배치뿐 아니라 대화형 분석, 머신러닝, 스트리밍까지 포괄하는 범용 엔진으로 진화했다.

즉 두 프레임워크의 차이는 단순 속도 경쟁이 아니라, 디스크 기반 배치 중심 세대에서 메모리 기반 범용 분석 세대로의 전환으로 이해해야 한다.

MapReduce는 단계가 명확하고 단순하지만, 각 단계의 중간 결과를 디스크에 저장하므로 반복 알고리즘에서 비효율이 크다. Spark는 RDD (Resilient Distributed Dataset)와 메모리 캐시를 통해 이 문제를 줄였고, SQL·Streaming·MLlib를 통합해 범용 분석 플랫폼으로 발전했다.

3. 구조 및 원리

핵심 조건: 데이터가 분할 가능해야 하고, 작업이 병렬 실행 가능해야 하며, 셔플 비용이 계산 이득을 초과하지 않아야 한다. 또한 노드 실패를 감안한 재실행 모델이 있어야 분산 처리가 안정적으로 동작한다.

동작 순서:

  1. 입력 분할: 대용량 데이터를 블록 또는 파티션 단위로 나눈다. 분할이 병렬성의 출발점이다.
  2. 로컬 계산 실행: 각 워커가 자기 파티션에 대해 맵 또는 변환 작업을 수행한다. 이 단계에서는 데이터 지역성이 성능에 중요하다.
  3. 셔플 및 재배치: 같은 키를 가진 데이터를 한곳으로 모으기 위해 네트워크를 통해 재배치한다. 분산 처리의 가장 비싼 단계다.
  4. 집계/후속 변환: 리듀스 또는 다음 단계 연산을 수행한다. Spark는 여러 변환을 DAG로 최적화해 한 번에 실행 계획을 세울 수 있다.
  5. 결과 저장과 복구: 결과를 저장하고, 실패한 태스크는 원본 파티션과 실행 계획을 기준으로 재실행한다.
Input Data
   │ split
   ▼
[Partition 1] [Partition 2] [Partition 3] ...
   │              │              │
   ▼              ▼              ▼
 Map / Transform on workers (parallel)
   └───────┬──────────────┬───────┘
           ▼              ▼
        Shuffle / Exchange
           │
           ▼
      Reduce / Aggregate
           │
           ▼
        Final Result

MapReduce는 각 단계를 디스크 경계로 구분하므로 단순하고 복구가 쉽지만 느리다. Spark는 중간 결과를 메모리에 유지하고 실행 계획을 최적화해 반복 연산과 상호작용형 분석에서 훨씬 유리하다. 대신 메모리 관리, 셔플 튜닝, 데이터 스큐 대응이 중요해진다.

실무에서는 MapReduce가 완전히 사라진 것이 아니라, Spark가 대부분의 신규 워크로드를 흡수한 형태다. 또한 Spark는 Hadoop 생태계의 저장소와 자원 관리자를 활용할 수 있으므로 대체보다 진화로 보는 편이 정확하다. 최근에는 Flink, Ray, DuckDB 기반 분산 쿼리 등 다른 프레임워크도 등장했지만, 분산 처리의 기본 원리를 이해하는 데는 MapReduce와 Spark 비교가 가장 핵심적이다.

5. 실무 적용 및 판단

대규모 배치 집계, 로그 처리, 피처 엔지니어링, 레이크하우스 ETL에는 Spark가 사실상 표준이다. 반면 작업이 단순하고 응답시간 요구가 낮으며, 메모리 비용을 최소화해야 하는 일부 환경에서는 디스크 중심 배치가 여전히 합리적일 수 있다.

실무 체크리스트:

  • 데이터 크기가 단일 서버 한계를 넘는가?
  • 반복 연산이나 대화형 분석이 필요한가? 그렇다면 Spark 쪽이 유리한가?
  • 셔플 비용이 지나치게 큰 조인 구조는 아닌가?
  • 파티션 수와 데이터 스큐가 적절히 제어되는가?
  • 스토리지, 메모리, 네트워크 중 실제 병목이 무엇인지 측정하는가?

안티패턴은 작은 데이터를 위해 과도한 분산 프레임워크를 사용하는 것이다. 분산 처리에는 스케줄링, 직렬화, 네트워크 교환 오버헤드가 있으므로, 데이터 규모와 복잡도가 충분할 때만 이점이 생긴다.

6. 기대효과 및 결론

분산 처리 프레임워크는 값싼 범용 서버를 묶어 대규모 데이터를 계산 가능하게 함으로써 데이터 규모의 경제를 만들었다. MapReduce는 빅데이터 시대의 계산 모델을 정립했고, Spark는 이를 실시간성과 범용성 쪽으로 확장했다.

그러나 성능은 자동으로 주어지지 않는다. 파티셔닝, 셔플, 캐시, 스큐, 파일 포맷, 클러스터 자원 관리가 모두 성능에 직접 영향을 준다. 즉 분산 처리의 본질은 많은 서버를 쓰는 것이 아니라, 데이터 이동을 통제하며 병렬성을 극대화하는 것이다.

결론적으로 MapReduce와 Spark는 세대 차이를 가진 연속선상 기술이며, 빅데이터 시스템의 구조와 병목을 이해하는 가장 중요한 학습 축이다.
