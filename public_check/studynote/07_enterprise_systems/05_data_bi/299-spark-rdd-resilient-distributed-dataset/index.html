0. 핵심 인사이트

핵심: RDD (Resilient Distributed Dataset)는 스파크가 분산 데이터를 불변 객체처럼 다루면서도 장애 시 원본과 연산 계보를 이용해 필요한 파티션만 재계산하도록 설계한 기본 추상화다. 비유: 완성본을 매번 복사해 두는 대신 작업 순서를 적은 설계도를 보관해, 일부가 망가져도 해당 부분만 다시 만드는 조립 공정과 같다.

📝 모범 답안

1. 개요 및 필요성

하둡 MapReduce는 안정적이지만 각 단계의 중간 결과를 디스크에 기록하므로 반복 연산과 상호작용형 분석에 불리했다. 스파크는 메모리 중심 처리로 속도를 높이려 했지만, 메모리에만 데이터를 두면 노드 장애 시 유실 위험이 생긴다. 이 딜레마에 대한 해답이 RDD다.

RDD는 분산 데이터 집합을 불변(Immutable)하게 유지하고, 어떤 연산으로부터 생성되었는지 계보(Lineage)를 기록한다. 따라서 노드 일부가 실패해도 전체 데이터를 복제하지 않고, 유실된 파티션만 다시 계산할 수 있다. 이것이 "Resilient"의 의미다.

현재 스파크 실무는 DataFrame과 Dataset API가 중심이지만, 셔플·파티셔닝·캐시·체크포인트의 근본 원리는 여전히 RDD에서 출발한다. 따라서 RDD는 실무 API보다 더 하위의 실행 원리를 설명하는 개념으로 중요하다.

2. 구성요소

구성요소역할핵심 포인트
파티션 (Partition)데이터 분산 저장 및 병렬 실행 단위병렬성, 스큐, 복구 범위를 결정
트랜스포메이션 (Transformation)새로운 RDD 생성 연산map, filter, join 등, 지연 평가
액션 (Action)실제 계산을 트리거하는 연산count, collect, save 등
리니지 (Lineage)RDD 생성 경로 기록장애 시 재계산의 근거
캐시/퍼시스트반복 사용 RDD를 메모리/디스크에 보관성능 최적화 수단

RDD의 중요한 특징은 "수정"이 아니라 "새로운 RDD 생성"으로 모든 연산을 표현한다는 점이다. 이 불변성 덕분에 동시성 제어가 단순해지고, 어느 파티션이 어느 입력과 연산으로 생성되었는지 명확해진다. 또한 지연 평가(lazy evaluation)로 인해 액션이 호출되기 전까지는 최적화 기회가 유지된다.

3. 구조 및 원리

핵심 조건: 불변성, 파티션 기반 병렬성, 지연 평가, 리니지 기반 복구가 동시에 유지되어야 한다. 이 네 축이 있어야 스파크는 디스크 중심 프레임워크보다 빠르면서도 장애에 강한 실행 모델을 갖는다.

동작 순서:

  1. 기본 RDD 생성: 파일, HDFS, 객체 저장소, 기존 컬렉션 등에서 초기 RDD를 만든다. 이 RDD는 여러 파티션으로 분리된다.
  2. 변환 체인 기록: map, filter, flatMap, reduceByKey 같은 연산을 적용하면 즉시 실행하지 않고 새로운 RDD와 의존 관계만 기록한다.
  3. 액션 호출로 실행 계획 생성: count나 save가 호출되면 스파크는 여러 변환을 묶어 DAG를 만들고 스테이지로 분리한다.
  4. 파티션 단위 실행 및 셔플: 좁은 의존성은 로컬에서 빠르게 처리하고, 넓은 의존성은 셔플을 통해 재분배한다. 셔플이 성능의 핵심 병목이다.
  5. 장애 시 재계산: 특정 파티션이 유실되면 전체 작업을 다시 하지 않고, 해당 파티션을 생성한 상위 RDD와 연산 경로만 따라 재생성한다.

리니지 복구는 효율적이지만, 연산 체인이 너무 길어지면 장애 시 재계산 비용이 커진다. 이때 체크포인트(checkpoint)를 사용해 중간 결과를 안정 저장소에 기록하면 복구 경로를 단축할 수 있다. 따라서 RDD는 단순히 빠른 구조가 아니라, 계산과 저장 사이의 균형을 선택적으로 조절하는 구조다.

4. 비교 및 연결

항목RDDDataFrame / Dataset

대표 활용비정형 처리, 커스텀 로직, 실행 원리 이해대부분의 실무 ETL, SQL, 분석

RDD는 현재 주력 API는 아니지만, Spark 엔진의 기본 철학을 가장 잘 드러낸다. 또한 Spark Structured Streaming의 내부도 결국 분산 데이터셋, 파티션, 셔플, 상태 관리 논리 위에 세워져 있으므로 RDD 개념을 이해하면 상위 API의 병목도 읽을 수 있다.

5. 실무 적용 및 판단

실무에서는 대부분 DataFrame을 사용하되, 성능 병목을 해결하거나 특수한 비정형 로직을 구현할 때 RDD 수준 이해가 필요하다. 특히 데이터 스큐, 셔플 폭증, 캐시 남용, 파티션 과소/과다 설정 문제는 RDD 관점에서 봐야 원인을 정확히 찾을 수 있다.

실무 체크리스트:

  • 파티션 수가 클러스터 코어 수와 작업 특성에 맞는가?
  • 불필요한 wide transformation으로 셔플을 과도하게 유발하지 않는가?
  • 반복 사용되는 RDD/DataFrame만 선택적으로 캐시하는가?
  • 리니지가 지나치게 길어져 checkpoint가 필요한 시점은 아닌가?
  • 특정 키에 데이터가 몰리는 스큐가 없는가?

안티패턴은 메모리에 올리면 무조건 빠르다고 생각해 모든 중간 결과를 캐시하는 것이다. 메모리 부족과 가비지 컬렉션(GC) 압박으로 오히려 성능이 악화될 수 있다.

6. 기대효과 및 결론

RDD는 분산 처리에서 "복제를 통한 안정성"이 아니라 "재계산 가능한 설계"로 안정성을 확보한 혁신적 개념이다. 이 아이디어 덕분에 Spark는 디스크 기록을 줄이면서도 실용적인 장애 복구 능력을 확보했다.

물론 오늘날 사용자 관점에서는 RDD를 직접 다룰 일이 줄었지만, 스파크 튜닝과 아키텍처 이해 측면에서는 여전히 핵심이다. 데이터셋이 어떻게 나뉘고, 어떤 단계에서 셔플이 생기며, 왜 장애 시 특정 파티션만 복구되는지 모두 RDD 개념으로 설명된다.

결론적으로 RDD는 스파크의 역사적 API를 넘어, 분산 계산의 성능과 탄력성을 동시에 달성한 설계 철학 자체로 이해해야 한다.
