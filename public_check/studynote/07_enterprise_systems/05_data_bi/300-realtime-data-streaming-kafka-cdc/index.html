0. 핵심 인사이트

핵심: Kafka와 CDC (Change Data Capture)의 결합은 운영 데이터베이스의 변경 사항을 트랜잭션 로그에서 읽어 이벤트 스트림으로 전환함으로써, 원천 DB 부하를 최소화하면서 실시간 데이터 동기화와 이벤트 기반 처리를 가능하게 한다. 비유: 매번 창고 전체를 확인하러 가는 대신, 입출고 장부에 적힌 변경 내역만 실시간 전광판으로 흘려보내는 구조와 같다.

📝 모범 답안

1. 개요 및 필요성

전통적인 데이터 통합은 주기적 배치나 폴링 기반 ETL에 의존했다. 이 방식은 구현이 단순하지만, 데이터 시차가 크고 원천 DB에 반복 조회 부하를 준다. 특히 주문, 결제, 고객 행동처럼 초 단위 반응이 중요한 업무에서는 배치 지연이 곧 비즈니스 손실로 이어진다.

CDC는 데이터베이스 트랜잭션 로그를 읽어 변경 이벤트를 추출한다. 즉 어떤 행이 삽입, 수정, 삭제되었는지를 SQL 조회 없이 포착할 수 있다. Kafka는 이 이벤트를 내구성 있는 분산 로그로 저장하고 여러 소비자가 독립적으로 처리하게 한다. 이 둘의 결합이 현대 실시간 데이터 파이프라인의 표준 구조가 되었다.

핵심은 "운영 DB의 상태 변화"를 "재생 가능한 이벤트 스트림"으로 바꾸는 것이다. 이렇게 되면 DW 적재, 검색 색인 갱신, 실시간 추천, 캐시 무효화, 마이크로서비스 이벤트 연계까지 하나의 변경 흐름 위에 정렬할 수 있다.

실시간 스트리밍 파이프라인은 단순히 데이터를 빨리 보내는 것만으로 완성되지 않는다. 스키마가 계속 변하고, 장애가 발생하고, 같은 이벤트를 다시 처리할 수 있어야 하므로 이벤트 형식과 오프셋 관리, 재처리 전략까지 함께 설계해야 한다.

3. 구조 및 원리

핵심 조건: 로그 기반 CDC, 적절한 파티션 키, 이벤트 스키마 버전 관리, 소비자 멱등성, 재처리 가능한 저장소가 함께 갖춰져야 한다. 이 중 하나라도 빠지면 실시간성은 얻어도 정합성을 잃기 쉽다.

동작 순서:

  1. 초기 스냅샷 확보: CDC 엔진이 초기 데이터 상태를 읽거나 특정 시점부터 로그 구독을 시작한다. 증분만 보기 전에 기준 상태가 필요하다.
  2. 트랜잭션 로그 구독: DB에 새로운 변경이 발생하면 CDC 엔진이 로그를 읽어 테이블, 키, before/after 값을 해석한다.
  3. 이벤트 직렬화 및 게시: 변경을 Kafka 토픽에 이벤트로 저장한다. 키를 적절히 설정해야 같은 엔터티의 순서가 유지된다.
  4. 스트림 처리 및 배포: 소비자는 이벤트를 DW 적재, 검색 인덱싱, 캐시 갱신, 실시간 규칙 처리 등 목적별로 독립 소비한다.
  5. 오프셋 커밋과 재처리: 소비자는 처리 완료 후 오프셋을 관리하고, 장애 시 다시 읽어 복구한다. 이 단계에서 멱등성이 중요하다.
[Operational DB]
   │ transaction log
   ▼
[CDC Engine]
 Debezium / connector
   │ change events
   ▼
[Kafka Topic]
 key-based ordered log
   │            │             │
   ▼            ▼             ▼
[DW Sink]   [Search Index]  [Realtime App]

폴링 방식과의 결정적 차이는 데이터 감지 방식이다. 폴링은 현재 상태를 반복 조회하므로 삭제 감지나 세밀한 변경 순서 추적에 약하다. 반면 로그 기반 CDC는 데이터베이스가 실제로 기록한 변경 순서를 따라가므로 정합성과 실시간성 모두에서 유리하다.

다만 exactly-once semantics는 전체 파이프라인에서 자동으로 보장되지 않는다. Kafka 생산자는 멱등 전송을 지원하더라도, 최종 싱크가 중복 쓰기를 허용하면 결과는 at-least-once가 된다. 따라서 실무에서는 "재처리 가능 + 멱등성 보장"을 기준으로 설계하는 경우가 많다.

4. 비교 및 연결

항목폴링 기반 동기화Kafka + CDC
변경 감지주기적 조회트랜잭션 로그 기반
원천 DB 부하상대적으로 큼상대적으로 작음
지연폴링 주기에 비례초·밀리초 단위 가능

Kafka + CDC는 이벤트 기반 아키텍처, CQRS (Command Query Responsibility Segregation), Outbox Pattern, 실시간 레이크하우스 적재와 깊게 연결된다. 즉 단순 ETL 기술이 아니라 운영 시스템과 분석 시스템을 같은 이벤트 흐름으로 결합하는 아키텍처 요소다.

5. 실무 적용 및 판단

이 구조는 실시간 추천, 부정 거래 탐지, 재고 동기화, 고객 360, 캐시 무효화, 검색 색인 갱신처럼 변경 즉시 반응해야 하는 업무에서 효과가 크다. 반대로 데이터 양이 작고 지연 허용 범위가 넓다면 단순 배치가 더 경제적일 수 있다.

실무 체크리스트:

  • 원천 DB 로그 접근 권한과 보존 기간이 충분한가?
  • Kafka 토픽 키가 엔터티 순서를 보장하도록 설계되었는가?
  • 이벤트 스키마 진화 정책이 정의되어 있는가?
  • 소비자 멱등성 또는 중복 제거 로직이 있는가?
  • 초기 스냅샷과 증분 로그 전환 시점의 정합성을 검증했는가?

안티패턴은 모든 변경을 하나의 거대한 토픽에 넣고 소비자가 알아서 필터링하게 만드는 것이다. 이는 스키마 충돌과 소비자 복잡도를 급격히 증가시킨다. 테이블별, 도메인별, 이벤트 타입별 분리 전략이 필요하다.

6. 기대효과 및 결론

Kafka와 CDC를 결합하면 운영 데이터의 최신 상태를 분석과 서비스 계층에 거의 실시간으로 반영할 수 있고, 배치 지연으로 인한 의사결정 차이를 크게 줄일 수 있다. 또한 같은 변경 이벤트를 여러 시스템이 재사용하므로 파이프라인 중복 개발도 줄어든다.

그러나 실시간성은 운영 복잡도와 함께 온다. 스키마 진화, 순서 보장, 소비자 재처리, 로그 보존, 보안 통제가 모두 필요하다. 즉 스트리밍은 빠른 ETL이 아니라 장기 운영 가능한 이벤트 플랫폼을 만드는 일에 가깝다.

결론적으로 Kafka + CDC는 "데이터 복제"를 넘어 "상태 변화를 이벤트로 표준화"하는 구조다. 현대 실시간 데이터 아키텍처의 중심 축으로 이해해야 한다.
