0. 핵심 인사이트

핵심: 컬럼 지향 압축의 본질은 같은 속성끼리 모아 저장함으로써 값의 반복성과 분포 특성을 이용해 I/O와 저장 공간을 동시에 줄이는 데 있다. 비유: 서로 다른 물건을 한 상자에 뒤섞어 담는 대신, 같은 종류끼리 정리해 두면 찾기도 쉽고 더 촘촘하게 포장되는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

분석 시스템에서는 대량의 레코드 중 일부 컬럼만 읽는 경우가 대부분이다. 예를 들어 수십 개 컬럼이 있는 이벤트 로그에서 사용자는 시간, 국가, 매출만 읽고 싶을 수 있다. 전통적인 행 지향 저장 (Row-Oriented Storage)은 한 행의 모든 값을 함께 저장하므로, 필요한 몇 개 컬럼만 읽더라도 불필요한 I/O가 많이 발생한다.

Parquet와 ORC 같은 컬럼 지향 저장 포맷은 같은 컬럼을 연속적으로 저장해 선택적 읽기와 강한 압축을 동시에 달성한다. 특히 값의 반복이 많은 컬럼에서는 런 길이 인코딩 (Run-Length Encoding, RLE), 사전 인코딩 (Dictionary Encoding), 비트 패킹 (Bit Packing)이 매우 효과적으로 동작한다.

따라서 이 기술의 핵심은 단순 파일 포맷 차이가 아니라, 데이터 배치 방식을 분석 중심으로 바꾸는 것이다. 저장 구조가 바뀌면 쿼리 엔진의 읽기 전략, 압축 효율, CPU 사용 패턴까지 함께 달라진다.

2. 구성요소

컬럼 지향 포맷은 인코딩과 압축이 겹겹이 적용된다. 먼저 동일 컬럼의 반복성과 값 범위를 활용해 RLE나 사전 인코딩으로 구조적 압축을 수행하고, 그 뒤 바이트 단위 압축 코덱을 적용한다. 이중 구조 덕분에 단순 Gzip보다 훨씬 높은 효율을 내는 경우가 많다.

Parquet는 중첩 데이터 표현과 다양한 엔진 호환성에 강하고, ORC는 풍부한 스트라이프 통계와 일부 Hadoop 생태계 최적화에서 강점을 가진다. 그러나 둘 모두 컬럼 지향 압축이라는 공통 원리를 공유한다.

3. 구조 및 원리

핵심 조건: 컬럼 값의 지역성 (Locality), 반복성, 낮은/중간 카디널리티, 정렬 또는 클러스터링 효과가 있을수록 RLE와 컬럼 압축 효율이 커진다.

컬럼 지향 압축은 동일 컬럼 값이 연속 저장된다는 전제에서 출발한다. 예를 들어 국가 코드 컬럼이 KR, KR, KR, KR, US, US처럼 저장되면 RLE는 (KR,4), (US,2)처럼 표현할 수 있다. 행 저장에서는 국가 코드 사이에 이름, 금액, 시간 등 다른 값이 끼어들어 이런 압축이 어렵다.

동작 순서:

  1. 행을 컬럼 단위로 재배열: 입력 데이터가 컬럼 청크로 분리된다. 이것이 선택적 읽기와 컬럼별 인코딩의 전제다.
  2. 컬럼별 통계 수집: 최소값, 최대값, null 수, 값 분포를 계산한다. 이 정보는 인코딩 선택과 Predicate Pushdown에 활용된다.
  3. 인코딩 적용: 반복이 많은 값에는 RLE, 문자열은 사전 인코딩, 작은 정수는 비트 패킹이 적용된다. 인코딩은 데이터 유형별로 다르게 선택된다.
  4. 압축 코덱 적용: 인코딩된 바이트 스트림에 Snappy, ZSTD 등을 적용해 추가 압축한다. 구조적 인코딩 후라서 압축 효율이 더 높다.
  5. 질의 시 선택적 읽기: 필요한 컬럼만 읽고, 푸터 통계를 기반으로 불필요한 페이지/스트라이프를 건너뛴다.
행 지향 저장
[ID,국가,금액][ID,국가,금액][ID,국가,금액]

컬럼 지향 저장
ID   : [1][2][3]
국가 : [KR][KR][KR][US][US]  -> RLE -> (KR,3)(US,2)
금액 : [10][10][10][20][30]  -> Dictionary/Bit Packing 가능

질의: SELECT 국가, SUM(금액)
→ 필요한 컬럼만 읽기: 국가, 금액

Parquet와 ORC가 빠른 이유는 저장 공간이 줄어서만이 아니다. 읽어야 할 바이트 양 자체가 적고, 불필요한 컬럼을 아예 건너뛰며, 페이지 수준 통계로 조건에 맞지 않는 블록을 읽지 않기 때문이다. 즉 압축 효율과 쿼리 효율이 같은 구조에서 동시에 나온다.

4. 비교 및 연결

압축 효율높음높음상대적으로 낮음

적합 워크로드분석, 데이터 레이크분석, Hadoop 생태계트랜잭션 처리

Parquet와 ORC의 차이는 중요하지만, 더 본질적인 비교는 컬럼 저장과 행 저장의 차이다. 분석 시스템에서는 보통 많은 행과 적은 컬럼을 읽으므로 컬럼 저장이 유리하고, OLTP에서는 적은 행을 자주 갱신하므로 행 저장이 유리하다. 즉 포맷 선택은 워크로드 선택이다.

또한 RLE 효율은 정렬 전략과도 연결된다. 예를 들어 국가, 날짜, 상태 코드로 정렬된 데이터는 동일 값이 더 길게 이어져 RLE 효율이 올라간다. 따라서 저장 포맷만 바꾸는 것보다 파티셔닝과 정렬 전략을 함께 설계해야 진짜 효과가 난다.

5. 실무 적용 및 판단

적합한 경우

  • Spark, Hive, Trino, BigQuery 등 대규모 읽기 중심 분석 환경
  • 로그, 이벤트, 정산 데이터처럼 append 중심 배치 적재 환경
  • 특정 컬럼 일부만 자주 읽는 데이터 레이크 환경

주의할 경우

  • 레코드 단위 UPDATE/DELETE가 매우 많은 OLTP 환경
  • 고카디널리티 문자열이 매우 많아 사전 인코딩 효과가 낮은 경우
  • 작은 파일이 지나치게 많아 메타데이터 오버헤드가 커지는 경우

체크리스트:

  • 주요 질의가 전체 행보다 일부 컬럼만 읽는가?
  • 파티셔닝과 정렬이 압축 효율을 높이도록 설계되었는가?
  • Snappy, ZSTD 등 코덱을 지연시간 요구에 맞게 선택했는가?
  • 파일 크기가 엔진의 병렬 처리에 적합한가?
  • ORC/Parquet 선택이 주력 쿼리 엔진과 호환되는가?

실무에서는 Parquet + Snappy 또는 ZSTD 조합이 가장 보편적이며, Hive 계열에서는 ORC를 선호하는 경우가 있다. Delta Lake, Iceberg, Hudi 같은 테이블 포맷도 내부 데이터 파일로 Parquet를 많이 사용한다.

6. 기대효과 및 결론

컬럼 지향 압축을 적용하면 저장 공간 절감, 스캔 성능 향상, 네트워크 비용 감소, 분석 쿼리 시간 단축이라는 효과를 얻는다. 특히 대규모 데이터 레이크에서는 스토리지 비용뿐 아니라 쿼리 엔진이 읽는 데이터 양이 줄어 전체 비용 구조가 개선된다.

그러나 모든 상황에서 만능은 아니다. 작은 단건 조회, 잦은 갱신, 행 단위 일관성이 중요한 환경에서는 행 저장이 더 효율적이다. 또한 압축 효율은 데이터 분포와 정렬 전략의 영향을 크게 받는다.

결론적으로 Parquet·ORC·RLE의 핵심은 파일 포맷 선택이 아니라, 분석 시스템이 데이터를 어떻게 배치하고 얼마나 적게 읽을 것인가에 대한 구조적 최적화다.
