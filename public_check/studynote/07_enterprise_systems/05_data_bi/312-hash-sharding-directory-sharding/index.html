0. 핵심 인사이트

핵심: 샤딩의 본질은 데이터를 여러 노드에 나누는 것 자체가 아니라, 어떤 요청이 어느 노드로 가야 하는지를 안정적으로 결정하는 라우팅 규칙을 설계하는 데 있다. 비유: 도서관 책을 여러 서가에 분산해 두더라도 분류 규칙과 안내 데스크가 없으면 찾는 시간이 더 늘어나는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

단일 데이터베이스 서버는 저장 공간, CPU, 메모리, 네트워크, 락 경합 측면에서 한계를 갖는다. 서비스 규모가 커질수록 더 큰 장비로 수직 확장하는 방식만으로는 비용과 성능을 동시에 만족시키기 어렵다. 이때 데이터를 여러 노드에 분산해 수평 확장하는 대표 기법이 샤딩 (Sharding)이다.

그러나 샤딩은 단순히 데이터를 나누는 순간 끝나지 않는다. 키가 어느 샤드에 저장되는지, 노드가 추가되면 얼마나 재배치되는지, 범위 조회나 조인이 가능한지, 장애 시 라우팅이 어떻게 바뀌는지가 모두 핵심 문제다. 해시 샤딩 (Hash Sharding)과 디렉토리 샤딩 (Directory Sharding)은 이 라우팅 문제를 해결하는 서로 다른 접근이다.

해시 샤딩은 키에 해시 함수를 적용해 샤드를 결정하므로 균등 분산에 강하고, 디렉토리 샤딩은 별도의 매핑 테이블이나 라우팅 서비스가 키와 샤드의 대응을 관리하므로 유연성이 높다. 결국 둘의 차이는 분산 규칙을 계산으로 정할지, 관리 테이블로 정할지의 차이다.

2. 구성요소

요소역할핵심 포인트
샤드 키 (Shard Key)데이터 분산 기준카디널리티와 접근 패턴이 가장 중요
라우터/프록시요청을 적절한 샤드로 전달애플리케이션 분리 여부를 결정
샤드 노드실제 데이터 저장복제와 장애 조치가 함께 설계되어야 함
메타데이터/디렉토리키-샤드 매핑 저장디렉토리 샤딩의 핵심 구성요소
재샤딩 메커니즘노드 증설·축소 시 데이터 이동운영 난이도와 가용성에 큰 영향

샤딩 구조에서 가장 중요한 것은 샤드 키다. 사용자 ID처럼 균등한 키는 해시 샤딩에 잘 맞고, 지역·날짜처럼 범위 조회가 중요한 키는 디렉토리 또는 범위 샤딩이 더 유리할 수 있다. 라우터는 이 판단을 애플리케이션 밖으로 캡슐화해, 서비스 코드가 모든 샤드 구조를 알지 않아도 되게 만든다.

특히 디렉토리 샤딩은 메타데이터 서비스가 사실상 제어 평면 (Control Plane) 역할을 한다. 따라서 이 계층의 가용성과 일관성이 낮으면 전체 샤딩 구조가 흔들린다.

3. 구조 및 원리

핵심 조건: 샤드 키 분포, 조회 패턴, 재샤딩 빈도, 메타데이터 일관성 요구를 함께 고려해 라우팅 방식을 정해야 한다.

샤딩의 원리는 데이터와 요청을 같은 규칙으로 분할하는 것이다. 데이터는 여러 샤드에 분산 저장되고, 요청은 동일한 규칙을 통해 특정 샤드로 라우팅된다. 이 규칙이 단순 계산이면 해시 샤딩, 별도 매핑 참조면 디렉토리 샤딩이다.

동작 순서:

  1. 샤드 키 선정: 사용자 ID, 주문 ID, 테넌트 ID 등 분산 기준을 고른다. 잘못된 키는 핫스팟과 크로스샤드 질의를 만든다.
  2. 라우팅 방식 결정: 해시 샤딩은 hash(key) mod N 또는 일관성 해싱을 사용하고, 디렉토리 샤딩은 매핑 테이블에서 목적 샤드를 찾는다.
  3. 쓰기 라우팅: 요청이 들어오면 라우터가 키를 기준으로 샤드를 정하고 해당 노드에 기록한다. 애플리케이션이 직접 계산할 수도 있으나, 변경 대응이 어렵다.
  4. 읽기/집계 처리: 단일 키 조회는 효율적이지만, 범위 질의나 다중 샤드 집계는 scatter-gather가 필요할 수 있다. 이 지점이 샤딩 비용이다.
  5. 재샤딩 및 복구: 노드 증설·장애 복구 시 키 이동과 메타데이터 갱신이 발생한다. 해시 샤딩은 계산 기반이라 간단하지만 재분배 영향이 크고, 디렉토리 샤딩은 유연하지만 메타데이터 관리가 중요하다.
                [Application]
                      │
                      ▼
                  [Router]
            ┌────────┴────────┐
            │                 │
      Hash Sharding      Directory Sharding
      hash(key)→Shard    lookup(key)→Shard
            │                 │
      ┌─────┼─────┐      ┌────┼────┐
      ▼     ▼     ▼      ▼    ▼    ▼
   Shard1 Shard2 Shard3 Shard1 Shard2 Shard3

해시 샤딩은 균등성 측면에서 강하지만 범위 기반 접근과 테넌트 이동에 약하다. 디렉토리 샤딩은 특정 고객군을 별도 샤드로 옮기거나, 핫 테넌트를 분리하기 쉬우나, 매핑 저장소를 별도로 운영해야 한다. 즉 해시는 단순성과 균등성을, 디렉토리는 유연성과 제어 가능성을 제공한다.

4. 비교 및 연결

항목해시 샤딩디렉토리 샤딩범위 샤딩
라우팅 방식계산 기반매핑 조회 기반범위 규칙 기반
균등 분산좋음설계에 따라 다름핫스팟 가능
운영 유연성낮음높음중간
범위 질의불리함설계에 따라 가능유리함
재샤딩전면 영향 가능선택적 이동 가능경계 조정 필요

실무적으로 해시 샤딩과 디렉토리 샤딩은 경쟁 관계이면서도 함께 쓰이기도 한다. 예를 들어 상위 레벨에서 테넌트를 디렉토리 샤딩으로 특정 클러스터에 배치하고, 해당 클러스터 내부에서 사용자 ID를 해시 샤딩하는 식의 계층형 설계가 가능하다.

또한 일관성 해싱 (Consistent Hashing)은 해시 샤딩의 재배치 비용 문제를 완화한다. 노드 증설 시 모든 키를 재분배하는 대신 일부 구간만 이동시키기 때문이다. 따라서 해시 샤딩을 택하더라도 단순 모듈러 방식과 일관성 해싱 방식은 실무 난이도가 다르다.

5. 실무 적용 및 판단

해시 샤딩이 적합한 경우

  • 단일 키 조회가 대부분이고 트래픽 균등 분산이 중요한 경우
  • 샤드 간 데이터량 편차를 최소화하고 싶은 경우
  • 애플리케이션 단에서 단순한 라우팅을 선호하는 경우

디렉토리 샤딩이 적합한 경우

  • 대형 테넌트 분리, 고객별 배치, 지역별 격리가 필요한 경우
  • 핫 테넌트를 선택적으로 이동해야 하는 경우
  • 라우팅 정책을 운영 중 자주 바꿔야 하는 경우

체크리스트:

  • 샤드 키가 충분히 균등한가?
  • 범위 조회, 정렬, 조인이 얼마나 자주 발생하는가?
  • 노드 증설 시 허용 가능한 데이터 이동량은 어느 정도인가?
  • 디렉토리 메타데이터를 어떤 수준으로 고가용성 처리할 것인가?
  • 크로스샤드 트랜잭션을 어떻게 줄이거나 대체할 것인가?

대표 사례로는 MongoDB의 샤딩, Vitess의 키스페이스 기반 샤딩, Citus의 분산 PostgreSQL, Dynamo 스타일의 일관성 해싱 기반 분산 저장이 있다. SaaS 멀티테넌시에서는 디렉토리 샤딩이 자주 선택된다.

6. 기대효과 및 결론

샤딩을 올바르게 설계하면 저장 용량과 처리량을 선형에 가깝게 확장하고, 장애 범위를 샤드 단위로 격리하며, 대형 서비스의 비용 구조를 개선할 수 있다. 특히 해시 샤딩은 균형 잡힌 분산에, 디렉토리 샤딩은 운영 제어와 고객 격리에 강하다.

반대로 잘못된 샤드 키는 핫스팟, 불균형, 크로스샤드 조인, 운영 복잡성 폭증을 초래한다. 샤딩은 DB를 여러 개로 나눈다고 끝나는 문제가 아니라, 라우팅과 운영 자동화를 함께 설계해야 하는 아키텍처 문제다.

결론적으로 해시 샤딩과 디렉토리 샤딩의 선택 기준은 “데이터를 어떻게 나눌 것인가”보다 “변화하는 트래픽과 테넌트 특성을 얼마나 유연하게 다룰 것인가”에 있다.
