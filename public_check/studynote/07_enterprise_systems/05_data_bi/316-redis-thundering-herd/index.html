0. 핵심 인사이트

핵심: 캐시 스탬피드의 본질은 캐시가 빨라서 생기는 문제가 아니라, 동일한 만료 시점에 다수 요청이 동시에 원본 시스템으로 되돌아가도록 설계되어 있을 때 발생하는 동시성 붕괴다. 비유: 인기 매장의 자동문이 한순간에 잠기면 손님이 모두 계산대로 몰려 내부가 마비되는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

Redis 같은 캐시는 원본 데이터베이스 부하를 줄이고 응답 시간을 개선하는 데 매우 효과적이다. 그러나 핫 키 (Hot Key)가 동시에 만료되거나 캐시 노드 장애가 발생하면, 평소 캐시에 흡수되던 요청들이 한꺼번에 원본 시스템으로 몰린다. 이 현상이 바로 Thundering Herd 또는 Cache Stampede다.

문제는 캐시가 없을 때보다 더 큰 폭발을 일으킬 수 있다는 점이다. 캐시가 존재하는 동안에는 트래픽이 억제되다가 만료 순간 동시성 폭발이 발생하기 때문이다. 특히 인기 상품, 메인 페이지, 추천 결과, 인증 토큰 검증처럼 요청 집중도가 높은 키는 만료 한 번으로도 DB와 백엔드 서비스를 마비시킬 수 있다.

따라서 캐시 설계는 단순히 hit ratio를 높이는 것보다, miss가 발생하는 순간의 동시성 제어를 어떻게 할지를 함께 고려해야 한다. 캐시는 빠른 읽기 계층이면서도 동시성 조절 계층이어야 한다.

2. 구성요소

요소역할핵심 포인트
캐시 키/TTL데이터와 만료 시점 관리같은 TTL 일괄 적용은 동시 만료를 유발
원본 저장소캐시 미스 시 최종 조회 대상과부하 보호가 함께 필요
분산 락/싱글플라이트한 요청만 재생성 작업 수행나머지는 대기 또는 stale 데이터 사용
조기 재계산 전략TTL 이전에 일부 요청이 미리 갱신만료 순간 폭발 완화
보호 장치rate limit, circuit breaker, fallback캐시가 실패해도 백엔드 붕괴 방지

이 요소들은 조합되어야 효과가 있다. 분산 락만 있으면 대기열이 길어질 수 있고, TTL jitter만으로는 인기 키 집중을 완전히 막기 어렵다. stale-while-revalidate, 로컬 캐시, 요청 병합, 백엔드 보호 장치를 함께 사용해야 한다.

또한 캐시 스탬피드는 키 단위 문제이면서 시스템 단위 문제다. 한 키의 폭발이 DB 커넥션 고갈과 스레드 풀 고갈로 이어지면 전체 서비스 장애로 확산된다.

3. 구조 및 원리

핵심 조건: 핫 키, 동일 만료 시점, 고비용 원본 조회, 요청 병합 부재가 동시에 존재할 때 캐시 스탬피드가 발생하므로, 재생성 작업의 단일화와 만료 시점 분산이 필수다.

캐시 스탬피드의 원리는 단순하다. 동일한 키가 만료된 순간 다수 요청이 거의 동시에 캐시 미스를 경험하면, 각 요청이 모두 원본 DB나 API를 호출한다. 이때 원본 조회가 느리면 대기 중 요청이 더 쌓이고, 다시 타임아웃과 재시도로 증폭된다. 결국 캐시 미스가 시스템 폭주로 전이된다.

동작 순서:

  1. 핫 키 생성: 많은 사용자가 동일 데이터에 접근한다. 메인 배너, 인기 상품 목록, 사용자 세션 정보 등이 대표적이다.
  2. 동시 만료 또는 캐시 유실: 동일 TTL로 설정된 캐시가 한꺼번에 만료되거나 Redis 장애로 키가 사라진다.
  3. 동시 미스 발생: 수백~수천 요청이 동시에 캐시 미스를 경험하고 모두 원본 시스템을 조회한다.
  4. 백엔드 포화: DB 커넥션, 스레드, CPU가 포화되며 응답 시간이 증가한다. 느려진 응답은 또 다른 재시도를 부른다.
  5. 보호 메커니즘 동작: 분산 락, stale 반환, rate limit, 백오프, fallback이 있으면 붕괴를 완화하고, 없으면 장애가 확산된다.
정상 상태: Client -> Redis(hit) -> 응답

만료 순간:
Client1 ─┐
Client2 ─┼─> Redis miss ─> DB
Client3 ─┤
Client4 ─┘

개선 구조:
Client1 -> Redis miss -> Lock 획득 -> DB -> Cache set
Client2/3/4 -> 대기 또는 stale 데이터 반환

실무 핵심은 “한 명만 재생성하고 나머지는 기다리거나 오래된 값을 잠시 본다”는 전략이다. Redis의 SET key value NX PX ttl 패턴으로 락을 만들 수 있고, 애플리케이션 레벨 싱글플라이트, 확률적 조기 만료 (Probabilistic Early Expiration), TTL jitter가 이를 보완한다. stale 데이터 허용 범위를 정하면 백엔드 보호 효과가 크게 높아진다.

4. 비교 및 연결

방식장점한계적합 상황
분산 락중복 재생성 차단락 경합과 대기 발생재생성 비용이 큰 핫 키
TTL Jitter동시 만료 완화인기 키 폭발을 완전히 막진 못함대량 키 일반 완화
Stale-While-Revalidate가용성 높음잠시 오래된 데이터 노출약간의 stale 허용 가능
로컬 캐시 + Redis한 번 더 충격 흡수일관성 관리 필요초고QPS 읽기

이 기법들은 대체 관계보다 계층 관계다. 예를 들어 TTL jitter는 전체 키 동시 만료를 분산하고, 분산 락은 특정 핫 키 폭발을 막으며, stale-while-revalidate는 사용자 응답을 유지한다. 따라서 보통 세 기법을 함께 적용한다.

또한 스탬피드는 캐시 계층만의 문제가 아니라 서킷 브레이커 (Circuit Breaker), 레이트 리미터, bulkhead와 연결된다. 캐시가 실패했을 때 백엔드가 어디까지 버틸 수 있는지 전체 시스템 관점으로 봐야 한다.

5. 실무 적용 및 판단

우선 적용해야 하는 경우

  • 인기 키에 트래픽이 매우 집중되는 서비스
  • 캐시 미스 시 DB 조회 비용이 큰 서비스
  • 짧은 TTL을 많이 사용하는 추천, 가격, 콘텐츠 시스템

주의가 필요한 경우

  • stale 데이터가 치명적인 도메인(잔액, 결제 승인)
  • 락 해제 실패나 중복 재생성에 대한 예외 처리가 없는 경우
  • 캐시 갱신 실패를 모니터링하지 않는 경우

체크리스트:

  • 핫 키를 식별하고 있는가?
  • TTL에 jitter를 적용하고 있는가?
  • 재생성 작업을 단일화하는 락 또는 singleflight가 있는가?
  • stale 허용 범위를 도메인별로 정의했는가?
  • Redis 장애 시 fallback과 rate limit가 있는가?

실무 패턴으로는 Redis + Lua 스크립트 락, application-level singleflight, CDN stale-if-error, background refresh, local cache layered caching이 널리 쓰인다. 전자상거래 메인 페이지와 API gateway 캐시에서 특히 중요하다.

6. 기대효과 및 결론

적절한 스탬피드 방지 설계를 적용하면 캐시 만료가 시스템 장애로 전이되는 위험을 크게 줄일 수 있고, 원본 DB의 피크 부하를 안정적으로 제어할 수 있다. 이는 평균 성능보다 피크 순간 생존성을 높여 준다.

하지만 stale 데이터 노출, 락 경합, 구현 복잡성이라는 대가도 있다. 따라서 데이터 특성에 따라 stale 허용 범위와 재생성 정책을 다르게 가져가야 한다. 모든 데이터를 같은 캐시 정책으로 다루는 것은 위험하다.

결론적으로 Redis Thundering Herd 대응의 본질은 캐시 적중률 향상이 아니라, 캐시 실패 순간의 동시성 폭발을 제어하는 것이다. 장애는 평시가 아니라 미스 순간에 결정된다.
