0. 핵심 인사이트

핵심: SQL 인젝션 방어의 본질은 입력을 더 열심히 거르는 데 있지 않고, 사용자 데이터와 SQL 코드의 경계를 구조적으로 분리해 데이터가 문법으로 승격되지 못하게 만드는 데 있다. 비유: 손님이 주문서에 적은 말을 주방장이 메뉴 조리법으로 착각하지 않게, 주문 내용과 조리 지시는 반드시 별도 칸에 적는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

SQL Injection은 애플리케이션이 사용자 입력을 SQL 문자열에 직접 결합할 때 발생하는 대표적 취약점이다. 공격자는 입력값에 따옴표, 주석, 조건문, UNION, 서브쿼리 등을 삽입해 원래 의도와 다른 SQL을 실행하게 만든다. 그 결과 인증 우회, 데이터 탈취, 데이터 변조, 권한 상승까지 이어질 수 있다.

이 취약점이 오래되었음에도 반복되는 이유는 문자열 연결 방식이 구현은 쉽지만, 코드와 데이터의 경계를 무너뜨리기 때문이다. 입력 검증만으로는 모든 우회 패턴을 막기 어렵고, 데이터베이스 제품별 문법 차이도 존재한다. 따라서 근본 방어는 패턴 차단이 아니라 실행 구조 변경이어야 한다.

Prepared Statement와 파라미터 바인딩은 이 구조적 분리를 제공한다. SQL 문장은 미리 고정된 형태로 컴파일되고, 사용자 입력은 값으로만 전달되므로 입력이 SQL 문법으로 해석되지 않는다. 이것이 가장 중요한 1차 방어선이다.

2. 구성요소

요소역할핵심 포인트
Prepared StatementSQL 구조와 입력값 분리가장 우선되는 근본 방어
입력 검증/허용 목록형식, 길이, 범위, 식별자 제한파라미터 바인딩을 보완

이 요소들은 계층 방어를 이룬다. Prepared Statement가 핵심이지만, 테이블명·컬럼명·정렬 조건처럼 파라미터 바인딩이 어려운 식별자 영역에서는 허용 목록 검증이 필요하다. 또한 취약점이 남아도 DB 계정이 최소 권한이면 피해 범위가 줄어든다.

즉 SQL 인젝션 대응은 “정규식 하나로 막기”가 아니라 쿼리 생성, 입력 검증, DB 권한, 모니터링까지 연결된 설계 문제다.

3. 구조 및 원리

핵심 조건: 쿼리 구조는 고정하고 입력은 바인딩 값으로만 전달하며, 식별자와 동적 정렬은 허용 목록으로 제한하고, DB 권한은 최소화해야 한다.

SQL 인젝션의 원리는 데이터가 SQL 문법 일부로 해석되는 데 있다. 문자열 결합 방식에서는 WHERE id = ' 뒤에 사용자가 넣은 값이 곧바로 문장 안으로 들어가므로, OR 1=1 -- 같은 페이로드가 조건을 변형할 수 있다. 반면 Prepared Statement는 SQL 구조를 먼저 정하고 값은 별도 파라미터로 전달하므로, 입력이 따옴표를 포함해도 단지 값으로만 처리된다.

동작 순서:

  1. 입력 수신: 사용자 요청에서 검색어, 로그인 ID, 정렬 조건 등을 받는다. 이 단계에서 길이와 형식을 1차 검증한다.
  2. 허용 목록 판단: 정렬 컬럼, 테이블명, 방향(ASC/DESC)처럼 바인딩이 어려운 요소는 사전 정의된 목록에서만 선택한다. 자유 입력을 허용하면 바인딩만으로 충분하지 않다.
  3. 파라미터 바인딩 쿼리 생성: SQL 템플릿은 고정하고, 입력값은 ?, $1, :name 같은 바인딩 자리로 전달한다.
  4. 권한 제한된 계정으로 실행: 애플리케이션 계정은 필요한 SELECT/INSERT/UPDATE만 허용하고 DDL, 관리자 권한은 제거한다.
  5. 로그 및 탐지: 실패한 바인딩, 이상 쿼리 패턴, 과다 오류를 기록해 WAF·SIEM과 연계한다.
[Unsafe]
SQL = "SELECT * FROM users WHERE id = '" + input + "'"
                     ▲
                입력이 문법으로 해석됨

[Safe]
SQL = "SELECT * FROM users WHERE id = ?"
bind(input)
                     ▲
                입력은 값으로만 전달

실무에서 놓치기 쉬운 부분은 동적 ORDER BY, LIKE 패턴, IN 절 다중 값, raw SQL 기능이다. ORM을 사용해도 최종적으로 문자열 결합을 하면 취약해진다. 따라서 보안 코딩 규칙은 프레임워크 수준 가드레일과 코드 리뷰 기준으로 함께 운영해야 한다.

4. 비교 및 연결

방식효과한계위치
Prepared Statement근본 방어식별자 동적 생성은 별도 통제 필요1차 방어
입력 검증비정상 입력 축소우회 가능, 단독 방어 불충분보조 방어
ORM/Query Builder안전한 기본값 제공raw query 시 취약개발 편의 계층
WAF/DB Firewall알려진 패턴 탐지·차단우회·오탐 가능2차 방어
최소 권한피해 반경 축소취약점 자체는 제거 못 함영향 완화

여기서 가장 중요한 연결은 Prepared Statement가 예방, WAF가 탐지·완화, 최소 권한이 피해 축소를 담당한다는 점이다. 어느 하나도 단독으로 충분하지 않다. 특히 WAF는 보조 수단이지 1차 방어가 아니다.

또한 SQL 인젝션은 NoSQL Injection, LDAP Injection, Command Injection과 같은 “구문 주입” 계열 취약점과 본질적으로 같다. 모두 코드와 데이터의 경계 붕괴가 원인이다.

5. 실무 적용 및 판단

필수 적용 항목

  • 모든 사용자 입력 기반 쿼리에 Prepared Statement 강제
  • 동적 정렬·필터·테이블명은 allowlist로만 처리
  • 서비스 계정 최소 권한 적용
  • 에러 메시지 최소화 및 로깅 표준화

주의가 필요한 경우

  • 레거시 문자열 결합 SQL이 남아 있는 경우
  • 배치 스크립트, 운영 툴, 관리자 페이지가 보안 리뷰 밖에 있는 경우
  • 검색 기능 구현 시 % 와일드카드와 동적 조건을 직접 조합하는 경우

체크리스트:

  • 코드베이스에 문자열 결합 SQL이 남아 있는가?
  • ORM raw query 사용처가 검토되었는가?
  • 정렬 컬럼과 방향이 allowlist 기반인가?
  • DB 계정이 DDL/관리 권한을 갖고 있지 않은가?
  • WAF/DB 로그가 의심 패턴을 수집하는가?

실무 기준으로는 OWASP ASVS, CWE-89, Java의 PreparedStatement, Python DB-API parameter binding, .NET parameterized query, PostgreSQL pgBouncer/DB firewall 정책 등이 대표 참고 기준이다.

6. 기대효과 및 결론

올바른 SQL 인젝션 방어는 데이터 탈취와 인증 우회 같은 치명적 사고를 예방하고, 보안 감사와 규제 대응의 기본선을 확보한다. 무엇보다 개발팀이 일관된 안전 패턴을 따르게 만들어 취약점 재발을 줄인다.

그러나 기술적 방어만으로 충분하지 않다. 보안 라이브러리 표준화, 정적 분석, 코드 리뷰, 침투 테스트, 운영 로그 분석이 함께 돌아가야 지속성이 생긴다. 레거시 시스템에서는 일부 안전한 모듈을 도입했더라도 주변 배치·관리 툴이 취약할 수 있다.

결론적으로 SQL 인젝션 방어의 핵심은 필터링 경쟁이 아니라 구조적 분리다. 사용자 입력이 SQL 문법이 될 수 없는 구조를 만드는 순간 방어 수준이 근본적으로 올라간다.
