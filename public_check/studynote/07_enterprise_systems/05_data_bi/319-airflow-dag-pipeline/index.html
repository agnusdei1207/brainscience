0. 핵심 인사이트

핵심: Airflow DAG (Directed Acyclic Graph)의 본질은 태스크를 순서대로 실행하는 도구가 아니라, 데이터 작업의 의존성과 재실행 규칙을 명시적으로 모델링해 운영 가능성을 높이는 오케스트레이션 계층이라는 데 있다. 비유: 여러 공정이 얽힌 공장을 구두 지시로 돌리지 않고, 작업 순서도와 책임자를 붙인 생산 관리판으로 운영하는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

데이터 파이프라인은 추출, 정제, 적재, 품질 검증, 모델 학습, 리포트 생성처럼 여러 작업이 선후 관계를 갖고 연결된 구조다. 초기에는 cron과 셸 스크립트로도 운영할 수 있지만, 태스크 수가 늘어나면 실패 복구, 재실행, 의존성 추적, 일정 관리, 모니터링이 빠르게 복잡해진다.

Apache Airflow는 이런 문제를 해결하기 위해 파이프라인을 DAG로 표현한다. DAG는 태스크 간 방향성은 있지만 순환은 없는 그래프이므로, 어떤 작업이 먼저 끝나야 다음 작업을 실행할 수 있는지 명시적으로 모델링할 수 있다. 이 구조 덕분에 스케줄링, 병렬 실행, 재시도, 백필 (Backfill), 알림을 체계적으로 운영할 수 있다.

중요한 점은 Airflow가 데이터 처리 엔진이 아니라 오케스트레이터라는 것이다. 실제 계산은 Spark, dbt, Python, SQL, Kubernetes Job 등이 수행하고, Airflow는 이를 언제 어떤 의존성으로 실행할지 관리한다. 이 역할 구분을 이해해야 Airflow를 과도한 계산 플랫폼으로 오용하지 않는다.

2. 구성요소

요소역할핵심 포인트
DAG 정의태스크와 의존성 모델링코드로 관리되는 파이프라인 설계서
Scheduler실행 시점과 준비된 태스크 결정데이터 간격(Data Interval) 개념이 중요
Executor/Worker실제 태스크 실행Local, Celery, Kubernetes 등 다양
Metadata DB실행 이력, 상태, 재시도 정보 저장운영 가시성의 핵심
UI/모니터링실패 추적, 수동 재실행, SLA 확인운영자 경험을 좌우

이 구조는 선언과 실행을 분리한다. DAG 파일은 논리적 정의이고, Scheduler는 이를 해석해 실행 계획을 만든다. Worker는 실제 작업을 수행하며, Metadata DB는 모든 실행 이력을 저장한다. 따라서 Airflow 운영의 안정성은 코드 품질뿐 아니라 메타데이터 DB와 Executor 구성에도 달려 있다.

또한 태스크는 가능한 한 멱등성 (Idempotency)을 가져야 한다. 재시도와 백필이 잦은 오케스트레이션 환경에서는 같은 작업이 여러 번 실행될 수 있기 때문이다.

3. 구조 및 원리

핵심 조건: 태스크는 멱등적이어야 하고, 의존성은 명시적이어야 하며, 데이터 처리 시간과 스케줄 시간은 분리해서 설계해야 한다.

Airflow의 원리는 DAG를 실행 가능한 그래프로 해석하는 것이다. Scheduler는 특정 데이터 간격에 대해 어떤 DAG Run이 필요한지 계산하고, 각 태스크의 선행 조건이 충족되면 Executor에 실행을 위임한다. 실패한 태스크는 재시도 정책에 따라 재실행되며, 운영자는 UI에서 상태를 추적한다.

동작 순서:

  1. DAG 파싱: Airflow가 Python 코드로 작성된 DAG를 읽어 태스크, 의존성, 스케줄을 해석한다. DAG 생성 로직이 복잡하면 파싱 부담이 커진다.
  2. DAG Run 생성: 스케줄과 데이터 간격에 따라 특정 실행 단위를 만든다. 이때 실행 시각과 처리 대상 기간을 혼동하면 데이터 중복·누락이 생긴다.
  3. Task Scheduling: 선행 태스크가 성공한 뒤 준비된 태스크를 큐에 올린다. 병렬성 제한, 풀(Pool), 우선순위가 함께 작동한다.
  4. Worker 실행: PythonOperator, SQL, Bash, KubernetesPodOperator 등으로 실제 작업을 수행한다. Airflow는 직접 대규모 계산보다 외부 엔진 호출에 더 적합하다.
  5. 상태 기록과 재시도: 성공/실패/스킵 상태가 메타데이터 DB에 저장되고, 재시도 정책과 알림이 적용된다.
[DAG Code] -> [Scheduler] -> [Executor Queue] -> [Worker]
     │             │                 │               │
     └──────> [Metadata DB] <────────┴───────────────┘
                     │
                     ▼
                    UI / Retry / Backfill / SLA

핵심은 데이터 간격 기반 사고다. 예를 들어 “매일 1시 실행”은 단순 시각이 아니라 “어제 데이터 구간을 처리하는 실행”이어야 한다. 이 원칙을 놓치면 지연 실행, 백필, 재실행 시 데이터 중복과 누락이 발생한다. 그래서 Airflow는 execution_date보다 logical date, data interval 개념을 강조한다.

Airflow는 cron보다 훨씬 강력하지만 실시간 스트리밍 엔진을 대체하지는 못한다. 초 단위 이벤트 처리가 핵심이면 Kafka, Flink, Spark Structured Streaming이 적합하다. 반대로 일/시간 단위 배치, ML 파이프라인, 데이터 품질 검사, 백필 운영은 Airflow가 강하다.

또한 dbt, Spark, Kubernetes와의 연계가 중요하다. Airflow는 작업 자체를 수행하기보다 이들 도구를 연결하고 실패를 운영 가능하게 만드는 제어 계층이다.

5. 실무 적용 및 판단

적합한 경우

  • 의존성 있는 배치 파이프라인이 많고 실패 복구가 중요한 경우
  • 데이터 품질 검사, 알림, 재실행, 백필을 운영 수준으로 관리해야 하는 경우
  • 여러 처리 엔진을 하나의 워크플로우로 묶고 싶은 경우

주의가 필요한 경우

  • 초저지연 스트리밍 처리를 Airflow에 직접 맡기려는 경우
  • 무거운 데이터 처리를 Worker 내부에서 직접 수행하는 경우
  • 태스크가 멱등하지 않아 재시도 때 중복 적재가 발생하는 경우

체크리스트:

  • 태스크가 멱등적인가?
  • 의존성이 코드와 문서에 명확히 표현되는가?
  • Data Interval과 실제 처리 범위가 일치하는가?
  • 실패 시 재시도, 알림, 수동 개입 절차가 있는가?
  • Executor와 Metadata DB가 예상 규모를 감당하는가?

실무 사례로는 ETL/ELT, dbt 실행, ML 학습 파이프라인, 데이터 품질 검사, 리포트 배포, 외부 API 배치 동기화가 있다. CeleryExecutor나 KubernetesExecutor는 규모 확장 시 자주 사용된다.

6. 기대효과 및 결론

Airflow를 올바르게 쓰면 파이프라인 가시성, 재실행 용이성, 실패 복구력, 운영 표준화가 크게 향상된다. 특히 “어느 단계에서 왜 실패했는가”를 빠르게 파악할 수 있어 데이터 운영 품질이 올라간다.

하지만 DAG 수가 폭증하면 파싱 비용, 스케줄러 병목, 운영 복잡성이 증가할 수 있다. 또한 Airflow를 처리 엔진처럼 사용하면 Worker 리소스가 급격히 부족해진다. 따라서 오케스트레이션과 실제 계산을 분리하는 원칙을 지켜야 한다.

결론적으로 Airflow DAG의 본질은 태스크 실행 자체보다, 의존성과 운영 규칙을 코드로 표현해 재현 가능하고 관리 가능한 데이터 파이프라인을 만드는 데 있다.
