0. 핵심 인사이트

핵심: API 게이트웨이(API Gateway)는 모든 클라이언트 요청의 단일 진입점(Single Entry Point)으로서 인증/인가·속도 제한(Throttling)·로드 밸런싱·요청 집계(Aggregation)를 수행하는 엣지(Edge) 컴포넌트다. 비유: API 게이트웨이 인증 스로틀링 집계는 복잡한 현장을 한 장의 설계도와 운영 규칙으로 묶어 방향을 맞추는 나침반과 같다.

📝 모범 답안

1. 개요 및 필요성

MSA 환경에서 수십~수백 개의 마이크로서비스가 운영될 때, 클라이언트가 각 서비스를 직접 호출하면 ①서비스 위치 파악 복잡, ②각 서비스마다 개별 인증 구현, ③모바일 앱의 대역폭 낭비(여러 서비스 개별 호출), ④서비스 변경 시 클라이언트 코드 수정 등의 문제가 생긴다.

API 게이트웨이는 Netflix Zuul(2012), Kong(2013), AWS API Gateway(2014), Spring Cloud Gateway 등으로 발전했다. 엔터프라이즈 API 관리 플랫폼(APIM)으로는 Apigee(Google), Azure API Management, MuleSoft API Gateway가 대표적이다.

API GW 기능설명
인증/인가JWT 검증, OAuth 2.0 토큰 검증, API Key
속도 제한Rate Limiting (초당·분당·일별 요청 수 제한)
로드 밸런싱라운드 로빈·최소 연결 기반 분산
요청 집계여러 서비스 응답 단일 응답으로 합산
SSL 종단HTTPS 처리, 내부 HTTP 통신으로 전달
캐싱동일 요청 응답 캐시 (Redis 등)
로깅·추적모든 요청 중앙 로그·분산 추적 주입
변환요청/응답 포맷 변환 (XML→JSON)

3. 구조 및 원리

핵심 조건: 서비스 경계, 인터페이스 계약, 상태 관리, 관찰성이 함께 설계되어야 분산 구조의 유연성과 안정성을 동시에 확보할 수 있다.

API 게이트웨이 인증 스로틀링 집계는 기능을 나누는 것 자체가 아니라, 서비스 간 책임과 통제 지점을 명확히 해 분산 복잡도를 관리 가능한 형태로 바꾸는 데 있다. 따라서 구조를 볼 때는 호출 경로, 데이터 소유권, 장애 격리, 운영 자동화가 어떤 순환을 이루는지를 함께 이해해야 한다.

동작 순서:

  1. BFF 여부: 클라이언트 유형이 3개 이상 다르면 BFF 패턴 검토.
  2. Rate Limit 기준: IP 기반 vs API Key 기반 vs 사용자 기반 (OAuth 권장).
  3. 캐싱 전략: GET 요청 + TTL 설정 + Cache Invalidation 전략 수립.
  4. HA 구성: Active-Active 최소 2노드, 상태 공유는 Redis Cluster.

5. 실무 적용 및 판단

API 게이트웨이 도입으로 ①인증 로직 중앙화로 각 서비스 개발 비용 절감, ②Rate Limiting으로 DDoS·악용 방어, ③요청 집계로 모바일 앱 응답 시간 30~50% 단축, ④중앙 모니터링으로 API SLA 추적 용이 등의 효과를 거둔다.

한계: API 게이트웨이 자체가 모든 트래픽을 처리하므로 SPOF이자 성능 병목이 될 수 있다. 응답 지연이 수 ms 증가하며, 게이트웨이 장애 시 모든 서비스 접근이 차단된다. HA 및 수평 확장 설계가 필수다.

6. 기대효과 및 결론

API 게이트웨이 인증 스로틀링 집계는 가시성 향상, 의사결정 정합성 강화, 실행 통제 고도화 측면에서 조직의 성과와 안정성을 높일 수 있는 체계다. 다만 API 게이트웨이 자체가 모든 트래픽을 처리하므로 SPOF이자 성능 병목이 될 수 있다. 응답 지연이 수 ms 증가하며, 게이트웨이 장애 시 모든 서비스 접근이 차단된다. HA 및 수평 확장 설계가 필수다.가 발생하면 도입 효과가 빠르게 약화되므로, 명확한 책임 구조와 지속적 피드백 체계를 전제로 적용 범위와 우선순위를 단계적으로 관리해야 한다. 향후에는 서비스 메시, 정책 자동화, AI 기반 운영 분석이 결합되어 분산 구조의 복잡도를 더 낮추는 방향으로 발전할 가능성이 크다.
