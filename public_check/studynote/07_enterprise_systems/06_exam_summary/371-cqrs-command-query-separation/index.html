0. 핵심 인사이트

핵심: CQRS(Command Query Responsibility Segregation)는 데이터 변경(Command)과 데이터 조회(Query)의 모델을 분리하여, 읽기와 쓰기를 독립적으로 최적화·확장할 수 있게 하는 아키텍처 패턴이다. 비유: CQRS 명령 조회 모델 분리 패턴는 복잡한 현장을 한 장의 설계도와 운영 규칙으로 묶어 방향을 맞추는 나침반과 같다.

📝 모범 답안

1. 개요 및 필요성

Greg Young이 2010년 CQS(Command Query Separation, Bertrand Meyer 1988) 원칙을 아키텍처 수준으로 발전시켜 CQRS를 정립했다. 기존 CRUD 아키텍처에서는 동일한 데이터 모델로 읽기·쓰기를 모두 처리하므로, 복잡한 읽기 쿼리(JOIN, 집계)가 비즈니스 로직의 쓰기 모델을 오염시키고 인덱스·정규화 최적화 충돌이 발생한다.

문제 상황CQRS 해결
읽기 성능 최적화 vs 쓰기 정규화 충돌읽기용 비정규화 뷰 별도 구성
복잡한 집계 쿼리로 쓰기 DB 부하읽기 DB에서 독립적으로 집계
MSA 서비스 간 JOIN 불가읽기 모델이 여러 서비스 데이터 통합
읽기·쓰기 부하 비대칭 (보통 읽기 10배+)읽기·쓰기 스케일 독립

2. 구성요소

CQRS 아키텍처

클라이언트
  ├── Command (쓰기 요청)
  │   └──▶ Command Handler
  │          └──▶ Command Model (도메인 로직)
  │                 └──▶ Write DB (정규화, PostgreSQL)
  │                        └── 이벤트 발행 ──▶ Event Bus
  │                                              │
  └── Query (읽기 요청)                          ▼
      └──▶ Query Handler                   Event Handler
             └──▶ Read DB (비정규화, Redis/ES/MongoDB)
                   └──▶ 집계 뷰 업데이트

Command vs Query 분리 원칙

구분Command (명령)Query (조회)
목적상태 변경상태 조회
반환값없음 또는 ID만데이터 반환
부작용있음 (DB 변경)없음 (읽기 전용)
모델비즈니스 도메인 모델읽기 최적화 프로젝션
DB정규화 (3NF)비정규화, 집계 뷰
확장 방향쓰기 처리량 최적화읽기 성능 최적화

CQRS + 이벤트 소싱 연계

Command 처리:
  1. Command 수신 → 도메인 검증
  2. 이벤트 생성 → Event Store에 저장
  3. 현재 상태 = 이벤트 재생으로 도출

Query 처리:
  1. 이벤트 스트림 구독
  2. 이벤트 기반 읽기 뷰(Projection) 업데이트
  3. 읽기 DB(Redis/ES)에서 직접 조회 응답

3. 구조 및 원리

핵심 조건: 서비스 경계, 인터페이스 계약, 상태 관리, 관찰성이 함께 설계되어야 분산 구조의 유연성과 안정성을 동시에 확보할 수 있다.

CQRS 명령 조회 모델 분리 패턴은 기능을 나누는 것 자체가 아니라, 서비스 간 책임과 통제 지점을 명확히 해 분산 복잡도를 관리 가능한 형태로 바꾸는 데 있다. 따라서 구조를 볼 때는 호출 경로, 데이터 소유권, 장애 격리, 운영 자동화가 어떤 순환을 이루는지를 함께 이해해야 한다.

동작 순서:

  1. Command 수신 → 도메인 검증.
  2. 이벤트 생성 → Event Store에 저장.
  3. 현재 상태 = 이벤트 재생으로 도출.
  4. 이벤트 스트림 구독.
클라이언트
  ├── Command (쓰기 요청)
  │   └──▶ Command Handler
  │          └──▶ Command Model (도메인 로직)
  │                 └──▶ Write DB (정규화, PostgreSQL)
  │                        └── 이벤트 발행 ──▶ Event Bus
  │                                              │
  └── Query (읽기 요청)                          ▼
      └──▶ Query Handler                   Event Handler
             └──▶ Read DB (비정규화, Redis/ES/MongoDB)
                   └──▶ 집계 뷰 업데이트

CQRS 성숙도 단계

레벨 1 (단일 DB CQRS):
  동일 DB, 읽기·쓰기 모델만 코드 분리
  가장 단순, 동기 일관성 유지

레벨 2 (분리 DB CQRS):
  읽기 DB(Read Replica) 분리
  비동기 복제, 약간의 지연 허용

레벨 3 (다중 읽기 모델 CQRS):
  용도별 복수 읽기 뷰
  (Redis 캐시 + Elasticsearch + 리포트 DB)

CQRS와 MSA 데이터 집계

MSA에서 고객 주문 이력 화면을 구성할 때:

  • 주문 서비스 DB + 결제 서비스 DB + 배송 서비스 DB를 JOIN 불가
  • CQRS 읽기 모델: 주문·결제·배송 이벤트를 구독하여 단일 집계 뷰 유지
  • 읽기 요청: 집계 뷰에서 단일 쿼리로 전체 이력 조회

4. 비교 및 연결

CQRS 도입 적합성 판단

복잡한 비즈니스 도메인? YES
  → CQRS + DDD 조합 적합

읽기 부하 >> 쓰기 부하? YES
  → 읽기 DB 스케일 아웃 독립

MSA 서비스 간 데이터 집계 필요? YES
  → 이벤트 기반 CQRS 읽기 뷰 구성

단순 CRUD 앱? YES → CQRS 불필요 (오버엔지니어링)

구현 시 핵심 주의사항

  1. 최종 일관성 관리: 읽기 모델은 쓰기 이후 지연(수십ms~수초) 허용 필요
  2. 읽기 뷰 재구성: 이벤트 스토어에서 읽기 뷰를 언제든 재생성(Rebuild) 가능해야
  3. 이벤트 버전 관리: 이벤트 스키마 변경 시 하위 호환성 유지 (Event Upcasting)

5. 실무 적용 및 판단

CQRS 도입으로 ①읽기 성능 5~10배 향상(최적화된 읽기 뷰), ②쓰기 비즈니스 로직 단순화, ③MSA 서비스 간 데이터 집계 문제 해결, ④읽기·쓰기 독립적 확장(스케일 아웃) 가능 등의 효과를 거둔다. 대형 이커머스의 상품 상세 페이지(초당 수천 조회)와 주문 처리(초당 수십 쓰기)의 비대칭 부하를 CQRS로 해결하는 것이 대표 사례다.

한계: 읽기·쓰기 동기화 지연으로 인한 사용자 경험 저하(방금 저장한 데이터가 조회에 안 보이는 경우)를 UX 차원에서 처리해야 한다. 또한 이벤트 인프라(Kafka 등) 구축 및 이벤트 설계 역량이 필요하다.

6. 기대효과 및 결론

CQRS 명령 조회 모델 분리 패턴은 가시성 향상, 의사결정 정합성 강화, 실행 통제 고도화 측면에서 조직의 성과와 안정성을 높일 수 있는 체계다. 다만 읽기·쓰기 동기화 지연으로 인한 사용자 경험 저하(방금 저장한 데이터가 조회에 안 보이는 경우)를 UX 차원에서 처리해야 한다. 또한 이벤트 인프라(Kafka 등) 구축 및 이벤트 설계 역량이 필요하다.가 발생하면 도입 효과가 빠르게 약화되므로, 명확한 책임 구조와 지속적 피드백 체계를 전제로 적용 범위와 우선순위를 단계적으로 관리해야 한다. 향후에는 서비스 메시, 정책 자동화, AI 기반 운영 분석이 결합되어 분산 구조의 복잡도를 더 낮추는 방향으로 발전할 가능성이 크다.
