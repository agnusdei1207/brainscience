0. 핵심 인사이트

핵심: 스노우플레이크 스키마(Snowflake Schema)는 스타 스키마의 비정규화된 차원 테이블을 3NF 수준으로 정규화하여 계층적 서브 차원 테이블로 분해한 DW 모델이다. 비유: 스노우플레이크 차원 정규화 계층는 복잡한 현장을 한 장의 설계도와 운영 규칙으로 묶어 방향을 맞추는 나침반과 같다.

📝 모범 답안

1. 개요 및 필요성

스타 스키마에서 차원 테이블은 비정규화(Denormalized) 상태로 분석 속성을 모두 포함한다. 예를 들어 DIM_Product에 제품명·카테고리명·브랜드명이 모두 중복 저장된다. 스노우플레이크 스키마는 이를 정규화하여 DIM_Product → DIM_Category → DIM_Brand로 계층화한다. 눈송이(Snowflake)처럼 가지가 뻗어나간 구조에서 이름이 유래했다.

정규화를 통해 데이터 무결성이 향상되고 저장 공간이 절약되지만, BI 쿼리 시 다단계 조인이 발생하여 성능이 저하된다. 현대 컬럼형 DW에서는 성능 차이가 줄어들었으나 설계 복잡도는 여전히 트레이드오프다.

3. 구조 및 원리

핵심 조건: 데이터 원천, 스키마/변환 규칙, 저장·처리 방식, 메타데이터·거버넌스가 일관되게 연결되어야 신뢰 가능한 분석과 재사용이 가능하다.

스노우플레이크 차원 정규화 계층은 데이터를 한 번 저장하는 기술이 아니라 수집·변환·활용 전 구간의 흐름을 설계하는 방식이다. 즉 저장 구조만 보지 말고, 품질 관리와 메타데이터, 처리 성능, 소비 방식이 어떻게 연결되는지까지 함께 봐야 전체 원리가 드러난다.

동작 순서:

  1. 차원 테이블 수백만 행 이상 + 속성 변경 빈번: 스노우플레이크 선택.
  2. OLAP 쿼리 응답 SLA 엄격: 스타 스키마 선택.
  3. 컬럼형 DW(Snowflake, BigQuery): 조인 오버헤드 감소로 스노우플레이크 실용화.
  4. 혼용: 핵심 대형 차원만 정규화, 소형 차원은 비정규화 유지.

스노우플레이크 스키마는 갤럭시 스키마(Galaxy Schema, Fact Constellation)와도 구분된다. 갤럭시 스키마는 여러 팩트 테이블이 공유 차원을 참조하는 구조다. 스노우플레이크는 단일 팩트 테이블을 기준으로 차원만 정규화한다.

4. 비교 및 연결

의사결정 포인트:

  • 차원 테이블 수백만 행 이상 + 속성 변경 빈번: 스노우플레이크 선택
  • OLAP 쿼리 응답 SLA 엄격: 스타 스키마 선택
  • 컬럼형 DW(Snowflake, BigQuery): 조인 오버헤드 감소로 스노우플레이크 실용화
  • 혼용: 핵심 대형 차원만 정규화, 소형 차원은 비정규화 유지

5. 실무 적용 및 판단

스노우플레이크 스키마는 데이터 무결성과 저장 효율성을 높이며, 특히 차원 속성이 자주 변경되는 환경에서 유리하다. 단, 복잡한 조인으로 인한 쿼리 성능 저하와 설계 복잡도 증가가 한계다. 현대 클라우드 DW의 쿼리 최적화 엔진(Materialized Views, Query Cache)으로 단점을 일부 보완할 수 있다.

6. 기대효과 및 결론

스노우플레이크 차원 정규화 계층은 가시성 향상, 의사결정 정합성 강화, 실행 통제 고도화 측면에서 조직의 성과와 안정성을 높일 수 있는 체계다. 다만 형식적 도입에 머물 위험과 운영 복잡도 증가가 발생하면 도입 효과가 빠르게 약화되므로, 명확한 책임 구조와 지속적 피드백 체계를 전제로 적용 범위와 우선순위를 단계적으로 관리해야 한다. 앞으로는 실시간 스트리밍, 메타데이터 자동화, AI 기반 품질 관리가 결합되면서 더 자율적인 데이터 운영 체계로 진화할 가능성이 크다.
