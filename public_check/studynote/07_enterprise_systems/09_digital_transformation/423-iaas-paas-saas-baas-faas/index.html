0. 핵심 인사이트

핵심: 클라우드 서비스 모델은 IaaS(인프라)→PaaS(플랫폼)→SaaS(소프트웨어)→BaaS(백엔드)→FaaS(함수) 순으로 추상화 레벨이 높아지며, 사용자가 관리해야 하는 레이어가 줄어든다. 비유: 클라우드 서비스 모델은 이사 옵션 — IaaS는 빈 집(직접 꾸밈), PaaS는 가구 포함 집, SaaS는 호텔(다 준비됨), FaaS는 에어비앤비 시간제 이용이다.

📝 모범 답안

1. 개요 및 필요성

NIST SP 800-145는 IaaS·PaaS·SaaS를 클라우드 서비스 3대 모델로 정의했다. 이후 BaaS(Backend as a Service)와 FaaS(Function as a Service, Serverless)가 등장하여 서버리스 패러다임을 완성했다. 각 모델은 "무엇을 클라우드 제공자가 관리하고, 무엇을 고객이 관리하는가"의 책임 경계(Shared Responsibility Model)로 구분된다.

3. 구조 및 원리

핵심 조건: IaaS PaaS SaaS BaaS FaaS 클라우드 서비스 모델에서는 요구사항, 실행 플랫폼, 데이터 흐름, 운영 피드백이 하나의 아키텍처로 닫혀 있어야 실제 비즈니스 가치가 발생한다.

동작 순서:

  1. 요구사항 정의: 해결하려는 비즈니스 문제, 사용자 경험, 성능·비용 제약을 먼저 명확히 한다.
  2. 구성요소 배치: 플랫폼, 데이터 저장소, 인터페이스, 자동화 지점을 역할에 맞게 분리하여 배치한다.
  3. 정책 기반 실행: 요청·이벤트·데이터 흐름이 핵심 엔진을 통과하면서 권한, 일관성, 성능 조건을 함께 검증한다.
  4. 관측과 개선: 운영 결과를 로그·메트릭·비용 지표로 수집해 다시 설계와 운영 정책에 반영한다.
┌────────────────┐    ┌──────────────────────┐    ┌─────────────────┐
│ 비즈니스 요구사항 │ -> │ IaaS PaaS SaaS BaaS  핵심 처리 │ -> │ 서비스 결과/가치 │
└────────────────┘    └──────────────────────┘    └─────────────────┘
         ^                        |                         |
         |                        v                         |
         └──────── 데이터·정책·운영 피드백 루프 ────────────┘

Shared Responsibility Model: 클라우드 제공자는 "클라우드의 보안"(인프라), 고객은 "클라우드 안에서의 보안"(데이터·IAM·설정)을 책임진다. IaaS는 고객 책임이 가장 크고, SaaS/FaaS는 가장 작다.

4. 비교 및 연결

비교 관점적용 시 강조점연결되는 대안·인접 개념
가치 전달 방식기능 자체보다 서비스화·플랫폼화·사용자 경험의 통합이 중요하다.전통 단일 시스템, 패키지 SW, 온프레미스 운영
운영 모델자동화와 API 중심 연동이 커질수록 속도와 확장성이 높아진다.수작업 운영, 강결합 아키텍처, 배치 중심 처리
비용·위험초기 민첩성은 커지지만 종속성·복잡도·거버넌스 비용을 함께 본다.벤더 록인, 데이터 중력, 기술 부채

의사결정 포인트:

  • 기존 앱 마이그레이션(Lift & Shift): IaaS(VM 그대로 이전)
  • 신규 클라우드 네이티브 앱: PaaS/FaaS(개발 속도 최우선)
  • 업무용 패키지 도입: SaaS(총소유비용 절감)
  • 모바일 앱 백엔드: BaaS(Firebase: 인증·DB·스토리지 완전 관리)
  • 이벤트 기반 마이크로서비스: FaaS + API Gateway

5. 실무 적용 및 판단

채택 조건:

  • 서비스 확장성과 출시 속도가 중요하고, API·데이터 연동으로 추가 가치를 만들 수 있을 때
  • 운영 자동화와 관측성을 확보해 복잡도를 감당할 수 있을 때

회피 조건:

  • 규제·지연·비용 제약으로 인해 플랫폼 추상화보다 직접 제어가 더 중요한 경우
  • 조직 역량이 부족해 도입 후 운영 표준을 유지하기 어려운 경우

체크리스트:

  1. 핵심 기능과 지원 기능의 책임 경계가 분명한가?
  2. 성능·비용·보안 메트릭을 지속 측정할 수 있는가?
  3. 벤더 종속성과 데이터 이동 비용을 사전에 검토했는가?

클라우드 서비스 모델 다양화로 조직은 워크로드별로 최적 모델을 선택하여 민첩성·비용·보안을 최적화할 수 있다. FaaS는 서버리스 아키텍처로 이벤트 기반 마이크로서비스의 핵심이 됐으며, BaaS는 모바일 앱 개발 생산성을 획기적으로 높였다. 멀티 클라우드 환경에서 서비스 모델 간 데이터 이식성과 벤더 록인 회피가 중장기 아키텍처 과제다.

6. 기대효과 및 결론

IaaS PaaS SaaS BaaS FaaS 클라우드 서비스 모델 적용 시 출시 속도, 서비스 확장성, 운영 자동화, 데이터 기반 의사결정 역량을 동시에 끌어올릴 수 있다. 특히 단일 기능 도입이 아니라 비즈니스 모델과 운영 체계를 함께 바꾸는 경우 효과가 커진다.

반면 추상화 수준이 높아질수록 내부 동작 가시성이 떨어지고, 벤더 종속성·비용 구조 왜곡·거버넌스 공백이 생길 수 있다. 따라서 표준 인터페이스, 관측성, 책임 분리, 보안 설계를 병행해야 한다. 향후에는 AI 기반 자동화, 정책 기반 최적화, 분산 거버넌스가 결합되면서 IaaS PaaS SaaS BaaS FaaS 클라우드 서비스 모델의 활용 범위가 더 넓어질 가능성이 크다.

7. 발전 흐름도
