0. 핵심 인사이트

핵심: IaC(Infrastructure as Code)는 서버·네트워크·클라우드 리소스를 코드(선언적 또는 명령적)로 정의하고 버전 관리·자동화하는 방법론이며, 불변 인프라(Immutable Infrastructure)는 배포 후 절대 수정하지 않고 새로 교체하는 패러다임이다. 비유: IaC는 서버 설계도 — 설계도(코드)만 있으면 언제든 동일한 서버를 찍어낼 수 있고, 설계도가 변경되면 모두 추적 가능하다.

📝 모범 답안

1. 개요 및 필요성

전통 서버 관리는 수동 SSH 접속·패치·설정 변경으로 인프라 상태가 점점 문서와 달라지는 드리프트(Configuration Drift) 문제가 발생한다. IaC는 인프라를 코드로 선언하여 Git 버전 관리, 코드 리뷰, CI/CD 파이프라인을 인프라에 적용한다. 불변 인프라는 한 번 배포된 서버를 절대 수정하지 않고, 변경이 필요하면 새 이미지를 빌드하여 교체한다(Phoenix Server Pattern).

2. 구성요소

Terraform 워크플로우:
  ┌─────────┐    ┌─────────┐    ┌────────────┐    ┌──────────────┐
  │ .tf 코드 │──→ │terraform│──→ │  Plan 출력 │──→ │terraform     │
  │ (선언형) │    │  init   │    │  (diff 표시)│    │  apply       │
  └─────────┘    └─────────┘    └────────────┘    └──────────────┘
                                                          ↓
                                                  ┌──────────────────┐
                                                  │ terraform.tfstate │
                                                  │ (현재 상태 추적)  │
                                                  └──────────────────┘

불변 인프라 패턴:
  [기존 서버] → [신규 AMI/이미지 빌드] → [신규 서버 배포] → [트래픽 전환] → [구 서버 폐기]
도구유형특징
Terraform선언적, 멀티 클라우드HCL 언어, State 관리, Plan/Apply
Ansible명령적, 에이전트리스YAML Playbook, 가변 인프라
AWS CDK명령적, 단일 클라우드TypeScript/Python으로 CloudFormation 생성
Pulumi선언적, 멀티 클라우드범용 언어(Python/Go/TypeScript)

3. 구조 및 원리

핵심 조건: 불변 인프라 IaC 테라폼에서는 요구사항, 실행 플랫폼, 데이터 흐름, 운영 피드백이 하나의 아키텍처로 닫혀 있어야 실제 비즈니스 가치가 발생한다.

동작 순서:

  1. 요구사항 정의: 해결하려는 비즈니스 문제, 사용자 경험, 성능·비용 제약을 먼저 명확히 한다.
  2. 구성요소 배치: 플랫폼, 데이터 저장소, 인터페이스, 자동화 지점을 역할에 맞게 분리하여 배치한다.
  3. 정책 기반 실행: 요청·이벤트·데이터 흐름이 핵심 엔진을 통과하면서 권한, 일관성, 성능 조건을 함께 검증한다.
  4. 관측과 개선: 운영 결과를 로그·메트릭·비용 지표로 수집해 다시 설계와 운영 정책에 반영한다.
┌────────────────┐    ┌──────────────────────┐    ┌─────────────────┐
│ 비즈니스 요구사항 │ -> │ 불변 인프라 IaC 테라폼 핵심 처리 │ -> │ 서비스 결과/가치 │
└────────────────┘    └──────────────────────┘    └─────────────────┘
         ^                        |                         |
         |                        v                         |
         └──────── 데이터·정책·운영 피드백 루프 ────────────┘

Configuration Drift(드리프트): 수동 변경으로 실제 인프라와 코드가 달라지는 현상. Ansible은 멱등성(Idempotency)으로 드리프트 복구 가능. Terraform은 State 파일이 드리프트 탐지(terraform plan)의 기준이 된다.

4. 비교 및 연결

비교 관점적용 시 강조점연결되는 대안·인접 개념
가치 전달 방식기능 자체보다 서비스화·플랫폼화·사용자 경험의 통합이 중요하다.전통 단일 시스템, 패키지 SW, 온프레미스 운영
운영 모델자동화와 API 중심 연동이 커질수록 속도와 확장성이 높아진다.수작업 운영, 강결합 아키텍처, 배치 중심 처리
비용·위험초기 민첩성은 커지지만 종속성·복잡도·거버넌스 비용을 함께 본다.벤더 록인, 데이터 중력, 기술 부채

의사결정 포인트:

  • 멀티 클라우드 IaC: Terraform (AWS+Azure+GCP 동시 관리)
  • AWS 전용 + 개발자 친화: AWS CDK (TypeScript/Python)
  • 불변 인프라 구현: Packer(이미지 빌드) + Terraform(배포) + ASG(교체)
  • Terraform State 원격 관리: S3+DynamoDB(Lock) 또는 Terraform Cloud

5. 실무 적용 및 판단

채택 조건:

  • 서비스 확장성과 출시 속도가 중요하고, API·데이터 연동으로 추가 가치를 만들 수 있을 때
  • 운영 자동화와 관측성을 확보해 복잡도를 감당할 수 있을 때

회피 조건:

  • 규제·지연·비용 제약으로 인해 플랫폼 추상화보다 직접 제어가 더 중요한 경우
  • 조직 역량이 부족해 도입 후 운영 표준을 유지하기 어려운 경우

체크리스트:

  1. 핵심 기능과 지원 기능의 책임 경계가 분명한가?
  2. 성능·비용·보안 메트릭을 지속 측정할 수 있는가?
  3. 벤더 종속성과 데이터 이동 비용을 사전에 검토했는가?

IaC 도입으로 인프라 프로비저닝 시간 90% 단축, 환경 일관성 보장, 감사 추적(Git 이력) 확보가 가능하다. 불변 인프라는 운영 중 서버 상태 오염이 없어 예측 가능성이 높지만, 이미지 빌드 파이프라인과 데이터 영속성(DB 서버 불변화 어려움)이 설계 과제다.

6. 기대효과 및 결론

불변 인프라 IaC 테라폼 적용 시 출시 속도, 서비스 확장성, 운영 자동화, 데이터 기반 의사결정 역량을 동시에 끌어올릴 수 있다. 특히 단일 기능 도입이 아니라 비즈니스 모델과 운영 체계를 함께 바꾸는 경우 효과가 커진다.

반면 추상화 수준이 높아질수록 내부 동작 가시성이 떨어지고, 벤더 종속성·비용 구조 왜곡·거버넌스 공백이 생길 수 있다. 따라서 표준 인터페이스, 관측성, 책임 분리, 보안 설계를 병행해야 한다. 향후에는 AI 기반 자동화, 정책 기반 최적화, 분산 거버넌스가 결합되면서 불변 인프라 IaC 테라폼의 활용 범위가 더 넓어질 가능성이 크다.

7. 발전 흐름도

AI 보조 최적화·자율 운영 확장
