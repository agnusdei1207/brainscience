0. 핵심 인사이트

핵심: TDD(Test-Driven Development)는 테스트 먼저 작성하고 코드를 작성하는 개발 사이클이며, BDD(Behavior-Driven Development)는 TDD를 비즈니스 관점의 시나리오 언어(Given-When-Then)로 확장하여 개발자·QA·비즈니스 이해관계자가 공통 언어로 소통하게 한다. 비유: TDD는 맛집 레시피를 쓰기 전에 먼저 "완성된 요리의 맛 기준"을 정하는 것처럼, 코드 완성의 기준을 먼저 테스트로 정의하고 그 기준을 충족하도록 코드를 작성하는 방식이다.

📝 모범 답안

1. 개요 및 필요성

"테스트가 있다"와 "TDD로 개발한다"는 다르다. 코드를 먼저 작성하고 나중에 테스트를 추가하면 테스트는 코드의 구현을 그대로 따라가는 '코드 복사본'이 된다. TDD는 이 순서를 뒤집어 "이 코드가 무엇을 해야 하는가?"를 먼저 명세하게 함으로써 설계를 개선한다.

Kent Beck이 익스트림 프로그래밍(XP)의 일부로 제안한 TDD의 레드-그린-리팩터(Red-Green-Refactor) 사이클은 현대 애자일 개발의 기본 실천 방법이다.

BDD는 Dan North가 2003년 TDD의 "무엇을 테스트해야 하는가?"라는 혼란을 해결하기 위해 제안했다. "사용자가 X를 할 때 시스템은 Y를 해야 한다"라는 자연어 시나리오가 곧 실행 가능한 테스트가 되는 Cucumber, JBehave 같은 BDD 프레임워크가 이를 구현한다.

BDD Given-When-Then 구조

# Cucumber(Gherkin) BDD 시나리오 예시
Feature: 쇼핑몰 장바구니

  Scenario: 상품을 장바구니에 추가
    Given 사용자가 로그인되어 있다
    And 상품 "노트북"이 재고 5개이다
    When 사용자가 "노트북"을 장바구니에 1개 담는다
    Then 장바구니에 "노트북" 1개가 있다
    And 재고는 4개로 감소한다

3. 구조 및 원리

핵심 조건: TDD BDD 행동 주도 개발 객체 지향 구현에서는 정책 수립, 통제 집행, 모니터링, 증적 축적이 끊기지 않는 관리 루프로 연결돼야 실효성이 생긴다.

동작 순서:

  1. 보호 대상과 기준 정의: 자산, 사용자, 규제 요구, 위협 가정을 먼저 식별한다.
  2. 정책 결정과 통제 배치: 인증·인가·암호화·분리·검사 지점을 설계해 적용 범위를 확정한다.
  3. 실행과 검증: 실제 요청·행위·데이터 흐름을 정책과 대조해 허용·차단·격리·경보를 수행한다.
  4. 증적 축적과 개선: 로그, 감사 기록, 사고 결과를 다시 위험 평가와 통제 개선에 반영한다.
┌──────────────┐    ┌────────────────┐    ┌─────────────────┐
│ 사용자/시스템 요청 │ -> │ 정책 결정·통제 집행 │ -> │ 허용/차단/증적 생성 │
└──────────────┘    └────────────────┘    └─────────────────┘
         ^                     |                        |
         |                     v                        |
         └──────── 위험평가·모니터링·개선 루프 ──────────┘

테스트 피라미드(Test Pyramid)

레벨유형비율속도비용
상단E2E/UI 테스트10%느림높음
중간통합 테스트20%중간중간
하단단위 테스트70%빠름낮음

TDD는 피라미드 하단의 단위 테스트 작성에 집중하고, BDD 시나리오는 통합/E2E 레벨로 올라갈수록 강점을 발휘한다.

ATDD(Acceptance Test-Driven Development)와의 관계

  • TDD: 개발자 관점의 단위 설계 도구
  • BDD: TDD + 비즈니스 소통 언어 = ATDD의 구현 방식
  • ATDD: 인수 테스트를 먼저 정의하고 개발을 진행하는 방법론

4. 비교 및 연결

비교 관점적용 시 강조점연결되는 대안·인접 개념
통제 방식사후 대응보다 사전 정책화와 지속 검증의 비중이 크다.수동 점검, 경계형 방어, 단발성 심사
운영 증적로그·정책·설정·행위 데이터가 증적으로 축적돼야 한다.경험 의존 운영, 문서 중심 준수
확장 전략표준화된 통제 지점이 많을수록 대규모 환경에서도 일관성이 유지된다.예외 처리 남발, 부서별 분산 규칙

Spring Boot 기반 TDD 실천 예시

// 1단계: RED - 실패하는 테스트 작성 (주문 서비스)
@Test
void 재고보다_많은_수량_주문_시_예외발생() {
    // Given
    Product product = new Product("노트북", 3);
    // When & Then
    assertThrows(InsufficientStockException.class,
        () -> orderService.order(product, 5));
}

// 2단계: GREEN - 최소한의 코드로 통과
public void order(Product product, int quantity) {
    if (quantity > product.getStock()) {
        throw new InsufficientStockException();
    }
    // ...
}
// 3단계: REFACTOR - 도메인 객체로 로직 이동

TDD 도입 장벽 및 해결책:

  • "테스트 작성이 느려요" → 초기 속도 저하는 맞지만 버그 수정 비용 감소로 장기 투자 효율화
  • "레거시 코드에서 시작이 어려요" → Strangler Fig 패턴으로 신규 기능부터 TDD 적용
  • "Mock이 너무 많아요" → 테스트가 구현 세부사항을 너무 알고 있다는 신호 → 리팩터링 필요

5. 실무 적용 및 판단

채택 조건:

  • 규제 대응, 접근 통제, 감사 가능성처럼 반복 가능한 통제 체계가 필요한 경우
  • 사람 중심 운영을 정책·자동화·증적으로 전환해야 하는 경우

회피 조건:

  • 보호 대상 정의 없이 도구만 먼저 도입하려는 경우
  • 운영 조직과 프로세스가 준비되지 않아 경보·예외 처리만 늘어나는 경우

체크리스트:

  1. 자산·사용자·권한·로그의 기준 데이터가 정리되어 있는가?
  2. 통제 우회 경로와 예외 승인 절차가 문서화되어 있는가?
  3. 감사 증적과 실제 운영 로그가 일치하는가?

기대효과:

  • 단위 테스트 커버리지 70%+ 달성으로 리팩터링 안전망 확보
  • 버그로 인한 핫픽스 배포 빈도 50% 감소
  • BDD 시나리오가 '살아있는 문서'로 기능하여 별도 명세 문서 관리 부담 제거

한계 및 전제조건:

  • TDD 초기 학습 곡선 (평균 2~3개월 숙달 기간)
  • 외부 의존성(DB, 외부 API)이 많은 코드의 단위 테스트는 Mock 설계 복잡도 증가
  • BDD 시나리오 작성에 비즈니스 담당자의 참여가 저조하면 개발자만의 BDD로 전락
  • 기존 레거시 코드에 소급 적용은 높은 리팩터링 공수 필요

6. 기대효과 및 결론

TDD BDD 행동 주도 개발 객체 지향 구현의 가치는 단발성 통제가 아니라 정책과 운영을 연결하는 관리 체계로 접근할 때 가장 크게 나타난다. 제대로 정착하면 침해 확산 억제, 규제 준수, 감사 대응, 운영 표준화 측면에서 높은 효과를 제공한다.

다만 통제 수단만 늘리고 기준 데이터·운영 프로세스를 정비하지 않으면 오히려 복잡도와 오탐, 예외 처리 비용이 증가한다. 앞으로는 자동화된 증적 수집, AI 보조 분석, 프라이버시 강화 기술, 표준화된 인터페이스가 결합되며 TDD BDD 행동 주도 개발 객체 지향 구현의 실효성과 확장성이 함께 높아질 것이다.
