0. 핵심 인사이트

핵심: Parquet(파케이)는 Apache의 컬럼 지향(Columnar) 저장 형식으로, Delta Encoding·Dictionary Encoding·RLE(Run-Length Encoding) 등의 압축 기법과 컬럼별 Min/Max 통계를 활용하여 분석 쿼리의 I/O와 처리 비용을 획기적으로 절감한다. 비유: Parquet는 도서관의 책꽂이를 장르별로 정리하는 것처럼, 같은 종류의 데이터(동일 컬럼)끼리 모아 놓으면 특정 장르 책만 필요할 때 해당 선반만 가면 되어 훨씬 빠른 도서관 이용이 가능하다.

📝 모범 답안

1. 개요 및 필요성

빅데이터 시대에 데이터 엔지니어가 매일 직면하는 현실: S3에 쌓인 수 TB의 로그를 분석하는 데 CSV 형식으로 읽으면 수 시간이 걸리지만, Parquet 형식으로 변환하면 수 분이면 충분하다. 이 차이의 비결이 컬럼 지향 저장과 압축 알고리즘이다.

Hadoop, Spark, AWS Athena, Google BigQuery, Snowflake 등 현대 빅데이터/클라우드 분석 플랫폼이 Parquet를 기본 저장 형식으로 채택한 것이 이를 증명한다.

데이터 엔지니어링에서 스토리지 형식 선택은 단순한 기술적 선택이 아니라, 클라우드 스토리지 비용과 쿼리 실행 비용을 수십 배 차이나게 하는 비즈니스 아키텍처 결정이다.

2. 구성요소

행 지향 vs 컬럼 지향 저장 비교

│          행 지향 vs 컬럼 지향 저장 구조                        │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  원본 데이터:                                                   │
│  id │ name    │ age │ salary                                   │
│  ───┼─────────┼─────┼────────                                  │
│  1  │ Alice   │  30 │  5000                                    │
│  2  │ Bob     │  25 │  4500                                    │
│  3  │ Charlie │  35 │  6000                                    │
│                                                                │
│  행 지향 (CSV/RDB):                                            │
│  [1, Alice, 30, 5000][2, Bob, 25, 4500][3, Charlie, 35, 6000] │
│  → SELECT age FROM ...: 전체 행을 읽어 age만 추출 (낭비)       │
│                                                                │
│  컬럼 지향 (Parquet):                                          │
│  [id:   1,2,3]                                                │
│  [name: Alice,Bob,Charlie]                                    │
│  [age:  30,25,35]                                             │
│  [salary: 5000,4500,6000]                                     │
│  → SELECT age FROM ...: age 컬럼만 읽음 (75% I/O 절감)        │
│                                                                │
└────────────────────────────────────────────────────────────────┘

3. 구조 및 원리

핵심 조건: 델타 인코딩 압축 파케이 컬럼 스토리지에서는 정책 수립, 통제 집행, 모니터링, 증적 축적이 끊기지 않는 관리 루프로 연결돼야 실효성이 생긴다.

동작 순서:

  1. 보호 대상과 기준 정의: 자산, 사용자, 규제 요구, 위협 가정을 먼저 식별한다.
  2. 정책 결정과 통제 배치: 인증·인가·암호화·분리·검사 지점을 설계해 적용 범위를 확정한다.
  3. 실행과 검증: 실제 요청·행위·데이터 흐름을 정책과 대조해 허용·차단·격리·경보를 수행한다.
  4. 증적 축적과 개선: 로그, 감사 기록, 사고 결과를 다시 위험 평가와 통제 개선에 반영한다.

│ 사용자/시스템 요청 │ -> │ 정책 결정·통제 집행 │ -> │ 허용/차단/증적 생성 │
└──────────────┘    └────────────────┘    └─────────────────┘

4. 비교 및 연결

비교 관점적용 시 강조점연결되는 대안·인접 개념
통제 방식사후 대응보다 사전 정책화와 지속 검증의 비중이 크다.수동 점검, 경계형 방어, 단발성 심사
운영 증적로그·정책·설정·행위 데이터가 증적으로 축적돼야 한다.경험 의존 운영, 문서 중심 준수
확장 전략표준화된 통제 지점이 많을수록 대규모 환경에서도 일관성이 유지된다.예외 처리 남발, 부서별 분산 규칙

데이터 엔지니어링 파이프라인 최적화

  1. CSV → Parquet 변환: S3 원시 데이터를 Parquet로 변환하면 Athena 쿼리 비용 70~90% 절감
  2. 파티셔닝 전략: year=2026/month=04/day=21 경로 파티셔닝으로 Partition Pruning 효과
  3. 압축 코덱 선택: 속도 중심 → Snappy, 압축률 중심 → Zstd (최신 표준)
  4. Row Group 크기: 128MB~1GB 권장 (너무 작으면 Footer 오버헤드, 너무 크면 메모리 부담)
  5. 통계 활용: Min/Max 통계로 Predicate Pushdown 적용 → 불필요 Row Group 스킵

5. 실무 적용 및 판단

채택 조건:

  • 규제 대응, 접근 통제, 감사 가능성처럼 반복 가능한 통제 체계가 필요한 경우
  • 사람 중심 운영을 정책·자동화·증적으로 전환해야 하는 경우

회피 조건:

  • 보호 대상 정의 없이 도구만 먼저 도입하려는 경우
  • 운영 조직과 프로세스가 준비되지 않아 경보·예외 처리만 늘어나는 경우

체크리스트:

  1. 자산·사용자·권한·로그의 기준 데이터가 정리되어 있는가?
  2. 통제 우회 경로와 예외 승인 절차가 문서화되어 있는가?
  3. 감사 증적과 실제 운영 로그가 일치하는가?

기대효과:

  • 저장 용량 50~80% 절감 (압축 효과)
  • 분석 쿼리 I/O 80~90% 절감 (컬럼 프루닝)
  • 클라우드 쿼리 비용(Athena: 스캔 GB당 과금) 최대 90% 절감
  • 쿼리 응답 시간 10~100배 향상

한계 및 전제조건:

  • 쓰기 비용 높음 (행 단위 삽입/갱신 비효율)
  • 랜덤 갱신 불가 (Row 수정 시 파일 전체 재작성)
  • 소량 데이터(수 MB)에서는 오버헤드가 이득을 상회
  • Parquet 스키마 변경 시 하위 호환성 관리 필요

6. 기대효과 및 결론

델타 인코딩 압축 파케이 컬럼 스토리지의 가치는 단발성 통제가 아니라 정책과 운영을 연결하는 관리 체계로 접근할 때 가장 크게 나타난다. 제대로 정착하면 침해 확산 억제, 규제 준수, 감사 대응, 운영 표준화 측면에서 높은 효과를 제공한다.

다만 통제 수단만 늘리고 기준 데이터·운영 프로세스를 정비하지 않으면 오히려 복잡도와 오탐, 예외 처리 비용이 증가한다. 앞으로는 자동화된 증적 수집, AI 보조 분석, 프라이버시 강화 기술, 표준화된 인터페이스가 결합되며 델타 인코딩 압축 파케이 컬럼 스토리지의 실효성과 확장성이 함께 높아질 것이다.
