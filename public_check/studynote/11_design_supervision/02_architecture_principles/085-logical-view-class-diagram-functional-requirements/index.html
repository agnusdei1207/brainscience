0. 핵심 인사이트

핵심: 논리 뷰는 기능 요구사항을 도메인 개념과 책임 구조로 번역하여 시스템이 무엇을 중심으로 구성되는지를 드러내는 설계 관점이다. 비유: 복잡한 업무를 사람 이름이 아니라 역할과 책임 기준으로 재배치한 조직도와 같다.

📝 모범 답안

1. 개요 및 필요성

논리 뷰 (Logical View)는 4+1 뷰 모델에서 최종 사용자가 체감하는 기능 구조를 가장 직접적으로 표현하는 관점이다. 화면이나 서버보다 먼저, 시스템이 어떤 개념을 중심으로 동작하고 각 개념이 어떤 책임을 져야 하는지 정리한다. 따라서 논리 뷰는 분석 모델과 구현 모델 사이를 연결하는 핵심 설계 산출물이다.

기능 요구사항은 보통 유스케이스나 업무 규칙 형태로 제시되지만, 그대로는 코드 구조로 이어지지 않는다. 예를 들어 "주문을 생성하고 결제를 승인한다"는 요구는 주문, 결제, 고객, 재고 같은 도메인 개체와 서비스 책임으로 변환되어야 한다. 이 변환 과정이 불충분하면 구현 단계에서 클래스가 무질서하게 생성되고, 기능은 동작해도 구조는 빠르게 붕괴한다.

논리 뷰의 필요성은 추적성과 변경 용이성에서도 드러난다. 유스케이스와 클래스 책임이 연결되어 있으면 요구사항 변경 시 영향을 받는 클래스 집합을 예측할 수 있다. 반대로 추적성이 없으면 기능 하나가 여러 계층에 산재되어 변경 파급이 커진다. 특히 단일 책임 원칙 (SRP: Single Responsibility Principle), 개방-폐쇄 원칙 (OCP: Open-Closed Principle) 같은 객체지향 설계 원칙은 논리 뷰 수준에서 먼저 드러나야 구현에서도 유지된다.

2. 구성요소

요소역할핵심 포인트
도메인 클래스핵심 비즈니스 개념 표현엔터티, 값 객체, 집합체 등 역할 구분 필요
서비스여러 도메인 객체를 조정하는 행위 캡슐화비즈니스 규칙과 애플리케이션 흐름을 분리
패키지/서브시스템관련 책임을 묶는 경계응집도 향상과 의존성 통제가 핵심
인터페이스외부와의 계약 정의구현 교체 가능성과 테스트 용이성 확보
클래스 관계연관, 의존, 상속, 합성 관계 표현관계가 많을수록 결합도 증가에 유의
유스케이스 추적 링크기능 요구와 설계 요소를 연결요구 변경 시 영향 분석의 근거

논리 뷰에서 중요한 것은 클래스 자체보다 책임 배치의 논리다. 엔터티에 들어갈 규칙, 서비스에 위임할 조정 로직, 패키지로 묶을 응집 영역을 구분해야 한다. 또한 패키지 경계를 통해 향후 구현 뷰의 모듈 구조와 연결되어야 한다. 즉 논리 뷰는 분석 산출물이면서 동시에 구현 방향을 제약하는 설계 골격이다.

3. 구조 및 원리

핵심 조건: 유스케이스의 기능 흐름이 클래스·패키지·서비스 책임으로 추적 가능해야 하며, 각 요소는 높은 응집도 + 낮은 결합도를 유지하도록 배치되어야 한다.

동작 순서:

  1. 유스케이스와 도메인 용어를 식별한다: 요구사항 문장에서 핵심 명사와 행위를 추출하여 도메인 후보를 만든다. 용어 정의가 불명확하면 클래스 경계도 흐려진다.
  2. 책임을 분배한다: 어떤 객체가 상태를 보유하고 어떤 서비스가 흐름을 조정할지 결정한다. 책임이 집중되면 거대 클래스가 발생한다.
  3. 클래스 관계를 설계한다: 상속, 합성, 의존 관계를 선택해 협력 구조를 만든다. 이 단계에서 과도한 양방향 의존을 경계해야 한다.
  4. 패키지와 서브시스템으로 묶는다: 함께 변경되는 요소를 같은 패키지로 묶고, 그렇지 않은 요소는 분리한다. 변경 축을 기준으로 묶는 것이 핵심이다.
  5. 유스케이스-클래스 추적성을 검증한다: 각 기능이 어떤 클래스와 서비스에 의해 실현되는지 명시한다.
  6. 설계 원칙을 점검한다: SRP, OCP, 의존 역전 원칙 (DIP: Dependency Inversion Principle) 등이 논리 구조에서 지켜지는지 확인한다.

클래스 다이어그램은 논리 뷰의 대표 표현이지만 목적은 그림 자체가 아니다. 클래스 다이어그램은 기능 요구를 구조로 번역한 결과를 정적 관점에서 검토하기 위한 도구다. 따라서 메서드 목록을 길게 나열하기보다 책임과 관계가 드러나는 수준으로 작성해야 한다. 특히 객체지향 원칙은 구현 직전에 적용하는 미세 규칙이 아니라, 논리 뷰에서 책임을 어떻게 나눌지 결정하는 기준이다.

엣지 케이스는 기능 중심으로만 클래스명을 붙이는 경우다. 예를 들어 OrderProcessManager, PaymentProcessManager처럼 모든 것을 관리 객체에 몰아넣으면 논리 뷰가 절차 중심으로 퇴행한다. 이 경우 도메인 규칙이 서비스에 과집중되어 변경 용이성이 떨어진다. 반대로 지나친 추상화로 클래스 수만 늘리면 구조 파악이 어려워진다. 따라서 핵심은 도메인 의미와 변경 축을 기준으로 균형 있게 분할하는 것이다.

4. 비교 및 연결

항목논리 뷰구현 뷰프로세스 뷰
초점기능 구조와 책임코드 패키징과 빌드 단위런타임 실행과 동시성
주요 산출물클래스도, 패키지 구조컴포넌트도, 모듈 구조시퀀스도, 프로세스 상호작용
핵심 질문어떤 개념이 어떤 책임을 지는가어떻게 소스와 모듈로 조직되는가어떻게 실행되고 협력하는가
의사결정 영향변경 파급과 도메인 적합성팀 분업과 형상관리 효율성능과 장애 대응

논리 뷰는 유스케이스 뷰와 가장 직접적으로 연결된다. 유스케이스에서 식별된 행위가 어떤 클래스와 서비스에 매핑되는지 설명해야 하기 때문이다. 또한 구현 뷰와 연결될 때는 패키지 구조와 모듈 경계로 이어지고, 프로세스 뷰와 연결될 때는 논리적 서비스가 런타임에서 어떤 실행 단위로 활성화되는지 보여준다.

5. 실무 적용 및 판단

채택 조건:

  • 도메인 복잡도가 높고 업무 규칙이 시스템 차별성을 결정할 때
  • 장기간 유지보수가 예정되어 기능 변경 영향 분석이 중요할 때
  • 여러 팀이 같은 도메인 모델을 공유해야 할 때

회피 조건:

  • 화면 흐름만을 클래스 구조로 오인해 도메인 개념 없이 컨트롤러 중심으로 설계할 때
  • 패키지 경계를 기술 프레임워크 기준으로만 나누어 업무 의미가 사라질 때
  • 모든 규칙을 서비스 하나에 몰아넣어 엔터티를 빈 껍데기로 만들 때

체크리스트:

  1. 유스케이스가 클래스/서비스로 추적 가능한가?
  2. 함께 변경되는 책임이 같은 패키지에 있는가?
  3. 도메인 규칙이 적절한 객체에 배치되었는가?
  4. 인터페이스가 구현 세부사항을 과도하게 노출하지 않는가?
  5. SRP, OCP, DIP 위반 지점이 없는가?

실제 사례: 인터넷 뱅킹 시스템은 계좌, 거래, 한도, 승인 규칙을 도메인 모델로 명확히 구분해야 감사 추적과 변경 통제가 가능하다. 전자상거래에서는 주문, 결제, 배송, 프로모션 도메인을 분리해 패키지 경계를 설정하면 프로모션 정책 변경이 주문 코어를 오염시키지 않는다.

6. 기대효과 및 결론

논리 뷰를 잘 설계하면 기능 요구사항이 코드 이전 단계에서 의미 있는 구조로 정리되어 변경 용이성과 테스트 용이성이 크게 향상된다. 또한 도메인 용어가 설계와 구현 전반에서 일관되게 유지되어 팀 간 의사소통 비용이 줄어든다. 감리 관점에서도 논리 뷰는 요구 추적성과 책임 배치 적정성을 검토하는 핵심 근거가 된다.

다만 논리 뷰만으로 전체 아키텍처를 설명할 수는 없다. 실행 시 병목이나 배포 제약은 프로세스·배포 뷰가 보완해야 한다. 전제조건은 정확한 도메인 분석과 요구 추적성이다. 앞으로는 도메인 주도 설계와 이벤트 스토밍, 코드 생성 도구가 결합되면서 논리 뷰가 분석 문서가 아니라 실행 가능한 설계 자산으로 발전할 가능성이 높다.
