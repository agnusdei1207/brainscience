0. 핵심 인사이트

핵심: 프로세스 뷰는 시스템이 실행 중일 때 어떤 프로세스와 스레드가 어떤 방식으로 협력·경합·분산되는지를 설명하여 성능과 가용성의 실제 거동을 드러내는 관점이다. 비유: 설계도만으로는 공장의 생산량을 알 수 없고, 각 작업대가 동시에 어떻게 움직이는지 봐야 병목이 드러나는 것과 같다.

📝 모범 답안

1. 개요 및 필요성

논리 뷰가 시스템의 정적 책임 구조를 설명한다면, 프로세스 뷰 (Process View)는 런타임의 동적 행위를 설명한다. 동일한 기능 구조라도 스레드 모델, 메시지 전달 방식, 동기화 정책에 따라 성능과 장애 특성이 완전히 달라질 수 있다. 따라서 고부하 서비스, 분산 시스템, 실시간 처리 시스템에서는 프로세스 뷰가 사실상 품질 속성 설계의 중심이 된다.

프로세스 뷰가 필요한 이유는 많은 품질 문제들이 코드 구조보다 실행 구조에서 발생하기 때문이다. 응답 지연은 스레드 경합, 큐 적체, 네트워크 왕복, 락 경쟁에서 발생하고, 가용성 문제는 단일 프로세스 장애 전파, 세션 상태 공유 방식, 재시도 폭주에서 발생한다. 이러한 문제는 클래스 다이어그램으로는 잘 드러나지 않는다.

또한 현대 시스템은 단일 프로세스를 넘어 분산 노드, 비동기 메시지, 이벤트 스트림, 컨테이너 오케스트레이션 위에서 동작한다. 이때 프로세스 뷰는 어디서 병렬성이 일어나고 어디서 순차성이 강제되는지, 어떤 IPC (Inter-Process Communication) 또는 RPC (Remote Procedure Call) 메커니즘이 병목을 만들 수 있는지 설명해야 한다.

스레드/작업자 풀동시 실행을 담당스레드 수와 큐 길이가 성능 민감도점이 됨

프로세스 뷰에서 핵심은 실행 단위와 상호작용 방식의 조합이다. 같은 기능이라도 동기 RPC로 직렬 호출하면 응답 시간이 누적되고, 비동기 메시지로 분리하면 지연 허용성과 탄력성이 증가하지만 일관성 관리가 어려워진다. 따라서 프로세스 뷰는 단순히 실행 컴포넌트 목록을 적는 문서가 아니라, 품질 속성별 전략을 드러내는 구조도다.

3. 구조 및 원리

핵심 조건: 런타임 실행 구조는 요청량 × 처리시간 × 동시성 수준에 대응할 수 있어야 하며, 병렬화 지점과 직렬화 지점을 명확히 구분해 병목과 장애 전파를 통제해야 한다.

동작 순서:

  1. 주요 시나리오의 실행 흐름을 선택한다: 로그인, 주문 처리, 실시간 조회처럼 성능에 민감한 시나리오를 기준으로 분석한다.
  2. 실행 단위를 식별한다: 어떤 기능이 웹 프로세스, 워커, 배치, 이벤트 소비자로 실행되는지 분리한다.
  3. 통신 방식을 정한다: 프로세스 간 직접 호출인지, 메시지 브로커를 통한 비동기 전달인지, 공유 메모리·파일·소켓 기반 IPC인지 결정한다.
  4. 동시성 제어 정책을 설계한다: 스레드 풀 크기, 큐 백프레셔, 락 범위, 상태 공유 방식을 정의한다. 이 단계가 성능·안정성의 민감도점이 된다.
  5. 장애와 지연 전파를 분석한다: 타임아웃, 재시도, 서킷 브레이커, 격리 전략을 배치한다.
  6. 시퀀스 다이어그램으로 검증한다: 실제 시간 순서와 병렬 구간을 그려 병목과 교착 위험을 확인한다.
Client
  │ 요청
  ▼
[Web Process] --RPC--> [Application Service]
  │                       │
  │                       ├─sync→ [Auth Service]
  │                       ├─async→ [Message Queue] → [Worker Pool]
  │                       └─sync→ [DB/Cache]
  │
  └─timeout / retry / circuit breaker

이 구조에서 중요한 원리는 "실행 시간의 누적"과 "장애 전파"를 동시에 본다는 점이다. 동기 호출 체인이 길수록 평균 응답 시간이 늘고 tail latency가 악화된다. 반대로 비동기화는 응답 시간을 줄일 수 있으나, 메시지 중복 처리와 최종 일관성 문제가 생긴다. 따라서 프로세스 뷰는 동시성 증가가 성능을 높이는 지점과 오히려 경쟁 비용을 키우는 지점을 함께 분석해야 한다.

엣지 케이스로는 스레드 풀 고갈, 메시지 큐 적체, 교착 상태, 캐시 스탬피드, 재시도 폭주가 있다. 예를 들어 외부 API 장애 시 재시도를 무제한 허용하면 가용성을 높이기보다 장애를 확산시킨다. 따라서 프로세스 뷰는 단순 정상 흐름이 아니라 비정상 상황에서의 제어 흐름까지 포함해야 완전하다.

프로세스 뷰는 물리 뷰와 밀접하다. 런타임 실행 구조는 결국 어떤 노드에 배치되는지에 따라 실제 성능과 장애 특성이 달라지기 때문이다. 또한 논리 뷰의 서비스 경계가 프로세스 뷰에서 별도 프로세스 또는 스레드 풀로 분리되는지 여부는 구현 전략과 운영 비용에 직접 연결된다.

5. 실무 적용 및 판단

채택 조건:

  • 동시 접속자 수가 많거나 응답 시간 목표가 엄격한 시스템일 때
  • 비동기 이벤트 처리, 메시지 기반 통합, 실시간 스트리밍이 포함될 때
  • 장애 격리와 서비스 연속성이 중요한 시스템일 때

회피 조건:

  • 정적 구조만 보고 성능 문제가 해결될 것이라고 가정할 때
  • 모든 호출을 비동기화하여 복잡성만 높이고 일관성 요구를 무시할 때
  • 스레드 수, 큐 크기, 타임아웃 값을 측정 없이 임의 설정할 때

체크리스트:

  1. 핵심 시나리오의 호출 체인이 시퀀스 다이어그램으로 표현되었는가?
  2. 스레드 풀, 큐, 타임아웃, 재시도 정책이 정의되었는가?
  3. 동기/비동기 분기 기준이 품질 속성과 연결되는가?
  4. 장애 전파를 차단하는 격리 전략이 있는가?
  5. IPC/RPC/메시지 큐 선택 이유가 명확한가?

실제 사례: 고빈도 거래 시스템은 지연을 줄이기 위해 프로세스 간 복사 비용을 최소화하고, 로그 수집·후속 처리 같은 비핵심 경로는 메시지 큐로 비동기화한다. 대규모 전자상거래는 주문 접수는 동기 응답을 유지하되, 재고 예약·알림 발송·추천 갱신은 이벤트 기반 워커로 분리해 피크 부하에 대응한다.

6. 기대효과 및 결론

프로세스 뷰를 명확히 작성하면 성능과 가용성 문제를 코드 작성 이전에 예측할 수 있다. 어느 구간이 병렬화 가능한지, 어느 자원이 공유되어 경합이 발생하는지, 장애가 어떻게 전파되는지 드러나므로 운영 장애를 구조 차원에서 줄일 수 있다. 또한 테스트 설계에도 직접 도움이 되어 부하 테스트와 장애 주입 실험의 대상 지점을 명확히 할 수 있다.

다만 프로세스 뷰는 실제 측정과 함께 검증되어야 한다. 문서상으로 이상적인 병렬 구조가 실제 환경에서는 컨텍스트 스위칭, 네트워크 지연, 데이터베이스 잠금 때문에 기대한 성능을 내지 못할 수 있다. 전제조건은 성능 시나리오, 모니터링 지표, 장애 실험 체계다. 향후에는 분산 추적 (Distributed Tracing), 서비스 메시, eBPF 기반 관측성이 프로세스 뷰와 결합되어 런타임과 문서가 더 밀접하게 연결될 것이다.
