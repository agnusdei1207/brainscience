0. 핵심 인사이트

핵심: 유스케이스 뷰는 액터와 시스템 경계에서 출발해 핵심 시나리오를 정의함으로써 4개의 기술 뷰가 실제 사용자 요구를 향하도록 정렬시키는 통합 기준점이다. 비유: 건물의 평면도, 배관도, 전기도가 모두 최종 사용자의 생활 동선에 맞는지 확인하는 사용 시나리오와 같다.

📝 모범 답안

1. 개요 및 필요성

4+1 모델에서 +1인 유스케이스 뷰 (Use Case View)는 다른 네 뷰를 묶어주는 기준 축이다. 논리 뷰, 프로세스 뷰, 구현 뷰, 물리 뷰가 각각 기술 관점을 다룬다면, 유스케이스 뷰는 외부 사용자가 시스템과 상호작용하는 목적과 흐름을 설명한다. 이 뷰가 없으면 나머지 네 뷰는 기술적으로 정교해도 실제 요구사항과 어긋날 수 있다.

유스케이스 뷰가 필요한 이유는 아키텍처가 결국 기능과 품질 속성을 어떤 상황에서 달성해야 하는지를 명확히 해야 하기 때문이다. 단순 기능 목록은 구조 설계의 우선순위를 정해주지 못한다. 반면 주요 액터, 시스템 경계, 기본 흐름, 예외 흐름이 정의된 유스케이스는 어떤 시나리오가 아키텍처적으로 중요한지 알려준다.

특히 아키텍처 설계 초기에 모든 유스케이스를 동일하게 다루는 것은 비효율적이다. +1 뷰에서 중요한 것은 빈도가 높거나 실패 비용이 크거나 품질 속성 요구가 강한 핵심 시나리오를 선정하는 것이다. 이 시나리오가 다른 네 뷰를 검증하는 테스트 벡터 역할을 한다.

2. 구성요소

요소역할핵심 포인트
액터 (Actor)시스템 외부에서 상호작용하는 주체사람, 외부 시스템, 장치, 배치 주체 포함
유스케이스 (Use Case)액터가 달성하려는 목표 단위의 기능사용자 가치 중심으로 정의해야 함
시스템 경계 (System Boundary)시스템 내부와 외부를 구분책임 범위와 인터페이스 범위를 명확히 함
기본 흐름정상적인 시나리오 절차아키텍처의 주경로 검증 대상
예외/대안 흐름오류, 보완, 우회 시나리오보안성·가용성 설계에 중요
추적 링크유스케이스와 4개 뷰 연결어떤 클래스, 프로세스, 컴포넌트, 노드가 지원하는지 명시

유스케이스 뷰는 요구사항 문서와 아키텍처 문서의 접점이다. 액터와 시스템 경계가 명확해야 외부 인터페이스와 내부 책임이 섞이지 않는다. 또한 기본 흐름과 예외 흐름을 구분해야 정상 처리뿐 아니라 실패 시 복구, 보안 오류, 시간 초과 같은 현실적 문제를 설계에 반영할 수 있다.

3. 구조 및 원리

핵심 조건: 핵심 유스케이스는 시스템 경계를 명확히 한 상태에서 정의되어야 하며, 각 시나리오는 논리·프로세스·구현·물리 뷰에 추적 가능해야 한다.

동작 순서:

  1. 주요 액터를 식별한다: 최종 사용자, 관리자, 외부 결제 시스템, 배치 스케줄러 등 시스템과 상호작용하는 주체를 정의한다.
  2. 시스템 경계를 설정한다: 무엇이 시스템 내부 책임이고 무엇이 외부 서비스 의존인지 구분한다. 경계가 모호하면 통합 책임이 과소평가된다.
  3. 핵심 유스케이스를 선정한다: 빈도, 위험도, 사업 가치, 품질 속성 영향을 기준으로 아키텍처적으로 중요한 시나리오를 우선한다.
  4. 기본/예외 흐름을 서술한다: 정상 시나리오뿐 아니라 실패와 복구 경로를 함께 정의해야 품질 속성 설계가 가능하다.
  5. 4개 뷰와 연결한다: 논리 뷰에서는 어떤 클래스와 서비스가, 프로세스 뷰에서는 어떤 실행 흐름이, 구현 뷰에서는 어떤 컴포넌트가, 물리 뷰에서는 어떤 배치 구조가 이를 지원하는지 연결한다.
  6. 시나리오 기반 검증을 수행한다: 실제로 +1 뷰 하나를 따라가며 네 뷰가 모두 일관된 답을 제공하는지 확인한다.
[Actor]
  고객 ──> (주문 생성)
  관리자 ─> (상품 등록)
  외부결제 ─> (승인 응답)

        ┌──────────── System Boundary ────────────┐
        │  주문 서비스 / 결제 서비스 / 재고 서비스  │
        └─────────────────────────────────────────┘

주문 생성 유스케이스
  ├─ 논리 뷰: 주문/결제/재고 도메인 책임
  ├─ 프로세스 뷰: 동기 승인 + 비동기 후처리
  ├─ 구현 뷰: order-app / payment-adapter 컴포넌트
  └─ 물리 뷰: web/app/db 노드 배치

유스케이스 뷰의 원리는 기술적 완결성이 아니라 아키텍처적 대표성에 있다. 모든 상세 기능을 다 넣는 대신, 구조를 검증하기에 충분한 시나리오를 선택해야 한다. 예를 들어 "주문 생성"은 결제, 재고, 트랜잭션, 메시징, 배포, 보안 인증을 모두 포함하므로 아키텍처 검증 시나리오로 가치가 높다.

엣지 케이스는 사용자 인터페이스 (UI) 화면 단위를 유스케이스로 오인하는 경우다. 화면 전환 하나하나를 유스케이스로 만들면 기술적 중요성이 사라진다. 반대로 너무 추상적으로 "쇼핑 관리"처럼 정의하면 구조 검증에 사용할 수 없다. 따라서 유스케이스는 사용자 목표 수준의 적절한 세분성을 가져야 한다.

4. 비교 및 연결

항목유스케이스 뷰논리 뷰프로세스 뷰구현 뷰물리 뷰
초점사용자 목표와 시스템 경계기능 책임 구조실행 흐름과 동시성코드와 컴포넌트 조직인프라 배치
대표 요소액터, 유스케이스, 경계클래스, 서비스프로세스, 스레드패키지, 모듈노드, 네트워크
역할통합 검증 기준기능 실현성능/가용성 검증개발 구조 검증운영 구조 검증

유스케이스 뷰는 요구사항 명세와 아키텍처 명세를 연결하는 가교다. 품질 속성 시나리오와도 관련이 깊다. 유스케이스가 기능 중심의 시나리오라면, 품질 속성 시나리오는 성능·보안성·가용성 같은 비기능 요구를 구체화한다. 실제 아키텍처 평가는 두 종류의 시나리오를 함께 사용해야 완전해진다.

5. 실무 적용 및 판단

채택 조건:

  • 아키텍처 검토에서 기술 구조를 실제 요구사항과 연결해야 할 때
  • 사용자 흐름이 복잡하고 예외 시나리오가 중요한 시스템일 때
  • 다수 이해관계자가 기능 우선순위를 합의해야 할 때

회피 조건:

  • 유스케이스를 화면 목록이나 메뉴 구조로 축소할 때
  • 시스템 경계를 정의하지 않아 외부 서비스 책임을 내부 책임처럼 서술할 때
  • 예외 흐름을 생략해 정상 시나리오만으로 아키텍처를 검증할 때

체크리스트:

  1. 액터가 시스템 외부 주체로 명확히 정의되었는가?
  2. 시스템 경계가 외부 시스템과 구분되어 있는가?
  3. 핵심 유스케이스가 4개 뷰와 추적되는가?
  4. 기본 흐름과 예외 흐름이 모두 존재하는가?
  5. 품질 속성에 큰 영향을 주는 시나리오가 우선 선정되었는가?

실제 사례: 병원 정보시스템에서는 진료 접수, 처방 입력, 보험 청구 같은 핵심 유스케이스를 기준으로 권한 체계, 응답 성능, 외부 기관 연계를 검증한다. 전자상거래에서는 주문·취소·환불 유스케이스가 결제, 재고, 회계, 알림까지 관통하므로 아키텍처 핵심 시나리오가 된다.

6. 기대효과 및 결론

유스케이스 뷰를 중심에 두면 아키텍처 설계가 기술 자체의 완결성에 빠지지 않고 실제 사용자 가치에 정렬된다. 또한 4개 뷰를 통합 검증할 수 있어 문서 간 단절을 줄이고 요구사항 추적성을 높인다. 감리 관점에서도 +1 뷰는 "이 구조가 실제 업무를 지원하는가"를 확인하는 가장 직접적인 근거가 된다.

다만 유스케이스 뷰가 지나치게 기능 명세 수준에 머물면 아키텍처 검증 가치가 약해진다. 전제조건은 대표 시나리오 선정과 경계 정의의 정확성이다. 미래에는 이벤트 로그와 사용자 여정 분석이 결합되어 실제 운영 데이터에서 아키텍처 핵심 유스케이스를 지속적으로 갱신하는 방식으로 발전할 수 있다.
