0. 핵심 인사이트

핵심: CNI (Container Network Interface)는 쿠버네티스가 파드(Pod)에 IP를 할당하고 오버레이 통신망을 구성하는 과정을 외부 플러그인에게 위임하기 위한 표준 규격이다. 비유: 복잡한 시스템을 작은 운영 규칙으로 정리해 안정적으로 굴러가게 만드는 교통 관제 체계와 같다.

📝 모범 답안

1. 개요 및 필요성

CNI (Container Network Interface)는 K8s 클러스터 내에서 컨테이너 간의 네트워크 연결을 설정하고 삭제하는 공통 인터페이스다. 쿠버네티스는 자체적으로 네트워크를 구축하지 않고 "파드는 고유 IP를 가져야 하며, NAT 없이 서로 통신해야 한다"는 원칙만 제시한다. 이 조건을 만족시키기 위해 외부 네트워크 솔루션들이 K8s와 연동될 수 있도록 만든 표준 구멍이 바로 CNI다.

이 표준이 필요한 이유는 K8s가 모든 인프라(AWS, 온프레미스, 베어메탈)의 네트워크 장비와 라우팅 방식을 직접 제어할 수 없기 때문이다. CNI가 없다면 K8s 코어 코드는 세상의 모든 네트워크 벤더 종속적인 라우팅 규칙으로 비대해졌을 것이다. 따라서 네트워크 제어 권한을 CNI 플러그인으로 분리함으로써 시스템의 확장성과 유지보수성을 확보했다.

2. 구성요소

K8s의 Kubelet은 파드가 생성될 때 CNI 플러그인을 호출(ADD)하여 파드의 가상 네트워크 인터페이스(veth)를 생성하고 IP를 할당한다. 이후 서로 다른 노드에 있는 파드 간 통신을 위해 CNI는 주로 오버레이 네트워크 (Overlay Network) 캡슐화 기술을 사용한다.

물리 라우터는 파드의 가상 IP 대역을 모르기 때문에 패킷을 버린다. 따라서 CNI는 출발지와 목적지 물리 노드 IP를 적은 새 헤더로 원본 패킷을 감싸는 캡슐화 작업을 수행해 물리망을 통과시킨다.

3. 구조 및 원리

핵심 조건: 컨테이너/쿠버네티스 환경에서는 선언형 상태, 스케줄링 정책, 네트워크·스토리지 연동, 복구 자동화가 일관되게 맞물려야 운영 안정성이 확보된다.

동작 순서:

  1. 사용자가 원하는 최종 상태를 선언형으로 정의한다.
  2. 컨트롤 플레인이 스케줄링과 리소스 배치를 결정한다.
  3. 런타임이 컨테이너를 기동하고 네트워크·스토리지를 연계한다.
  4. 서비스 계층이 외부 트래픽과 내부 통신을 안정적으로 중계한다.
  5. 프로브·오토스케일링·정책 엔진이 복구와 최적화를 반복한다.

CNI 플러그인은 기능의 무거움과 통신 방식에 따라 3세대로 나눌 수 있으며, 인프라의 요구사항에 따라 뚜렷한 경계를 가진다.

항목Flannel (플란넬)Calico (칼리코)Cilium (실리움)
통신 방식VXLAN 기반 오버레이BGP 기반 다이렉트 라우팅 (필요시 오버레이)eBPF (Extended Berkeley Packet Filter) 기반
Network Policy미지원 (보안 통제 불가)완벽 지원 (L3/L4 방화벽)완벽 지원 (L7 가시성 및 보안)
성능 및 복잡도성능 낮음, 매우 단순함성능 높음, 엔터프라이즈 표준초고성능, 최신 커널 요구

Flannel은 단순 통신만 뚫어주기 때문에 소규모 개발망에 적합하다. 반면 Calico는 패킷 캡슐화 오버헤드를 없앤 BGP 통신과 방화벽 정책을 지원해 사실상의 산업 표준이 되었다. 최근에는 리눅스 커널 수준에서 네트워크를 낚아채는 eBPF 기술을 적용한 Cilium이 차세대 CNI로 부상하고 있다.

4. 비교 및 연결

클러스터를 구축할 때 CNI 선택은 아키텍처의 근간을 결정하는 핵심 의사결정이다. 한 번 설치된 CNI를 운영 중에 교체하는 것은 전체 네트워크 단절을 의미하므로 초기 선택이 매우 중요하다.

체크리스트

  1. Network Policy 필요 여부: 파드 간 통신을 차단하는 보안 규칙이 필요한가? (그렇다면 Flannel은 배제한다.)
  2. 물리망 BGP 연동 가능성: 노드가 위치한 스위치 장비가 BGP 라우팅을 지원하는가? (지원한다면 Calico의 Non-Overlay 모드를 채택해 성능을 극대화한다.)
  3. 커널 버전 제약: OS 커널이 최신 eBPF를 지원할 만큼 최신 버전인가? (구형 커널이라면 Cilium 도입을 보류해야 한다.)

안티패턴

  • 보안이 중요한 금융권 망에서 성능만 보고 Network Policy를 미지원하는 CNI를 채택하는 설계.
  • 여러 리전에 걸친 노드 간 통신 환경에서 암호화(IPsec/WireGuard) 기능 없이 오버레이 터널만 뚫어 평문 통신을 방치하는 설계.

5. 실무 적용 및 판단

표준화된 CNI 규격을 도입함으로써 K8s는 플랫폼 자체의 결합도를 낮추고 거대한 서드파티 네트워크 생태계를 만들어냈다. 관리자는 클러스터의 목적에 맞춰 가벼움, 보안, 성능 중 하나를 취사선택할 수 있게 되었다.

향후 K8s 네트워크 환경은 iptables와 kube-proxy의 성능 병목을 완전히 제거하는 방향으로 진화할 것이다. 따라서 CNI의 발전 방향은 오버레이의 복잡도를 줄이고 eBPF 같은 커널 네이티브 기술을 활용하여 성능과 보안 가시성을 동시에 잡는 형태로 수렴할 것이다.

6. 기대효과 및 결론

CNI (Container Network Interface) - 파드 간 오버레이 통신 표준를 올바르게 적용하면 확장성, 운영 안정성, 자동화 수준, 가시성을 함께 높일 수 있다. 다만 이 효과는 기술 자체만으로 생기지 않으며, 책임 경계·표준화·보안 통제·비용 관리가 함께 설계될 때 비로소 현실화된다.

향후에는 관리형 서비스, 정책 자동화, AI 기반 운영 최적화와 결합되면서 CNI (Container Network Interface) - 파드 간 오버레이 통신 표준의 중요성이 더 커질 것이다. 따라서 핵심은 특정 도구를 도입하는 것이 아니라, 업무 특성과 조직 역량에 맞는 적용 범위와 운영 모델을 설계하는 데 있다.
