0. 핵심 인사이트

핵심: 마이데이터(MyData)는 금융·의료·공공 데이터의 정보 주체(개인)가 자신의 데이터를 직접 관리·활용할 권리를 갖는 패러다임으로, 스크래핑(화면 긁기) 방식을 금지하고 OAuth 2.0 기반 표준 API로 안전하게 데이터를 이동시킨다. 비유: 스크래핑은 은행 직원에게 내 마스터키를 맡기는 것이다. 마이데이터 API는 특정 금고만 열 수 있는 임시 키(Token)를 발급하는 것으로, 필요한 것만, 정해진 기간만 접근할 수 있다.

📝 모범 답안

1. 개요 및 필요성

기존 핀테크 앱들은 사용자의 금융 데이터를 수집하기 위해 "화면 스크래핑(Screen Scraping)"을 사용했다. 이는 사용자의 인터넷 뱅킹 ID/PW를 핀테크사 서버에 저장하고, 해당 ID/PW로 은행 웹사이트에 자동 로그인하여 데이터를 긁어오는 방식이다. 심각한 보안 위험이 존재했다.

마이데이터(MyData) 제도는 2021년 금융 마이데이터를 시작으로, 스크래핑을 법적으로 금지하고 표준 API로만 데이터를 전송하도록 의무화했다.

[기존 스크래핑 vs 마이데이터 API]

기존 스크래핑 (위험):
사용자 ID/PW → 핀테크사 서버 저장
                    │
                    ▼ (자동 로그인)
             은행 웹사이트 화면 파싱
                    │ 보안 위험, 불법화

마이데이터 API (안전):
사용자 → [동의 화면] → Access Token 발급
                              │
                              ▼
핀테크 앱 → API 호출(Bearer Token) → 금융기관 서버
                              (사용자 ID/PW 불필요)

3. 구조 및 원리

핵심 조건: 데이터 플랫폼은 수집·저장·처리·제공·거버넌스가 한 체계로 설계되어야 품질, 확장성, 비용 효율을 동시에 확보할 수 있다.

동작 순서:

  1. 데이터를 원천 시스템이나 이벤트 스트림에서 수집한다.
  2. 수집된 데이터를 적절한 저장 구조와 포맷에 적재한다.
  3. 배치·스트림·쿼리 엔진이 목적에 맞게 변환·처리한다.
  4. 분석·서빙·ML·애플리케이션 계층에 결과를 제공한다.
  5. 품질, 거버넌스, 비용, 보안을 기준으로 지속 최적화한다.

전송 동의 항목:
- 금융기관: 은행, 카드사, 증권사 (선택)
- 데이터 범위: 계좌 잔액, 거래 내역, 대출 정보 (세분화)
- 전송 주기: 수시/일 1회/수동 (선택)

- 유효 기간: 최대 1년 (법적 제한)

보안 구현 핵심

# Access Token 검증 (Introspection)
import requests

def verify_token(access_token: str) -> dict:
    """리소스 서버에서 인가 서버로 토큰 직접 검증"""
    response = requests.post(
        'https://mydata-auth.fsc.or.kr/introspect',
        data={'token': access_token},
        headers={'Authorization': f'Basic {client_credentials}'}
    )
    token_info = response.json()
    if not token_info.get('active'):
        raise UnauthorizedException("Invalid or expired token")
    return token_info

기술사 시험 판단 포인트

  • 스크래핑 금지 이유: ID/PW 위탁으로 인한 무제한 접근 위험 → 범위 제한 토큰으로 대체
  • OAuth 2.0 Grant 유형: 마이데이터는 Authorization Code Grant (사용자 동의 흐름) 사용
  • mTLS(상호 TLS): 클라이언트·서버 양방향 인증으로 API 호출 주체 식별

5. 실무 적용 및 판단

기대효과

영역효과

금융 혁신개인 맞춤형 금융 서비스 (자산 통합, 신용 분석)

한계 및 주의사항

  • 동의 피로: 세분화된 동의 항목으로 인한 사용자 동의 번거로움
  • 데이터 품질: 금융기관별 API 응답 형식 비표준화 → 정규화 비용
  • 토큰 관리 복잡성: 다수 금융기관의 다수 토큰 갱신·관리 로직 복잡
  • 본인 인증 병목: 금융기관별 인증 절차 상이 → 사용자 경험 일관성 저하

6. 기대효과 및 결론

마이데이터 (MyData) 오픈 API - 토큰 보안 인증를 올바르게 적용하면 확장성, 운영 안정성, 자동화 수준, 가시성을 함께 높일 수 있다. 다만 이 효과는 기술 자체만으로 생기지 않으며, 책임 경계·표준화·보안 통제·비용 관리가 함께 설계될 때 비로소 현실화된다.

향후에는 관리형 서비스, 정책 자동화, AI 기반 운영 최적화와 결합되면서 마이데이터 (MyData) 오픈 API - 토큰 보안 인증의 중요성이 더 커질 것이다. 따라서 핵심은 특정 도구를 도입하는 것이 아니라, 업무 특성과 조직 역량에 맞는 적용 범위와 운영 모델을 설계하는 데 있다.
