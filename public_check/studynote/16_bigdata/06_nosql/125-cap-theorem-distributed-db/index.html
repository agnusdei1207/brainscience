0. 핵심 인사이트

핵심: CAP 정리 (CAP Theorem)은(는) 관계형 데이터베이스의 확장 한계를 넘어 분산 환경에 맞는 일관성·성능·유연성을 선택하게 하는 저장 기술이다. 비유: 한 종류의 서랍장 대신 용도별 보관함을 골라 쓰는 공구실과 같다.

📝 모범 답안

1. 개요 및 필요성

  1. 분산 환경의 숙명: 노드가 여러 개로 나뉘어 데이터를 복제하는 환경에서는 네트워크 장애가 필연적으로 발생하며, 이때 데이터를 어떻게 처리할지가 시스템의 성격을 결정함.
  2. 트레이드오프 관계: 모든 것을 가질 수는 없으므로, 비즈니스 요건에 맞춰 "무엇을 버릴지"를 결정하는 엔지니어링적 통찰을 제공함.

2. 구성요소

  • CAP Theorem Triangle & Node Interaction
          [ Consistency ] (C)
              /   \
             /     \
      (CP)  /       \  (CA)
           /         \
          /           \
[ Partition ]-------[ Availability ]
 Tolerance (P)  (AP)      (A)

1. C: 모든 노드가 같은 시점에 같은 데이터를 보아야 함.
2. A: 일부 노드 장애 시에도 모든 요청에 응답해야 함.
3. P: 노드 간 네트워크 단절 시에도 시스템이 작동해야 함.
  1. CP (Consistency + Partition Tolerance):
    • 네트워크 단절 시, 데이터 불일치를 막기 위해 서비스 응답을 거부(에러 반환)함. 완벽한 데이터 무결성이 중요한 금융권, HBase, MongoDB(기본)가 대표적임.
  2. AP (Availability + Partition Tolerance):
    • 네트워크 단절 시, 최신 데이터가 아닐지라도 일단 응답을 제공함. 중단 없는 서비스가 중요한 SNS, Cassandra, DynamoDB가 대표적임.
  3. CA (Consistency + Availability):
    • 네트워크 장애가 없음을 가정하므로 단일 노드 시스템(RDBMS)에 해당함. 분산 시스템에서는 P를 포기할 수 없으므로 사실상 성립하기 어려움.

3. 구조 및 원리

핵심 조건: 일관성 수준, 파티셔닝, 복제, 접근 패턴을 함께 선택해야 한다.

동작 순서:

비교 항목CP 시스템 (Consistency focus)AP 시스템 (Availability focus)
장애 대응일관성을 위해 "느린 응답" 또는 "거절"가용성을 위해 "부정확한 응답" 허용
주요 기술Quorum, Paxos, Raft 합의 알고리즘Gossip Protocol, Vector Clock
데이터 정합성강한 정합성 (Strong Consistency)결과적 정합성 (Eventual Consistency)
사용 사례결제, 인벤토리 관리, 사용자 프로필뉴스 피드, 댓글, 장바구니
철학적 기반ACID (안정성)BASE (속도)

4. 비교 및 연결

  1. 네트워크 장애(P)는 상수다 (Strategic View):
    • 분산 시스템에서 P를 선택하지 않는 것은 장애 시 시스템 전체 침묵을 의미함. 따라서 현대 클라우드 설계는 CP와 AP 사이의 균형점을 찾는 과정임.
  2. 기술사적 판단: CAP 정리는 고정된 불변의 진리라기보다 '극한 상황에서의 기준'임. 최근에는 PACELC 정리를 통해 네트워크가 정상인 시점의 Latency와 Consistency 사이의 트레이드오프까지 고려하는 고도화된 설계가 필요함.

5. 실무 적용 및 판단

  1. 기대효과: 시스템 요구사항에 최적화된 데이터 저장소를 선택하고, 장애 상황에서도 비즈니스 연속성을 보장하는 구조적 설계를 가능하게 함.
  2. 결론: CAP 정리는 분산 아키텍트의 기초 문법임. 이를 통해 우리는 기술의 한계를 명확히 인식하고, 최선의 차선책을 선택할 수 있는 전문적 역량을 갖추게 됨.

6. 기대효과 및 결론

CAP 정리 (CAP Theorem)은(는) 해당 영역의 성능, 확장성, 운영 안정성, 거버넌스 수준을 직접 좌우하는 핵심 요소다. 따라서 도입 여부는 기능 비교를 넘어 데이터 특성, 팀 역량, 비용 구조, 규제 요구를 함께 보는 아키텍처 판단이어야 한다.

실무에서는 초기 효과보다 지속 운영 가능성과 연계 확장성이 더 중요하다. NoSQL 선택은 정답 찾기가 아니라 업무 패턴에 맞는 일관성과 확장성의 균형점을 고르는 일이다.
