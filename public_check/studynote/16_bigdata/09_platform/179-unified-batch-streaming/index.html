0. 핵심 인사이트

핵심: 통합 배치/스트리밍 플랫폼 (Unified Batch/Streaming) — Spark/Flink 통합은(는) 수집·저장·처리·분석·운영을 하나의 아키텍처로 연결하기 위한 빅데이터 플랫폼 설계 요소다. 비유: 도시 전체의 도로, 창고, 관제, 배송 체계를 한 번에 설계하는 종합 교통망과 같다.

📝 모범 답안

1. 개요 및 필요성

1-1. Lambda 아키텍처의 문제

Lambda: 배치 레이어 + 스피드 레이어 병행 운영 → 동일 비즈니스 로직을 두 곳에서 별도로 구현·유지보수 → 불일치 발생 리스크, 운영 복잡도 2배

1-2. 통합 접근법 비교

접근프레임워크배치 처리 방식스트리밍 처리 방식
Batch as StreamingApache Flink유한 스트림으로 배치 처리네이티브 이벤트 시간 스트리밍
Streaming as Micro-batchSpark Structured Streaming기존 Spark 배치마이크로배치 (100ms~수초)
Continuous ProcessingFlink, Kafka Streams해당 없음레코드 단위 처리

3. 구조 및 원리

핵심 조건: 데이터 흐름, 운영 자동화, 비용 구조, 확장 전략을 함께 결정해야 한다.

동작 순서:

통합 처리의 실용적 이점

  • 단일 코드베이스: 배치 재처리와 실시간 처리 로직 공유
  • 일관된 결과: 동일 윈도우 정의로 배치·스트리밍 결과 일치
  • 운영 간소화: 하나의 클러스터 관리

이벤트 시간 vs 처리 시간

  • 이벤트 시간(Event Time): 데이터가 실제 생성된 시간 → 네트워크 지연·리오더링 처리 필요
  • 처리 시간(Processing Time): 시스템이 처리한 시간 → 단순하지만 지연 데이터 처리 불가
  • Watermark: 이벤트 시간 기반 처리 시 지연 데이터 허용 임계치

4. 비교 및 연결

4-1. 통합 파이프라인 설계 패턴

Kafka (이벤트 소스)
   ↓
Flink Job (실시간 처리 + 배치 재처리 동일 로직)
   ↓
┌──────────────────────────────┐
│ 실시간: Kafka/Redis 서빙     │
│ 배치 재처리: S3/DW 저장      │
└──────────────────────────────┘

4-2. 상태 백엔드 선택

  • Heap State Backend: 소규모, JVM 메모리 내 저장, 빠르지만 메모리 한계
  • RocksDB State Backend: 대규모 상태, 디스크 저장, 비동기 체크포인트

4-3. 기술사 시험 포인트

  • Flink vs Spark Streaming: 지연 요구사항이 100ms 미만 → Flink 필수
  • Watermark 설계: 비즈니스 요구사항에 따른 지연 허용 범위 결정
  • 체크포인트 간격: 짧을수록 복구 빠름, 길수록 처리 부하 감소 (트레이드오프)

5. 실무 적용 및 판단

효과내용
개발 생산성Lambda 이중 파이프라인 유지 비용 50% 절감
일관성배치·스트리밍 동일 로직으로 결과 불일치 해소
운영 간소화단일 클러스터 관리로 운영 복잡도 감소

통합 배치/스트리밍 플랫폼은 현대 데이터 엔지니어링의 핵심 방향이다. Flink와 Spark Structured Streaming 중 선택 시 지연 요구사항(ms vs 초)과 팀의 기존 기술 스택이 가장 중요한 기준이 된다.

6. 기대효과 및 결론

통합 배치/스트리밍 플랫폼 (Unified Batch/Streaming) — Spark/Flink 통합은(는) 해당 영역의 성능, 확장성, 운영 안정성, 거버넌스 수준을 직접 좌우하는 핵심 요소다. 따라서 도입 여부는 기능 비교를 넘어 데이터 특성, 팀 역량, 비용 구조, 규제 요구를 함께 보는 아키텍처 판단이어야 한다.

실무에서는 초기 효과보다 지속 운영 가능성과 연계 확장성이 더 중요하다. 플랫폼 설계의 승패는 기능 나열보다 운영 가능성과 비용 지속 가능성을 확보하느냐에 달려 있다.

7. 발전 흐름도

[Lambda Architecture]
    │
    ▼
[Checkpoint/Barrier]
    │
    ▼
[Watermark]
    │
    ▼
[RocksDB (상태 저장)]
    │
    ▼
[2PC (Exactly-once 보장)]

이 흐름도는 Lambda Architecture에서 출발해 2PC (Exactly-once 보장)까지 이어지며, 중간 단계가 기초 개념을 실무 구조로 발전시키는 과정을 보여준다.
